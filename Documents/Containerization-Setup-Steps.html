Before You Start (All Environments)

Every path below assumes you have a copy of the FHIRBridge repository on your computer already (cloned from source control) and a terminal open in the repo's root folder. All commands are shown for a bash-style terminal (Git Bash, macOS/Linux Terminal, or WSL) — a PowerShell equivalent script exists for every .sh script mentioned (same name, ending in .ps1, with equivalent flags spelled out in full, e.g. -Yes instead of -y).

Azure and AWS cost real money the moment resources are created The Local path is entirely free. The Azure and AWS paths both start billing your cloud account as soon as terraform apply (or the Bicep deploy) finishes — not when someone visits the site. Always finish with the teardown steps at the end of each section when you're done testing. See Containerization-Multi-Cloud-Guide.html in this same folder for the exact resource-by-resource cost breakdown.

🐳Local Setup

Runs the whole product — all 5 pieces — on your own computer, for free, using Docker.

Prerequisites

NeededHow to check / get it
Docker Desktop, installed and runningOpen a terminal and run docker version — if it prints version info for both a "Client" and a "Server," you're set. If not installed, download from docker.com/products/docker-desktop, install it, and make sure the whale icon in your system tray shows it's running before continuing.

Setup Steps

1
Build the 3 custom images

This compiles the actual application code into runnable packages. The first run downloads a fair amount (base images, dependencies) and can take 5–10 minutes; later runs are much faster since most of it is cached.

cd containerization/scripts
./build-images.sh
# Windows PowerShell:  ./build-images.ps1
You'll know it worked if the last line printed is Done. Images tagged with prefix '' and tag 'local'. with no red "error" text above it.
2
Set up your secrets file

This is a one-time step per computer. It creates a private settings file that never gets shared or committed to source control.

cd ../compose
cp .env.example .env

Now open .env in any text editor and change these three lines to real values:

SQL_SA_PASSWORD=Ch4ngeMe!Str0ng
JWT_SIGNING_KEY=replace-with-a-long-random-string-at-least-32-chars
REDIS_PASSWORD=replace-with-a-strong-redis-password

SQL_SA_PASSWORD needs at least 8 characters with a mix of upper case, lower case, and a digit (SQL Server will refuse to start otherwise). JWT_SIGNING_KEY and REDIS_PASSWORD just need to be reasonably long random strings — mash the keyboard or use a password generator, they don't need to be memorable.

3
Start everything 
docker compose up -d

The -d means "run in the background" so you get your terminal prompt back immediately. Docker will print a line for each of the 5 containers as it starts them.

4
Wait for it to finish starting up, then check on it

The database takes the longest — give it about 20–30 seconds after the previous command before checking.

docker compose ps
You'll know it worked if all 5 rows say "Up" in the Status column, and sqlserver / redis specifically say "Up (healthy)." If fhirbridge-app shows a very recent "Up" time (like 5–10 seconds ago) even though you started it a while back, that's fine — see the troubleshooting note below about a harmless one-time restart.
5
Open it in a browser
  • http://localhost:8080 — the main FHIRBridge portal
  • http://localhost:5500 — the Demo app (log in with admin@healthapp.local / Admin@123, or patient@healthapp.local / Patient@123)

If Something Goes Wrong

The main app container restarted once, right after starting This is expected and self-healing, not a real problem: on a brand-new database, the main app and the background worker both try to set up the database's tables at the exact same moment, and one of them loses that race and briefly restarts. It comes back up cleanly within a few seconds and works correctly after that — you don't need to do anything.
"port is already allocated" error Something else on your computer is already using port 8080, 5500, 1434, or 6380. Either stop that other program, or open .env and change the corresponding *_HOST_PORT value to a free port (e.g. APP_HOST_PORT=8090), then run docker compose up -d again.

To see what a specific container is actually doing or why it's failing, check its logs:

docker compose logs -f fhirbridge-app
# Ctrl+C to stop watching

Tearing It Down

When you're done testing:

cd ../scripts
./cleanup-local.sh

Answer y at the prompt. This removes all 5 containers, their shared network, and their saved data (so the next run starts completely fresh). Since this is entirely local, there's no cost urgency — running this is just good housekeeping.

☁Azure Setup

Two different ways to get the same result in Azure — pick the one that matches what you're doing.

Which path should I use? Path A (Terraform) if you're setting this up yourself, want it fully scriptable/repeatable, or plan to tear it down and rebuild it often during testing. Path B (Bicep) if the end goal is handing a customer a single command/button to deploy it into their own Azure subscription.

Prerequisites (Both Paths)

NeededHow to check / get it
An Azure subscriptionAny existing one, or sign up for a free trial with $200 credit at azure.microsoft.com/free.
Azure CLICheck with az version. If missing: winget install --id Microsoft.AzureCLI (Windows), or see Microsoft's install guide for Mac/Linux.
Terraform (Path A only)Check with terraform version. If missing: winget install --id Hashicorp.Terraform (Windows), or see HashiCorp's install guide.
Bicep CLI (Path B only)Comes bundled with a recent Azure CLI automatically the first time you run a bicep/deployment command; or install standalone with winget install --id Microsoft.Bicep.
0
Sign in to Azure (do this once per terminal session, before either path) 
az login

This opens a browser window (or shows a device code — follow the on-screen instructions) to sign into your Microsoft account. If you have access to more than one subscription, confirm you're pointed at the right one:

az account show

az account set --subscription "<name or id>"

Path A: Terraform

1
Create the resource group this deployment goes into (one-time, if it doesn't exist yet) 
az group create --name rg-tusharpuri --location eastus

This Terraform config deploys into an existing resource group — it does not create or delete the group itself, only what lives inside it. Skip this step if rg-tusharpuri (or whatever name you're using) already exists.

2
Go to the Azure Terraform folder and set up your secrets 
cd containerization/terraform/environments/azure
cp terraform.tfvars.example terraform.tfvars

Open terraform.tfvars and fill in real values (same password rules as the Local section above):

name_prefix         = "segue"
resource_group_name = "rg-tusharpuri"
image_tag           = "v1"
sql_sa_password     = "<a real password>"
jwt_signing_key     = "<a real 32+ character random string>"
redis_password      = "<a real strong password>"

resource_group_name must match a resource group that already exists (step 1) — every resource this config creates lands inside it, and its Azure region is inherited from that group rather than set separately here. The three passwords are only seed values — the first apply writes them into a Key Vault this config creates, and every Container App reads them from the Vault after that (more on rotating them in the last step below). Optional overrides sql_port and redis_port also exist in the same file if you need non-default internal ports; the defaults work fine for almost everyone, so leave them commented out unless you have a reason not to.

3
Initialize Terraform 
terraform init
You'll know it worked if the last line says Terraform has been successfully initialized!
4
Create just the image registry first

The registry has to exist before anything can be uploaded to it — this creates only that one piece.

terraform apply -target=azurerm_container_registry.acr

Terraform will show you a plan and ask Do you want to perform these actions? — type yes and press Enter. When it finishes, note the acr_login_server value it prints (looks like segueacr1a2b3c.azurecr.io) — you'll need it in the next two steps.

5
Log in to that registry, then build and upload the 3 images 
az acr login --name segueacr1a2b3c
# (use just the part before ".azurecr.io" from the previous step's output)

cd ../../../scripts
./build-images.sh -r segueacr1a2b3c.azurecr.io -t v1 -p

The -p flag means "and upload it," on top of just building. This step can take several minutes the first time.

You'll know it worked if you see Done. Images tagged with prefix '...' and tag 'v1'. with no errors, and each image showed a "Pushing" line before it.
6
Deploy everything else 
cd ../terraform/environments/azure
terraform apply

Type yes when prompted. This is the step that actually creates the database, cache, and all 5 running containers — it typically takes 2–5 minutes for Azure to finish provisioning everything.

7
Get the URLs and open them 
terraform output

Prints fhirbridge_app_url, demo_app_url, and now also key_vault_name — open the first two in a browser. (You can also see everything visually by searching for the resource group name in portal.azure.com.)

Rotating a password later? Don't edit terraform.tfvars sql_sa_password, jwt_signing_key, and redis_password are only seed values used on the very first apply. To rotate one afterward, write the new value straight into the Key Vault the deploy created (name from key_vault_name above): 
az keyvault secret set --vault-name <key_vault_name output> \
  --name sql-sa-password --value "<new value>"
# or: jwt-signing-key / redis-password
Then restart the affected Container App revision(s) (Portal, or az containerapp revision restart) so they pick up the new value. Re-running terraform apply with a changed terraform.tfvars value will not overwrite an already-rotated secret — that's intentional, so a stale local tfvars file can never silently undo a rotation.

Optional: put a real domain on fhirbridge_app and/or demo_app new

8a
Get the verification value (already available from the apply you just ran) 
terraform output fhirbridge_app_domain_verification
terraform output demo_app_domain_verification

These are always populated, whether or not you ever set a custom domain — no extra apply needed to get them.

8b
At your DNS provider, add two records for the domain you want to use

A CNAME pointing your domain (e.g. app.customer.com) at the app's existing hostname from fhirbridge_app_url/demo_app_url, and a TXT record named asuid.app.customer.com whose value is the verification output from step 8a. Wait for DNS to propagate before continuing — this can take anywhere from a few minutes to longer depending on your provider.

8c
Set the domain and apply again 
terraform apply -var="fhirbridge_app_custom_domain=app.customer.com"
# or add it to terraform.tfvars instead of passing -var each time

This is the step that actually validates DNS, issues the free managed certificate, and binds the domain — it will fail with a clear error if step 8b's records haven't propagated yet. Just wait a bit longer and re-run this same command.

You'll know it worked if terraform output fhirbridge_app_custom_domain_url now prints your domain instead of null, and it loads over HTTPS in a browser.
Setting a domain on demo_app too? Make sure fhirbridge_app gets redeployed after (a plain terraform apply with no changes is enough) — it needs to pick up the demo app's new origin in its CORS allowlist, or the demo app's own calls into the API will start failing.

Path B: Bicep (One-Command / Customer Install)

1
Create a resource group to deploy into 
az group create --name segue-rg --location eastus
2
Make sure the 3 images are already published somewhere reachable

Unlike Path A, this template doesn't create its own registry — it expects the images to already be built and uploaded (e.g. to an ACR you already have, or a public registry). If you don't have one yet, the quickest option is creating one manually and pushing to it:

az acr create --resource-group segue-rg --name segueacrXXXX --sku Basic --admin-enabled true
az acr login --name segueacrXXXX
cd containerization/scripts
./build-images.sh -r segueacrXXXX.azurecr.io -t v1 -p
az acr credential show --name segueacrXXXX
# note the username and one of the two passwords shown — needed in the next step
3
Set up your parameters file and deploy 
cd ../azure-deploy
cp main.parameters.example.json main.parameters.json

Edit main.parameters.json with your real values: sqlSaPassword, jwtSigningKey, and redisPassword (all three are secure params, same pattern), plus the registry name and — since the ACR above requires credentials — the username/password from the previous step. sqlPort and redisPort are also there if you need non-default internal ports, but the defaults are fine as-is. Each container also has a *Size parameter (sqlServerSize, redisSize, fhirbridgeAppSize, demoAppSize, workerSize) — one of Small/Medium/Large/ XLarge, defaulting to today's values; bump sqlServerSize to XLarge if SQL Server's first-run setup crashes with an out-of-memory exit code.

az deployment group create \
  --resource-group segue-rg \
  --template-file main.bicep \
  --parameters main.parameters.json

This single command creates literally everything — takes 2–5 minutes.

Optional: a real domain for fhirbridgeAppCustomDomain/demoAppCustomDomain Same two-phase idea as the Terraform path above (deploy once with these blank, read fhirbridgeAppDomainVerificationId/demoAppDomainVerificationId from the deployment's outputs, add the CNAME + TXT records at your DNS provider, wait for propagation, then redeploy with the domain filled in) — see Path A's step 8 for the full walkthrough, it's identical here, just via main.parameters.json instead of terraform.tfvars. The one-click Portal wizard version of this same flow has its own dedicated "Custom Domains" step.
4
Get the URLs 
az deployment group show --resource-group segue-rg --name main --query properties.outputs

If Something Goes Wrong

"The registry name ... is not available" when creating the ACR — registry names must be globally unique across all of Azure, not just your subscription. Pick a different, more unique name and try again.
A Container App shows "Failed" or won't start after the full apply — almost always means the image wasn't actually pushed successfully in the earlier step, or the tag doesn't match. Re-run the build/push step and confirm the tag in terraform.tfvars (or main.parameters.json) matches exactly what you pushed.
SQL password rejected — SQL Server requires at least 8 characters with 3 of: upper case, lower case, digit, symbol. Pick a stronger password and re-apply.
Key Vault secret write fails with a permission error, right after a brand-new subscription/identity setup — Azure RBAC role assignments can take a minute or two to propagate. If terraform apply fails writing the seed secrets on the very first run after setting things up, just wait a minute and re-run terraform apply — it resolves itself once the role assignment has propagated.

Tearing It Down

Path A (Terraform):

cd containerization/scripts
./cleanup-azure.sh
Don't skip this Every Azure resource this Terraform config created keeps billing until it's deleted — there's no "pause" button. This path deploys into an existing resource group (rg-tusharpuri by default) rather than creating one, so terraform destroy removes everything Terraform created but leaves the resource group itself in place — confirm with az resource list --resource-group rg-tusharpuri (should come back empty once destroy finishes). The Key Vault is deleted the same way, but Azure Key Vault has a 7-day soft-delete retention period — if you try to recreate a vault with the exact same name right away, you may need to purge the soft-deleted one first.

Path B (Bicep):

cd containerization/azure-deploy
./cleanup.sh -g segue-rg
Precise by default now This first reads main.bicep's own resourceManifest output (every resource ID this deployment created, kept in the deployment's history for free) and deletes exactly those — safe even against a resource group shared with other, unrelated resources. It only falls back to deleting the entire resource group named here (-g) if that manifest can't be found, and even then it refuses outright if the group contains any disk snapshot (a snapshot is how a backup is protected — this script will never delete one). Use -e <environment-tag-value> instead for a shared group where the manifest genuinely isn't available. Confirm the deployment's own resources are gone afterward with az resource list --resource-group segue-rg.
Changing sqlSaPassword and redeploying into the same resource group + name prefix won't actually change SQL Server's password — it only applies the very first time SQL Server initializes its data directory; every later restart keeps whatever password was set originally, even though the app containers pick up the new one immediately. You'll see a persistent Login failed for user 'sa' that looks like a misconfiguration but isn't. Fix: delete and recreate the sql-data Azure File share (az storage share delete/create, passing --account-key explicitly since these two subcommands don't accept --auth-mode key), then restart the SQL container app revision so it reinitializes against the empty share. Also avoid $, backticks, and quote characters in this password and the JWT signing key/Redis password — one was directly observed being corrupted by shell metacharacter expansion on the way into the container. Plain letters and digits, made long, are both safer and plenty strong.

☁AWS Setup

One path here — Terraform, using AWS ECS Fargate.

Prerequisites

NeededHow to check / get it
An AWS accountAny existing one, or sign up at aws.amazon.com.
An AWS access keyIn the AWS Console: your account menu → Security credentials → Access keys → Create access key. Save both the Access Key ID and Secret Access Key it shows you — the secret is only ever shown once.
AWS CLICheck with aws --version. If missing: winget install --id Amazon.AWSCLI (Windows), or see AWS's install guide.
TerraformCheck with terraform version. If missing: winget install --id Hashicorp.Terraform.

Setup Steps

1
Configure your AWS credentials 
aws configure

It will ask 4 questions in turn: your Access Key ID, your Secret Access Key, a default region (e.g. us-east-1), and a default output format (press Enter to accept the default, json).

aws sts get-caller-identity
You'll know it worked if this prints your Account number and User/Role ARN back to you, instead of an error.
2
Go to the AWS Terraform folder and set up your secrets 
cd containerization/terraform/environments/aws
cp terraform.tfvars.example terraform.tfvars
name_prefix     = "fhirbridge"
aws_region      = "us-east-1"
image_tag       = "v1"
sql_sa_password = "<a real password>"
jwt_signing_key = "<a real 32+ character random string>"
redis_password  = "<a real strong password>"

Optional overrides also live in this file: fhirbridge_app_port and demo_app_port (the public ports clients use through the load balancer), plus sql_port and redis_port (internal-only). The defaults work fine for almost everyone, so leave them commented out unless you have a reason not to.

3
Initialize Terraform 
terraform init

This one downloads the AWS provider, which is large — expect it to take a bit longer than the Azure or Local equivalents.

4
Create just the 3 image registries first 
terraform apply \
  -target=aws_ecr_repository.fhirbridge_app \
  -target=aws_ecr_repository.demo_app \
  -target=aws_ecr_repository.worker

Type yes when prompted.

5
Log in to those registries, then build and upload the 3 images 
aws ecr get-login-password --region us-east-1 \
  | docker login --username AWS --password-stdin <your-account-id>.dkr.ecr.us-east-1.amazonaws.com

cd ../../../scripts
./build-images.sh -r <your-account-id>.dkr.ecr.us-east-1.amazonaws.com/fhirbridge -t v1 -p

Find <your-account-id> from the aws sts get-caller-identity output in step 1. This step can take several minutes the first time.

6
Deploy everything else 
cd ../terraform/environments/aws
terraform apply

Type yes when prompted. This is the biggest step — it builds the network (including private subnets and a NAT Gateway, so all 5 containers can run without public IPs), the database and cache storage, the load balancer, and all 5 running containers. Expect this to take 5–10 minutes, noticeably longer than Azure or Local — the NAT Gateway alone adds a couple of minutes to provision.

7
Get the URL and open it 
terraform output

Prints fhirbridge_app_url and demo_app_url (both point at the same load balancer address, on different ports, both now https://) and ecr_repository_urls. Give it another minute or two after the apply finishes before it responds — the load balancer takes a short while to recognize the containers as healthy.

Expected: your browser will show a security warning like "Your connection is not private" or NET::ERR_CERT_AUTHORITY_INVALID the first time you open either URL. This is normal, not a broken deployment — the load balancer uses a self-signed certificate until a real domain and a trusted certificate are wired up. Click Advanced (Chrome/Edge) or Accept the Risk and Continue (Firefox), then Proceed, to get through to the site.

If Something Goes Wrong

The site doesn't load right after terraform apply finishes — this is normal for the first minute or two; the load balancer needs a short warm-up period to start routing traffic to newly-created containers. Wait a minute and refresh.
"no basic auth credentials" when pushing images — the aws ecr get-login-password | docker login step in step 5 wasn't run (or expired — those logins time out after several hours). Re-run it.
A service is stuck with 0 running tasks — usually means the image tag in terraform.tfvars doesn't match what was actually pushed, or the push itself failed. Check with aws ecr list-images --repository-name fhirbridge/fhirbridge-app to confirm the tag actually exists in the registry.
A task can't pull its image or times out on startup, and the tag/push are confirmed correct — rare, but tasks now run in private subnets and reach ECR through a NAT Gateway, so if that Gateway isn't fully available yet the pull can stall. Check its state: 
aws ec2 describe-nat-gateways --filter Name=state,Values=available
If your NAT Gateway doesn't show up as available (e.g. still pending), give it a few more minutes and the stuck task should recover on its own.

Tearing It Down

cd containerization/scripts
./cleanup-aws.sh
Don't skip this The load balancer and all 5 containers bill continuously for as long as they exist — there's no "pause" button here either. Confirm everything is gone afterward by checking the ECS console or running terraform show (it should report no resources).

📦Publishing & Distributing Versions

A one-time setup, then a repeatable two-step cycle for every real release: publish a version (built locally), then hand a specific client that exact version — without their Azure account, or anyone else's, ever touching source code.

Prerequisites

NeededHow to check / get it
Azure CLI + TerraformSame as the Azure section above — az version / terraform version.
Docker Desktop, runningdocker info should return engine details with no connection errors. Publishing a version always builds locally — there's no remote-build step here.
Access to a resource groupCan be the same one you already use for testing (e.g. rg-tusharpuri) — see the callout below on why a dedicated one is better long-term.

One-time registry setup

1
Confirm (or create) the target resource group 
az group show --name rg-tusharpuri

If it doesn't exist yet: az group create --name rg-tusharpuri --location eastus.

2
Set up the registry 
cd containerization/terraform/vendor-registry
cp terraform.tfvars.example terraform.tfvars

Open terraform.tfvars and confirm resource_group_name matches step 1.

terraform init
terraform apply

Type yes when prompted.

You'll know it worked if terraform output acr_login_server prints something like fhirbridgevendor8ae7f3.azurecr.io.
Using the same resource group as your test deployment, for now That's fine to start — but this registry is meant to persist permanently, unlike the azure/aws test environments which get destroyed and recreated often. Move it to a dedicated resource group later by changing one line (resource_group_name) in terraform.tfvars and re-applying — no other changes needed.

Publishing a new version

1
Log in to the registry 
az acr login --name fhirbridgevendor8ae7f3

Use the short registry name here (terraform output acr_name) — not the full .azurecr.io address.

2
Build locally and push 
cd ../../scripts
./build-images.sh -r fhirbridgevendor8ae7f3.azurecr.io -t v1.0.0 -p
# PowerShell: ./build-images.ps1 -Registry fhirbridgevendor8ae7f3.azurecr.io -Tag v1.0.0 -Push

Use the full registry hostname here (terraform output acr_login_server) — the opposite of step 1. This is the same script used for local/Azure/AWS testing; Docker builds each image on your own machine, then pushes only the finished, compiled image. Your source code is never uploaded anywhere — this deliberately does not use Azure's remote-build option (az acr build), which would upload your full source tree to a cloud build sandbox instead.

You'll know it worked if you see Done. Images tagged with prefix '...' and tag 'v1.0.0'. with no errors, and each image showed a "Pushed" line (not "Mounted from," which just means Docker reused an identical layer already in the registry — still a successful push).
3
Confirm what actually landed in the registry 
az acr repository list --name fhirbridgevendor8ae7f3 --output table
az acr repository show-tags --name fhirbridgevendor8ae7f3 --repository fhirbridge-app --output table

Installing a version for a client

1
Copy the published version into the client's own registry 
az acr import --name <client-acr-name> --source fhirbridgevendor8ae7f3.azurecr.io/fhirbridge-app:v1.0.0 --image fhirbridge-app:v1.0.0
az acr import --name <client-acr-name> --source fhirbridgevendor8ae7f3.azurecr.io/demo-app:v1.0.0 --image demo-app:v1.0.0
az acr import --name <client-acr-name> --source fhirbridgevendor8ae7f3.azurecr.io/fhirbridge-worker:v1.0.0 --image fhirbridge-worker:v1.0.0

A server-to-server image copy — no rebuild, no source involved, and no local Docker needed for this step. <client-acr-name> is whichever registry that client's own Terraform (or Bicep) deployment already created for itself.

2
Point that deployment at the imported version

Set image_tag = "v1.0.0" in that deployment's terraform.tfvars (or imageTag in main.parameters.json for the Bicep path), then apply as usual.

If Something Goes Wrong

denied: requested access to the resource is denied, and the push log shows docker.io/... — -Registry/-r was given the short registry name instead of the full .azurecr.io hostname, so Docker assumed Docker Hub instead of your ACR (Docker's rule: no dot in the first path segment means Docker Hub). Re-run with the full acr_login_server value.
Publishing the same tag again — re-running step 2 above with a tag that already exists in the registry simply overwrites it; that's expected, not an error. Anyone already deployed on that exact tag won't automatically pick up the change — re-run the az acr import + redeploy (or az containerapp update --image ... for a fast one-off nudge) to actually push it out to a specific client.

Tearing It Down

Rarely needed — this registry is meant to persist across every test teardown above.

cd containerization/scripts
./cleanup-vendor-registry.sh
# PowerShell: cleanup-vendor-registry.ps1
Double-check before confirming Since this may currently share a resource group with a test deployment, confirm the preview list this script prints only shows the registry itself before typing yes.
