⚡Commands

Setting up the two one-time resources: the vendor registry & the hosting storage account

These two resources only need to exist once, ever — they're not part of any customer's oneclick-* deployment. The registry (seguebuilds) is where you publish versioned release images; the storage account (fhirbridgedeployfiles) is where main.json/createUiDefinition.json live at a public HTTPS URL so the Deploy-to-Azure button can fetch them. Run the registry commands from containerization/terraform/vendor-registry.

1. Create (or confirm) the vendor registry — seguebuilds

terraform init
terraform apply

Creates the persistent, protected ACR if it doesn't exist yet. A rerun against an already-existing registry shows "0 to add, 0 to change" — that's the confirmation it's already live, not an error.

2. Read its name and login server

terraform output -raw acr_name
terraform output -raw acr_login_server

acr_name is the short name (seguebuilds); acr_login_server is the full seguebuilds.azurecr.io. The login server is what must be used everywhere else (Docker, createUiDefinition.json's registry fields) — passing the short name to docker makes it silently default to Docker Hub instead of this registry.

3. Confirm both are genuinely reachable before relying on them

az account show --query "{name:name, id:id}" -o table
az acr show --name seguebuilds --query "{name:name, loginServer:loginServer}" -o table

Confirms you're on the intended subscription and the registry actually exists before trying to build/push against it.

4. Create the hosting storage account — fhirbridgedeployfiles

az storage account create --name fhirbridgedeployfiles --resource-group rg-tusharpuri --location eastus --sku Standard_LRS --allow-blob-public-access true
az storage container create --account-name fhirbridgedeployfiles --name deploy --public-access blob --auth-mode key

A plain Standard storage account with public blob read access enabled — this is the only thing that has to be public in this whole setup, and only these two specific files ever get uploaded to it (see the next section). This is a one-time setup too; only the two blob uploads need repeating whenever main.bicep or createUiDefinition.json changes.

Build, push, and verify images

az acr login --name <acr_name>
.\build-images.ps1 -Registry <acr_login_server> -Tag v1.0.0 -Push

Authenticates Docker against the ACR, then builds and pushes all 3 custom images tagged v1.0.0. Requires Docker Desktop running locally.

az acr repository show-tags --name <acr_name> --repository fhirbridge-app -o table
az acr repository show-tags --name <acr_name> --repository demo-app -o table
az acr repository show-tags --name <acr_name> --repository fhirbridge-worker -o table

Confirms each image actually landed in the registry with the expected tag before relying on it in a deployment.

Scoped ACR pull token

az acr token create --registry <acr_name> --name one-click-pull --scope-map _repositories_pull

Creates a read-only, revocable credential (pull-only, nothing else) that gets embedded in createUiDefinition.json so a customer's one-click deploy can pull images without ever seeing a real registry admin credential. Revoke independently at any time with az acr token delete --registry <acr_name> --name one-click-pull.

Compile the Bicep template

az bicep build --file main.bicep --outfile main.json

Recompiles main.json from main.bicep — the Portal's custom-deployment blade only fetches compiled ARM JSON, never .bicep source directly. Re-run this any time main.bicep changes, before re-hosting or re-clicking the Deploy-to-Azure link.

Upload (or re-upload) the deploy files to fhirbridgedeployfiles

az storage blob upload --account-name fhirbridgedeployfiles --container-name deploy --name main.json --file main.json --auth-mode key --overwrite
az storage blob upload --account-name fhirbridgedeployfiles --container-name deploy --name createUiDefinition.json --file createUiDefinition.json --auth-mode key --overwrite

Run these two every time main.bicep (recompiled to main.json) or createUiDefinition.json changes — the Deploy-to-Azure link doesn't change, but it always fetches whatever is currently sitting at these blob URLs, so a stale upload here means the wizard runs against an outdated template. --auth-mode key is used instead of --auth-mode login throughout because a management-plane Contributor role doesn't include the data-plane Storage Blob roles the latter needs.

Build the Dynamic Deployment URL (the actual Deploy-to-Azure link)

$MainJsonUrl = az storage blob url --account-name fhirbridgedeployfiles --container-name deploy --name main.json -o tsv
$UiDefUrl = az storage blob url --account-name fhirbridgedeployfiles --container-name deploy --name createUiDefinition.json -o tsv
$DeployUrl = "https://portal.azure.com/#create/Microsoft.Template/uri/$([System.Uri]::EscapeDataString($MainJsonUrl))/createUIDefinitionUri/$([System.Uri]::EscapeDataString($UiDefUrl))"
Write-Host $DeployUrl

The first two lines read each blob's actual public URL back from Azure (rather than hand-constructing it) so it's always exactly correct. The third line assembles the real clickable link: portal.azure.com/#create/Microsoft.Template/uri/<url-encoded main.json URL>/createUIDefinitionUri/<url-encoded createUiDefinition.json URL> — both pieces have to be URL-encoded since they're themselves full URLs being embedded inside another URL's query-like path.

This link carries no information about whose Azure account it deploys into — the signed-in user's own subscription/resource group choice inside the wizard decides that. It also doesn't change when passwords change (those are typed live into the wizard fields, never baked into the URL), so the same $DeployUrl can be reused across every redeploy attempt — only re-run this block if the storage account or blob names themselves change.

Diagnosing a stuck deployment

az containerapp revision list --name oneclick-app --resource-group $Rg -o table
az containerapp replica list --name oneclick-app --resource-group $Rg -o table
az containerapp logs show --name oneclick-app --resource-group $Rg --type console --tail 100

Checks whether the app is crash-looping (restart count via replicas) and pulls the actual console output — this is where FHIRBridge.Api's own startup exception (the SQL login failure) first showed up.

Finding the SQL password on both sides, to compare

The whole password-mismatch saga came down to one question asked repeatedly at different layers: what password does the app think it's sending, versus what password does SQL Server actually have? These four steps check progressively deeper — configured value → live container env var → an actual login attempt — because each earlier layer can look clean while a later one is still wrong (e.g. the configured secret can be perfectly clean while the file share underneath SQL Server is still running on an older, different password).

1. What the Container Apps config says each secret is

az containerapp secret list --name oneclick-sqlserver --resource-group $Rg --show-values -o table
az containerapp secret list --name oneclick-app --resource-group $Rg --show-values -o table

Prints the actual configured secret values (not just names) on each app — used to confirm both sides genuinely had the same sql-sa-password value, ruling out a Bicep wiring bug. This only proves what's configured, not what SQL Server is actually enforcing right now (see step 3).

2. What the app's own connection string literally contains

$appConfig = az containerapp show --name oneclick-app --resource-group $Rg -o json | ConvertFrom-Json
$appConfig.properties.template.containers[0].env | Where-Object { $_.name -eq 'ConnectionStrings__FHIRBridgeDb' } | Select-Object -ExpandProperty value

Extracts the exact literal connection string FHIRBridge.Api is configured to use, without the bracket-heavy --query JMESPath syntax that breaks under PowerShell + the az CLI's Windows batch wrapper (see Gotchas). Filtering in PowerShell after pulling plain JSON avoided that entirely. This is a plain, non-secret env value (not a secretRef), so it's fully visible this way.

3. What SQL Server's own live container process actually has, right now

az containerapp exec --name oneclick-sqlserver --resource-group $Rg --command "/bin/bash"
# once connected (prompt changes to mssql@...:/$):
printenv MSSQL_SA_PASSWORD | wc -c
printenv MSSQL_SA_PASSWORD | cat -A

This is the most authoritative check — it reads the environment variable directly inside the running SQL Server container, rather than trusting Azure's own reported config, which only tells you what was configured, not necessarily what's still enforced if the container's data volume was never actually reinitialized (see the volume-wipe gotcha). wc -c gives a byte count you can compare against the expected password length plus one (printenv always appends a trailing newline). cat -A shows the string with every character made visible, including a stray space that would otherwise be invisible in a terminal.

4. The actual, unambiguous test: try logging in from inside the container

az containerapp exec --name oneclick-sqlserver --resource-group $Rg --command "/opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P Fhir2026SecureSqlBridge91 -C -Q SELECT@@VERSION"

Rather than comparing strings and hoping they match, this attempts a real login with a specific candidate password and reports exactly what SQL Server itself decides — success (prints the version string) or a genuine Login failed for user 'sa'. Avoid quoted arguments with spaces here (e.g. -Q "SELECT 1") — az containerapp exec's own command-string parsing mangles nested quotes; a query with no internal space like SELECT@@VERSION sidesteps that entirely, as does a password with no special characters (no quotes needed).

Quick length check, either side

$sqlSecret.value.Length

Compares a secret's actual character count against the expected password length — caught a stray leading space in seconds that would otherwise have looked like an unexplained, persistent auth failure.

Fixing the stale SQL password (volume wipe)

az storage account keys list --account-name <name> --resource-group $Rg --query "[0].value" -o tsv

Fetches an explicit account key — az storage share delete/create don't accept --auth-mode key in this az CLI version, only an explicit --account-key or connection string.

az storage file list --account-name <name> --share-name sql-data --account-key <key> -o table
az storage share delete --account-name <name> --name sql-data --account-key <key>
az storage share create --account-name <name> --name sql-data --account-key <key>

Lists the share's contents to confirm it's actually pre-initialized (.system/, data/, log/, secrets/ — SQL Server's own data directories from an earlier deploy attempt), then wipes it. SQL Server only applies MSSQL_SA_PASSWORD the very first time it initializes an empty data directory — deleting and recreating the share is what forces a genuine reinitialization with the current password.

Restarting containers

az containerapp revision restart --name oneclick-sqlserver --resource-group $Rg --revision (az containerapp revision list --name oneclick-sqlserver --resource-group $Rg --query "[0].name" -o tsv)
az containerapp revision restart --name oneclick-app --resource-group $Rg --revision (az containerapp revision list --name oneclick-app --resource-group $Rg --query "[0].name" -o tsv)

Forces SQL Server to restart against the now-empty share (reinitializing with the current password), then restarts the app so it retries the connection immediately instead of waiting for its own crash-loop backoff.

Testing SQL from outside (and reverting)

az containerapp ingress enable --name oneclick-sqlserver --resource-group $Rg --type external --target-port 1433 --transport tcp --exposed-port 1433
az containerapp ingress show --name oneclick-sqlserver --resource-group $Rg -o json

Temporarily exposes SQL Server publicly so it can be reached from a local SSMS/sqlcmd client — main.bicep keeps it internal-only by design, so this is a deliberate, temporary exception for testing.

az containerapp ingress enable --name oneclick-sqlserver --resource-group $Rg --type internal --target-port 1433 --transport tcp

Reverts back to the original, secure internal-only state. Must be run right after testing — leaving SQL Server externally reachable, even password-protected, is real exposure. (az containerapp ingress disable is a different, wrong command here — it would remove ingress entirely, breaking the app's and worker's own internal connections to SQL Server too.)

az containerapp exec --name oneclick-sqlserver --resource-group $Rg --command "/opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P '<password>' -C -Q 'SELECT 1'"

Opens a shell inside the running SQL container and attempts a login directly with sqlcmd — a safer way to test the password against the real running instance without exposing anything externally. (This exact command is also what surfaced the $$ → PID-substitution mangling described in the Gotchas section, since az containerapp exec's own command-string handling passes through a shell.)

Cleanup

.\cleanup.ps1 -EnvironmentTag oneclick -WhatIf
.\cleanup.ps1 -EnvironmentTag oneclick

Previews (deletes nothing), then actually deletes every resource tagged Environment=oneclick, ManagedBy=Bicep — the tag-based path was used here instead of the manifest path because this deployment went through the Portal wizard, which doesn't name its deployment record main by default. Automatically excludes the unrelated VM stack and its disk snapshot (both untagged).

VM backup (unrelated pre-existing resource sharing the same resource group)

az vm show -g rg-tusharpuri -n vm-fhirbridge-dev --query id -o tsv
az vm show -g rg-tusharpuri -n vm-fhirbridge-dev --query storageProfile.osDisk.managedDisk.id -o tsv

Resolves the VM's own resource ID and its OS disk's resource ID directly through the dedicated az vm show command — not the generic az resource show --resource-type Microsoft.Compute/virtualMachines, which hit a NoRegisteredProviderFound error from picking an API version not yet available for that provider/region.

az group export --resource-group rg-tusharpuri --resource-ids $ids

Exports the ARM configuration (settings, not data) for the VM and its networking stack (NSG, public IP, VNet, NIC) — redeployable later with az deployment group create --template-file <export>.json if any of those resources gets deleted by mistake.

az disk show --ids <os-disk-id> --query location -o tsv
az snapshot create --resource-group rg-tusharpuri --name <snapshot-name> --location <disk-location> --source <os-disk-id>

Snapshots the actual disk content (OS, installed software, files). The explicit --location matters: az snapshot create defaults to the resource group's region, not the disk's — here the group is eastus but the disk is westus, so omitting it caused a "Resource ... is not found" error even though the disk genuinely existed.

az snapshot show --resource-group rg-tusharpuri --name <snapshot-name> --query provisioningState -o tsv

Confirms the snapshot actually completed (Succeeded) — worth checking explicitly, since a failed native command doesn't stop a PowerShell script under default settings (see Gotchas).

⚠Gotchas Found This Session

SQL Server's sa password only applies on first initialization Changing MSSQL_SA_PASSWORD and redeploying doesn't change the password if the mounted Azure File share already has data from an earlier attempt — SQL Server silently keeps the original. Fix: delete and recreate the file share, then restart the container.
$, backticks, and quotes in passwords are risky A password containing $$ was directly observed being corrupted into a PID substitution when passed through a shell-processed path. Stick to letters and digits for SQL/JWT/Redis secrets — length and case-mixing are enough for strength without this risk.
Copy-pasting a password from a chat window or table can introduce a stray space ADO.NET trims it when parsing a connection string; a raw container environment variable does not — the two sides end up with different actual passwords. Check (secretValue).Length against the expected character count to catch this instantly.
PowerShell + az CLI's Windows batch wrapper mishandles JMESPath brackets --query "[?starts_with(name,'x')]" can throw a cmd.exe-style parse error ("] was unexpected at this time"). Fetch a plain list with --query "[].name" and filter with PowerShell's own Where-Object instead.
az storage share delete/create don't accept --auth-mode key Unlike many other az storage subcommands, these two need an explicit --account-key or connection string.
Generic az resource show --resource-type Microsoft.Compute/virtualMachines can pick a bad API version Hit NoRegisteredProviderFound for an API version not yet available in that region. The dedicated az vm show command resolves its own correct version and doesn't have this problem.
az snapshot create defaults to the resource group's region, not the source disk's If they differ (as they did here — group in eastus, disk in westus), it looks for the disk in the wrong region and fails with a misleading "not found." Pass --location explicitly, matching the disk.
PowerShell doesn't treat a native command's non-zero exit code as terminating Even with $ErrorActionPreference = "Stop", a failed az/terraform call won't stop the script or trigger a catch — check $LASTEXITCODE explicitly after anything that must succeed before continuing.
