1.Overview

The goal was to host the FHIRBridge API and Portal UI on a Windows Server today, using a deployment mechanism that would carry over to a Linux server later without redesigning anything. That ruled out IIS (Windows-only) in favor of running everything as plain Kestrel processes, with the previously-empty FHIRBridge.Gateway (YARP) project built out as the single public entry point in front of the API and the portal's static files. The server itself is a domain-less internal/local Windows Server (Azure VM), so TLS uses a self-signed certificate for now, with a clear path to a real Let's Encrypt certificate (via the already-staged win-acme tool) once a domain is registered.

2.Why Kestrel + YARP instead of IIS

The initial plan was a conventional IIS deployment (ASP.NET Core Hosting Bundle, IIS sites, web.config, win-acme wired into IIS bindings). That was reworked once the actual requirement surfaced: the same deployment approach needs to work on Linux too, and IIS simply doesn't exist there. Kestrel is built into ASP.NET Core on every platform, and YARP (a .NET reverse proxy that itself runs on Kestrel) was already scaffolded in this repo as FHIRBridge.Gateway — unused, but exactly the right shape for this. Building that out means the entire stack (API, Gateway, and the portal's static files served through it) is nothing but Kestrel processes, identical on Windows and Linux; only the process supervisor (Windows Service vs. systemd) and the TLS certificate tooling (win-acme vs. certbot) differ per OS.

3.Architecture

Single public entry point, path-based routing, one domain, one certificate:

  • FHIRBridge.Gateway binds the public ports (80/443) and is the only internet-facing process.
  • Requests to /api/** are reverse-proxied via YARP to FHIRBridge.Api, which binds to loopback only (127.0.0.1:5000) — set via ASPNETCORE_URLS on the service, not in code, so local dotnet run is unaffected.
  • Requests to /swagger/** are also proxied to the same API cluster, gated behind a Swagger:Enabled config flag (temporarily on in Production, per an explicit request — trivially switched back off later, no redeploy needed).
  • Everything else is served as static files from the portal's production build, with SPA fallback to index.html for any non-file, non-API path (Angular client-side routing).
  • Cross-platform process hosting: both FHIRBridge.Api and FHIRBridge.Gateway call UseWindowsService().UseSystemd() right after WebApplication.CreateBuilder(args) — no-ops unless actually launched by that OS's service manager, so the same published output runs as a Windows Service today or a systemd unit later.
Same-origin by design Because the portal is served by the same Gateway/origin as /api/**, the portal's production apiBase is simply empty — every API call becomes a relative path (/api/v1/...), which is same-origin and needs no CORS configuration in production at all.

6.Setup steps, in order

6.1 — Prerequisites

1
Install the .NET 9 ASP.NET Core RuntimeNot the Hosting Bundle — there's no IIS in this model. Also requires the separate plain .NET Runtime (Microsoft.NETCore.App) — see 7.1.
2
FirewallAllow inbound 80/443 if reachable from other machines on the LAN. FHIRBridge.Api stays loopback-only regardless.

6.2 — Build, publish, copy

dotnet publish src/Api/FHIRBridge.Api -c Release -o C:\deploy\fhirbridge-api
dotnet publish src/Gateway/FHIRBridge.Gateway -c Release -o C:\deploy\fhirbridge-gateway
cd portal; npm ci; npm run build   # -> portal/dist/fhirbridge-ui/browser

Copy each output into its matching C:\inetpub\wwwroot\fhirbridge-* folder on the server.

6.3 — Self-signed certificate (no domain needed yet)

$cert = New-SelfSignedCertificate `
  -DnsName "localhost", "<server-hostname>", "<server-lan-ip>" `
  -CertStoreLocation "cert:\LocalMachine\My" `
  -NotAfter (Get-Date).AddYears(5)

$pwd = ConvertTo-SecureString -String "<pfx-password>" -Force -AsPlainText
Export-PfxCertificate -Cert $cert -FilePath "C:\inetpub\FHIRBridge-certs\gateway.pfx" -Password $pwd

The SAN list must include whatever hostname/IP ends up in the browser's address bar, or you get a name-mismatch warning on top of the expected self-signed one.

6.4 — Production config

C:\inetpub\wwwroot\fhirbridge-api\appsettings.Production.json:

{
  "ConnectionStrings": { "FHIRBridgeDb": "Server=<sql-host>;Database=FHIRBridge;User Id=...;Password=...;TrustServerCertificate=True;Encrypt=True" },
  "Authentication": { "SigningKey": "<long random secret>" },
  "DataProtection": { "KeyRingPath": "C:\\inetpub\\dataprotection-keys" },
  "Swagger": { "Enabled": true },
  "AllowedHosts": "*"
}

C:\inetpub\wwwroot\fhirbridge-gateway\appsettings.Production.json:

{
  "ReverseProxy": {
    "Routes": {
      "api-route": { "ClusterId": "api-cluster", "Match": { "Path": "/api/{**catch-all}" } },
      "swagger-route": { "ClusterId": "api-cluster", "Match": { "Path": "/swagger/{**catch-all}" } }
    },
    "Clusters": { "api-cluster": { "Destinations": { "destination1": { "Address": "http://127.0.0.1:5000/" } } } }
  },
  "StaticFiles": { "RootPath": "C:\\inetpub\\wwwroot\\fhirbridge-portal" },
  "Kestrel": {
    "Endpoints": {
      "Http": { "Url": "http://0.0.0.0:80" },
      "Https": { "Url": "https://0.0.0.0:443", "Certificate": { "Path": "C:\\inetpub\\FHIRBridge-certs\\gateway.pfx" } }
    }
  },
  "AllowedHosts": "*"
}
Filename matters ASP.NET Core only auto-loads files named exactly appsettings.json and appsettings.{Environment}.json. A file named anything else (e.g. API-Server-AppSetting.json) is silently never loaded — see 7.6.

The PFX password is not stored in this file — it's set via an environment variable on the service (next step) so it isn't sitting in plaintext config.

6.5 — Register as Windows Services

New-Service -Name "FHIRBridge.Api" -BinaryPathName '"C:\inetpub\wwwroot\fhirbridge-api\FHIRBridge.Api.exe"' -DisplayName "FHIRBridge API" -StartupType Automatic
New-Service -Name "FHIRBridge.Gateway" -BinaryPathName '"C:\inetpub\wwwroot\fhirbridge-gateway\FHIRBridge.Gateway.exe"' -DisplayName "FHIRBridge Gateway" -StartupType Automatic

Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Services\FHIRBridge.Api" -Name Environment -Value ([string[]]@(
  "ASPNETCORE_ENVIRONMENT=Production",
  "ASPNETCORE_URLS=http://127.0.0.1:5000"
)) -Type MultiString

Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Services\FHIRBridge.Gateway" -Name Environment -Value ([string[]]@(
  "ASPNETCORE_ENVIRONMENT=Production",
  "Kestrel__Endpoints__Https__Certificate__Password=<pfx-password>"
)) -Type MultiString

Restart-Service FHIRBridge.Api
Restart-Service FHIRBridge.Gateway

Grant the service account read/write on C:\inetpub\dataprotection-keys and C:\inetpub\FHIRBridge-certs.

6.6 — First-run setup

The database schema self-provisions on boot (EF Core migrations run automatically, and IRbacBootstrapper seeds the permission catalog and system roles idempotently every startup) — but by design, no admin user is seeded from config. The very first SuperAdmin is created interactively: 

https://localhost/setup

This route is one-shot — once any user exists, it locks itself out and any further attempt returns an error.

7.Errors faced & corrections

In the order they actually came up, grouped by theme.

7.1 — Runtime & Windows Service issues

SymptomRoot causeFix
Restart-Service failed: "Cannot start service ... on computer '.'" (generic SCM error, no detail) The Service Control Manager's error is a wrapper — it never shows the real exception. Run the published .exe directly in a console (bypasses SCM, behaves like a normal console app) to see the actual startup exception.
"You must install or update .NET to run this application" — needed Microsoft.NETCore.App 9.0.0, only 10.0.10 present App targets net9.0; .NET doesn't roll forward across major versions by default. Installed the ASP.NET Core Runtime 9.0.18 (matching the app's TFM), side-by-side with the existing 10.0.10.
Downloaded runtime installer, ran dotnet.exe from the extracted folder — appeared to do nothing Downloaded the zip/binaries archive, not the installer — a portable copy that doesn't register anything system-wide; running its bare dotnet.exe with no args just prints usage and exits. Re-downloaded the actual installer (a single .exe, not a folder) and ran that.
Same "install .NET" error persisted even after installing the ASP.NET Core Runtime The ASP.NET Core Runtime installer didn't bring its Microsoft.NETCore.App dependency along this time (normally bundled together). Separately installed the plain .NET Runtime 9.0.18 (dotnet-runtime-9.0.18-win-x64.exe).
Set-ItemProperty ... -Name Environment -Value @(...) threw "RegistryKey.SetValue does not support arrays of type 'Object[]'" PowerShell built the array literal as generic Object[], but REG_MULTI_SZ needs a real String[]. Explicit [string[]]@(...) cast plus -Type MultiString.
Startup warning: "No XML encryptor configured. Key may be persisted to storage in unencrypted form" Data Protection key ring persisted to disk as plaintext XML, with no encryption-at-rest layer. Recommended .ProtectKeysWithDpapi(protectToLocalMachine: true) — machine-level DPAPI is right for a single Windows Server, and protectToLocalMachine specifically matters since the app runs interactively (current user) during testing but as a Windows Service (different identity) in production.

7.2 — Port & process conflicts

SymptomRoot causeFix
API failed to bind port 5000: SocketException 10013 ("forbidden by its access permissions") Another already-running process (one of several stray leftover dotnet.exe processes) already held the port. Identified via netstat -ano, freed the port before retrying.
FHIRBridge.Gateway service showed Stopped immediately after starting Port 80 was already LISTENING under PID 4 (System/HTTP.sys) — IIS's default site, pre-installed on this Azure Windows Server image, auto-bound to port 80. Stop-Service W3SVC -Force; Set-Service W3SVC -StartupType Disabled, since IIS isn't used in this design at all.
Invoke-WebRequest https://localhost/ → "Unable to connect to the remote server" Gateway genuinely wasn't running yet at that point — both services had failed to start earlier in the sequence (runtime issue, then the port-80 conflict). Confirmed via Get-Service + netstat, then started both services properly once the underlying issues above were fixed.

7.3 — TLS / browser testing quirks

SymptomRoot causeFix
Invoke-WebRequest -SkipCertificateCheck → "A parameter cannot be found" -SkipCertificateCheck only exists in PowerShell 7+; this server runs Windows PowerShell 5.1. Override [System.Net.ServicePointManager]::ServerCertificateValidationCallback for the session instead (session-scoped — must be re-applied in any new console window).
Same cert bypass reapplied but request still failed: "underlying connection was closed: unexpected error on a send" The bypass had been set in a different PowerShell window/session than the one running the test. Re-ran the two ServicePointManager override lines in the same session as the test (or switched to real curl.exe -k, which doesn't depend on session state).

7.4 — Application-level bugs found

SymptomRoot causeFix
Gateway crashed on start: System.ArgumentException: The path must be absolute. (Parameter 'root') PhysicalFileProvider requires an absolute path; the local-dev StaticFiles:RootPath config value was relative. Resolve the configured path via Path.GetFullPath(...) before constructing the provider — works for both relative (dev) and absolute (prod) values.
Browser console: CORS policy blocked requests to http://localhost:5000/api/v1/config and /auth/setup-status from origin https://localhost Real, pre-existing bug in portal/angular.json: the production build configuration was missing fileReplacements to swap in environment.prod.ts. Every "production" build had silently kept using the dev environment file (apiBase: 'http://localhost:5000') the whole time, regardless of any edits made to environment.prod.ts itself. Added the missing fileReplacements entry to angular.json. Verified by inspecting the rebuilt bundle directly — confirmed the environment chunk now bundles {production:true, apiBase:""}.
https://localhost/swagger/index.html loaded the Angular login page instead of Swagger UI, with the same CORS-looking errors Gateway's YARP route only proxied /api/**; a request to /swagger/** fell through to the static-file branch, which serves index.html for any unmatched path (the SPA fallback) — it was never reaching the API at all. Added a second YARP route for /swagger/{**catch-all} pointed at the same API cluster.

7.5 — Configuration mistakes

SymptomRoot causeFix
Recurring "Bad Request – Invalid Hostname" / "HTTP Error 400. The request hostname is invalid." on /api/v1/config and /setup-status, through the Gateway Kestrel's own Host-header validation, driven by AllowedHosts: "localhost" in the base appsettings.json — rejected because the browser's actual Host header didn't match that literal string exactly. Reproduced and confirmed empirically (same request with a matching Host header succeeded; YARP itself was confirmed to forward the original Host header correctly, ruling out the proxy as the cause). "AllowedHosts": "*" in appsettings.Production.json — safe here since Gateway is the only thing that talks to this loopback-only API directly.
Production config edits appeared to have no effect at all The two override files were named API-Server-AppSetting.json and Gateway-appsetting.json — ASP.NET Core only auto-loads appsettings.json / appsettings.{Environment}.json by exact name, so neither file was ever actually being loaded. Renamed both to appsettings.Production.json in their respective app folders.
Even after renaming, the added swagger-route still didn't work JSON indentation bug: swagger-route was nested as a sibling of Routes/Clusters directly under ReverseProxy, instead of inside Routes. Confirmed by parsing the file: ReverseProxy keys came back as ['Routes', 'swagger-route', 'Clusters']. YARP only reads routes from ReverseProxy:Routes:*, so it was silently ignored. Corrected the nesting so swagger-route sits inside the Routes object alongside api-route.
Draft production config files had SigningKey, DataProtection:KeyRingPath still empty, and AllowedHosts still "localhost" despite intending to override them The files were essentially a copy of the base appsettings.json with only the connection string filled in — the other intended overrides were never actually added. Filled in the generated signing key, the key-ring path, AllowedHosts: "*", and the Swagger:Enabled flag explicitly.

8.Open items / still verifying

FHIRBridge.Api.exe appeared to hang with zero console output Most likely cause: the very first thing that runs at boot is the Epic endpoint directory seeder's outbound HTTPS call to https://open.epic.com/Endpoints/R4, wrapped in a Polly resilience/retry pipeline that only logs after an attempt completes — if outbound internet access from this VM is blocked (NSG/firewall silently dropping packets rather than actively refusing), nothing prints until the retries exhaust (the seeder is deliberately designed to log a warning and continue rather than block startup forever, so this should self-resolve within roughly 30–60 seconds). Diagnostic steps handed off: check Get-NetTCPConnection -OwningProcess <pid> for a stuck SynSent connection, or capture a live thread stack with dotnet-dump collect / clrstack -all for a definitive answer. Not yet confirmed which it was.
Database connection appeared to still read from appsettings.Development.json values Most likely cause: ASPNETCORE_ENVIRONMENT=Production is session-scoped when set via $env:... and doesn't persist across PowerShell windows — a fresh console without it re-set would fall through to a different value. Diagnostic steps handed off: check for a persisted machine/user-level ASPNETCORE_ENVIRONMENT override, confirm the current session's value, and confirm the Windows Service's registry Environment value actually stuck. Not yet confirmed which it was.

  • Production bundle check: after the angular.json fix, inspected the built JS bundle directly to confirm the environment chunk bundles {production:true, apiBase:""} rather than the dev URL.
