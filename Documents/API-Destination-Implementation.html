1.Overview

ApiEndpoint is FHIRBridge's general-purpose, fully-configurable outbound REST destination — the one built specifically so an arbitrary customer- or partner-owned API never forces a workaround. Every other destination type assumes a fixed shape (a SQL table, a CSV file, a specific vendor's ingestion contract); ApiEndpoint instead lets the caller describe exactly what their API expects — HTTP method, batching, payload framing, and (via the Request Body Template) the literal JSON shape the receiving API needs — and FHIRBridge substitutes each record's mapped values into it.

3.Call-setup types

Set via dest_apiPayloadShape (and, for the last two, dest_apiMultiResourceMode) — how a batch of mapped records is framed into the request body. Every "Setup steps" box below references the destination card's "⇩ Load JSON payload" button — a solid blue pill on the card's toolbar, deliberately styled to stand out from the small "+"/"Add" buttons next to it (and to read as the same weight of action as the source-side tree's own "⇩ Load JSON payload" toolbar button above it).

1. Single object — one record per request

RecordPerRequest
Matches Demo_TestApp's SingleRecord sample · POST http://localhost:5500/api/apitest/single-record

For an API that can't accept a batch at all. Every batching setting (dest_apiBatchSize, dest_apiMaxRequestBytes) is ignored — the destination sends one bare JSON object per mapped record, one request per record.

Setup steps
1Select resources: check Patient only — a single resource type, one card.
2Destination structure: on the Patient card, "Load JSON payload" with {"mrn":"...","firstName":"...","lastName":"...","dateOfBirth":"...","gender":"..."} — no separate template needed, this shape IS the request body (this is the default fixed shape's values object; you can skip Load JSON payload entirely and just let mapped fields flow through unmapped-to-a-template).
3Map fields: drag Patient.identifier[MRN].value → mrn, Patient.name.given → firstName, Patient.name.family → lastName, Patient.birthDate → dateOfBirth, Patient.gender → gender.

4. Envelope — run metadata plus records

Matches Demo_TestApp's RecordsEnvelope sample · POST http://localhost:5500/api/apitest/records-envelope

Wraps the batch with provenance — { "meta": {...}, "records": [...] } — for an API that wants to know what a batch IS before reading what's in it. meta fields are regular mappable columns on the Mapping Profile screen (prefixed "Meta"), resolved from the batch's first record; recordCount is the one field auto-computed from the real batch size, never mapped.

Setup steps
1Select resources: check Patient only — the envelope wraps ONE resource type's records, same as JSON array.
2Destination structure: on the Patient card, "Load JSON payload" with the FULL envelope shape — {"meta":{"resourceType":"...","recordCount":0,"routeName":"..."},"records":[{"mrn":"...","firstName":"...","lastName":"..."}]} — this is what makes "MetaResourceType"/"MetaRouteName" appear as their own mappable columns, distinct from the per-record ones.
3Map fields: mrn/firstName/lastName as usual, PLUS (optionally) a source field onto MetaResourceType/MetaRouteName if your API needs real values there — leave them unmapped and they render as their literal template text. Never map anything onto recordCount — it's auto-computed, not a mapping target.

5. Custom shape — Request Body Template

Matches Demo_TestApp's CustomEvent sample · POST http://localhost:5500/api/apitest/custom-event

Pairs with any payload shape above. Paste the exact JSON your partner API expects into dest_apiBodyTemplateJson, with {{fieldName}} placeholders anywhere inside it — a value that is exactly one placeholder keeps its real JSON type (a number stays a number); a placeholder embedded in a longer string is text-substituted. sourceResourceId, resourceType, destinationObject and pipelineRunId are addressable by name alongside your mapped field names. The destination wizard's "Load JSON payload" feature (mapping canvas) can auto-generate this template — and its matching mappable columns — straight from a pasted example of the target API's shape, so no hand-typed {{}} is required.

Setup steps
1Select resources: check Patient only.
2Destination structure: on the Patient card, "Load JSON payload" with the partner's OWN event shape — {"eventType":"PatientUpdated","patient":{"id":"...","fullName":"...","age":0},"source":"FHIRBridge"} — even though it's nested and not FHIRBridge's own conventions, this becomes the columns FullName/Age etc. AND auto-fills dest_apiBodyTemplateJson in one step.
3Map fields: Patient.name.text → FullName, a computed/derived age field → Age. eventType and source stay as the literal static text from your pasted example unless you also map something onto them — a template value only becomes dynamic where you actually dragged a field onto it.

6. Multi-resource — Flat

Combine mode
Matches Demo_TestApp's MultiResourceFlat sample · POST http://localhost:5500/api/apitest/multi-resource-flat

Combines more than one mapped resource type (e.g. Patient + Encounter) into ONE outgoing document as top-level sibling arrays, with no nesting — correlation is left to the receiving API (e.g. via its own patientMrn-style field). Handled entirely inside MappedApiEndpointDestinationWriter via an in-process accumulator that holds each resource type's records until every declared type has landed for the run — no change to how the pipeline calls the writer, and every other destination is unaffected.

Setup steps (full walkthrough in §4)
1Select resources: check BOTH Patient AND Encounter — two separate checkboxes, two separate cards.
2Destination structure: on the Patient card, Load JSON payload with {"mrn":"...","firstName":"...","lastName":"..."}. Separately, on the Encounter card, Load JSON payload with {"encounterId":"...","patientMrn":"...","reason":"..."} — two independent operations, one per card, never one combined paste covering both.
3Map fields: Patient fields onto the Patient card as usual. On the Encounter card: Encounter.id → encounterId, a reason field → reason, and — the important one — Encounter.subject.reference (flattened to the same MRN format Patient uses) → patientMrn. This last mapping must live on the Encounter card, not Patient's.
4Destination settings: set dest_apiMultiResourceMode=flat and dest_apiResourceRelationsJson referencing patientMrn exactly as it's spelled on the Encounter card.

7. Multi-resource — Nested

Combine mode
Matches Demo_TestApp's MultiResourceNested sample · POST http://localhost:5500/api/apitest/multi-resource-nested

Correlates a child resource type to its parent (by a mapped reference field) and nests it directly inside the parent's own record — { "patients": [{ ..., "encounters": [...] }] }. CorrelationColumn is the mapped column ON THE CHILD holding the parent's key; ParentKeyColumn is the mapped column ON THE PARENT it's matched against. Only the (now-nested) parent array is placed at the top level — the child never also appears there.

Setup steps (full walkthrough in §4)
1Select resources: check BOTH Patient AND Encounter.
2Destination structure: Patient card gets {"mrn":"...","firstName":"...","lastName":"..."}. Encounter card gets {"encounterId":"...","reason":"..."} — note NO patientMrn field needed here in Nested mode (unlike Flat), since the correlation column just needs to exist as a mapped value, not necessarily appear in the outgoing shape itself.
3Map fields: on the Patient card, also map a field onto an Id column (Load JSON payload it in, or add it as a free column) — this is the parentKeyColumn every child correlates against. On the Encounter card, map Encounter.subject.reference onto a PatientId column (also add it as a free column if it's not part of your pasted sample) — this is the correlationColumn.
4Destination settings: set dest_apiMultiResourceMode=nested and dest_apiResourceRelationsJson's correlationColumn/parentKeyColumn to those exact mapped column names (PatientId on Encounter, Id on Patient).

N levels deep, not just 2 — Patient → Encounter → Observation → Component

Nesting depth is unbounded. Any resource type's ParentResourceType can itself be another entry's ResourceType, and that entry's own ParentResourceType can point further up again — nothing in MappedApiEndpointDestinationWriter caps how long that chain can be. It resolves nesting depth-first (by walking each relation's ParentResourceType back to its root), so the order entries appear in dest_apiResourceRelationsJson never matters — the deepest relation is always folded into its immediate parent before that parent is folded into its own parent, all the way up to the root, for as many levels as you declare.

Add one row in the "Participating resource types" builder per level, however many you need — there's no fixed count, and the builder's Parent dropdown can point at any row already added, including one that's itself someone else's child. Every resource type that isn't the true root or an innermost leaf needs BOTH: a Parent key column (a mapped column identifying it, matched against by whatever nests inside it) and a Correlation column (a mapped column identifying which of ITS OWN parent's records it belongs to) — Encounter above needs its own Id (for Observation to match against) as well as PatientId (to match against Patient.Id); Observation needs its own Id (for Component) as well as EncounterId. 4.How to configure multi-resource mapping (step-by-step)

§3.6/3.7 above showed the destination settings (dest_apiMultiResourceMode, dest_apiResourceRelationsJson, …) for Flat and Nested combining. Those settings only reference field names — they don't create the mappings themselves. Every participating resource type needs its own, separate field mapping on the Mapping Profile / mapping canvas screen, done in exactly the same way any other multi-table destination (SQL Server, MySQL, Mongo…) maps more than one resource type: each selected resource gets its own destination card, and you map that resource's own FHIR fields onto that card's own columns. The walkthrough below builds the running Patient + Encounter (Flat) example from §3.6 end to end.

This is the step people skip A destination row can have dest_apiResourceRelationsJson and dest_apiRecordTemplatesByResourceType filled in perfectly and still send nulls, because those two settings are just JSON text — they don't verify that the column names they reference actually exist as real mappings on the resource type they're supposed to belong to. If a field ends up mapped on the wrong resource's card (see §4.5 below), FHIRBridge has no way to know that was a mistake — it just resolves that placeholder to nothing for the resource type that's actually missing it, every run, silently.

Step 1 — Select resources

On the wizard's Resources step, check off every resource type that participates in the combined document — not just the root. For the running example, check both Patient and Encounter. Each checked resource gets its own destination card further down the wizard, each with its own independent set of columns and mappings — they do not share anything by default.

Step 2 — Give each resource its destination JSON structure

On the Mapping step, you'll now see two destination cards: one for Patient, one for Encounter. On each card separately, click "Load JSON payload" and paste that ONE resource's own record shape — not the combined document, just the one resource's own per-record object:

CardPaste this (that resource's own record shape only)
Patient card{"mrn":"MRN-5001","firstName":"Grace","lastName":"Kim"}
Encounter card{"encounterId":"ENC-9001","patientMrn":"MRN-5001","reason":"Annual checkup"}

This creates real columns on each card — Mrn/FirstName/LastName on Patient, EncounterId/PatientMrn/Reason on Encounter — and auto-generates that card's own Request Body Template. The Encounter card's PatientMrn column is the correlation field — it exists on Encounter specifically so a mapped value can land there identifying which patient this encounter belongs to (see Step 3).

Step 3 — Map fields onto each resource's own card

Drag FHIR fields onto columns exactly as you would for any single-resource destination — the source tree above each card is already scoped to that card's own resource type, so there's no way to drag an Encounter field onto the Patient card by accident. Map:

  • Patient card: Patient.identifier[MRN].value → Mrn, Patient.name.given → FirstName, Patient.name.family → LastName.
  • Encounter card: Encounter.id → EncounterId, Encounter.type.text (or similar) → Reason, and — the field that makes correlation work — Encounter.subject.reference (the FHIR reference back to the patient, flattened to the patient's MRN/id by your source connector) → PatientMrn. This mapping must exist ON THE ENCOUNTER CARD. Nothing needs to be mapped on the Patient card for this relationship — Patient doesn't need to know which encounters reference it.

Step 4 — Configure the multi-resource settings

Now a builder, not raw JSON dest_apiResourceRelationsJson and dest_apiRecordTemplatesByResourceType are still the underlying values FHIRBridge reads — but you no longer type JSON by hand to set them. The destination's own settings panel now shows a "Participating resource types" builder (add/remove rows, plain fields, a Parent dropdown for Nested mode) that writes dest_apiResourceRelationsJson for you, and dest_apiRecordTemplatesByResourceType fills itself in automatically the moment you use "⇩ Load JSON payload" on each resource's own card back in Step 2 — no separate step here at all for that one. The raw JSON shown below is what those two end up producing, useful for understanding what's actually stored or for troubleshooting, but you'll rarely type it directly.

On the destination's own settings (not the mapping canvas), set "Multiple resources in one document" to Flat, then use the Participating resource types builder — click "+ Add resource" once per resource type, filling in each row:

Builder fieldRow 1 (Patient)Row 2 (Encounter)
Resource typePatientEncounter
Nest keypatientsencounters

That produces the exact same dest_apiResourceRelationsJson as before — [{"resourceType":"Patient","nestKey":"patients"},{"resourceType":"Encounter","nestKey":"encounters"}] — just without typing a brace or an escaped quote. dest_apiRecordTemplatesByResourceType needs no action here: it already picked up Encounter's template ({"encounterId":"{{EncounterId}}","patientMrn":"{{PatientMrn}}","reason":"{{Reason}}"}) the moment you ran "Load JSON payload" on the Encounter card in Step 2, keyed automatically — you'll see it listed as a pill under "Configured for:" above that field.

For Nested mode, each non-root row's builder gets a Parent dropdown (populated from your other rows' resource types) plus Correlation column and Parent key column inputs once a parent is picked — same rule as before, just as builder fields instead of JSON keys: Correlation column must be a column mapped on the CHILD's own card (Encounter's PatientMrn), and Parent key column must be a column mapped on the PARENT's own card (Patient's Mrn) — see §3.7. The same builder chains to any depth (§3.7's "N levels deep") by picking an already-added row as another row's Parent.

Common mistakes

The correlation field gets mapped on the wrong card The single most common failure: instead of mapping the patient-link field on the Encounter card (Step 3 above), it gets mapped on the Patient card instead — often because "Load JSON payload" was run with a combined, nested sample pasted onto ONE card instead of each resource's own flat shape pasted onto its OWN card (Step 2). The symptom looks exactly like a bug: the combined document comes out with the correlation value sitting under patients[].values (e.g. as some auto-named column like EncountersPatientMrn) while every encounter's own patientMrn field is null — because Encounter's mapping profile genuinely has nothing mapped to that name. Fix: map the correlation field on the CHILD resource's own card, matching whatever name you reference as correlationColumn/the template placeholder for that resource type.
Field names are case-sensitive {{PatientMrn}} and a mapped column named patientMrn do NOT match. Whatever casing "Load JSON payload" (or you, typing a column name by hand) actually produced is the casing every reference to it — in dest_apiRecordTemplatesByResourceType, correlationColumn, and parentKeyColumn — must use exactly.
A resource type declared in dest_apiResourceRelationsJson but not selected in Step 1 never contributes any records — the accumulator waits forever for a resource type that's never actually routed to this destination, and the combined document never sends at all. Every resourceType in the JSON must have a matching checked box on the Resources step.

Worked example: diagnosing this exact symptom

A real Flat-mode run produced this (trimmed to one patient/encounter pair):

{
  "patients": [{
    "resourceType": "Patient",
    "values": {
      "PatientsFirstName": null,
      "PatientsLastName": null,
      "PatientsMrn": "egqBHVfQlt4Bw3XGXoxVxHg3",
      "EncountersPatientMrn": "egqBHVfQlt4Bw3XGXoxVxHg3"
    }
  }],
  "encounters": [{
    "encounterId": "emhwuharfnf8VhCQg97qP7Q3",
    "patientMrn": null,
    "reason": null
  }]
}
SymptomWhat it means
PatientsFirstName / PatientsLastName are nullPatient is using its DEFAULT record shape (no per-resource-type template configured for it) — these two are unmapped/unresolved FHIR source fields, unrelated to the multi-resource setup itself; check the Patient card's own mappings.
A field named EncountersPatientMrn holds the real MRN, but it's sitting under patients[]Someone mapped the correlation field on the Patient card (giving it that auto-generated name) instead of on the Encounter card — see the "correlation field gets mapped on the wrong card" callout above.
encounters[].encounterId resolves fine, but patientMrn and reason are both nullEncounter DOES have its own per-resource-type Request Body Template (that's why its shape is flat, not the default envelope) — but its {{PatientMrn}}/{{Reason}} placeholders don't match any column actually mapped on the Encounter card, because (per the row above) the real mapping never landed there.

Fix, following Steps 2–3 above:

  1. On the Encounter card, run "Load JSON payload" with {"encounterId":"...","patientMrn":"...","reason":"..."} if that card doesn't already have a PatientMrn column.
  2. Drag the FHIR field that identifies the encounter's patient (e.g. Encounter.subject.reference, flattened to the same MRN format as Patient's own MRN field) onto the Encounter card's PatientMrn column — not the Patient card.
  3. Remove the stray EncountersPatientMrn mapping from the Patient card if it's not otherwise needed there.
  4. Separately, fix Patient's own FirstName/LastName mappings — that null is a plain unmapped-field issue, not a multi-resource one.
A related cause is now fixed automatically The Patient card's own values-wrapped shape above (instead of a flat one like Encounter's) used to also happen when someone ran "Load JSON payload" on the Encounter card but never on the Patient card at all — dest_apiRecordTemplatesByResourceType simply had no entry for Patient. "⇩ Load JSON payload" now always writes into the correct resource type's own entry the moment multi-resource mode is on (previously it silently overwrote the single-resource dest_apiBodyTemplateJson field instead, which does nothing in multi-resource mode) — so running it once per card, per resource, is now enough. The "Configured for: …" pill list above the (now-collapsed) raw JSON field is the fastest way to confirm every resource type actually has one before running the destination.
