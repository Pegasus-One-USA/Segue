Client Credentials — Trigger a Workflow

How to generate a Client ID/Secret in FHIRBridge and use it to trigger any workflow's execution from your own backend, server-to-server — no FHIRBridge login, no per-workflow setup.

01Generate a Client ID/Secret

Unlike the SMART Standalone launch flow (a separate document), this is not tied to any single workflow, EHR vendor, or patient login — it's a tenant-wide machine credential an admin creates once, then any of your own backend services can use to trigger any workflow.

What an admin does, once
1

In the FHIRBridge portal, go to Settings → System Settings → General → API Clients and click New Client.

2

Give it a name (e.g. "HealthApp integration"). FHIRBridge generates a Client ID (safe to log/share, like a username) and a Client Secret, shown exactly once.

3

Copy both immediately into your application's own secret storage (environment variables, a secrets manager) — the Secret cannot be retrieved again. If it's lost, use Regenerate Secret to issue a new one (the Client ID stays the same).

Tenant-wide, not per-workflow A single Client ID/Secret pair can trigger any workflow's /run endpoint, independent of whether that workflow is opted into public SMART launch. There is nothing to configure per workflow — grab the workflow's id from the portal (or the Workflows list API) and you're ready to trigger it.

02Request flow end-to-end

Two actors only: your backend, and FHIRBridge. No browser redirect, no EHR login — this is a pure server-to-server exchange.

Your Backend
FHIRBridge
1 · POST/api/v1/oauth/token
{ grant_type, client_id, client_secret }
← { access_token, token_type, expires_in }
The token is short-lived (15 minutes by default) — cache it and request a new one when it's close to expiring, rather than requesting one per call.
2 · POST/api/v1/workflows/{{ '{' }}workflowId{{ '}' }}/run
Authorization: Bearer <access_token>
← { workflowRun, outputsByNodeId }
3 · use the resultRead workflowRun.status / outputsByNodeId the same way the portal's own Run button does
What this token can and can't do A Client Credentials token only ever works against /workflows/{{ '{' }}id{{ '}' }}/run. It carries no user identity and satisfies none of the portal's own role/permission checks — it can't be used to log into the portal, read/write configuration, or call any other authenticated endpoint. If a token is compromised, its blast radius is "can trigger workflow runs in this tenant," nothing more.

04Code samples

Every sample does the same two calls: get a token, then run the workflow. Substitute your own Client ID/Secret, FHIRBridge base URL, and workflow id.

4.1 curl

terminal
# 1. Get a token
curl -X POST https://your-fhirbridge-host/api/v1/oauth/token \
  -H 'Content-Type: application/json' \
  -d '{"grant_type":"client_credentials","client_id":"cid_xxxxxxxxxxxxxxxxxxxxxxxx","client_secret":"YOUR_SECRET"}'

# 2. Use the returned access_token to run the workflow
curl -X POST https://your-fhirbridge-host/api/v1/workflows/00000000-0000-0000-0000-000000000000/run \
  -H 'Authorization: Bearer <access_token>' \
  -H 'Content-Type: application/json' \
  -d '{}'

4.2 Node / TypeScript

trigger-workflow.ts
const FHIRBRIDGE_BASE_URL = 'https://your-fhirbridge-host';
const CLIENT_ID = process.env.FHIRBRIDGE_CLIENT_ID!;
const CLIENT_SECRET = process.env.FHIRBRIDGE_CLIENT_SECRET!;

// Cache the token in memory (or your own store) and reuse it until close to expiry —
// no need to request a new one on every call.
let cachedToken: { accessToken: string; expiresAtMs: number } | null = null;

async function getAccessToken(): Promise<string> {
  if (cachedToken && cachedToken.expiresAtMs > Date.now() + 5_000) {
    return cachedToken.accessToken;
  }

  const response = await fetch(`${FHIRBRIDGE_BASE_URL}/api/v1/oauth/token`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ grant_type: 'client_credentials', client_id: CLIENT_ID, client_secret: CLIENT_SECRET }),
  });

  if (!response.ok) {
    throw new Error(`Token request failed: ${response.status}`);
  }

  const { access_token, expires_in } = await response.json();
  cachedToken = { accessToken: access_token, expiresAtMs: Date.now() + expires_in * 1000 };
  return access_token;
}

export async function triggerWorkflow(workflowId: string): Promise<unknown> {
  const accessToken = await getAccessToken();

  const response = await fetch(`${FHIRBRIDGE_BASE_URL}/api/v1/workflows/${workflowId}/run`, {
    method: 'POST',
    headers: { 'Authorization': `Bearer ${accessToken}`, 'Content-Type': 'application/json' },
    body: JSON.stringify({}),
  });

  const result = await response.json();
  if (result.workflowRun?.status !== 'Succeeded') {
    throw new Error(result.workflowRun?.errorMessage ?? 'Workflow run failed.');
  }

  return result.outputsByNodeId;
}

4.3 C# / .NET

FhirBridgeWorkflowTrigger.cs
public sealed class FhirBridgeWorkflowTrigger
{
    private readonly HttpClient _http;
    private readonly string _clientId;
    private readonly string _clientSecret;
    private (string Token, DateTime ExpiresOnUtc)? _cachedToken;

    public FhirBridgeWorkflowTrigger(HttpClient http, string clientId, string clientSecret)
    {
        _http = http; // BaseAddress already set to your FHIRBridge host
        _clientId = clientId;
        _clientSecret = clientSecret;
    }

    private async Task<string> GetAccessTokenAsync(CancellationToken ct)
    {
        if (_cachedToken is { } cached && cached.ExpiresOnUtc > DateTime.UtcNow.AddSeconds(5))
        {
            return cached.Token;
        }

        var response = await _http.PostAsJsonAsync("/api/v1/oauth/token", new
        {
            grant_type = "client_credentials",
            client_id = _clientId,
            client_secret = _clientSecret,
        }, ct);
        response.EnsureSuccessStatusCode();

        var body = await response.Content.ReadFromJsonAsync<JsonElement>(cancellationToken: ct);
        var token = body.GetProperty("access_token").GetString()!;
        var expiresIn = body.GetProperty("expires_in").GetInt32();
        _cachedToken = (token, DateTime.UtcNow.AddSeconds(expiresIn));
        return token;
    }

    public async Task<JsonElement> TriggerAsync(Guid workflowId, CancellationToken ct = default)
    {
        var token = await GetAccessTokenAsync(ct);

        using var request = new HttpRequestMessage(HttpMethod.Post, $"/api/v1/workflows/{workflowId}/run")
        {
            Content = JsonContent.Create(new { }),
        };
        request.Headers.Authorization = new AuthenticationHeaderValue("Bearer", token);

        var response = await _http.SendAsync(request, ct);
        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<JsonElement>(cancellationToken: ct);
    }
}

05Security notes

Handle the Secret like any other production credential
  • Store it in your own secrets manager / environment variables — never in source control, logs, or client-side JavaScript. It's only ever shown once, right after creation or regeneration.
  • Tokens are short-lived (15 minutes by default) and there is no refresh token for this grant — request a new one with the Client ID/Secret when the cached one is close to expiring, rather than trying to keep one alive indefinitely.
  • Disabling a client in Settings → API Clients blocks new token issuance immediately. A token it already holds still works until it naturally expires (at most a few minutes later) — there is no separate revoke-in-flight-tokens step to run.
  • If a Secret leaks, use Regenerate Secret right away — the Client ID stays the same, so you only need to update the secret value in your own config, not re-provision anything.

06Browser-redirect trigger (no token round trip)

For a third-party page (not a backend service) that wants to trigger a workflow and land the user back on its own site — think "redirect to pay, redirect back" — FHIRBridge offers a second, simpler path: POST /api/v1/workflows/external/run. A plain HTML form submit does the whole thing; no token request, no JavaScript required.

This needs one extra setup step the token flow doesn't Because the credential and the redirect target arrive together in one browser-driven request, FHIRBridge requires every Return URL to be pre-registered against the Client ID before it will honor it — otherwise an attacker could pass any URL as return_url and get a real workflow trigger to redirect a victim's browser wherever they like (an open redirect). Register one under Settings → API Clients → Edit → Return URLs.
FieldMeaning
client_id / client_secretSame credentials as the token flow
workflow_idThe workflow to trigger
return_urlMust exactly match one URL registered for this client (scheme+host+path, no query/fragment)
ehr_endpoint_codeOptional — a specific hospital/practice endpoint code, when the workflow's source supports more than one
modeasync (default) — redirect immediately, run continues in the background; or sync — wait for the run to finish first

On success, the browser is redirected to {return_url}?status=Triggered|Succeeded|Failed&workflowRunId=.... On a credential, Return URL, or Referer failure, FHIRBridge responds with a plain JSON error instead of redirecting — it will never redirect to a URL it hasn't already validated.

Referer, checked when present When the browser sends a Referer header, its origin must also match one of this client's registered Return URLs. A missing Referer is not itself a failure (browsers often omit it for privacy on a cross-origin navigation) — but a Referer that is present and doesn't match is treated as a real signal of misuse and rejected.

Minimal HTML form

trigger-workflow.html
<form method="post" action="https://your-fhirbridge-host/api/v1/workflows/external/run">
  <input type="hidden" name="client_id" value="cid_xxxxxxxxxxxxxxxxxxxxxxxx" />
  <input type="hidden" name="client_secret" value="YOUR_SECRET" />
  <input type="hidden" name="workflow_id" value="00000000-0000-0000-0000-000000000000" />
  <input type="hidden" name="return_url" value="https://your-app.example.com/trigger-page" />
  <input type="hidden" name="mode" value="async" />
  <button type="submit">Trigger Workflow</button>
</form>

Listing workflows (for a picker)

POST /api/v1/workflows/external/list takes just client_id/client_secret (JSON body) and returns every workflow as [{ id, name }] — useful for populating a dropdown before the form above is submitted. Call this from your own backend, not directly from the browser: it's a JSON POST, so the secret would otherwise sit in client-side JS with no reason to.

07Testing it against the demo app

The bundled demo app (Demo_TestApp/) includes a login-free console for each flow — useful for confirming a Client ID/Secret works before wiring your own integration.

Server-to-server flow
1

Start the demo backend and frontend (see Demo_TestApp/docs/), then open http://localhost:5501/client-credentials-console (or click "Client Credentials test console" on the demo app's login screen).

2

Fill in your FHIRBridge base URL, a workflow id, and the Client ID/Secret you generated. Click Run Test.

3

The console shows both real HTTP calls — the token request and the workflow run — with their exact status codes and response bodies, made server-to-server by the demo backend (see backend/ClientCredentialsDemoEndpoints.cs), so the Secret never touches your browser and there's no CORS configuration to fight with.

Browser-redirect flow
1

Register the demo console's own URL (http://localhost:5501/external-trigger-console) as a Return URL for your test client under Settings → API Clients → Edit → Return URLs first — the demo console pre-fills this exact value, but FHIRBridge will refuse it until it's registered.

2

Open http://localhost:5501/external-trigger-console (or click "External Trigger test console" on the login screen), fill in the Client ID/Secret, click List Workflows, pick one, and click Trigger Workflow.

3

That button is a real HTML form submit (see frontend/.../external-trigger-console.html) — the browser fully navigates to FHIRBridge and back, landing on the same console with ?status=Triggered (or Succeeded/Failed) displayed, exactly as your own integration would see it.
