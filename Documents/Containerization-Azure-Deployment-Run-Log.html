What is “registering Microsoft.App”, and why do we need it?

Self-contained enough to forward to whoever administers the Azure subscription, if needed:

What the command does Azure groups every service it offers into “resource providers” — namespaces like Microsoft.Storage (Storage Accounts), Microsoft.KeyVault (Key Vault), or Microsoft.App (Container Apps, the service this deployment's 5 containers run on). Before a subscription can create any resource of a given service type, that service has to be switched on for the subscription first — a one-time, per-subscription step, not something per-user or per-resource-group. az provider register --namespace Microsoft.App is exactly that switch: it makes the Container Apps service available for use on this subscription. It doesn't create any resources, doesn't touch anything that already exists, and has no cost of its own — a pure feature-enablement action.
Why this deployment needs it This Terraform config creates a Container Apps Environment and 5 Container Apps (fhirbridge-app, demo-app, sqlserver, redis, worker) — all resource types that belong to Microsoft.App. Until that namespace is registered, Azure rejects any attempt to create them with MissingSubscriptionRegistration, no matter what tool asks (Terraform, the Portal, the CLI). This isn't a bug in this config — proven by the fact that every other resource type used here (Microsoft.Storage, Microsoft.KeyVault, Microsoft.ContainerRegistry, Microsoft.OperationalInsights) was already registered and created successfully in the same run. Microsoft.App is simply a newer, less universally pre-registered service.
Why it has to be someone else, not this account Registering a provider is a subscription-wide action (Microsoft.App/register/action) that only works for an identity holding Owner (or a custom role explicitly granting that action) at the subscription scope. This account's access is scoped to the rg-tusharpuri resource group, which is a narrower scope that this specific action doesn't recognize — confirmed directly by attempting it (see Issue 4).

3.Issue 1 fixed

-target=azurerm_container_registry.acr parsed as just azurerm_container_registry

Symptom: Error: Invalid target "azurerm_container_registry" — Resource specification must include a resource type and name.

The target address is valid and matches the resource block in main.tf exactly. Reproducing the identical command locally showed PowerShell passing the argument through intact, pointing to a copy-paste artifact — most likely a line-wrap in the chat UI getting pasted as an actual line break, silently truncating everything after the wrap point.

Fix: re-typed/re-pasted the command with the target value quoted: terraform apply -target="azurerm_container_registry.acr" — worked immediately. No code change; a one-off input issue.

4.Issue 2 fixed

Terraform tried to auto-register ~40 Azure resource providers it doesn't need, and this account can't register any of them

Symptom: a wall of AuthorizationFailed errors for providers like Microsoft.Kusto, Microsoft.AVS, Microsoft.Databricks, Microsoft.Sql, Microsoft.ServiceBus — none of which this deployment actually uses.

The azurerm provider's default behavior is to auto-register every resource provider it supports on first use — a subscription-level action (<Namespace>/register/action) this account doesn't have for any namespace, only some of which this project actually needs.

Fix: added skip_provider_registration = true to the provider "azurerm" block in main.tf. First attempt used the newer resource_provider_registrations = "none" setting the error text itself suggested — that argument doesn't exist on the installed provider version (3.117.1), confirmed by querying its schema directly (terraform providers schema -json); the older boolean argument is what's actually supported here.

5.Issue 3 fixed

Docker Desktop wasn't running

Symptom: az acr login failed with DOCKER_COMMAND_ERROR — open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified.

Both az acr login and the image build script need an active Docker engine. Nothing to do with the Terraform/Bicep config — purely an environment prerequisite.

Fix: started Docker Desktop, waited for it to report ready, verified with docker info, then re-ran az acr login successfully. All 3 images built and pushed cleanly afterward.

6.Issue 4 open — needs a subscription admin

Microsoft.App resource provider isn't registered on this subscription

Symptom: Error: creating Managed Environment … unexpected status 409 (409 Conflict) — MissingSubscriptionRegistration: The subscription is not registered to use namespace 'Microsoft.App'.

This is genuine Azure subscription state, not a Terraform config issue — no setting in this repo can work around it. The Azure Container Apps service (Microsoft.App) has to be registered on the subscription before any tool (Terraform, the Portal, the CLI) can create a Container Apps Environment. Every other provider this deployment needs (Microsoft.ContainerRegistry, Microsoft.Storage, Microsoft.KeyVault, Microsoft.OperationalInsights) was already registered — confirmed by the fact that the ACR, Storage Account, Log Analytics workspace, and Key Vault all created successfully in the same run. Microsoft.App is simply less universally pre-registered since Container Apps is a newer service.

Attempting self-registration confirmed the account can't do it either:

PS> az provider register --namespace Microsoft.App
(AuthorizationFailed) The client 'mitul.shah@pegasusone.com' … does not have authorization
to perform action 'Microsoft.App/register/action' over scope '/subscriptions/4e94fee6…'

Status: blocked. This is a subscription-wide action — not scoped to rg-tusharpuri, so no amount of resource-group-level access fixes it. Needs someone with Owner (or a role granting that specific register action) at the subscription level — see Next steps.

7.Issue 5 fixed

Key Vault RBAC role assignment failed with 403

Symptom: AuthorizationFailed — does not have authorization to perform action 'Microsoft.Authorization/roleAssignments/write' over scope '…/vaults/fhirbridge-kv-0a5d2b/…'

The config originally granted the applying identity "Key Vault Secrets Officer" via an azurerm_role_assignment, using the Vault's RBAC authorization mode. Creating an RBAC role assignment needs Microsoft.Authorization/roleAssignments/write, which requires Owner or User Access Administrator — a narrower permission than Contributor, which this account has instead.

Fix: switched the Key Vault to classic Access Policies (enable_rbac_authorization = false), replacing the role assignment with an azurerm_key_vault_access_policy resource granting Get/List/Set/Delete/Purge on secrets. Access Policies are set via the vault resource itself (Microsoft.KeyVault/vaults/write), which Contributor already includes — same end goal (Key Vault as the secrets source of truth), an authorization model that actually matches this account's real permissions.

8.Issue 6 fixed

The cleanup script's own tag-preview query was invalid az CLI syntax

Symptom: you cannot use '--tag' with '--resource-group'(If the default value for resource group is set, please use 'az configure --defaults group=""' command to clear it first)

This az CLI version rejects combining --tag and --resource-group on az resource list — a real CLI limitation discovered only by actually running the cleanup script, not something documented clearly up front.

Fix: both cleanup-azure.sh and cleanup-azure.ps1 now filter by tag across the whole subscription and narrow to the target resource group client-side instead: az resource list --tag Project=FHIRBridge --query "[?resourceGroup=='rg-tusharpuri']". Purely a preview/confirmation step either way — terraform destroy itself was never affected by this bug, since it works from state, not this query.

9.Issue 7 fixed

Key Vault purge-on-destroy failed, and the cleanup script reported success anyway

Symptom: Error: purging Key Vault … does not have authorization to perform action 'Microsoft.KeyVault/locations/deletedVaults/purge/action' — immediately followed by the script printing Done. Everything this Terraform config created has been removed…

Two separate problems here. First: terraform destroy, by default, doesn't just soft-delete a Key Vault — it also tries to immediately purge it, a separate and more privileged action this account doesn't have (same permission class as Issue 5). The soft-delete itself succeeded; only the automatic follow-up purge failed.

Second, and more important: cleanup-azure.ps1 printed its "Done" success message regardless of whether terraform destroy actually succeeded. The root cause is a genuine PowerShell gotcha — PowerShell does not treat a non-zero exit code from a native executable as a terminating error, even with $ErrorActionPreference = "Stop"; that setting only governs PowerShell's own cmdlets and exceptions, never $LASTEXITCODE from an external process like terraform.exe. Without an explicit check, the script would keep announcing success on any partial failure.

Fix, two parts:

  • Added features { key_vault { purge_soft_delete_on_destroy = false } } to the provider block in main.tf — destroy now only soft-deletes the vault, which then ages out of the 7-day soft-delete retention window on its own, no elevated permission needed.
  • Both cleanup scripts now explicitly check the destroy exit code ($LASTEXITCODE in PowerShell, $? captured under set +e in bash) before printing anything, and report a clear warning instead of a false "Done" when destroy didn't fully succeed.

Re-running cleanup afterward confirmed the fix working as intended in both directions: it correctly reported the failure the first time (instead of masking it), and on the next run Terraform's own state refresh had already detected the Key Vault no longer existed as a live resource and dropped it from state automatically — leaving only random_id.suffix (a local-only value, no real Azure resource) to clean up.

10.This account's actual permission profile

Worth recording plainly, since it explains four of today's six issues and will matter for anyone else running this Terraform against the same subscription with the same account (mitul.shah@pegasusone.com on 4e94fee6-c28c-4cb4-989f-ce4092537c3c).

Can doCan't do
Create/manage resources within rg-tusharpuri: Storage Accounts, Key Vaults, Container Registries, Log Analytics workspaces, Container Apps (once Microsoft.App is registered) Register subscription-level resource providers (<Namespace>/register/action) — blocked Container Apps creation until someone else registers Microsoft.App
Set Key Vault Access Policies directly on a vault it created (Microsoft.KeyVault/vaults/write) Create Azure RBAC role assignments, even on its own resources (Microsoft.Authorization/roleAssignments/write) — needs Owner or User Access Administrator
Soft-delete a Key Vault via terraform destroy Purge a soft-deleted Key Vault (Microsoft.KeyVault/locations/deletedVaults/purge/action)

In short: a Contributor-shaped role on the resource group, without User Access Administrator and without subscription-level provider-registration rights. The Terraform config now works entirely within that profile — see the change table below — except for the one action that's genuinely impossible to work around: registering a resource provider is always subscription-scoped in Azure, full stop.
