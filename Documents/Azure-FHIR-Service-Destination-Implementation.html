1.Overview

Azure FHIR Service (Azure Health Data Services' FHIR API) is now a first-class destination type in FHIRBridge — DestinationType.AzureFhirService. Azure's FHIR service is a standard FHIR R4 RESTful server (the same engine family as a self-hosted Aidbox), so rather than writing a whole new writer, this destination is registered to the existing MappedFhirRepositoryDestinationWriter — the same class the generic "FHIR Repository (Aidbox)" destination already uses — and gets its rich feature set (individual/bundle/transaction write modes, reference resolution, topological write ordering) for free. The only genuinely new piece is authentication: Azure always secures its FHIR API with Microsoft Entra ID, so this work adds a managedIdentity auth mode alongside the already-supported clientCredentials (OAuth2 client-credentials) mode, plus a dedicated Angular form, workflow-canvas wiring, and an auto-fetch-missing-reference capability.

2.What was built

  • New DestinationType.AzureFhirService enum value, registered to the existing MappedFhirRepositoryDestinationWriter in ConfiguredDestinationWriterFactory — same pattern already used for AzureSql → MappedSqlServerDestinationWriter.
  • Managed-identity authentication — a new AzureManagedIdentityFhirTokenProvider using Azure.Identity.DefaultAzureCredential, wired into FhirRepositoryAuthResolver as a new managedIdentity branch of dest_fhirAuthType, alongside the existing none/bearer/basic/clientCredentials values.
  • A dedicated Angular form (AzureFhirServiceDestinationFormComponent) with an auth-mode toggle (client credentials vs. managed identity), a scope override field, and an auto-fetch-missing-references checkbox — modeled on Azure Blob Storage's own auth-mode-conditional-validator pattern.
  • Full workflow-canvas wiring — the node now appears in the Node Library palette, opens its own configuration form, saves/edits/runs correctly, and shows up in Step 4's review screen — across five separate, independent hardcoded destination-type lists that had to each be found and extended (see §8).
  • Auto-fetch missing references — lets the writer pull a referenced resource (e.g. a Patient's managing Organization) straight from the source EHR on demand instead of requiring every referenced resource type to be pulled into the same batch.
  • Test Connection button — validates client ID/secret/tenant/URL (or a managed identity) against the real FHIR service before anything is saved, reusing the same ad-hoc test endpoint the Aidbox form already had, extended to skip SMART-configuration discovery (Azure already knows its own tenant) and to support managedIdentity. See §6.
  • Improved write-failure diagnostics — the writer's HTTP failures now surface the FHIR server's actual OperationOutcome body in the thrown error instead of a bare, uninformative status code, which is what let us actually diagnose the RBAC "Authorization failed" error during testing.
  • One real bug fixed — the Mapping node's wholeResourceFhir passthrough flag (which lets a FHIR-native destination receive whole resources with no field mappings configured) didn't include the new destination type, so every record was silently dropped with zero mapped fields. Now fixed.

3.Azure setup — where every field's value comes from

Everything below is done in the Azure Portal, before you ever open FHIRBridge.

1
Create the Azure Health Data Services workspaceAzure Portal → search "Health Data Services" → + Create → pick subscription/resource group/region → name it (e.g. azurefhirpeg).
2
Create the FHIR service inside that workspaceWorkspace → FHIR services blade → + Add FHIR service → name it (e.g. segue) → FHIR version R4 (the only version supported). Azure always secures it with Entra ID — there is no anonymous-access option.
3
Get the FHIR service URLFHIR service → Authentication blade → Audience field, e.g. https://azurefhirpeg-segue.fhir.azurehealthcareapis.com. This is the exact value for FHIRBridge's FHIR service URL field — no trailing slash, no /metadata suffix. (If you only have the "FHIR metadata endpoint" link from the Overview page, strip the trailing /metadata.)
4
Get the Tenant IDSame Authentication blade → Authority field, e.g. https://login.microsoftonline.com/d5ae9301-08f4-4e80-b0b0-1b8a97b7687f — the GUID at the end is the Tenant ID. This is the only tenant this FHIR service will accept tokens from — use this value even if another screen (e.g. an app registration in a different tenant) shows something else.
5
Client credentials mode — create an app registrationMicrosoft Entra ID → App registrations → + New registration → name it (e.g. fhirbridge-ahds-client). On its Overview page: Application (client) ID and Directory (tenant) ID (must match step 4's tenant). Then Certificates & secrets → + New client secret → copy the Value column immediately — not the Secret ID column, which is a different GUID that will never authenticate (this exact mistake produces AADSTS7000215, see §16).
6
Managed identity mode instead — enable it on the compute resourceIf FHIRBridge's Worker/API runs on an Azure App Service/VM/AKS pod: that resource → Identity blade → System assigned → On. For a user-assigned identity instead, create one under Managed Identities and note its Client ID for the form's optional field. No secret to generate at all.
7
Grant access — required either wayFHIR service → Access control (IAM) → + Add → Add role assignment → Role: FHIR Data Writer or FHIR Data Contributor → Members: search for the app registration (client-credentials mode) or the managed identity (managed-identity mode) → Review + assign. Propagation is usually fast but can occasionally take up to 15–30 minutes.

6.Test Connection button

Every Azure FHIR Service destination form now has a Test Connection button, so client ID, secret, tenant ID, and the FHIR service URL can all be validated on the spot — before anything is saved — the same way the SQL-family and Aidbox forms already work.

Where it lives

Destination Wizard → Step 1 "Configure" → bottom of the Azure FHIR Service form, right below the auto-fetch settings.

What it does

Sends the form's current, unsaved field values — never a value already stored in Key Vault — to POST /api/v1/destination-schema/fhir-test, which does two real checks in sequence:

  1. An authenticated GET {baseUrl}/metadata — confirms the token/tenant/audience are valid.
  2. A real write-authorization probe — PUTs a synthetic, harmless Basic resource (id fhirbridge-connection-test-probe) to the destination, then immediately deletes it. This step exists because Azure Health Data Services (and FHIR servers generally) typically do not enforce the FHIR Data Writer/Contributor RBAC role on /metadata — only on actual writes. Without this second step, a principal with a valid token but no write role would pass Test Connection and only discover the problem on the first real pipeline run.

Reports back Connected: true/false plus an error message on failure — a failure at step 2 shows as "Write check failed — PUT '...' returned 403 ...: {OperationOutcome}", the exact same wording a real pipeline write failure would show.

Client credentials modeEnabled once Tenant ID + Client ID + Client secret + FHIR service URL are all filled in. Skips Aidbox's SMART-configuration discovery entirely — the Entra ID token endpoint is computed directly from Tenant ID (https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token), since Azure FHIR Service already tells us its own tenant.
Managed identity modeEnabled once just the FHIR service URL is filled in (no secret to check). Caveat: this still calls DefaultAzureCredential server-side — testing it only produces a meaningful result when FHIRBridge itself is actually running in Azure with the identity attached and the IAM role assignment already granted, or when a local fallback credential (see box below) is available. From a local dev box with neither, it will report a connection failure regardless of whether the eventual production role assignment is correct.
Result displayGreen "Connected — the FHIR service URL and credentials are valid" callout, or a red "Connection failed: <reason>" callout with the real error text (e.g. an AADSTS code, or the FHIR server's own message) — the same wording you'd see from the errors catalogued in §18.
What changed to support this FhirConnectionTestRequest gained four new optional fields (TenantId, Scope, ManagedIdentityClientId, AuthorityHost); FhirDestinationConnectionTestService gained a managedIdentity branch, a direct-tenant client-credentials path that bypasses discovery when TenantId is supplied, and the write-authorization probe described above — all purely additive, so the existing Aidbox "Test Connection" flow gets the stronger write check too (for free), with its discovery-based token endpoint resolution unaffected.
Testing managed identity from a local dev box DefaultAzureCredential tries a chain of credential sources, falling through each one that isn't available: Environment variables → Managed Identity → Azure CLI → others. You can use that chain to genuinely exercise the managed-identity code path locally, without deploying anywhere. Note: the "Managed identity" option is currently commented out of the Azure FHIR Service form's auth-mode dropdown (see §7) — to test it via the UI, temporarily uncomment the <option value="managedIdentity"> in azure-fhir-service-destination-form.component.ts, or drive POST /api/v1/destination-schema/fhir-test directly with "authType": "managedIdentity" (Postman/curl) — the backend endpoint itself was never restricted.
  1. Easiest: run az login (signs in as your own account), then grant that account the FHIR Data Writer/Contributor role on the FHIR service (same IAM screen as the app). With no real attached managed identity on your laptop, DefaultAzureCredential falls through to your Azure CLI session instead — same code path as production, different backing identity.
  2. Alternative: set AZURE_TENANT_ID/AZURE_CLIENT_ID/AZURE_CLIENT_SECRET environment variables (matching a service principal) in the terminal that launches the backend, then restart it — the "Environment Credential" step picks these up before Managed Identity is even tried.
Common trap: if you try both approaches across different terminal sessions, leftover AZURE_* environment variables in whichever terminal actually launched the backend take priority over an az login session — check echo $env:AZURE_CLIENT_ID etc. in that exact terminal (empty output = unset) before assuming az login is what's being used.

7.Authentication modes

1. Client credentials (service principal)

Default
wizard value: clientCredentials · metadata key: dest_fhirAuthType=clientCredentials

A standard OAuth2 client-credentials exchange against Entra ID's v2.0 token endpoint. Internally reuses the existing generic FhirDestinationOAuth2TokenProvider (the same one the plain "FHIR Repository" destination already used) — no new backend auth code was needed for this mode, only the right token endpoint/scope values.

Tenant IDSee §3 step 4. Required.
Client IDSee §3 step 5. Required.
Client secretSee §3 step 5 — the Value, never the Secret ID. Required for a new connection; never repopulated on edit.
Token endpointComputed automatically as https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token — not a field you fill in.
ScopeComputed automatically as {FHIR service URL}/.default unless overridden.

2. Managed identity

Hidden in UI
wizard value: managedIdentity · no secret is ever stored or resolved

The host running FHIRBridge (App Service, VM, AKS) authenticates as itself via Azure.Identity.DefaultAzureCredential — the AzureManagedIdentityFhirTokenProvider class. No Key Vault secret is ever resolved for this mode — FhirRepositoryAuthResolver's managedIdentity branch skips secret retrieval entirely. Only works when FHIRBridge itself runs in Azure with that identity assigned the right role (see §3 step 7); it cannot work from a dev laptop unless you're separately signed in via Azure CLI with an identity that also holds that role.

Temporarily removed from the "Authentication" dropdown The <option value="managedIdentity"> is commented out of the Azure FHIR Service form's auth-mode select (same treatment BlobStorageDestinationFormComponent already gives its own managedIdentity/servicePrincipal options), so it can no longer be picked for a new destination. Nothing else changed: the backend (FhirRepositoryAuthResolver, the writer, Test Connection, the workflow-duplicate fix below) still fully supports it, and a destination saved with managedIdentity before this change keeps running exactly as before. Re-enabling it is a one-line uncomment in azure-fhir-service-destination-form.component.ts. This was pulled from the UI because its scope/destination-host validation gap (see §17's High-severity finding) is still open — hiding the option keeps it from being newly selected until that's addressed.
User-assigned identity client IDOptional — leave blank to use the system-assigned identity.
ScopeComputed automatically as {FHIR service URL}/.default unless overridden.

9.Auto-fetch missing references

The shared writer's dangling-reference protection blocks (rather than writes) any record whose FHIR reference (e.g. a Patient's managingOrganization) can't be resolved — neither present in the same batch nor already at the destination. This is correct defense-in-depth, but it means pulling only Patient resources into a run against a brand-new/empty FHIR service blocks every record, since none of their referenced Organizations/Practitioners exist anywhere yet.

Two ways around this:

  • Include the referenced types in the same run — e.g. also pull Organization and Practitioner from the source alongside Patient. The writer topologically orders writes so referenced types land first. No configuration needed.
  • Enable auto-fetch (the checkbox on the Azure FHIR Service form) — the writer pulls a missing reference straight from the same source EHR connection already feeding the pipeline, recursively (a fetched Encounter that itself references a Practitioner gets that resolved too), up to the configured cap.
What had to be added for this The generic Aidbox destination already had this wired; Azure FHIR Service's node executor did not. AzureFhirServiceDestinationNodeExecutor's constructor now also accepts IFhirSourceClientFactory/ISourceConnectionRuntimeResolver, mirroring FhirRepositoryDestinationNodeExecutor exactly, so ResolveFetchMissingReferenceDelegateAsync (in the shared DestinationNodeExecutor base class) has something to wire up.

The traces below cover both the canvas save/provisioning path and the actual run-time execution path — the exact sequence exercised while building and testing this feature.

8.3 Inside the writer — auth resolution, reference resolution, the actual HTTP write

MappedFhirRepositoryDestinationWriter.WriteAsync — full trace 
MappedFhirRepositoryDestinationWriter.WriteAsync(destination, mappingProfile, records, context, ct)
  authType = ConnectionMetadataReader.GetString(destination.ConnectionMetadataJson, "dest_fhirAuthType") ?? "none"

  if authType == "none":
    baseUrl = destination.Target ?? (await _secretProvider.GetSecretAsync(destination.SecretReference, ct))
    authHeader = null
  else:
    if destination.Target is blank: throw InvalidOperationException("...must set Target...")
    baseUrl = destination.Target.TrimEnd('/')
    authHeader = await FhirRepositoryAuthResolver.ResolveAsync(
        destination.ConnectionMetadataJson, destination.SecretReference,
        _secretProvider, _tokenProvider, _managedIdentityTokenProvider, baseUrl, ct)
    // -> see auth-resolution trace below

  autoFetchEnabled  = dest_autoFetchMissingReferences == "true"
  autoFetchMaxCount = dest_autoFetchMaxCount ?? 25

  (writableRecords, referenceErrors) = await ResolveMissingReferencesAsync(
      httpClient, baseUrl, authHeader, records, resolvedResourceCache,
      autoFetchEnabled, autoFetchMaxCount, context.FetchMissingReferenceAsync, ct)
    // for each record's parsed FHIR references (managingOrganization, generalPractitioner, etc.):
    //   1. present in this same batch?           -> OK, no destination lookup needed
    //   2. else: batched existence check          -> GET {baseUrl}/{Type}?_id=a,b,c&_elements=id
    //      (see CheckExistingInAidboxAsync, also goes through EnsureSuccessOrThrowAsync)
    //   3. else, if autoFetchEnabled: fetch via context.FetchMissingReferenceAsync(type, id, ct)
    //      -> recursively re-checks the fetched resource's OWN references too
    //   4. else: record (and anything that depends on it) is excluded, with a precise

    //      RecordsWritten: 0 "partial success" result during testing before auto-fetch

14.Verifying data actually landed

The Azure Portal has no built-in FHIR data browser (no table/grid view like Cosmos DB's Data Explorer). Three ways to actually confirm a write:

  • Resource visualizer (FHIR service's own sidebar) — shows resource-type counts (e.g. Patient: 9). Confirms totals, not content.

16.Clearing / deleting test data

The FHIR service has no single "delete everything" API call built in. Three options, simplest first for a small test dataset:

Option A — delete & recreate the FHIR service

Simplest full wipe, but also wipes the Authentication blade config and IAM role assignment — both need redoing afterward.

Option B — $bulk-delete (if available on your service version)

POST {fhirServiceUrl}/$bulk-delete
Authorization: Bearer <token>

Option C — scripted per-type delete (works everywhere, keeps config intact)

param(
    [Parameter(Mandatory)]
    [string]$ClientSecret,

    [ValidateSet('All','Single')]
    [string]$Mode = 'All',

    [string[]]$ResourceTypes = @('Patient','Organization','Practitioner'),

    [string]$ResourceType,
    [string]$ResourceId
)

$tenantId = "<tenant-id>"
$clientId = "<client-id>"
$fhirUrl  = "<fhir-service-url>"

# Always mint a fresh token right before use.
$tokenBody = @{
    grant_type    = "client_credentials"
    client_id     = $clientId
    client_secret = $ClientSecret
    scope         = "$fhirUrl/.default"
}
$token = (Invoke-RestMethod -Uri "https://login.microsoftonline.com/$tenantId/oauth2/v2.0/token" -Method Post -Body $tokenBody).access_token
$headers = @{ Authorization = "Bearer $token" }

function Remove-FhirResource {
    param($Type, $Id)
    try {
        Invoke-RestMethod -Uri "$fhirUrl/$Type/$Id" -Method Delete -Headers $headers | Out-Null
        Write-Host "Deleted $Type/$Id"
    } catch {
        Write-Warning "Failed to delete $Type/$Id : $($_.Exception.Message)"
    }
}

if ($Mode -eq 'Single') {
    if (-not $ResourceType -or -not $ResourceId) {
        Write-Error "Single mode requires -ResourceType and -ResourceId."
        return
    }
    Remove-FhirResource -Type $ResourceType -Id $ResourceId
    return
}

# Mode = All: page through every resource of each type (follows the Bundle's own
# "next" link, so it isn't limited to the first 100 per type) and delete each one.
foreach ($type in $ResourceTypes) {
    $nextUrl = "$fhirUrl/$type`?_count=100"
    while ($nextUrl) {
        $result = Invoke-RestMethod -Uri $nextUrl -Headers $headers
        foreach ($entry in $result.entry) {
            Remove-FhirResource -Type $type -Id $entry.resource.id
        }
        $nextLink = $result.link | Where-Object { $_.relation -eq 'next' } | Select-Object -First 1
        $nextUrl = $nextLink.url
    }
}

Usage:

# Delete everything (Patient + Organization + Practitioner, the default)
.\Clear-FhirData.ps1 -ClientSecret "<secret>"

# Delete everything, only specific types
.\Clear-FhirData.ps1 -ClientSecret "<secret>" -ResourceTypes @('Patient','Encounter')

# Delete just one resource
.\Clear-FhirData.ps1 -ClientSecret "<secret>" -Mode Single -ResourceType Patient -ResourceId egqBHVfQlt4Bw3XGXoxVxHg3
Soft delete by default A plain DELETE {Type}/{id} on Azure Health Data Services marks the resource deleted but keeps its history rather than purging it — a true permanent wipe needs the service's hard-delete/$purge capability if enabled.

17.Known issues & recommended follow-ups

High — managed-identity scope & destination host are both unvalidated (credential-theft / SSRF-style risk)

Neither dest_fhirAzureScope nor Target/dest_baseUrl is validated server-side (CreateDestinationConfigurationRequestValidator.ValidateFhirRepositoryMetadata only checks Target is non-blank). A user holding only the routine, non-admin permission required to create/edit a destination (the generic sourceconnections.create/.edit fallback, since neither FhirRepository nor AzureFhirService has a dedicated PermissionGroupCode) could set managedIdentity auth mode with an arbitrary Target host and an arbitrary dest_fhirAzureScope, causing FHIRBridge's own compute identity to mint a live Azure AD token for whatever scope was requested and send it to an attacker-controlled host. Recommendation: restrict dest_fhirAzureScope to the derived {Target}/.default value (disallow arbitrary override, or require it match Target's host), and/or allow-list Target's host to the expected *.azurehealthcareapis.com pattern for FHIR-native destinations using managedIdentity/clientCredentials.

Partial mitigation applied: the "Managed identity" auth-mode option is now commented out of the Azure FHIR Service (and Blob Storage) portal forms (see §7), so it can no longer be newly selected through the UI. This is a UI-only speed bump, not a fix — the underlying API endpoints (POST /api/v1/destinations, POST /api/v1/destination-schema/fhir-test) still accept and process managedIdentity with no server-side scope/host validation, and any destination saved with it before this change keeps running unchanged. The recommendation above is still open.

Medium — write-failure error messages can carry PHI fragments past the existing log redaction

EnsureSuccessOrThrowAsync now embeds up to 600 characters of the raw FHIR server response body in thrown exception messages (previously a bare status code, no body). The project's existing PhiMaskingEnricher/IPhiRedactor is a defensive, regex-based backstop keyed on a fixed field-name list (familyName, givenName, etc.) that doesn't match real FHIR JSON key names (family, given, identifier) and doesn't fully redact array/object-shaped values. If a FHIR server's validation-error diagnostic ever echoes a fragment of the submitted resource, it could reach logs or the persisted ErrorLogs table unredacted. Recommendation: parse the OperationOutcome and surface only its issue[].severity/code fields rather than the raw body, and/or extend the redactor's field list and value-matching to cover real FHIR key names and nested structures.

Low — no write-mode UI control on the Azure FHIR Service form

dest_fhirWriteMode (individual/bundle/transaction) has no field on the new form yet — set it directly in ConnectionMetadataJson if bundle/transaction behavior is needed.

Low — sanitized-id substitution doesn't rewrite cross-batch references

When an oversized/invalid FHIR id is replaced with a deterministic UUID (see §11, §18), any other resource in the same batch that references it by its original id is not updated to point at the new id. Not yet observed in real Epic data (the field this hit, Observation, isn't itself commonly referenced by id within a batch), but a resource type that is commonly referenced (e.g. Patient, Encounter) hitting this path would produce a dangling reference. Recommendation: if this surfaces, extend the id-sanitization step to also rewrite in-batch references, mirroring the existing (currently unused) RewriteNumericReferences/SafenReference pattern already present in the same file.

18.Troubleshooting — every error hit and its fix

"Nothing to configure — This module type doesn't have a configuration screen yet"

Cause: workflow-builder.component.ts's onOpenWizard() had its own separate destination-type allowlist that didn't yet include dest-azurefhir.

Fix: extended (see §10). A node created before this fix was in place may still need to be deleted and re-added fresh.

Tile doesn't appear in the Node Library at all

Cause: phase-config.service.ts's Phase-1 enabledTransformIds allowlist hides tiles entirely (not just disables them) — a completely separate gate from the type-union/registry wiring.

Fix: added dest-azurefhir to that list.

Mapping node shows "Records": [] even though source resources exist

Cause: the wholeResourceFhir bug — AzureFhirService wasn't in the destination-type check that lets a FHIR-native destination receive whole-resource carrier records with zero real field mappings.

Fix: extended in TransformNodeExecutors.cs (see §2, §8.2).

"An invalid request URI was provided. Either the request URI must be an absolute URI or BaseAddress must be set."

Cause: a graph-driven run's Target stayed null (the wizard never stamps a top-level "target" field on a freshly-created node) and dest_fhirAuthType was never bridged from dest_authType — both fallbacks existed only for the generic Aidbox node type.

Fix: both extended to also cover AzureFhirServiceDestination (see §8.2).

AADSTS90014 — "The required field 'scope' is missing from the credential"

Cause: the client-credentials secret blob never included a scope field — Entra ID's v2.0 token endpoint requires one, unlike some generic OAuth2 servers.

Fix: buildFhirSecretBlob (both copies) now folds dest_fhirAzureScope (or the computed {baseUrl}/.default default) into the secret blob. Re-typing the client secret is required afterward to actually rebuild the stored blob.

AADSTS7000215 — "Invalid client secret provided... not the client secret ID"

Cause: the Secret ID column (a GUID, always visible) was copied instead of the Value column (shown once, at creation).

Fix: create a new client secret, copy the Value immediately, re-enter it in the form.

AADSTS700016 — "Application with identifier '...' was not found in the directory"

Cause: a one-character-truncated Client ID (copy/paste dropped the last character).

Fix: carefully re-verify the full GUID matches the app registration's Application (client) ID exactly.

403 Forbidden — bare "Response status code does not indicate success"

Cause: the writer called a bare .EnsureSuccessStatusCode() with no response body, so the real reason was invisible.

Fix: replaced with EnsureSuccessOrThrowAsync, which surfaces the FHIR server's actual OperationOutcome (see §15's Medium finding for the corresponding PHI caveat).

403 Forbidden — OperationOutcome: "Authorization failed."

Cause (transient case): a stale, already-minted-but-insufficiently-authorized token was cached from before the RBAC role assignment had finished propagating; token minting itself succeeded (so it wasn't re-fetched), and the cache has no way to know the token got rejected downstream. Fix: restart the backend process to clear the in-memory token cache (Redis in prod, memory in local dev) and force a fresh mint.

Cause (persistent case — the actual root cause hit in this branch's testing): the signed-in principal (or app registration) had been granted the generic "Contributor" Azure role on the FHIR service resource, not "FHIR Data Contributor" (or "FHIR Data Writer"). Azure Health Data Services keeps a hard split between control-plane roles (Contributor/Owner — manage the resource itself: settings, networking, scaling) and data-plane roles (FHIR Data Reader/Writer/Contributor — read/write the actual FHIR resources inside it). Holding Contributor lets you configure the service in the Azure Portal but every FHIR REST write still comes back 403.

Fix: on the FHIR service resource → Access control (IAM) → Add role assignment, grant FHIR Data Contributor (write) or FHIR Data Writer to the exact principal being used (the app registration's service principal for client-credentials mode, or the signed-in user/managed identity for managed-identity mode) — not just its owning app registration or resource group. Role assignments can take a few minutes to propagate; a backend restart afterward clears any token cached from before propagation finished. The Test Connection button's write-authorization probe (see §6) now catches exactly this class of misconfiguration before a real pipeline run does.

RecordsWritten: 0 with "partial success" and no thrown error

Cause: the writer's dangling-reference protection correctly blocked every record because the pulled resource type (Patient only) referenced Organization/Practitioner resources that existed neither in the same batch nor at the (brand-new, empty) destination.

Fix: pull the referenced types into the same run, or enable auto-fetch (see §7).

401 Unauthorized when running a manual delete/verification script

Cause: reusing an access token past its ~60–65 minute lifetime.

Fix: mint a fresh token immediately before each script run rather than reusing one from earlier in the session.

Epic source token endpoint returns 503 Service Unavailable

Cause: an outage on Epic's own token endpoint, external to FHIRBridge — the response body is a generic IIS error page, not an Epic-specific error, and it clears on its own.

Fix: no code change; retry the pipeline run once Epic's endpoint recovers. If it persists more than a few minutes, check Epic's own status/support channel rather than FHIRBridge logs.

400 Bad Request — "Id must be any combination of upper/lower case ASCII letters ('A'-'Z', 'a'-'z'), numerals ('0'-'9'), '-' and '.', with a length limit of 64 characters"

Cause: Epic occasionally issues resource ids longer than FHIR's 64-character id limit (observed: 66 characters on an Observation) — Azure Health Data Services enforces the limit strictly and rejects the write outright.

Fix: MappedFhirRepositoryDestinationWriter.ParseFhirResource now detects any id that doesn't match FHIR's id pattern and substitutes a deterministic, name-based UUID in its place (same source id always produces the same replacement id), preserving the original as a secondary identifier (see §11). Known limitation: if another resource in the same batch references the oversized id by its original value, that cross-reference is not rewritten — not yet observed in practice, listed as a follow-up in §17.

Editing a saved destination shows "Client credentials" even though it was saved as "Managed identity"

Cause: the form's patchFrom() only checked the bridged metadata key dest_fhirAuthType. Re-opening a saved canvas node instead goes through destination-wizard.component.ts's _populateFromNode(), which passes the node's own raw dest_* fields verbatim — still carrying the form's internal key dest_authType, which is never bridged at that layer. The auth mode silently fell back to its default (clientCredentials) every time.

Fix: patchFrom() now checks dest_fhirAuthType first, falling back to dest_authType (see §12).

"Duplicate Workflow" on a managed-identity workflow fails with a generic "An unexpected error occurred..." page

Cause: duplicating a workflow deep-clones every referenced DestinationConfiguration, including re-provisioning its stored secret under a brand-new secret name (CloneSecretAsync in WorkflowEndpoints.cs). A managed-identity destination always carries non-blank KeyVaultName/SecretName placeholder values (required by validation), but — because there's no secret to store for that auth mode — nothing was ever actually written under those names in the first place. CloneSecretAsync saw the non-blank names, assumed a real secret existed, and tried to read it; the read threw SecretNotConfiguredException, uncaught, surfacing as the generic error page.

Fix: CloneSecretAsync now catches SecretNotConfiguredException and treats it the same as "no secret reference to clone" — the duplicate destination just gets the same secret-less placeholder reference the original has, exactly matching how managed-identity auth already behaves. This also silently fixed the identical latent bug for Blob Storage's own managed-identity mode, which hits the same code path.
