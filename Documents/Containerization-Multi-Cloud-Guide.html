1.Overview

This guide documents everything under the new containerization/ folder: Dockerfiles, the local Compose stack, the build scripts, and three separate Terraform environments (local Docker, Azure Container Apps, AWS ECS Fargate) that all stand up the same 5-container topology. It is additive — the repo-root docker-compose.yml (a dev/E2E dependency stack: HAPI FHIR, RabbitMQ, output DBs, etc.) and the existing Windows Service / GitHub Actions deploy path (deploy/windows/, .github/workflows/deploy.yml) are both untouched.

3

The design leans hard on reuse: FHIRBridge.Api and FHIRBridge.Gateway already implement exactly the topology needed (Api loopback-only, Gateway as the sole public entry point reverse-proxying /api/** and /swagger/**) for the existing Windows Service deployment described in deploy/windows/README.md — the container design reproduces that instead of inventing a new reverse proxy (no nginx anywhere). Both the Api and the Demo app backend already auto-provision their own database schema on startup (Database.Migrate() / EnsureCreated()), so the SQL Server container needs no init scripts.

docker/fhirbridge-app/Dockerfile new

A 3-stage build producing the one image that runs both FHIRBridge.Api and FHIRBridge.Gateway.

# ---- Stage 1: Angular portal build ----
FROM node:20-alpine AS portal-build
ARG PORTAL_CONFIG=production
WORKDIR /src/portal
# .npmrc (legacy-peer-deps=true) must be present before `npm ci` — without it npm's default
# strict peer-dependency resolution flags several transitive version pairs (chokidar, ajv, keyv)
# as an out-of-sync lockfile, even though the lockfile itself is fine under the project's own
# npm config.
COPY portal/package.json portal/package-lock.json portal/.npmrc ./
RUN npm ci
COPY portal/ ./
RUN npm run build -- --configuration=${PORTAL_CONFIG}

# ---- Stage 2: .NET publish (Api + Gateway) ----
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS dotnet-build
WORKDIR /src
COPY src/ ./src/
RUN dotnet publish src/Api/FHIRBridge.Api/FHIRBridge.Api.csproj \
      -c Release --no-self-contained -o /app/publish/api \
    && dotnet publish src/Gateway/FHIRBridge.Gateway/FHIRBridge.Gateway.csproj \
      -c Release --no-self-contained -o /app/publish/gateway

# ---- Stage 3: runtime ----
FROM mcr.microsoft.com/dotnet/aspnet:9.0 AS final
WORKDIR /app
COPY --from=dotnet-build /app/publish/api ./api
COPY --from=dotnet-build /app/publish/gateway ./gateway
COPY --from=portal-build /src/portal/dist/fhirbridge-ui/browser ./portal
COPY containerization/docker/fhirbridge-app/entrypoint.sh ./entrypoint.sh
RUN chmod +x ./entrypoint.sh

EXPOSE 80
ENTRYPOINT ["./entrypoint.sh"]
  • Stage 1 (portal-build) — builds the Angular portal with the same ng build --configuration convention already used everywhere else in this repo (production / staging / qa / dev / working, selectable via the PORTAL_CONFIG build arg). Copies .npmrc alongside package.json/package-lock.json — this was the source of a real bug, see the bugs section for the sibling issue and quick reference generally; without .npmrc's legacy-peer-deps=true, npm ci fails with a false "lockfile out of sync" error even though the lockfile itself is fine.
  • Stage 2 (dotnet-build) — publishes both FHIRBridge.Api and FHIRBridge.Gateway from the same src/ copy, into two separate output folders (/app/publish/api, /app/publish/gateway).
  • Stage 3 (final) — assembles the runtime image on mcr.microsoft.com/dotnet/aspnet:9.0 (needs the ASP.NET Core shared framework, not just the bare .NET runtime, since both Api and Gateway are Kestrel-hosted). Copies the Api publish output to /app/api, the Gateway publish output to /app/gateway, and the Angular build to /app/portal (the Gateway's static-file root). Only port 80 is exposed — the Api's port 5000 is loopback-only inside the container and is never meant to be published by the orchestrator, matching the "not reachable from outside the server" note in the existing Windows deploy docs.

docker/fhirbridge-app/entrypoint.sh new

The script that actually launches both processes inside the one container, since a Dockerfile's ENTRYPOINT can only name one command.

#!/bin/bash
set -e

env ASPNETCORE_URLS=http://127.0.0.1:5000 \
    ASPNETCORE_CONTENTROOT=/app/api \
    dotnet /app/api/FHIRBridge.Api.dll &
API_PID=$!

env ASPNETCORE_URLS=http://+:80 \
    ASPNETCORE_CONTENTROOT=/app/gateway \
    StaticFiles__RootPath=/app/portal \
    dotnet /app/gateway/FHIRBridge.Gateway.dll &
GATEWAY_PID=$!

terminate() {
  kill -TERM "$API_PID" "$GATEWAY_PID" 2>/dev/null || true
}
trap terminate TERM INT

# If either process dies, the container should die too so the orchestrator restarts it.
wait -n "$API_PID" "$GATEWAY_PID"
EXIT_CODE=$?
terminate
exit $EXIT_CODE
  • Two scoped env VAR=value command & invocations — each process gets its own ASPNETCORE_URLS (Api binds loopback-only on 5000; Gateway binds all interfaces on 80) without needing a container-wide ENV, which would force both processes to the same bind address.
  • ASPNETCORE_CONTENTROOT per process — the fix for the real bug documented in Bugs Found & Fixed #3. ASP.NET Core resolves appsettings.json (and wwwroot) relative to the process's content root, which defaults to its current working directory — not the folder containing its DLL. Both dotnet invocations here run from the script's own cwd (/app, the image's WORKDIR), so without this each process would look for config next to /app instead of /app/api or /app/gateway and silently start with none of it.
  • StaticFiles__RootPath=/app/portal — only set for the Gateway process; tells it where the Angular build lives (read by src/Gateway/FHIRBridge.Gateway/Program.cs's StaticFiles:RootPath config key).
  • trap + wait -n — forwards SIGTERM/SIGINT to both children on container stop, and exits the whole container the moment either process dies (rather than leaving a half-alive container running), so the orchestrator's restart policy actually gets a chance to recover it.

docker/demo-app/Dockerfile new

A simpler 3-stage build — HealthAppBackend already self-hosts its own Angular build as a single process (same pattern as the Api's own wwwroot convention, just wired through the DEMOAPP_PORTAL_PATH env var instead), so there's no second process to juggle here.

# ---- Stage 1: Angular frontend build ----
FROM node:20-alpine AS frontend-build
ARG DEMO_CONFIG=production
WORKDIR /src/frontend
COPY Demo_TestApp/frontend/package.json Demo_TestApp/frontend/package-lock.json ./
RUN npm ci
COPY Demo_TestApp/frontend/ ./
RUN npm run build -- --configuration=${DEMO_CONFIG}

# ---- Stage 2: .NET publish ----
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS dotnet-build
WORKDIR /src
COPY Demo_TestApp/backend/ ./backend/
RUN dotnet publish backend/HealthAppBackend.csproj \
      -c Release --no-self-contained -o /app/publish

# ---- Stage 3: runtime ----
FROM mcr.microsoft.com/dotnet/aspnet:9.0 AS final
WORKDIR /app
COPY --from=dotnet-build /app/publish ./
COPY --from=frontend-build /src/frontend/dist/frontend/browser ./portal

ENV ASPNETCORE_URLS=http://+:5500
ENV DEMOAPP_PORTAL_PATH=/app/portal

EXPOSE 5500
ENTRYPOINT ["dotnet", "HealthAppBackend.dll"]

Note this Dockerfile did not hit the same content-root bug as fhirbridge-app — the published DLL and its appsettings.json land directly in /app, which is also the container's WORKDIR and therefore also the process's default content root, with no subfolder mismatch.

docker/worker/Dockerfile new

The simplest of the three — FHIRBridge.Worker has no HTTP endpoint at all.

# ---- Stage 1: .NET publish ----
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS dotnet-build
WORKDIR /src
COPY src/ ./src/
RUN dotnet publish src/Worker/FHIRBridge.Worker/FHIRBridge.Worker.csproj \
      -c Release --no-self-contained -o /app/publish

# ---- Stage 2: runtime ----
# Despite having no Kestrel endpoint, FHIRBridge.Worker pulls in the ASP.NET Core shared framework
# transitively (via FHIRBridge.Infrastructure/Observability) — the plain dotnet/runtime image is
# missing it and fails at launch with "Framework: 'Microsoft.AspNetCore.App' ... No frameworks
# were found", so this needs the aspnet base image too.
FROM mcr.microsoft.com/dotnet/aspnet:9.0 AS final
WORKDIR /app
COPY --from=dotnet-build /app/publish ./

ENTRYPOINT ["dotnet", "FHIRBridge.Worker.dll"]

The comment in Stage 2 documents a real bug found and fixed during verification — see Bugs Found & Fixed #2. The original version used the smaller, ASP.NET-Core-free dotnet/runtime:9.0 image, which is the theoretically "correct" choice for a worker with no web server — except this specific worker's dependency graph needs the ASP.NET Core shared framework anyway, so it crashed on launch until switched to dotnet/aspnet:9.0.

compose/docker-compose.yml new

The fast, manual local path — brings up all 5 containers on one bridge network with container-name-based DNS (so Server=sqlserver,1433;... and redis:6379 just resolve).

name: fhirbridge-containerized

services:
  sqlserver:
    image: mcr.microsoft.com/mssql/server:2022-latest
    environment:
      ACCEPT_EULA: "Y"
      MSSQL_PID: "Express"
      MSSQL_SA_PASSWORD: "${SQL_SA_PASSWORD}"
    ports: ["${SQL_HOST_PORT:-1434}:1433"]
    volumes: [sqlserver-data:/var/opt/mssql]
    healthcheck: { test: [...sqlcmd SELECT 1...], interval: 10s, retries: 10 }

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--requirepass", "${REDIS_PASSWORD}"]
    ports: ["${REDIS_HOST_PORT:-6380}:6379"]
    volumes: [redis-data:/data]
    healthcheck: { test: ["CMD", "redis-cli", "-a", "${REDIS_PASSWORD}", "ping"], interval: 10s, retries: 10 }

  fhirbridge-app:
    build:
      context: ../../
      dockerfile: containerization/docker/fhirbridge-app/Dockerfile
      args: { PORTAL_CONFIG: "${PORTAL_BUILD_CONFIG:-production}" }
    depends_on:
      sqlserver: { condition: service_healthy }
      redis: { condition: service_healthy }
    environment:
      ConnectionStrings__FHIRBridgeDb: "Server=sqlserver,1433;Database=FHIRBridge;User Id=sa;Password=${SQL_SA_PASSWORD};Encrypt=True;TrustServerCertificate=True"
      ConnectionStrings__Redis: "redis:6379,password=${REDIS_PASSWORD}"
      Authentication__SigningKey: "${JWT_SIGNING_KEY}"
      DataProtection__KeyRingPath: "/app/keys"
      Portal__AllowedOrigins__0: "http://localhost:${DEMO_HOST_PORT:-5500}"
      Swagger__Enabled: "true"
    ports: ["${APP_HOST_PORT:-8080}:80"]
    volumes: [fhirbridge-dataprotection-keys:/app/keys]
    restart: unless-stopped   # see "migration race" bug below

  demo-app:
    build: { context: ../../, dockerfile: containerization/docker/demo-app/Dockerfile,
             args: { DEMO_CONFIG: "${DEMO_BUILD_CONFIG:-production}" } }
    depends_on: { sqlserver: { condition: service_healthy } }
    environment:
      ConnectionStrings__Default: "Server=sqlserver,1433;Database=HealthAppDb;User Id=sa;Password=${SQL_SA_PASSWORD};Encrypt=True;TrustServerCertificate=True"
      AllowedFrontendOrigin: "http://localhost:${DEMO_HOST_PORT:-5500}"
    ports: ["${DEMO_HOST_PORT:-5500}:5500"]
    restart: unless-stopped

  worker:
    build: { context: ../../, dockerfile: containerization/docker/worker/Dockerfile }
    depends_on:
      sqlserver: { condition: service_healthy }
      redis: { condition: service_healthy }
      fhirbridge-app: { condition: service_started }   # head start, not a guarantee
    environment:
      ConnectionStrings__FHIRBridgeDb: "Server=sqlserver,1433;Database=FHIRBridge;User Id=sa;Password=${SQL_SA_PASSWORD};Encrypt=True;TrustServerCertificate=True"
      ConnectionStrings__Redis: "redis:6379,password=${REDIS_PASSWORD}"
      RuntimeWorker__Enabled: "true"
      Messaging__Provider: "InMemory"
    restart: unless-stopped

volumes:
  sqlserver-data:
  redis-data:
  fhirbridge-dataprotection-keys:

(Abbreviated for readability — the real file has the full healthcheck commands and every key spelled out; see the file on disk for the byte-for-byte version.)

  • Host ports are all offset from the repo-root dev/E2E docker-compose.yml's defaults (1433/6379) — sqlserver uses 1434, redis uses 6380 — so both stacks can run at the same time without a port clash. fhirbridge-app publishes 8080, demo-app publishes 5500 (matching its established convention from the Windows deploy docs).
  • Every config value flows in via environment variables using ASP.NET Core's Section__Key double-underscore override convention — nothing here depends on baking secrets into an image or editing appsettings.json.
  • restart: unless-stopped on all three custom app services is the safety net for the migration race documented in Bugs Found & Fixed #1.
  • Swagger__Enabled: "true" — Swagger:Enabled defaults to false outside Development in FHIRBridge.Api's own Program.cs; without this override, the Gateway's /swagger/** proxy route would have nothing to forward to.
  • Redis now requires a password everywhere — the HIPAA hardening pass added --requirepass to the redis container's command (and a matching redis-cli -a healthcheck), and every connection string that points at Redis changed from host:6379 to host:6379,password=<password> (StackExchange.Redis's comma-separated option syntax). Every SQL Server connection string also now carries Encrypt=True alongside TrustServerCertificate=True — some previously had only the latter, meaning traffic between app and database wasn't actually encrypted.

scripts/build-images.sh & build-images.ps1 new

Identical logic in bash and PowerShell — builds all 3 custom images from the repo root and optionally pushes them to a registry. This is deliberately the only place images get built: neither the Azure nor AWS Terraform ever runs docker build itself.

# Usage
./build-images.sh                                          # local tags only, no push
./build-images.sh -t v1.2.0                                 # local tags, specific version
./build-images.sh -r myregistry.azurecr.io -t v1.2.0 -p     # build, tag, push to ACR
./build-images.sh -r <account>.dkr.ecr.<region>.amazonaws.com/fhirbridge -t v1.2.0 -p  # ECR

# PowerShell equivalent
./build-images.ps1 -Registry myregistry.azurecr.io -Tag v1.2.0 -Push
  • -r/-Registry — registry/repo prefix (blank means local-tag-only, e.g. fhirbridge-app:local).
  • -t/-Tag — image tag, default local.
  • -p/-Push — pushes each image after building; requires a registry and that you're already authenticated to it (az acr login / aws ecr get-login-password | docker login).
  • Both scripts iterate the same 3-entry map — fhirbridge-app, demo-app, fhirbridge-worker — each pointing at its Dockerfile under containerization/docker/, and both resolve the repo root relative to their own script location so they work from any current directory.

Rotating a secret sticks — on purpose lifecycle { ignore_changes = [value] } means that after the first apply, Terraform never overwrites a secret's value again. Deploys the same 5-container topology to AWS ECS Fargate — chosen over EKS (too much Terraform/operational surface for this scope) and plain EC2 + Compose (least "cloud-native", though simplest mentally). HIPAA hardening pass: private subnets, one NAT Gateway, self-signed TLS on the ALB All 5 ECS Fargate tasks now run in private subnets with assign_public_ip = false — only the ALB itself sits in the public subnets and is internet-facing. Outbound internet access for the tasks (pulling images from ECR, calling out) is routed through a single NAT Gateway, not one per AZ — a deliberate cost/simplicity trade-off, not high availability; if that NAT Gateway's AZ has an outage, all 5 tasks lose outbound connectivity together. The ALB listeners also moved from HTTP to HTTPS using a self-signed certificate — real encryption in transit today, with a swap to a CA-issued certificate (e.g. via ACM DNS validation) left as a deliberate later step; until then, browsers will show a trust warning.

🐛Bugs Found & Fixed During Live Verification

None of this was taken on faith — all 3 images were built and actually run (individually, then via the full docker compose stack, against a real SQL Server Express container) before being called done. That live verification surfaced 3 real bugs, all fixed before considering the work complete.

1. Api / Worker migration race on a fresh database

Found via: full docker compose up · Fixed in: compose/docker-compose.yml, all 3 Terraform environments

FHIRBridge.Api and FHIRBridge.Worker both call Database.Migrate() against FHIRBridgeDb independently on startup. On a brand-new SQL Server instance, both can race to run CREATE DATABASE at the same moment — the loser crashes with SqlException: Database 'FHIRBridge' already exists. This is a latent bug in the application's own dual-auto-migration design, not something introduced by containerization — the same race could occur in the real Windows Service deployment too if both services start close together.

Fix: restart: unless-stopped added to all 3 custom app services in Compose (and the Terraform equivalent — Container Apps/ECS both restart failed replicas/tasks automatically already) turns a lost race into a self-healing retry: the loser restarts, finds the database already created, and proceeds normally. A worker depends_on: fhirbridge-app { condition: service_started } head start was also added everywhere to make the race far less likely in the first place — documented in code as "a head start, not a guarantee."

2. Worker container needed the aspnet base image, not plain runtime

Found via: standalone worker container smoke test · Fixed in: docker/worker/Dockerfile

FHIRBridge.Worker has no Kestrel endpoint, so the "correct-looking" runtime base image is the smaller mcr.microsoft.com/dotnet/runtime:9.0 (no ASP.NET Core shared framework). It crashed immediately on launch:

You must install or update .NET to run this application.
Framework: 'Microsoft.AspNetCore.App', version '9.0.0' (x64)
No frameworks were found.

The worker's dependency graph (FHIRBridge.Infrastructure / FHIRBridge.Observability) transitively requires the ASP.NET Core shared framework even though the Worker itself never starts a web server.

Fix: switched the final stage to mcr.microsoft.com/dotnet/aspnet:9.0, matching the other two images. Re-verified against a real SQL Server container afterward — clean startup, no crash.

3. Gateway loaded zero YARP routes — wrong content root, not CORS

Found via: full compose stack, browser DevTools showed a 404 on /api/v1/auth/setup-status · Fixed in: docker/fhirbridge-app/entrypoint.sh, src/Gateway/FHIRBridge.Gateway/Program.cs

The most involved of the three. A same-origin GET /api/v1/auth/setup-status (page and API both on localhost:8080 — CORS never applies to same-origin requests at all) returned a bare, header-less 404. Direct testing inside the container proved the Api itself answered correctly on its loopback port; the Gateway was the one returning 404 for every path under /api/**, uniformly, with zero log output — meaning the request never reached a matched endpoint at all.

Root cause, confirmed by instrumenting the Gateway with a temporary diagnostic dump of its loaded proxy config: Loaded 0 route(s), 0 cluster(s). ASP.NET Core resolves appsettings.json relative to the process's content root, which defaults to its current working directory — not the directory containing its DLL. entrypoint.sh launched both processes from the container's shared WORKDIR /app (e.g. dotnet /app/gateway/FHIRBridge.Gateway.dll) without ever cd-ing into /app/gateway first or setting the content root explicitly — so the Gateway looked for config at /app/appsettings.json (doesn't exist) instead of /app/gateway/appsettings.json (the real file, with the correct ReverseProxy section), and silently started with none of it. The exact same defect also explains a WebRootPath was not found: /app/wwwroot warning visible in every log capture throughout this work — the clue was there from the start.

This is a bug in the container's own entrypoint.sh design (two apps sharing one WORKDIR without per-process content roots) — not pre-existing Gateway application code, correcting an earlier misdiagnosis during the investigation.

Fix: ASPNETCORE_CONTENTROOT=/app/api and ASPNETCORE_CONTENTROOT=/app/gateway added to each process's scoped env invocation in entrypoint.sh. A small, genuinely separate pre-existing issue was fixed at the same time while in that code: the Gateway's static-file/SPA-fallback branch only excluded /api from its predicate, not /swagger, so real Swagger UI was being shadowed by the portal's index.html:

// before
context => !context.Request.Path.StartsWithSegments("/api")
// after
context => !context.Request.Path.StartsWithSegments("/api") && !context.Request.Path.StartsWithSegments("/swagger")

Re-verified live after the fix: /api/v1/auth/setup-status → 200 {"requiresSetup":true}, /swagger/index.html → real Swagger UI, portal and demo app both still 200.
