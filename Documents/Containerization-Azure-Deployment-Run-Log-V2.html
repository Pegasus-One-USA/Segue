3.The three deployment-mode toggles

All three are independent booleans in main.bicep, each exposed as a plain-language choice in the createUiDefinition.json wizard.

Postgres

Containerized (default) runs Postgres in a Container App on local ephemeral disk, using a mounted Azure Files share purely as an at-rest backup target (see Issue 6 for why). Managed uses Azure Database for PostgreSQL Flexible Server — no container, no backup/restore tradeoff, Azure handles patching/backups/HA.

useAzurePostgresql

Redis

Containerized (default) runs the custom fhirbridge-redis image (self-signed TLS) in a Container App. Managed provisions Azure Managed Redis (Microsoft.Cache/redisEnterprise) — classic Azure Cache for Redis is being retired and is already blocked for new caches on some subscriptions.

useAzureCacheForRedis

Tenant/app secrets

Local database (default) keeps tenant connection secrets and app-level secrets on the local DataProtection-encrypted table. Azure Key Vault creates a dedicated RBAC-enabled vault and grants the app's managed identities access to it — needs Owner/User Access Administrator on the resource group to grant that RBAC.

enableTenantSecretsKeyVault

4.Step-by-step: deploying from scratch

The same flow whether you use the plain az deployment group create CLI path or the "Deploy to Azure" button (which drives the same template through the createUiDefinition.json wizard).

4.1 Publish the images (one-time, or whenever code changes)

Build and push the 4 custom images to whatever registry you control (containerization/scripts/build-images.ps1|sh), then confirm they're pullable from the Container Apps environment before proceeding — see README.md in this folder for the full publish story, including the read-only ACR pull-token pattern used for a vendor registry.

Region matters more than it looks The location parameter (set here) applies to every resource in the deployment, including a managed Postgres Flexible Server if you choose that mode. Some subscriptions (Sponsorship offers in particular) restrict PostgreSQL Flexible Server provisioning in specific regions — see Issue 3 before picking a region if you plan to use Managed Postgres.

6.Issue 1 fixed

Container Apps couldn't pull the freshly-pushed images — UNAUTHORIZED

Symptom: Failed to provision revision … GET https:?scope=repository%3Afhirbridge-redis%3Apull…: UNAUTHORIZED: authentication required

The images pushed to the vendor ACR successfully, but the deploy script (deploy-vendor.ps1) never passed imageRegistryUsername/imageRegistryPassword to the deployment — the ACR has neither the admin user nor anonymous pull enabled, so Container Apps had no way to authenticate.

Fix: wired in the same read-only, scoped one-click-pull ACR token already used by the customer-facing wizard's createUiDefinition.json — same credential, same trust boundary, just also passed on this script's own direct deploy path.

7.Issue 2 fixed

Free-text SKU/capacity fields let an invalid raw Azure value reach the ARM API

Symptom: ParameterOutOfRange — The value of the 'Version' should be in: [] for Postgres; properties.sku.Capacity cannot be updated to C0 for Redis

Two related problems. The Postgres SKU parameter took Terraform's combined tier_size string format (e.g. B_Standard_B1ms) directly as the ARM sku.name field, which the raw ARM API doesn't accept — it wants sku.name and sku.tier as two separate fields. Separately, Redis capacity and SKU were two independent free-choice fields that could combine into an invalid pair (e.g. a Premium-range capacity under a Basic SKU).

Fix: both became curated dropdown keys (Burstable_B1ms, GeneralPurpose_D2s_v3, etc. for Postgres; Basic_C0, Premium_P1, etc. for Redis), mapped internally in main.bicep to the correct real Azure name/tier/capacity values — an invalid combination is no longer representable, let alone submittable.

8.Issue 3 resolved — environment fact, not a bug

PostgreSQL Flexible Server provisioning is restricted in some regions, for some subscriptions

Symptom: same ParameterOutOfRange — Version should be in: [] error, persisting after Issue 2's fix, on a fresh resource with no leftover state

Confirmed directly via az postgres flexible-server list-skus --location <region>: the response's top-level reason field read "Provisioning is restricted in this region. Please choose a different region." — for every SKU, not just the one selected. This is a subscription-level capacity/policy restriction (common on Sponsorship-type offers), not anything this template controls.

Resolution: checked several regions the same way; some (this session found centralus, westus3, northcentralus) are unrestricted for the same subscription and support the same SKU/version. No template change fixes this — picking an unrestricted location is the only actual fix. A support ticket ("Service and subscription limits") can be filed to request an exception, but Sponsorship-type restrictions are usually by design and often declined.

9.Issue 4 resolved — operational, not a bug

A partially-created resource from an earlier failed deploy blocked a clean redeploy

Symptom: Invalid update request: properties.sku.Capacity cannot be updated to C0

When one resource in a deployment fails (Issue 3's Postgres error), independent resources with no dependency on it — here, an Azure Cache for Redis instance — can still be created successfully in that same failed run. Azure Cache for Redis doesn't support scaling capacity down via a later redeploy, so a subsequent attempt targeting a smaller size than what already exists fails with this error.

Resolution: deleted the specific orphaned resource (not the whole resource group) and redeployed fresh. General lesson: after any partially-failed deployment, check what actually got created (az resource list --resource-group <rg>) before assuming a clean slate.

10.Issue 5 fixed

Containerized Postgres crash-looped — "must not be run as root"

Symptom: repeated ./entrypoint.sh: line 33: Aborted (core dumped), then the whole container (and Api alongside it) restarting endlessly

The container's command override (['postgres', '-p', <port>]) replaced the postgres:16-alpine image's ENTRYPOINT entirely — skipping docker-entrypoint.sh, the script that drops the process from root to the unprivileged postgres user before starting the server. Postgres refuses outright to run as root, so it aborted immediately every time.

Fix: switched from command to args — ARM's Container Apps schema treats these the same way Kubernetes does: command replaces ENTRYPOINT, args only replaces CMD. With args, the image's own entrypoint stays intact and does the privilege drop correctly. The identical bug existed in the Terraform azure environment's equivalent resource and was fixed there too.

11.Issue 6 worked around — platform limitation

Postgres's own startup permission check can never pass directly on Azure Files

Symptom: error: could not change permissions of directory "…/pgdata": Operation not permitted, immediately after Issue 5's fix let initdb actually run

Postgres's initdb unconditionally chmods its data directory to 0700 as a hard-coded security check — on every startup, not just first init. Azure Files, as mounted by Container Apps' azureFile storage type, is SMB, which has no concept of POSIX permission bits at all. Confirmed by directly probing the ARM type schema: azureFile only exposes accountName/accountKey/ shareName/accessMode — no mount-options or NFS alternative exists to work around it. This isn't fixable from inside a container image; the permission check lives in the compiled postgres binary, and the mount is controlled entirely by the Container Apps platform.

Workaround, not a fix: a new custom image (containerization/docker/postgres-local) keeps PGDATA on the container's own local (ephemeral) disk — real POSIX permissions, no SMB involved — and treats the Azure Files mount purely as an at-rest backup target, restored on container start and saved back out only on a graceful stop. See Known limitations for the real durability cost this accepts. For anything where that tradeoff isn't acceptable, use useAzurePostgresql=true instead, which has no such caveat.

12.Issue 7 fixed

Binding a custom domain silently stripped the app's managed identity

Symptom: the app (confirmed healthy and working right up until this point) went completely unresponsive afterward — Gateway logged Connection refused (127.0.0.1:5000) and Api produced zero log output, not even its own startup line

identity is a resource-level property on a Container App — a sibling of properties, not something inside properties.template or properties.configuration. The custom-domain deployment's app-update module (custom-domain-app-update.bicep) carefully reads back and passes through every property-level setting (env vars, secrets, volumes, registries) to avoid drifting them on a domain-only redeploy — but it declared the updated container app resource with no identity block at all, which silently resets identity to None. With Key Vault mode on, the app's managed identity is exactly what DefaultAzureCredential uses to authenticate at startup — losing it made that authentication hang indefinitely, with no log output, well before Kestrel even started listening.

Fix: the module now always sets identity: { type: 'SystemAssigned' }, matching what main.bicep sets on first deploy. Confirmed live: the previously-broken app's Identity blade showed Status Off before the fix.

Recovering an already-broken app (this fix only prevents it going forward, it doesn't retroactively repair a live app): re-enable System-assigned identity on the Container App directly (Portal → Identity → toggle On), then manually re-grant the same Key Vault roles (Secrets Officer, Crypto User) to the new identity — the old role assignments now point at a deleted principal and won't apply to the new one. Redeploying main.bicep again instead is not a safe shortcut here: its role-assignment resources use a name derived from the app name, not the principal ID, and Azure doesn't allow changing an existing role assignment's principal in place — that redeploy would likely fail outright on those resources.

13.Known limitations to keep in mind

LimitationWhy, and what to do about it
Containerized Postgres only backs up on a graceful shutdown A crash, a forcibly-killed replica, or Container Apps exceeding its (generously set, 90s) termination grace period loses every write since the last graceful stop — there's no continuous replication or WAL archiving, just a full-directory snapshot copy. Acceptable for a demo/test environment; use useAzurePostgresql=true for anything that needs guaranteed durability.
Redeploying main.bicep without re-supplying the custom domain parameters wipes the bound domain ingress.customDomains is fully replaced on every deploy of the container app; it defaults to blank. Any future main.bicep redeploy against a domain-bound stack needs fhirbridgeAppCustomDomain and bindCustomDomainCertificates=true passed again, or the domain binding disappears (though the certificate resource itself usually survives, since it's a separate resource).
Granting the tenant-secrets Key Vault RBAC needs Owner/User Access Administrator A Contributor-only deploying identity can create the vault itself but will hit an authorization error on the 3 role-assignment resources specifically. See enableTenantSecretsKeyVault's description in main.bicep for the manual az role assignment create fallback.
PostgreSQL Flexible Server may be region-restricted for some subscriptions See Issue 3 — check az postgres flexible-server list-skus --location <region> before committing to a region if using Managed Postgres.

Context: FHIRBridge Azure Bicep one-click deployment — Postgres/Redis/Key Vault toggles, live-verified

Branch: Main_Working_Mapping_V1_Terraform_with_Keyvault. Commits 350bd638 and ac9660e2, tagged v2.1.0 (verified working end-to-end against real Azure subscriptions). Full write-up: Documents/Containerization-Azure-Deployment-Run-Log-V2.html.

What changed: containerization/azure-deploy/main.bicep (the single-template “Deploy to Azure” path) gained three independent boolean toggles, all defaulting to the cheaper/local option:

  • useAzurePostgresql — containerized Postgres vs. managed Azure Database for PostgreSQL Flexible Server
  • useAzureCacheForRedis — containerized Redis vs. managed Azure Managed Redis (Microsoft.Cache/redisEnterprise — classic Microsoft.Cache/redis is being retired)
  • enableTenantSecretsKeyVault — local DB-stored secrets vs. an RBAC-enabled Key Vault

Two facts to not rediscover the hard way:

1. Containerized Postgres can't put its data directory on Azure Files. Postgres's initdb hard-codes a chmod 0700 check on every startup; Azure Files (SMB, the only persistent storage Container Apps supports) can't honor POSIX permission bits at all — confirmed by probing the ARM type schema directly, no mount-options escape hatch exists. The fix in place: a custom fhirbridge-postgres image (containerization/docker/postgres-local/) runs Postgres on the container's local ephemeral disk and treats the Azure Files mount purely as an at-rest backup target, restored on start / saved on a graceful stop only. Real cost: anything written since the last graceful shutdown is lost on a crash or forced kill. Don't try to “fix” this further with more mount tricks — it's a platform ceiling, not a bug.

2. identity: { type: 'SystemAssigned' } must be set explicitly on every template/module that redeploys the fhirbridge-app/worker Container Apps — not just the original main.bicep. It's a resource-level property (sibling of properties), easy to silently drop in a module that otherwise carefully preserves everything else. This exact bug lived in custom-domain-app-update.bicep (the Step 2 custom-domain binder) — it read back and passed through env vars/secrets/volumes meticulously but never touched identity, so binding a domain silently reset a working app's identity to None, breaking Key Vault auth with zero log output and no crash. If you're writing or reviewing any new Bicep module that touches these Container Apps, grep for every resource ... 'Microsoft.App/containerApps@...' declaration and confirm each one either sets identity or is provably read-only.

Also worth knowing: PostgreSQL Flexible Server region availability is subscription-specific (a Sponsorship-type subscription hit a hard “provisioning restricted in this region” wall in eastus/eastus2/westus2/ southcentralus/westeurope but not centralus/westus3/northcentralus — check with az postgres flexible-server list-skus --location <region> before assuming a region works). And if an app already had a custom domain bound before the identity fix existed, it may be live-broken right now independent of any code fix — check its Identity blade (Status On/Off) and see Issue 7's recovery steps in this document (re-enable identity, manually re-grant the 2 Key Vault roles to the new principal, restart) rather than assuming a redeploy fixes it.

Before trusting a port to another branch: cherry-pick both commits, re-run az bicep build/terraform validate, rebuild the compiled JSON (main.json, custom-domain.json — a stale compiled JSON next to a fixed .bicep source caused real confusion this round), republish via publish-deploy-artifacts.ps1|sh, and make sure the fhirbridge-postgres image actually exists in whatever registry the target points at before deploying.

Two commits carry everything in this document: 350bd638 (“Migrate FHIRBridge DB from SQL Server to PostgreSQL; replace retiring Azure Cache for Redis with Azure Managed Redis” — the bulk of the Postgres/Redis toggle work, the fhirbridge-postgres image, the wizard changes) and ac9660e2 (“Fix custom-domain deploy stripping the app's managed identity…” — Issue 7 and the entrypoint crash-path fix).
