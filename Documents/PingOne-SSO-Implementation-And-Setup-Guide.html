1Overview and how it works

Before this change, Segue supported local password login, magic link, Microsoft Entra ID, Google and SAML. This work adds PingOne as an OpenID Connect (OIDC) sign-in provider, and — the important part — makes PingOne the source of truth for roles. At every Ping sign-in Segue asks PingOne which groups the user belongs to, maps those groups to a Segue role using an admin-defined list, and applies the result.

What was built

  • A "Continue with Ping" button on the login page (authorization-code flow with PKCE, no client secret in the browser).
  • Server-side validation of the PingOne ID token (signature, issuer, audience, lifetime).
  • A live role lookup through the PingOne Management API using a separate "worker" application.
  • An ordered group → role mapping editable on Settings → SSO Configurations, with policies for conflicts, unmapped users and role mismatches.
  • Just-in-time (JIT) account creation for new Ping users whose group maps to a role.
  • A Test connection button, an audit trail of role changes, and a "Role Source" note on the user detail page.
  • Everything is editable at runtime (stored as system settings); appsettings.json only provides defaults. No restart needed.

Sign-in sequence

1. PortalCreates PKCE verifier, state and nonce; redirects to PingOne /authorize.
→
2. PingOneUser signs in; PingOne redirects back to the portal root with ?code=….
→
3. PortalChecks state, exchanges the code at /token, checks the nonce, gets the ID token.
→
4. APIValidates the ID token (JWKS, issuer, audience).
→
5. APIWorker app token → memberOfGroups → map groups to roles → apply policy.
→
6. APIIssues the normal Segue session (JWT).
Redirect URIThe portal sends its own origin (for example http://localhost:4200) as the redirect URI. The exact same string must be registered on the PingOne portal app. The response is handled on the next app boot (the same pattern Entra uses).

Design decisions (the "why")

DecisionReason
Roles fetched live at every login, not cached in SegueRemoving someone from a PingOne group takes effect at their next sign-in. PingOne stays the single place to manage access.
A user holds one Segue role; the mapping list is orderedMatches how Segue works. The order decides which role wins when "Use mapping order" is selected.
Strict defaults (Deny) and strict fallback on unreadable valuesA mis-saved or unknown value must never loosen access. Unknown values fall back to Deny / RestrictMismatch.
Worker secret is write-only; stored via the secret storeNever returned to the browser and never written to a settings row. Only a hint (length + last four characters) is shown so an admin can spot a bad paste.
Each provider validator owns its own "enabled" checkThe repo forbids switching on provider types. Adding Ping meant adding a class, not editing a switch in the composite validator.
Host names validated as bare host namesThe domains are put into URLs the server calls with credentials attached; a scheme, path, port or user-info must never be accepted (prevents credential forwarding / SSRF). The API host must be a *.pingone.* host.
Pagination links must stay on the configured API hostThe bearer token is never sent to another host if PingOne (or an attacker) returns a foreign next link.
Outage must not lock out existing users (except in the strict mode)If PingOne can't be reached, existing users keep their last roles — unless "Restrict sign-in if roles do not match" is selected, which refuses rather than fail open.

Validation rules enforced on Save

  • When enabled: Environment ID must be a GUID and Portal Client ID is required.
  • Auth Domain must be a bare host name (auth.pingone.com, not https://… or with a path/port).
  • API Domain must be a PingOne host (api.pingone.com, api.pingone.eu, …).
  • Every mapping row needs both a group and a role; a group cannot be mapped twice.
  • The serialized mapping must fit in 1,900 characters (the setting value limit is 2,000).

4Conditions and combinations, with examples

The examples use these mappings (top row = highest priority) and Segue roles that already exist:

#PingOne group (ID or name)Segue role
1Segue-AdminsAdmin
2Segue-OperatorsOperations
3Segue-AuditorsAudit

Group matching is case-insensitive and works with either the PingOne group ID or its name. A role name in the mapping that does not exist in Segue is ignored (a warning is logged).

4.1 Decision order at sign-in

  1. Provider enabled? Ping off → "The 'Ping' identity provider is not enabled."
  2. ID token valid? Bad signature, issuer, audience or expired → rejected and logged.
  3. Find the Segue user by PingOne subject, else by email.
  4. Role lookup (Ping, or SAML when "apply to SAML" is on): worker token → memberOfGroups → mapped roles in mapping order.
  5. Several different roles? Apply the conflict setting (4.3).
  6. No account? Apply JIT (4.5). Account exists? Apply no-mapped-group (4.4) and mismatch (4.2) policies.
  7. Account disabled? Refuse.
  8. Issue the Segue session.

4.2 Existing user: Segue role vs. Ping role

Applies when the user already has a Segue account and at least one group maps to a role.

SettingSegue role = Ping roleSegue role ≠ Ping roleExample
Auto-switch (AutoSwitch)Sign in no changeSign in role is changed to the Ping role; note saved on the user; audit entry SSO:Ping:RoleUpdatedJane is Audit in Segue, in group Segue-Admins → becomes Admin. User page shows "Role updated via Ping SSO on 2026-10-14: Audit to Admin".
Allow different (AllowDifferent)Sign inSign in keeps the Segue role; nothing changesSame Jane signs in as Audit even though Ping says Admin.
Restrict (RestrictMismatch)Sign inRefused "Your Segue role (Audit) does not match your PingOne role (Admin). Ask an administrator to align them."Jane is blocked until an admin aligns the roles.
"Matches" means exactly one roleA user matches only if they hold exactly one Segue role and it is the Ping-mapped one. A user with two roles in Segue is treated as a mismatch; auto-switch reduces them to the single Ping role.

4.3 User in several mapped groups (conflict)

Only triggers when the groups map to different roles. Two groups that both map to Admin, or groups not in the list, never cause a conflict.

4.5 User with no Segue account

JIT settingMapped group?Result
OnYesAccount created and signed in. Role = mapped role; note "Created via Ping SSO on … with role …"; audit entry SSO:Ping:Provisioned. Example: new hire Lee in Segue-Auditors gets an Audit account on first sign-in.

The "no-mapped-group" setting never lets a person without a Segue account in.

4.6 Disabled account

If the matching Segue user is disabled, sign-in is refused: "Your Segue account is disabled. Ask an administrator to re-enable it." No role changes are applied to a disabled user.

4.7 PingOne cannot be reached or misconfigured

Mismatch settingExisting userNew user
Auto-switch / Allow differentSigns in with the last-known roles (a PingOne outage does not lock people out); warning loggedRefused — no account and no role information
RestrictRefused "Your role could not be verified with PingOne right now. Please try again shortly." (strict mode never fails open)Refused

4.8 SAML logins

  • Apply to SAML on and Ping enabled: the SAML user is located in PingOne by email. Zero or more than one match → no roles are assumed ("do not guess"), so the no-mapped-group rule applies.
  • Apply to SAML off, or Ping disabled: SAML behaves exactly as before; Ping is not consulted.

6Setting up the PingOne account

6.1 Create an account and environment

  1. Sign up for PingOne (a free trial is enough) and sign in to the admin console.
  2. Create or choose an environment (e.g. "Segue Dev"). Pick the region deliberately — it decides your Auth/API domains and cannot be changed later.
  3. Make sure the environment includes the PingOne SSO service (needed for sign-in and the user directory).
  4. Note the Environment ID (section 5).

6.2 Create the groups

  1. Go to Directory → Groups → Add Group (+).
  2. Create one group per Segue role you want to grant, for example Segue-Admins, Segue-Operators, Segue-Auditors. Add a description.
  3. Use clear, unique names; if you map by name, the match is on the exact (case-insensitive) name.
  4. Open each group and copy its Group ID if you prefer to map by ID.
Keep it simpleOne group per Segue role works best. Put people in the single highest-privilege group they need to avoid conflicts (section 4.3).

6.3 Create users and put them in groups

  1. Go to Directory → Users → Add User. Fill in username, email address (required — Segue matches existing accounts by email), given and family name, and set a password (or send an invitation).
  2. Open the user → Groups tab → Add Groups → select the group(s) → Save. (Alternatively, from the group's Users tab.)
  3. Make sure the user is enabled and the email is spelled exactly as in Segue.

6.4 Create the Portal application (Single-Page App)

  1. Go to Applications → Applications → Add Application (+).
  2. Choose Web App / Single-Page App and select OIDC. Name it e.g. "Segue Portal".
  3. On Configuration set:
    • Response Type: Code
    • Grant Type: Authorization Code
    • PKCE Enforcement: S256 Required (Segue always sends S256)
    • Token Endpoint Authentication Method: None (public client — the browser has no secret)
    • Redirect URIs: the portal origin, e.g. http://localhost:4200 (add one per environment: local, test, prod)
    • Sign-off URLs (optional): the same origin
  4. On Resources → Scopes allow openid, profile and email (Segue requests openid email profile).
  5. Toggle the application Enabled (top right). Copy the Client ID.
Most common mistakeThe Redirect URI must match the portal's origin exactly (scheme, host, port; no trailing slash, no /auth/login path). A mismatch shows a PingOne "redirect_uri mismatch" error.

6.5 Create the Worker application

  1. Go to Applications → Add Application and choose Worker. Name it e.g. "Segue Role Reader".
  2. On Configuration note the Client ID and Client Secret. Token Endpoint Authentication Method may be Client Secret Basic or Client Secret Post — Segue tries Basic first and then Post, so either works.
  3. Open the Roles tab → Grant Roles and assign Identity Data Read Only with the environment as the scope. This is what allows reading groups and memberships. Without it the test reports "not allowed to read groups".
  4. Toggle the application Enabled.
Least privilegeDo not give the worker app an administrator role. Read-only identity data is sufficient. Treat the client secret like a password and rotate it if exposed.

6.6 (Optional) PingOne user attributes

Segue reads sub (PingOne user id), email and name from the ID token. If the name is empty, check the application's Attribute Mappings and the user's profile.

7Configuring Segue

  1. Make sure the Segue roles you plan to map already exist (Role Management) and that the database has the new migration (Users.RoleSyncNote) applied.
  2. Sign in as an administrator and open Settings → SSO Configurations.
  3. In Ping Identity (PingOne) fill in Environment ID, Auth Domain, API Domain, Portal App Client ID, Worker App Client ID and Worker App Client Secret (section 5).
  4. Add the group mappings (top row = highest priority) and choose the policies (section 4.9).
  5. Tick Enabled and click Save.
  6. Click Test connection. Expect: "Connected to PingOne. The worker application can read groups."
  7. Sign out and confirm the Continue with Ping button appears on the login page.

10Security notes

  • No secrets in the browser. The portal is a public PKCE client. The worker secret lives only on the server, in the secret store, and is write-only.
  • Strict token checks. Signature (JWKS), issuer, audience (the portal client id) and lifetime are validated on the server; the nonce is checked in the browser, bound to the tab.
  • State and PKCE are one-shot. The record is removed from sessionStorage on return and the response is removed from the address bar.
  • Hosts are constrained. Bare host names only; the API host must be PingOne; pagination links are rejected if they point to another host.
  • Fail closed. Unknown policy values fall to the strictest option; the restrict mode refuses when PingOne cannot be queried.
  • PHI/PII-safe logging. Logs contain counts and role names only — never tokens, emails or group contents. Error text from PingOne is length-limited and shown only to administrators on the test screen.
  • Auditable. Provisioning and role changes create authentication-log entries and a note on the user.
  • Least privilege. The worker app needs only Identity Data Read Only.
