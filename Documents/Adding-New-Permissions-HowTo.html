1.The one rule

You never hand-pick a permission's Id, wire-format code, or display name. You only ever declare which Group and Action an endpoint needs — everything else is generated. If the Group/Action/Category you need doesn't exist yet, add it first, then use it.

1
file to edit per new Category/Group/Action
0
GUIDs you compute by hand
2
ways to gate an endpoint — fixed or resource-based

2.Adding a new Category

Edit one file: src/FHIRBridge.Application/Rbac/PermissionCategoryCode.cs.

public enum PermissionCategoryCode
{
    [PermissionCategory("40000000-0000-0000-0000-000000000001", "Access Control")]
    AccessControl = 1,

    [PermissionCategory("40000000-0000-0000-0000-000000000002", "Platform")]
    Platform = 2,

    [PermissionCategory("40000000-0000-0000-0000-000000000003", "Pipelines")]
    Pipelines = 3,

    // Add your new category here:
    [PermissionCategory("40000000-0000-0000-0000-000000000004", "Reporting")]
    Reporting = 4,
}
  • Pick the next unused integer value.
  • Pick a new, never-before-used Guid — any valid unique Guid works; this project's built-in categories happen to follow a 40000000-...-000N pattern for readability, but that's a convention, not a requirement.
  • The second argument is the human-readable display name shown in the permission-management UI.
Nothing else to touch RbacSeedData.Categories is built from Enum.GetValues<PermissionCategoryCode>(), so the new category appears automatically on the next boot.

3.Adding a new Group

Edit one file: src/FHIRBridge.Application/Rbac/PermissionGroupCode.cs.

public enum PermissionGroupCode
{
    [PermissionGroup("30000000-0000-0000-0000-000000000004", PermissionCategoryCode.AccessControl, "User")]
    User = 1,

    // ...existing groups...

    // Add your new group here:
    [PermissionGroup("30000000-0000-0000-0000-000000000012", PermissionCategoryCode.Reporting, "Dashboard")]
    Dashboard = 12,
}
  • Same rules as a category: next unused int, a fresh unique Guid.
  • The second argument is the PermissionCategoryCode that owns this group — must already exist.
  • Third argument is the display name.
Re-categorizing later is free Just change the PermissionCategoryCode argument in this one attribute — RbacBootstrapper re-syncs the row's CategoryId on the next boot, no migration, no data loss.
Vendor groups are special If this group represents an EHR vendor (a SourceSystemType value), name the member identically to the SourceSystemType member — see section 6. SourceSystemPermissionGroups.GroupFor resolves the group by that exact name match, not a lookup table.

4.Adding a new Action

Edit one file: src/FHIRBridge.Application/Rbac/PermissionActionCode.cs.

public enum PermissionActionCode
{
    [PermissionDisplayName("View")]
    View = 1,

    // ...existing actions...

    // Add your new action here:
    [PermissionDisplayName("Export")]
    Export = 13,
}
  • Next unused int, and the display text used when building a permission's display name (e.g. "Export Dashboard").
  • Actions don't carry their own Guid — never a standalone row, only ever combined with a Group to derive a permission's Id.
Check before reusing an action View/Create/Edit/Delete are meant to be reused across groups (user.view and role.view are two different permissions, same Action). Only add a brand-new action if none of the existing ones fit what you mean.

5.Gating a fixed endpoint Backend

Use this when the required Group/Action is known at compile time — the default case.

[HttpGet]
[StandardPermission(PermissionGroupCode.Dashboard, PermissionActionCode.Export, description: "Export the operations dashboard to PDF.")]
public async Task<IActionResult> ExportDashboard(CancellationToken cancellationToken)
{
    ...
}
  • First two arguments: the Group and Action this endpoint requires. Category is not an argument — it's derived from the group automatically.
  • description is optional but should always be supplied for a new permission — skip it and the permission still works, but a startup warning reminds you to add one.
That's it On the next boot: PermissionCatalog discovers the attribute via reflection, SyncDiscoveredPermissionsAsync creates the row (IsSystem = false) if it doesn't exist and grants it to SuperAdmin, and an authorization policy (HasPermission:{group}.{action}) is registered automatically.

6.Gating a resource-based endpoint Dynamic

Use this instead when the endpoint's required Group can't be known until the request is inspected — the running example is ConfigurationsController.AddSourceConnection, where the permission depends on which EHR vendor (SourceSystemType) the request is for.

Case A — the vendor already exists as a SourceSystemType, it just has no dedicated group yet

This is a one-line change:

// PermissionGroupCode.cs — the ONLY change needed. The member name must match the
// SourceSystemType member name exactly (case-sensitive) — that's the whole mechanism.
[PermissionGroup("30000000-0000-0000-0000-000000000013", PermissionCategoryCode.Pipelines, "Allscripts")]
Allscripts = 13,
Nothing else to touch No attribute change, no seed-data edit, no controller change. On the next boot, SourceSystemPermissionGroups.GroupFor(SourceSystemType.Allscripts) resolves to PermissionGroupCode.Allscripts by name, PermissionCatalog's dynamic pass crosses it with the Edit action already declared on ConfigurationsController.AddSourceConnection, and allscripts.edit appears as a real, grantable permission. Proven end to end in tests/FHIRBridge.Api.IntegrationTests/Tests/SourceConnectionPermissionTests.cs.

Case B — wiring up a brand-new resource-based endpoint from scratch

[HttpPost("source-connections")]
[DynamicSourceSystemPermission(typeof(SourceSystemType), PermissionActionCode.Edit, description: "Add or edit a source connection.")]
public async Task<IActionResult> AddSourceConnection([FromBody] CreateSourceConnectionRequest request, CancellationToken cancellationToken)
{
    var denied = await this.AuthorizePermissionAsync(_authorizationService, request.SourceSystemType, PermissionActionCode.Edit);
    if (denied is not null) return denied;

    // ... normal action body ...
}
  • [DynamicSourceSystemPermission(typeof(TEnum), action, description)] declares which enum type to loop over and which action to cross it with. Metadata only — enforces nothing by itself.
  • this.AuthorizePermissionAsync(_authorizationService, <the enum value from the request>, action) is the real check, called explicitly in the action body. It resolves the group from the value the same way the attribute above tells PermissionCatalog to at startup, so the two can never disagree.
  • A value with no same-named PermissionGroupCode member falls back to the generic SourceConnections group automatically — no error, just shared with every other unmapped value.
Don't reach for this by default Only use the dynamic mechanism when the group genuinely can't be decided until a request arrives. If it's fixed and known at compile time, use section 5 instead.

7.Reusing a permission on multiple endpoints

Just apply the same [StandardPermission(group, action)] pair on as many controllers/methods as need it:

// UsersController.cs
[StandardPermission(PermissionGroupCode.Report, PermissionActionCode.View, description: "View reports and analytics.")]
public async Task<IActionResult> GetUserReports(...) { ... }

// ReportsController.cs
[StandardPermission(PermissionGroupCode.Report, PermissionActionCode.View, description: "View reports and analytics.")]
public async Task<IActionResult> GetAllReports(...) { ... }

Both resolve to the exact same report.view permission (same Id, one database row). If the two descriptions differ, both are kept (joined with " | ") rather than one silently overwriting the other. The Instances column on the Permission row records every declaring ClassName.MethodName, so you can always see everywhere a permission is actually enforced.

8.Seed-declared or discovered-only?

Usually, leave it as discovered-only (do nothing extra). Only promote it to a seed-declared, built-in permission if you specifically want that.

Discovered-only (default)Seed-declared
IsSystemfalsetrue
Granted to SuperAdmin automaticallyYesOnly if also added to SystemRoleDefaultPermissions
Removable by just deleting the attribute usageYes — deactivates automaticallyNo — must remove the RbacSeedData.Permissions entry
Typical useAny new feature-gated endpointCore platform permissions you want to explicitly curate

If you do add one to RbacSeedData.Permissions, also decide whether SuperAdmin/Admin/Operations/Audit should be granted it by default — SuperAdmin/Admin get every seed-declared permission automatically; Operations/Audit need an explicit entry in SystemRoleDefaultPermissions.Grants.

9.Checklist

1
Does the Group you need already exist?If not, add it (and its Category, if that's also new).
2
Does the Action you need already exist and mean what you want?If not, add it.
3
Is the required group fixed and known at compile time?Apply [StandardPermission]. Does it depend on request data instead? Use the dynamic mechanism (section 6).
4
Build and boot once locally.Confirm the permission gets created — check the Permissions table, or GET /api/v1/permissions/catalog.
5
Should this be a built-in, curated permission?If yes, add it to RbacSeedData.Permissions and decide which built-in roles get it by default.
6
Double-check your new int value and Guid aren't copy-pasted.RbacDefinitionValidator catches a duplicate at boot and logs an error instead of writing corrupted data — but pick a genuinely fresh Guid and the next unused int every time regardless.
