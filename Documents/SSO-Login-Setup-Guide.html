Section 1 of 2Microsoft (Entra ID) Login

1.Overview

FHIRBridge already had a "Continue with Microsoft" button and a backend Entra token validator, but two things stood in the way of it actually working end to end: the Entra client/tenant configuration was hardcoded to appsettings.json (any change needed a service restart, and there was no screen to change it from), and the sign-in flow used MSAL's popup mode, which silently got stuck on Microsoft's cross-origin login page in this deployment. This work made the Entra configuration live-editable from a new admin screen and switched the sign-in flow to MSAL's redirect mode, which resolved the stuck-popup issue. It was verified against a real Azure AD tenant and a real App Registration, and the user confirmed sign-in works end to end.

2.How the Azure application was set up

Microsoft's "Continue with Microsoft" flow needs an App Registration in Azure AD / Microsoft Entra ID — this is a different object from a SAML Enterprise Application (see Section 2). An App Registration can be created self-service by anyone holding the Application Developer Entra role; a true non-gallery Enterprise Application (for SAML) needs an admin with the Cloud Application Administrator role instead.

Step 1 — Register the application

Azure Portal: Microsoft Entra ID → App registrations → New registration, or via CLI:

az ad app create --display-name "FHIRBridge Portal" --sign-in-audience AzureADMyOrg

This returns the application's Object ID and Application (client) ID — both are needed in the next steps.

Step 2 — Add the portal as a Single-Page Application (SPA) redirect URI

The portal uses MSAL's redirect flow, which requires the redirect URI to be registered under the SPA platform (not "Web") — the SPA platform is what allows a browser-only app with no client secret to complete the OAuth code exchange. az ad app create has no direct flag for this, so it's set via a Microsoft Graph API call: 

az rest --method PATCH `
  --uri "https://graph.microsoft.com/v1.0/applications/<object-id>" `
  --body '{"spa":{"redirectUris":["https://segue.pegasusone.com:6003"]}}'

The redirect URI must exactly match the app's own origin — the portal's MSAL config (sso.service.ts) uses window.location.origin as its redirectUri, since the redirect flow lands the browser tab back on the app's own root, not a dedicated page.

Step 3 — Grant the Microsoft Graph User.Read permission and admin consent

az ad app permission add --id <client-id> `
  --api 00000003-0000-0000-c000-000000000000 `
  --api-permissions e1fe6dd8-ba31-4d61-89e7-88639da4683d=Scope

az ad app permission admin-consent --id <client-id>

00000003-0000-0000-c000-000000000000 is Microsoft Graph's fixed resource ID; e1fe6dd8-ba31-4d61-89e7-88639da4683d is the User.Read delegated permission ID. The admin-consent call needs a Global Administrator or Privileged Role Administrator — a non-admin account gets a 403 here, which is expected and just means a tenant admin needs to run that one command (or click "Grant admin consent" in the Portal's API permissions tab).

Step 4 — Read back the values the SSO Configurations screen needs

az ad app show --id <object-id> --query "{appId:appId}" -o tsv
az account show --query tenantId -o tsv

5.User provisioning requirement

Microsoft login does not create FHIRBridge accounts — it only signs in to one that already exists. Before anyone can use "Continue with Microsoft":

  • A FHIRBridge user must already exist with the same email address as the Microsoft/Entra account (the address in the Microsoft account's email, preferred_username, or UPN claim) — created the normal way, e.g. via an admin invitation.
  • That user must be enabled. A disabled account is rejected with the same "no matching account" error as a genuinely unknown email.
  • First successful sign-in auto-links the identity. SsoAuthService.LoginWithIdentityAsync looks the user up by the stable Entra subject (oid) first, and only falls back to matching by email for that very first sign-in — once linked, every subsequent login resolves directly by subject, so a later email change on either side won't break sign-in.
  • No match → a clear rejection, not a new account. The attempt is logged to Authentication Logs (governance audit trail) and the user sees: "No matching account found for this identity. Ask an administrator for an invitation."

6.Login flow, step by step

1
User clicks "Continue with Microsoft"signInWithEntra() calls MSAL's loginRedirect(), which navigates the whole browser tab away to Microsoft's sign-in page — no popup window is involved.
2
User authenticates with MicrosoftStandard Microsoft sign-in/consent screen; on success Microsoft redirects the browser back to the app's own origin (the registered SPA redirect URI).
3
App boot picks up the responseThe APP_INITIALIZER's completeEntraRedirectIfReturning() calls handleRedirectPromise(), which resolves the Entra ID token — this runs before the router's own initial navigation, so no page has flashed yet.
4
Token exchanged for a FHIRBridge sessionThe ID token is POSTed to the SSO login endpoint. EntraTokenValidator validates its signature against the tenant's live JWKS and checks issuer/audience using the currently configured Instance/Tenant/Client (resolved fresh from ISystemSettingsCache on every call).
5
User match & session issuedSsoAuthService.LoginWithIdentityAsync resolves the matching enabled FHIRBridge user (see Section 5), links the identity if this is the first SSO sign-in, and issues a normal session — the same session type as password or SAML login.
6
Redirect into the appSuccess → /dashboard. Failure (token invalid, or no matching enabled user) → /auth/login?error=sso_failed, which shows a toast explaining no matching account was found.

7.Known limitations & troubleshooting notes

AADSTS50011 — redirect URI mismatch The SPA redirect URI registered on the App Registration must be an exact match for the portal's origin (scheme, host, and port). If this deployment's URL changes, re-run the az rest PATCH command in Section 2, Step 2, with the new origin.
interaction_in_progress If a user closes the Microsoft sign-in tab/window manually mid-flow, MSAL's sessionStorage-tracked interaction flag can get stuck, causing this error on the next attempt. A fresh tab, or clearing sessionStorage for the site, clears it.
Popup mode is not used, deliberately loginPopup() was tried first and abandoned: the browser severs the popup's window.opener reference once it navigates to Microsoft's cross-origin login page, so the popup never signals completion back to the opener tab, with no visible error. Do not reintroduce popup mode for Entra without a different completion-detection mechanism.
Entra's separate JWT-bearer scheme is unaffected If a caller ever presents a raw Entra token directly as an API Authorization header (a distinct, legacy path from the login flow documented here), that scheme is still registered once at ASP.NET Core startup and still needs a service restart to pick up a changed Tenant/Client ID — this is a pre-existing limitation, not something this work changed.

Section 2 of 2Organization SSO

SAML 2.0 "Organization SSO" is for hospital/corporate identity providers (Okta, ADFS, Azure AD configured as a SAML app) — distinct from the Microsoft Entra ID login covered in Section 1. The backend (SAML endpoints, live-editable configuration via the same SSO Configurations screen, ACS/metadata URLs) and frontend (SAML button, redirect flow) are already implemented and have been verified end to end against a test IdP (below). A real production IdP (Okta or Azure AD SAML Enterprise Application) is in progress but not yet finalized.

Testing option — MockSAML Verified working

mocksaml.com is a small hosted test IdP built specifically for SAML SP integration testing — no signup, no catalog, no app to register. It accepts any SP and always signs its response with its own published test certificate, which sidesteps the intermittent IDX13515 (non-NCName ID) bug that makes samltest.dev unreliable for this SP. This is the fastest way to confirm the SAML plumbing (redirect → ACS → user match → session) works before spending time on a real enterprise IdP.

How to test Enter the three values above into the SAML card on the SSO Configurations screen (Service Provider Entity ID / Redirect URLs can stay whatever you already use for Section 1's Entra flow, or any value — MockSAML doesn't validate the SP's registration), enable SAML, save. Click "Continue with SAML" on the login page → MockSAML shows a simple form asking what email/name to assert (no real credentials) → it posts a signed assertion back to the ACS URL. As with Entra (Section 1.5), whatever email you type into that form must already belong to an existing, enabled FHIRBridge user, or the attempt is rejected and logged to Authentication Logs.

Testing option — Auth0 Verified working

Auth0 (an Okta company — a separate console from Okta itself) can also act as a full SAML IdP for testing, using its SAML2 Web App add-on. Unlike MockSAML this exercises a real identity platform with actual user accounts, connections, and logs — closer to a real hospital/corporate IdP than MockSAML's throwaway form.

Setup steps used

  1. Create (or use) an Auth0 application of type Regular Web Application — the SAML2 Web App add-on only appears on this type.
  2. On the app's Settings tab, add the FHIRBridge ACS URL to Allowed Callback URLs. Skipping this produces the generic "Oops! something went wrong" error below with no other symptom.
  3. On the app's Addons tab, enable SAML2 Web App. Set Application Callback URL to the same ACS URL, and set the add-on's Settings JSON to force the NameID to the user's email (this SP reads the SAML subject as the email, and its own metadata declares emailAddress NameID format): 
    {
  "nameIdentifierFormat": "urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress",
  "nameIdentifierProbes": [
    "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress"
  ],
  "mappings": {
    "email": "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress"
  }
}
  4. On the app's Connections tab, create/enable a database connection for the test user (e.g. Username-Password-Authentication) and toggle it on for this application. A newly created connection needed "Promote Connection to Domain Level" before Auth0 would resolve it for this SP-initiated SAML request — without it, Auth0 returned "The connection is not yet configured" with an empty connection_id in its logs. Use Test Connection on that tab to confirm it works before retrying the SSO login.
  5. Create a test user in that connection whose email matches an existing, enabled FHIRBridge account.
