1What is Segue?

Segue moves healthcare data from one place to another. On one side is a source — typically an EHR system like Epic, speaking the FHIR standard. On the other side is a destination — a database table or a CSV file. In between, you draw a pipeline (Segue calls it a Workflow) that says "pull these kinds of records from here, and write them there, mapped to these columns."

Sources: Epic, Generic FHIR Destinations: SQL Server, CSV Everything is role-protected Every change is logged forever
Note on scope. This deployment is currently configured to only offer two destination types — SQL Server and CSV — even though the product supports many more under the hood. If you don't see Snowflake, S3, MongoDB, etc. in your Node Library, that's expected — it's a deliberate configuration choice, not a bug.

4The Dashboard

The first thing you see after signing in. It's a health check for the whole platform — how many pipeline runs succeeded, failed, or are still running, plus a quick list of recent activity.

  • Succeeded / Failed / Running / Pending / Cancelled — live counts across every pipeline run, updated whenever you click Refresh.
  • + New Workflow — the starting point for building a new pipeline (covered next).
  • Recent Workflows — the last few pipelines that ran, their source, status, and when they last ran. Click View all to see the full execution history.
  • The left-hand menu is your main navigation for the rest of the app: Role, User Management, Workflows, Execution History, Settings, and Logs & Compliance.

5Building your first pipeline

A pipeline (Workflow) always starts the same way: give it a name, then add a source node (where the data comes from), then attach a destination node downstream of it (where the data goes). Click Workflows in the left menu, then + New Workflow.

The Workflows list — every pipeline you've built, with its status and last run. This is also where you'd click into an existing one to edit it.

A brand-new, empty pipeline canvas. Type a name in the top-left field, then click + Add module to place your first node.

Choosing a node

Clicking + Add module opens the Node Library — every source and destination type this deployment currently allows.

  • Epic — connects to an Epic EHR's FHIR API. The one you'll use for a real hospital/clinic system.
  • Generic FHIR R4 — connects to any other standards-compliant FHIR server (test servers, non-Epic EHRs).
  • SQL Server — writes incoming records into tables in a SQL Server database.
  • CSV — writes incoming records out as delimited text files (downloaded, emailed, or delivered over SFTP).
A destination is greyed out until you've placed a source node first — Segue always connects a destination to whatever's upstream of it, so it needs something to connect to.

About the other source, "Generic FHIR R4": it works the same way but with far fewer fields — just a base URL, a polling method (Search via REST), and a run schedule — since it doesn't need OAuth or vendor-specific setup. It's useful for connecting to a plain test FHIR server. This manual focuses on Epic since that's the source most deployments actually use.

7Mapping fields (the details)

This is the heart of Segue: connecting a field from the incoming FHIR data (left) to a column in your destination table (right). It looks visual and free-form, but every connection you draw becomes one exact, reviewable rule.

  • Left panel (Payload) — every field that can appear in this FHIR resource, organized as a tree you can expand. A field tagged array means the source can send more than one of it (e.g. a patient can have several addresses).
  • Right panel (Table) — the destination table's columns. Use + Add column to create a new one, or + Add a table from your database… / + Create a new table… to bring in a different target.
  • Suggest mappings — auto-matches source fields to columns with obviously similar names, so you're not connecting everything by hand.
  • Mark as Master — flags this group's mapping as the authoritative one used elsewhere in the product (e.g. lineage displays).
  • Load JSON payload — paste a real example FHIR record so the source tree reflects fields your actual data really uses, not just the generic shape.

This runs a real ALTER TABLE against your destination database the moment you finish the wizard (via Add to Workflow / Save) — not immediately. Nothing touches the real schema until then, so it's safe to experiment while mapping.

Turning a repeating field into one column — three ways

FHIR records are full of arrays (a list of "based on" references, several categories, multiple components). A single SQL column can't hold a list directly, so Segue gives you three ways to flatten one down. Which one you want depends on the answer to: "do I need every item, or just one?"

Array → JSON. Drag the whole array group (e.g. BasedOn) straight onto a column — Segue tags it JSON and stores the entire list as one JSON-text string. Best when you need every item and every sub-field, and don't mind reading it back with a JSON query later.

The Mapping list at the bottom of the canvas is the plain-English record of every rule you've created — source field(s), mode, destination column, and instance selection, all in one table.

Click + Add mapping to build a rule by hand instead of dragging:

SettingWhat it means
Source field(s)Pick one specific leaf field from the tree (e.g. Category › Text), not a whole array group.
Instance — All recordsArray → comma-separated. Pulls every value from the array and joins them into one string in a single column. Pair this with the combine as one delimited row checkbox below (see next screenshot).
Instance — FirstArray → single record. Only the first item in the array is used — everything after it is ignored. Use this when you only ever care about one value (e.g. the primary category).
Instance — NthSame idea as First, but lets you pick a specific position (2nd, 3rd, …) instead of always the first.
Instance — CriteriaPicks whichever array item matches a condition you define (e.g. "the one where use = official"), rather than by position.

With Instance = All records and combine as one delimited row checked, every value in the array is joined into a single comma-separated string in that one column — Array → comma-separated, the third mode.

This manual-mapping panel is marked "preview" in the product itself (you'll see a small ⚠ next to Direct mode) — meaning it's shown for review but not yet fully enforced by the pipeline engine. The drag-and-drop Array → JSON mapping described above is the fully working path today.

Marking a primary / upsert key

Every mapped column has a small 🔑 button. Click it to mark that column as the key Segue uses to tell "this is the same record as before" from "this is a brand-new one" — which is what makes Upsert by source id (from the Configure step) actually work. Typically you'd mark the column holding the FHIR resource's own id as the key.

9Managing saved connections

Every source and destination you've ever configured — plus mapping profiles and transformation rules — has its own dedicated admin screen, separate from the pipeline canvas. Find them under Settings → Workflow Configurations.

Source Connections — every EHR/FHIR connection, searchable by name, EHR vendor, audience, or status. + New Source Connection creates one without needing to open the pipeline canvas at all.

Destination Connections — every SQL Server/CSV target, its status, and who last touched it. The pencil icon edits; the trash icon deletes (blocked once a connection has real run history, to protect that history).

Mapping Profiles — a saved, reusable field-mapping (source → target object → field list) that can be applied to more than one pipeline, so you don't have to redraw the same mapping twice.

Transformation Rules — set a default once (globally, for a resource type, for a destination type, or for one specific source field) instead of repeating the same per-column rule in every pipeline. A per-column override is still available from the "Rules" button next to any mapped field on the canvas.

10The EHR endpoint directory

Under Settings → EHR Endpoints is a pre-loaded directory of hundreds of real Epic MyChart FHIR endpoints across the US — a lookup table, not something you need to fill in yourself.

  • Search by hospital/health-system name, vendor, or base URL to quickly find the exact endpoint you need when configuring an Epic source — instead of hunting it down manually.
  • + Add Endpoint lets you register one that isn't already listed.
  • The pencil icon opens an entry for editing if a URL or name ever changes.

11Branding & system settings

Also under Settings: how the platform looks, security secrets, and the deeper runtime configuration knobs. Most people will only ever touch Branding, Email, and Terminology Codes — the rest is here for completeness.

Branding — company name, brand colors, and logos. Changes preview live before you save, so you can see the effect immediately.

System Settings → Email — the same SMTP fields from first-time setup, editable later. Use Send Test Email to confirm it actually works before relying on it.

Security — the app-wide signing secrets, generated automatically the first time the app started. Regenerating one immediately signs every user out — only do this if a secret may have leaked.

Terminology Codes — keeps the local copy of medical code systems (LOINC, SNOMED CT, RxNorm, ICD-10) up to date by downloading official releases on a schedule, or on demand via Synchronize Now. Needed if pipelines validate or translate codes.

Allowed Origins — the web addresses permitted to call Segue's API from a browser. If you run your own portal on a different domain, add it here — changes apply immediately, no restart needed.

System Settings → General exposes dozens of low-level runtime switches (rate limits, retry counts, background-worker timers, feature toggles). These are meant for technical administrators troubleshooting a specific issue, not day-to-day configuration — leave them at their defaults unless you've been told to change a specific one.

13Execution history & audit logs

Two different views of "what happened": one for pipeline runs, one for everything anyone changed in the system.

Execution History — every time a pipeline ran, its status, how long it took, and what/who triggered it. Filter by status or trigger type to find a specific run quickly.

Logs & Compliance → Audit Logs — an immutable, hash-chained record of every configuration and entity change: who did it, what module, what action, and when. Search by Correlation ID to trace one specific event across the system.

Compliance Reports — generates a ready-to-share HIPAA §164.312(b) or SOC 2 evidence PDF for a date range: audit-trail integrity, authentication activity, data-access summaries, security events, and errors — pick your dates and click Generate & Download PDF.
