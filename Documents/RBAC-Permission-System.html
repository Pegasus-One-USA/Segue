1.Overview

Before this system, every permission needed a hand-picked GUID, a hand-typed wire-format code, and a hand-typed display name — three places to keep in sync, and nothing stopped a typo ([StandardPermission("usr.viw")]) from silently registering a policy nobody could ever satisfy. Now a permission's entire identity is a pure function of two enum values (PermissionGroupCode, PermissionActionCode) — the same pair always produces the same Id, wire-format code, and display name, in every environment, on every boot, with nobody hand-picking anything.

  • Built-in permissions. A curated list (RbacSeedData.Permissions) self-provisions and self-heals on every boot.
  • Static discovered permissions. A [StandardPermission(group, action)] attribute on any controller/action auto-registers itself — no seed-data edit needed.
  • Dynamic / resource-based permissions. For endpoints whose required group can only be known once the request is inspected (e.g. which EHR vendor a source connection is for), a permission is auto-discovered per vendor with zero code beyond adding one enum member.
  • Direct user-level overrides. An admin can grant or deny a specific permission for one user, overriding whatever their role would otherwise give them — merged in at login time.
  • Duplicate-definition guard. A copy-pasted enum value, Guid, or display name is caught at boot and logged as an error instead of silently corrupting the permission table.

3.Boot-time flow

Both passes run synchronously during startup, before app.Run() — a request is never served against a partially-synced permission table.

1
dbContext.Database.Migrate()Apply any pending EF Core migrations.
2
RbacDefinitionValidator.Validate()Runs first, inside RbacBootstrapper.EnsureAsync, before any write. Any duplicate value/Id/display-name/seed-pair → every error logged, method returns immediately, database untouched this boot.
3
RbacBootstrapper.EnsureAsyncUpserts Categories → Groups → built-in Permissions (by Id, then by Name fallback) → deactivates orphans → upserts the 4 system Roles → upserts Role→Permission grants.
4
SyncDiscoveredPermissionsAsync (Program.cs)Calls PermissionCatalog.DiscoveredPermissions, skips anything already seed-declared, deactivates orphaned discovered permissions, upserts the rest (static and dynamic together), grants new ones to SuperAdmin.
5
Policy registrationOne ASP.NET Core authorization policy ("HasPermission:{code}") registered per code returned by PermissionCatalog.AllPermissionCodes — the union of declared and discovered.

What PermissionCatalog.DiscoveredPermissions actually does Core

This method does the combining, not Program.cs — by the time SyncDiscoveredPermissionsAsync sees a DiscoveredPermission, duplicates are already merged and static-vs-dynamic origin is already resolved.

Static pass — reflects over every ControllerBase-derived type for [StandardPermission] on the class and each method, tagging each occurrence with its declaring location. Groups all occurrences by wire-format code (case-insensitive); for each group, combines descriptions (deduplicated, joined with " | ") and instances into one DiscoveredPermission with IsDynamic = false.

Dynamic pass — groups every [DynamicSourceSystemPermission] occurrence by (EnumType, Action), calls SourceSystemPermissionGroups.AllGroupsFor(enumType) to get every group a value of that enum resolves to right now, crosses each with the action, and skips any code a static declaration already produced. Everything else becomes a DiscoveredPermission with IsDynamic = true — see section 5.

Why IsDynamic exists It's what lets FindUndeclaredCodes (the typo-detection check logged at startup) tell a genuine [StandardPermission] typo apart from a dynamically-discovered code that's supposed to have no seed entry — without it, every dynamic code falsely warned as "used but not declared" on every single boot.

4.Request-time authorization flow

Everything above is how permissions get into the database. This is how a live HTTP request is actually checked against them — the part most implementation notes skip.

Step A — login issues the token

1
LocalAuthService.GetPermissionCodesAsync(userId, roleIds)roleCodes = union of every granted role's Permission.Name. userAllocations = this user's direct PermissionAllocation rows. Result = (roleCodes minus anything the user has an allocation for) ∪ every allocation the user has enabled — a direct override always wins over the role default, granting or denying.
2
JwtAccessTokenIssuer.Issue(user, roleNames, permissionCodes)One "permissions" claim per code, e.g. Claim("permissions", "epic.edit"). Token returned to the client.
This is a snapshot, not a live check The merge happens once, at login. A permission override made after that only takes effect on the user's next login — the currently-issued access token is unaffected (verified by PermissionEnforcementTests.Granting_a_direct_override__adds_the_permission_on_next_login_only).

Step B — every subsequent request re-checks the token's claims

1
app.UseAuthentication()Validates the JWT signature/expiry, populates HttpContext.User with its claims.
2
Password-change-required gate (Program.cs)403s any /api/v1/* call (except change-password/me) if the pwd_change_required claim is "true".
3
app.UseAuthorization()Evaluates [Authorize(Policy = "HasPermission:{code}")] against the policies registered at boot.
4
PermissionAuthorizationHandler.HandleRequirementAsyncReads ICurrentUserService.CurrentUser.Permissions — HttpContextCurrentUserService filters HttpContext.User.Claims down to type "permissions". Succeeds if the required code is present (case-insensitive); otherwise the request is rejected with 403 before the controller action ever runs.
5
Controller action runsFor a [StandardPermission]-gated action, nothing further to do — already authorized above. For a [DynamicSourceSystemPermission]-gated action, the action body calls this.AuthorizePermissionAsync(...) itself, using the same policy machinery with a group resolved from the request instead of one fixed at startup.

Step C — the Angular portal's role in this Frontend

The portal never calls a "check my permission" endpoint at request time. It decodes the permissions claim array out of the JWT once (on login and on app boot) into its own AuthStore signal, and every AuthService.hasPermission('epic.edit') call afterward is a local string comparison against that decoded array — not a network call. The frontend's view of "what am I allowed to do" is a snapshot from login time too, exactly like the backend's token, just on the other side of the wire.

5.The dynamic / resource-based mechanism Dynamic

Some endpoints can't use a fixed [StandardPermission(group, action)]: the actual permission group they need depends on data inside the request, only known once it's inspected. The canonical example is ConfigurationsController.AddSourceConnection — a source connection's required permission depends on which EHR vendor (SourceSystemType) it's for, and Epic/Cerner/Athenahealth/Allscripts each need their own dedicated permission.

SourceSystemPermissionGroups.GroupFor(Enum value)

Resolves the PermissionGroupCode for any enum value by name, not a hand-maintained dictionary: Enum.TryParse<PermissionGroupCode>(value.ToString()). A value with no same-named group falls back to the generic SourceConnections group. Checks Enum.IsDefined on the incoming value first — otherwise an out-of-range integer (allowed through by the default JsonStringEnumConverter) could coincidentally parse into an unrelated vendor's group by number.

SourceSystemPermissionGroups.AllGroupsFor(Type enumType)

Every group a value of enumType can resolve to right now, deliberately excluding the generic SourceConnections fallback (curated by hand instead of auto-discovered).

DynamicSourceSystemPermissionAttribute(Type enumType, action, description)

Metadata only — does not extend AuthorizeAttribute and enforces nothing by itself. Only tells PermissionCatalog which enum type + action to cross so one permission per resolved group is auto-discovered at startup.

ControllerAuthorizationExtensions.AuthorizePermissionAsync

The actual enforcement, called imperatively inside the action body:

var denied = await this.AuthorizePermissionAsync(_authorizationService, request.SourceSystemType, PermissionActionCode.Edit);
if (denied is not null) return denied;

This overload takes the enum value directly, resolves the group via GroupFor internally, then builds the code and calls IAuthorizationService.AuthorizeAsync against the same HasPermission:{code} policy every other check uses. Because both the attribute (read at startup) and this call (evaluated per request) resolve the group the same way, they can never disagree about which permissions exist versus which get checked.

Proven end to end Adding PermissionGroupCode.Allscripts (matching the pre-existing SourceSystemType.Allscripts, which had no dedicated group before) produced a working allscripts.edit permission with zero other code changes — no attribute edit, no seed-data edit, no controller change. See tests/FHIRBridge.Api.IntegrationTests/Tests/SourceConnectionPermissionTests.cs.

6.Same permission on multiple endpoints

Fully supported by design — it's normal for the same permission to gate more than one endpoint.

  • Same Group+Action, same description everywhere. Instances accumulates every declaring method; Description stays that one text.
  • Same Group+Action, different descriptions. Description becomes every distinct text joined with " | " — nothing is silently dropped (an earlier version used .DistinctBy(p => p.Code), which kept only the first attribute's description; that bug is what this replaced).
  • New text on an already-synced row. Appended ("{existing} | {new}"), guarded so re-appending the same text next boot is a no-op.
  • Removing all but one usage. Instances drops the removed location; the permission stays active as long as one usage remains.
  • Removing every usage. The permission is deactivated, never deleted.

7.Duplicate-definition validation

The entire scheme is a pure function of the taxonomy enums — a mistake inside that taxonomy can silently corrupt every Id/Code derived from it. RbacDefinitionValidator.Validate() runs at the very top of RbacBootstrapper.EnsureAsync, before any database write.

CheckCatches
Duplicate underlying enum value C# allows two members to share an int (Epic = 10, Foo = 10) — once that happens, .ToString()/(int) conversions can no longer tell them apart. Checked via reflection over the enum's declared fields directly, since Enum.GetValues alone renders both colliding members as the same first-declared name.
Duplicate declared Id A copy-pasted [PermissionCategory]/[PermissionGroup] where the Guid literal wasn't changed for the new member.
Duplicate display name Not a data-corruption risk like the two above, but almost always a copy-paste mistake that leaves two permissions indistinguishable in the permission-management UI.
Duplicate (Group, Action) seed pair Two RbacSeedData.Permissions entries declaring the same pair produce the exact same duplicate code, since Id/Name/Code are all derived from that pair, never hand-picked.
What happens on failure Every error is logged via ILogger.LogError and RbacBootstrapper.EnsureAsync returns immediately — no category, group, or permission row is written that boot. The database is left exactly as it was rather than risk seeding data derived from an ambiguous definition. Unit-tested in RbacDefinitionValidatorTests.cs against deliberately-broken private test enums (never the real production enums), plus one live regression test asserting today's real definitions are clean.

13.Why the Id looks the way it does

Guid.Parse($"{(int)group:D8}-0000-0000-0000-{(int)action:D12}");
  • Group occupies the first 8 digits, Action the last 12; the two middle segments are always zero.
  • Category is deliberately excluded. A group's owning category is a mutable fact (re-synced by RbacBootstrapper on the next boot) — not part of a permission's identity. Baking it into the Id would make the Id stale the moment that mapping changes.
  • "D" (decimal), not "X" (hex). Every digit reads back as the enum's literal int value — with hex formatting, any value ≥ 10 would render as a letter (10 → a); decimal keeps it 10. Example: Epic (group = 10) + Read (action = 11) → 00000010-0000-0000-0000-000000000011.
  • The same Action reused under a different Group naturally produces a different Id — e.g. View under both User and Role never collides.
