1.Overview & concept

Previously, every destination column in the mapping node had to be mapped from a source field (or left unmapped). This feature adds a third option: a column can be set to always write a fixed value — either a literal constant you type in (e.g. every row's "ClientType" column always says "Patient"), or a pipeline/runtime value that JSON MappingEngine already has access to at execution time (the current timestamp, the pipeline run's own id, a freshly generated GUID, etc.).

Core design decision A column is either mapped from a source, or set to a default — never both. There is only ever one MappingRow per destination column; setting a default replaces whatever mapping that column had, and mapping a new source onto a default column replaces the default right back. This is what makes the two mutually exclusive without needing extra validation flags — see §7.

2.Where it lives in the UI

In the workflow builder's destination wizard (node-library-v2), the mapping canvas shows one card per destination table, one row per column. Every column row now has a small flag button (⚑) next to the existing edit/delete controls. Clicking it opens the Set default value modal. A column currently set to a default shows a DEFAULT badge on its row, and its upsert-key toggle (🔑) is hidden — see §7 for why.

Clicking a column already mapped, or its "Edit…" link in the flat mapping list at the bottom of the canvas, re-opens the same modal (pre-filled with the current value) if that column is set to a default — instead of the ordinary source-mapping popover.

4.Currently visible options — detail

@default — Literal value

You type free text and every record writes that exact value. The only option with a second input field (the literal text) and a data-type picker, since there's no source to infer a type from. Works for any destination column type the value type dropdown offers (String/Integer/Decimal/Boolean/Date/DateTime) — pick whichever matches the real column so CreateMappingProfileRequestValidator's type check passes at save time.

@now — Current date/time (UTC)

The moment the pipeline run starts writing — one single UTC timestamp, computed once and shared by every record that run writes (not a per-record "row write time"). Good for "ImportedOnUtc" / "LastSyncedUtc" style columns. Must map onto a DateTime-typed column.

@runId — Pipeline run ID

The GUID identifying this specific pipeline execution. Every record written by the same run shares the same value. Useful for audit/traceability columns ("which run produced this row"), or for grouping rows from the same execution for later cleanup/debugging.

@newGuid — New GUID

The only default that is genuinely different for every record, not shared across a run. Intended as a surrogate primary key when the source data has no natural id you'd want to map (or you deliberately don't want to reuse the source's own id). See §7 for the important caveat about combining this with upsert mode.

5.Currently hidden options — detail & how to re-enable

These seven presets were built, tested, and are fully wired end-to-end (backend included) — they're just temporarily filtered out of the picker at your request, to keep the initial rollout's option list short. Nothing about them was removed.

@resourceType HIDDEN

The FHIR resource type this mapping profile maps (e.g. "Patient"). Since one mapping profile always maps exactly one resource type, this is a run-level constant, not per-record.

@sourceResourceId HIDDEN

The source FHIR resource's own .id — the same value a normal $.id source mapping would extract, but reachable as a "default" without having to map the field explicitly. Genuinely per-record (every row gets its own source resource's id).

@mappingProfileName / @mappingProfileId HIDDEN

Records which mapping profile (by name or GUID) actually wrote a given row — useful for provenance when more than one profile can write to the same destination table.

@destinationObject HIDDEN

The table/file this row was written to. Resolved per field, not just per run: a field on a genuine child table (e.g. a repeating Patient.name array fanned out onto dbo.PatientName) correctly reports "dbo.PatientName", not the mapping profile's primary table — see §9's "hardening" note and JsonMappingEngine.cs in the file list.

@sourceConnectionId HIDDEN

The GUID of the source connection the data came from — useful when a destination table can receive data from more than one source connection (e.g. two different Epic environments feeding the same table).

@triggeredBy HIDDEN

Who or what started the pipeline run: a user's identifier for a manual trigger, or "scheduled" / "webhook" for an automated one. Only populated by the Configured Pipeline (the production execution path this UI feeds) — the Runtime Plane's DAG executor has no trigger identity to report, so this resolves to null there. It is also the one token that can genuinely be null even in the Configured Pipeline (some scheduled/system-initiated runs carry no identifier) — mapping it onto a NOT NULL column is still validated normally at save time, unlike every other token here (which the validator trusts to always resolve to something).

How to re-enable a hidden option

Open field-mapping-model.ts, find the preset's entry in DEFAULT_VALUE_PRESETS, and remove (or set to false) its hidden: true flag:

// Before:
{ token: '@triggeredBy', label: 'Triggered by', description: '…', valueType: 'String', hidden: true },

// After (re-enabled):
{ token: '@triggeredBy', label: 'Triggered by', description: '…', valueType: 'String' },

Nothing else needs to change — the modal, the mapping list, JsonMappingEngine, and the validator already handle every token regardless of visibility. Visibility only filters the picker's dropdown (via the derived VISIBLE_DEFAULT_VALUE_PRESETS export).

6.How it behaves across destination types

Default-value resolution happens in JsonMappingEngine, entirely before any destination-specific writer runs — the engine just produces a plain value for the column; every destination writer then persists it exactly like any other mapped value. That means every default option works identically in principle across every destination type. The differences below are about what the destination's own schema constrains, not the default-value mechanism itself.

Destination familyWhat matters when setting a default
SQL Server / MySQL / PostgreSQL
(relational, real schema)		 The column has a real, fixed data type. Pick the matching Data type in the modal (String/Integer/Decimal/Boolean/Date/DateTime) — CreateMappingProfileRequestValidator rejects a mismatch at save time (e.g. a DateTime default on an int column). A default on a NOT NULL column is always safe for every token except @triggeredBy, which can genuinely resolve to null.
CSV / Blob / Datalake / Fabric
(no live schema)		 Columns are free-text; the data-type picker is advisory only (used for the wire's ValueType, which downstream consumers of the file may care about). No live-schema type-mismatch check applies.
Mongo Schemaless — the default value is written as a normal document field with whatever BSON-mappable type its declared ValueType implies. Works the same as any other mapped field.
Medplum / Aidbox / Azure FHIR Service
(whole-resource FHIR destinations)		 These destinations write the source resource largely verbatim, so field-level default columns are a less common use case there — but the mechanism still works identically for any mapping profile that does target individual fields on these destinations.
Upsert mode — the one real cross-destination caveat Whenever a destination's write mode is upsert (SQL family and Mongo both support this), a default-value column cannot be the upsert key, on any destination type. A run-constant token (e.g. @mappingProfileId) would make every row collide on the same key; a per-record token (@newGuid, @now) would never match a row from a previous run. Both the UI (the 🔑 toggle is hidden on default columns) and the backend validator (rejects it, scoped specifically to upsert-mode destinations) enforce this. Insert-only mode is unaffected — using @newGuid as a surrogate primary key on an Insert-only table is the intended, supported use case.

7.Mutual exclusivity with source mapping

A column is either mapped from a source or set to a default — never both, and this needs no separate validation flag to enforce. There is only ever one MappingRow object per (resource, table, column). Setting a default calls replaceRow(...), which wholesale-replaces whatever row that column had — any prior source mapping is simply gone. Conversely, dragging a new source field onto a column that's currently set to a default replaces the default row right back with a normal source-mapped row. Each action fully owns the column's identity; there's structurally nothing left over from the other state.

8.Do's and don'ts

✅ Do

  • Match the default's Data type to the real destination column's type — mismatches are rejected at save time, not silently truncated at run time.
  • Use @newGuid as a surrogate primary key when a table has no natural source id and the destination write mode is Insert only.
  • Use @now / @runId for audit-trail columns (ImportedOnUtc, RunId) rather than hand-rolling the same thing with a transform rule.
  • Re-open a default column via its ⚑ button (or Edit…) to check/change its value — the modal always reflects exactly what's currently saved.
  • Save the whole workflow and reopen it after setting a default, to confirm the value round-trips correctly before relying on it in production.

❌ Don't

  • Don't mark a default-value column as the upsert key on an upsert-mode destination — no token is a sound upsert key (see the callout in §6). The UI already prevents this; don't try to work around it via a raw API call either, the validator rejects it too.
  • Don't map @triggeredBy onto a NOT NULL column without also marking the field required or supplying a literal fallback — it's the one token that can genuinely be null.
  • Don't assume @now/@runId/most tokens vary per record — they're one shared value for the whole run. Only @newGuid and @sourceResourceId vary per row.
  • Don't expect a default value to fan out correctly across a RepeatParent array field — if a single source resource produces multiple destination rows, they all share the same resolved default (the token resolves once per source resource, not once per fanned-out row).
  • Don't re-set an already-hidden preset's visibility as a way to "delete" it if it turns out unwanted long-term — flip hidden, don't remove the whole entry, or you also remove support for any already-saved column still using it.

9.The round-trip bug that was found and fixed

During implementation, saving a workflow with a default column and reopening it later silently corrupted the mapping and, on the next save, wrote the entire raw source resource JSON into the default column. This was found and fixed before release; documented here since it explains several of the files in §10–11.

1
Save — The canonical "Mapping JSON" save format (field-mapping-summary.model.ts's toSummaryColumn) had no branch for mode: 'default' rows. They silently fell through to the ordinary "direct field" shape with an empty sources array, losing the token/literal entirely.
2
Reload — applyMappingSummaryDocument reconstructed that as an empty, broken mode: 'value' row with no source at all — this is why re-opening a saved default column showed nothing.
3
Re-save — That broken empty row's path resolved through workflow-build-assembler.service.ts's toJsonPath(''), which has a fallback: if (!p || p === resourceType) return '$'; — $ means "the whole document" to the mapping engine. Every subsequent pipeline run wrote the entire raw resource JSON into that column.
Fix Both toSummaryColumn and applyMappingSummaryDocument (frontend) and the matching backend MappingImportService.BuildJsonPathAndFormat/BuildFieldAsync now handle mode: "default" explicitly, carrying defaultToken/defaultValue/ defaultValueType through the full round trip. The "Select Existing" profile picker (destination-wizard.component.ts's _applyExistingProfile) had the identical gap and was fixed the same way.

15.Known limitations

  • No per-fanned-out-row variation. A source resource that fans out into multiple destination rows via RepeatParent shares one resolved default value across all of them — the token resolves once per source resource, not once per output row (documented in each preset's own code comment).
  • No automated end-to-end (Karma) coverage. The Angular test runner is currently broken in this development environment (a corrupted ajv dependency under node_modules, unrelated to this feature) — new frontend logic was verified via TypeScript compilation and manual live testing instead of an automated browser test run.
  • Hidden presets have no dropdown fallback for already-set values. If a column is already set to a now-hidden token and you reopen its modal, the dropdown won't visually show it as selected (native <select> behavior when its bound value has no matching option) — but the underlying saved value is untouched and submits correctly if you don't change the dropdown. Purely cosmetic, and only reachable today via a token that's already hidden by design.
