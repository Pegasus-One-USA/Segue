1. System overview

FHIRBridge (product name in the UI/Swagger: Segue) is a healthcare data-integration platform. It pulls clinical data from EHR/FHIR sources (currently enabled in code: Epic, athenahealth, eClinicalWorks/Healow, generic FHIR, sample; HL7 v2 via MLLP; Cerner, Allscripts and MEDITECH are modelled but their clients are gated off), runs it through a configurable workflow graph (extraction → governance / de-identification → transform / mapping → output), and writes it to one of 20+ destinations (SQL Server, Postgres, MySQL, Snowflake, Mongo, Blob/S3/SFTP, CSV/Parquet/Avro/PDF, FHIR repositories, REST APIs, etc.). An Angular admin portal configures tenants, connections, workflows, RBAC and licensing.

Logical architecture

Hosts – FHIRBridge.Api (REST + SignalR + portal), FHIRBridge.Worker (background services), FHIRBridge.Gateway (YARP front door: serves the portal, proxies the API), FHIRBridge.LicenseServer (vendor-side licensing)
Infrastructure – EF Core, 20+ destination writers, secret providers, source connectors/token providers, terminology sync, e-mail, licensing
Application – use-case services, DTOs, abstractions (ports), RBAC/security policies, mapping engine
Domain – entities (for example Tenant, User, SourceConnection), enums, value objects
Runtime plane (own Domain / Application / Infrastructure) – workflow definitions, graph validation, ranked orchestrator, node executors, source clients
Building blocks – SharedKernel, Integration (FHIR/HL7), Observability, Governance (exception management)

Dependency direction is always inward: Domain ← Application ← Infrastructure ← Api/Worker, and the same inside the Runtime plane. This is enforced by automated architecture tests (section 8).

4. Request flow — from entry to destination

4.1 Middleware pipeline (every HTTP request, in order)

Defined in src/Api/FHIRBridge.Api/Program.cs after builder.Build().

  1. Forwarded headersapp.UseForwardedHeaders() – X-Forwarded-For/Proto/Host, ForwardLimit default 2
  2. Correlation idinline middleware + WorkflowCorrelationResolver – sets TraceIdentifier / X-Correlation-Id; pushed into the Serilog LogContext
  3. Global exception handlerapp.UseExceptionHandler – MapException → <500: safe message + “expected” governance record; ≥500: IGlobalExceptionManager.CaptureAsync → ErrorLogs row + ErrorReferenceId
  4. Security response headersnosniff, X-Frame-Options DENY, Referrer-Policy no-referrer, CSP (default-src 'none' for /api) outside Development
  5. HSTS + HTTPS redirectnon-Development only
  6. Swaggeronly if Development or Swagger:Enabled=true
  7. Startup bootstrapBootstrapDatabase, ProvisionAppSecrets, LoadLicense, SyncDiscoveredPermissions (run once, not per request)
  8. Inbound API request loggingInboundApiRequestLoggingMiddleware – durable SQL record of workflow/launch API calls, including refused ones
  9. Serilog request loggingone event per request; no query strings (may carry PHI); adds ClientIp, CorrelationId, UserId
  10. Static files / healthportal build in wwwroot; /health
  11. CORSUseCors("Portal") → DynamicPortalCorsPolicyProvider (origins managed in DB, no restart)
  12. CSRF double-submit checkPOST/PUT/PATCH/DELETE under /api/v1 with the access-token cookie must echo X-CSRF-Token = CSRF cookie; skipped for [AllowAnonymous] and [CsrfExempt] endpoints
  13. Authenticationapp.UseAuthentication() – policy scheme chooses Local HS256 JWT or Entra ID
  14. License gatenon-Active license ⇒ 403 license_not_active for all /api/v1 except an allow-list (login, setup, license screens)
  15. Session gatesclaims pwd_change_required / mfa_setup_required confine the session to the change-password / MFA endpoints
  16. Authorizationapp.UseAuthorization() – policies & handlers; denials logged by GovernanceAuditingAuthorizationMiddlewareResultHandler
  17. Rate limiterUseRateLimiter, only when RateLimiting:Enabled is true (default true); policies auth / oauth / webhook, per client IP, configurable
  18. Endpoint executionMapControllers, MapWorkflowEndpoints, MapHub (RunStatusHub, TerminologyStatusHub); SPA fallback to index.html

4.2 Example A — a portal user clicks “Run” on a workflow

POST /api/v1/workflows/{workflowId}/run — handler in Workflows/WorkflowEndpoints.cs (route is anonymous at route level; authorization is done inside the handler because the endpoint serves three caller types).

  1. AuthenticateFhirBridgeAuthenticationExtensions → cookie fhirbridge_access_token read in JwtBearer OnMessageReceived → JWT validated (Local HS256 or Entra)
  2. Classify callerWorkflowEndpoints (/run): portal user (has uid, not token_use=client_credentials) / machine client (client-credentials token) / anonymous SMART standalone launch
  3. Portal user: RBAC checkIAuthorizationService.AuthorizeAsync(HasPermission("workflow.run")) → PermissionAuthorizationHandler → IUserPermissionsProvider (DB, short cache)
  4. Anonymous callerallowed only if workflow.IsPubliclyLaunchable, otherwise 404 (so ids cannot be probed)
  5. Override guardExecute V2 overrides (other EHR endpoint, group id, search criteria) only for signed-in portal users; length limits; ValidateEhrEndpointForRunAsync
  6. License quotaILicenseQuotaGuard.EnsureCanStartNewRunAsync (expired license or monthly record cap ⇒ 403)
  7. Per-node permission + license allow-listfor each Source/Destination node: HasPermissionAsync(source/destination type, Execute) and EnsureSourceConnectionStillAllowed / EnsureDestinationTypeAllowed
  8. Build execution contextWorkflowExecutionContext(runId, correlationId, triggeredBy, triggerType, patient/criteria, overrides); continues a “Validated” run if validate-run created one
  9. Dispatchsync: orchestrator.ExecuteAsync inline; async: Task.Run in a fresh DI scope with IAmbientActorContext, returns 202 + status URL; run tracked by IWorkflowRunTracker so it can be cancelled
  10. OrchestrateRankedWorkflowOrchestrator.ExecuteAsync → WorkflowGraphValidator.Validate → create WorkflowRun → persist “Running” → SignalR notify → audit WorkflowRunStarted → RunNodesAsync
  11. Node loopTopologicalSort; per node: IWorkflowNodeExecutorRegistry.GetRequired(nodeType).ExecuteAsync(context, node, inputs). Outputs are passed to downstream nodes via WorkflowNodeOutput
  12. ExecutorsSource (e.g. EpicSourceNodeExecutor → FhirSourceClientFactory → connector + ApplicationType strategy + token provider) → Transform / Mapping (MappingNodeExecutor, JsonMappingEngine) → Compliance (Consent, DeIdentification, AuditLineage) → Destination (DestinationNodeExecutor → ConfiguredDestinationWriterFactory → Mapped*Writer)

4.3 Example B — a typical admin CRUD request (e.g. create a source connection)

  1. ControllerControllers/V1/SourceConnectionsController — [Authorize(Policy…)] / [StandardPermission(group, action)]; thin: binds DTO, calls service
  2. Application serviceConfigurationService (Application/Services) — validation, business rules, secret handling (stores a reference, not the secret value)
  3. Port → adapterIConfigurationRepository → EfConfigurationRepository → FHIRBridgeDbContext
  4. SaveChanges interceptorsAuditingSaveChangesInterceptor (writes AuditLog rows with hash chain, blocks edits to append-only tables); LicenseEnforcementSaveChangesInterceptor (rejects rows violating the license at creation)
  5. ResponseDTO returned; on expected failure the global handler maps it to 4xx with a safe message

4.4 Example C — third-party app triggers a workflow (client credentials)

  1. TokenPOST ClientCredentialsTokenController → ClientCredentialsTokenService verifies the client secret via IPasswordHasher (dummy-hash comparison for timing parity) → ClientCredentialsAccessTokenIssuer issues an HS256 JWT with token_use=client_credentials and no uid
  2. RunPOST /workflows/{id}/run (or /workflows/external/run) with the bearer token; because it has no uid it cannot satisfy any HasPermission:* policy and is accepted only where the handler recognises token_use
  3. Public-launch endpoints/workflows/external/* are [AllowAnonymous] + [CsrfExempt] + RequireRateLimiting("oauth"), guarded by a short-lived launch ticket (ExternalRunTicketService) and unguessable callerId

4.5 Example D — scheduled and webhook-triggered runs (no HTTP user)

  1. ScheduleDispatcherWorkerWorker: every ~30 s (configurable, min 15 s) → dispatcher.DispatchDueRunsAsync → finds due ResourcePipelineRoute rows (ScheduleExpressionMatcher) → publishes PipelineRunCommand
  2. PipelineRunCommandProcessorIMessageConsumer<PipelineRunCommand> → scoped IPipelineRunCommandHandler → pipeline execution
  3. Webhook ingestionWebhookIngestionController: reads raw body, verifies HMAC-SHA256 signature (X-FHIRBridge-Signature, required by default), rate limit “webhook”, enqueues; WebhookIngestionCommandProcessor consumes
  4. Bulk exportsource node may pause run (AwaitingBulkExport); BulkExportPollWorker polls and calls RankedWorkflowOrchestrator.ResumeAfterBulkExportAsync, rebuilding context from the persisted BulkExportJob
  5. HL7 v2Hl7MllpListenerService (TCP MLLP) → Integration parser → FHIR mapper → pipeline
Two pipeline paths coexist. (1) The Configured Pipeline (IConfiguredPipelineService, tenant-config-driven, used by trigger endpoints and the scheduler). (2) The Runtime plane workflow engine (graph + executors) used by /api/v1/workflows/*. CLAUDE.md describes the Runtime plane as “PipelineOrchestrator with Extraction→Governance→Transform→Output”; in the current code the user-facing run path is RankedWorkflowOrchestrator with a configurable node graph, and PipelineOrchestrator remains as the bounded-parallel extraction component. Worth reconciling in the docs before the review.

4A.4 Orchestrator internals (RankedWorkflowOrchestrator)

  1. Restrict (optional)ExecuteAsync(definition, context, targetNodeId): a checkpoint run restricts the graph to the target node’s ancestors (RestrictToAncestorClosure)
  2. Validate the graphIWorkflowGraphValidator.Validate → throws WorkflowGraphValidationException (mapped to a 4xx by the API)
  3. Resolve overridesResolveEhrEndpointOverrideAsync — only when the run explicitly named an EHR endpoint; otherwise skipped entirely
  4. Create the run, persist “Running” immediatelyPersistRunStartedAsync (best-effort) so the portal shows the run as Running for its whole duration; then NotifyRunStatusAsync (SignalR) and audit WorkflowRunStarted
  5. Order the nodesTopologicalSort(definition) using edges, then Rank/SubRank for ties (CompareNodes)
  6. For each node, in ordercheck cancellation → collect incoming outputs along the edges (GetIncomingOutputs) → create WorkflowNodeRun → audit NodeExecutionStarted → open a log scope carrying WorkflowRunId, WorkflowId, NodeId, NodeType, NodeRank, CorrelationId
  7. Execute_executorRegistry.GetRequired(node.NodeType).ExecuteAsync(context, node, incomingOutputs, ct)
  8. Bulk-export pause checkif output metadata carries BulkExportDeferredJobId: store prior node outputs on the BulkExportJob, set run status AwaitingBulkExport, persist, notify, and return — BulkExportPollWorker resumes later via ResumeAfterBulkExportAsync
  9. Record successoutputsByNodeId[node.Id] = output; nodeRun.Succeed(lineageJson); record resource history (PHI columns encrypted by IPhiFieldEncryptor); audit NodeExecutionCompleted; log duration and record count
  10. Failure handling per nodethree catches: WorkflowRunCancelledException and OperationCanceledException → node marked Cancelled (not Failed), audit NodeExecutionCancelled, rethrow; any other Exception → node marked Failed, audit NodeExecutionFailed, rethrow

Run statuses (WorkflowRunStatus): Pending, Running, Succeeded, Failed, Cancelled, PartialSuccess, AwaitingBulkExport, Validated (validate-run passed, waiting for /run; non-terminal) and ValidationFailed (validate-run rejected the request; terminal, nothing executed). PartialSuccess is a normal completion path (no exception), so the code logs a warning and writes an informational governance record to keep it visible.

4A.5 Source stage in detail (SourceNodeExecutor.ExecuteAsync)

Vendor classes such as EpicSourceNodeExecutor are thin: they pass a node-type string and a RuntimeSourceType to this shared base. The base class does the work:

  1. Read node configresourceType, searchParameters (or the wizard’s “Search criteria” field), the wizard’s “Resources” list
  2. Resolve the live source connectionISourceConnectionRuntimeResolver.ResolveAsync (or ResolveWithRunOverridesAsync for Execute V2): loads the SourceConnection, fetches secrets through ISecretProvider (private key PEM, client secret), validates the PEM shape, builds a FhirSourceConfiguration
  3. Apply per-run EHR endpoint overrideEhrEndpointSourceOverride.Apply (only if the run named a hospital endpoint)
  4. Apply per-resource-type criteriaApplyResourceTypeCriteriaAsync (criteria authored in the destination wizard)
  5. Apply node-scoped retrieval settingsretrieval method (search-rest, bulk-export, single-patient), export scope, group id, patient ids, output format. A single-patient run with no patient id throws instead of silently becoming a tenant-wide search
  6. Pick the clientIFhirSourceClientFactory.Create(sourceType) → dictionary lookup → Epic / Athena / eCW (Healow) / Generic / Sample client resolved from DI
  7. Decide which resource types to fetchpriority: node “Resources” → connection ResourceTypes → types derived from granted SMART scopes → node resourceType → destination’s selected types; otherwise fail loudly with an explanatory message. Then narrow to what downstream destinations actually selected
  8. Order and fetchPatient first (its ids become the cohort that scopes every other patient-compartment type); reference-scoped types (Practitioner, Organization, Medication, PractitionerRole) last, built from references collected in already-fetched data; bulk export uses $export instead of paged search
  9. OutputWorkflowNodeOutput with contract ResourceBatch (resource envelopes); types the connection is not authorised for are reported through skippedResourceTypes → PartialSuccess

How the connector talks to the EHR

  • Connector base class (FhirSourceConnectorBase): paged search following next links (stops if a server hands out a link that does not advance), a maximum page cap, retry on transient status codes with jitter and Retry-After, and a per-source request throttle shared across calls (SourceThrottles).
  • Vendor axis: subclasses override only what differs (display name, vendor headers such as athenahealth practice id).
  • Auth axis: ISourceApplicationStrategy (one per ApplicationType: Backend, EHR launch, Standalone, Patient) describes the OAuth flow, validates configuration and gets the access token. BackendServicesApplicationStrategy chooses between SmartBackendServicesTokenProvider (RS384 private_key_jwt, used when a private key is present — Epic) and OAuth2ClientCredentialsTokenProvider (client secret — athenahealth) by which credential exists, not by vendor name.
  • Token caching: DistributedFhirAccessTokenCache (Redis in production). Interactive flows keep authorization codes and OAuth state in Redis-backed stores with PKCE.
Enabled sources. FhirSourceClientFactory.DefaultRegistrations currently registers Epic, Sample, GenericFhir, Athenahealth and Healow (eClinicalWorks). Cerner, Allscripts and MEDITECH Greenfield client registrations are commented out (“gated”) although their node executors and enum values exist. Describe those as planned, not delivered, in the review.

4A.6 Transform and compliance stages

  • MappingNodeExecutor turns ResourceBatch into MappedRecordBatch (MappedDestinationRecord: resource type, target table/object, key, field values, original JSON). It resolves mapping profiles per resource type from the node’s own saved profile ids (never by a shared search, so one workflow cannot pick up another’s profile) or from an inline self-contained mapping, and applies the field-level transform nodes through ITransformNodeRegistry.
  • DeIdentificationNodeExecutor, ConsentNodeExecutor, AuditLineageNodeExecutor implement the compliance stage; services behind them include Safe Harbor and k-anonymity de-identification and the consent / resource-type-access governance rules.
  • PassThrough executors (UsCoreValidation, DataQualityScoring, Normalization, FlattenExtensions, PatientMatching, several terminology nodes) forward their input unchanged at present. WorkflowNodeExecutorBase’s default output even carries the metadata text “Placeholder until existing Segue service is wired behind this node.”

4A.7 Destination stage in detail (DestinationNodeExecutor.ExecuteAsync)

  1. Read mapped records from the inputswhole-resource FHIR destinations (FHIR Repository, Medplum, Azure FHIR Service) may receive a raw ResourceBatch and are converted to pass-through records
  2. Filter to selected resource typesdrops types the user did not select for this destination (guarded so it never filters the whole batch to nothing); reported in metadata as filteredOutResourceTypes
  3. Make FHIR-conformantFhirConformanceSanitizer.Sanitize on each record’s JSON before any writer sees it
  4. Load destination configurationnode config or CreateDestinationConfiguration; secrets stay references until the writer resolves them
  5. Create the writerIConfiguredDestinationWriterFactory.Create(destinationType) → registry lookup → writer from DI, wrapped in LoggingConfiguredDestinationWriter (decorator adding uniform write telemetry and governance rows)
  6. Build the write contextPipelineWriteContext: AllowInlineDelivery=false (a background node has no HTTP response), workflow name, correlation id, run id, optional FetchMissingReferenceAsync delegate (resolved by walking graph edges back to exactly one upstream source node), user identity
  7. Writerelational / Mongo / Blob / Fabric / webhook / API destinations: group records by resource type, order groups so referenced tables are written first (OrderGroupsByReferenceDependency), write each group with its own resolved profile; other destinations: one WriteAsync call
  8. Per-record failure isolationwriters return DestinationWriteResult.RecordErrors instead of throwing, so one bad row does not discard the batch. The executor collects them into skippedResourceTypes so the run becomes PartialSuccess instead of a misleading Succeeded. A later group that fails because an earlier group lost its rows gets an exception that names the earlier causes
  9. OutputWorkflowNodeOutput with contract DestinationWriteResult: destination id, records written, timestamp, optional download URL and email-delivery details

5.2 Authorization (RBAC)

  • Roles → permissions in the database. JWTs do not carry permission codes; PermissionAuthorizationHandler resolves them per request via IUserPermissionsProvider (CachedUserPermissionsProvider, short cache) keyed by the uid claim. Revoking a permission takes effect without waiting for token expiry.
  • Named policies: UnifiedAdmin (GlobalAdmin or TenantAdmin), SuperAdminOnly, WorkflowModuleAccess, MappingCatalogAccess, SourceDiscoveryAccess, PermissionCatalogAccess, and generated HasPermission:<group.action> policies for every permission code.
  • Per-vendor / per-destination Execute permissions are checked at run time for every node in the graph, in addition to workflow.run.
  • Denials are audited centrally (GovernanceAuditingAuthorizationMiddlewareResultHandler → AuthorizationLog) so no controller must remember to log.
  • Permission drift detection: startup FindUndeclaredCodes warns when a [StandardPermission] has no seed row; DiscoveredPermissionSynchronizer syncs discovered permissions.

5.5 Audit, accountability and tamper evidence

  • AuditLog row per audited entity change, written by AuditingSaveChangesInterceptor; each row has EntryHash and PreviousHash (hash chain). AuditChainVerificationWorker / EfAuditChainVerificationService re-verify the chain.

5.5 Multi-tenancy

Tenant is the isolation entity for identity: each User and BrandConfiguration belongs to exactly one tenant, resolved per request by ICurrentTenantResolver (cached). Source connections, destinations, mapping profiles and routes are flat configuration records without a tenant id, and workflow definitions are not tenant-scoped. Reviewers will ask whether that is intended for a multi-customer deployment (see Q&A).

9. Known gaps & review hot-spots (stated openly)

These are things an experienced reviewer will find; raising them first builds credibility.

Local JWT validation is relaxed. In ConfigureLocalBearer, ValidateIssuer = false and ValidateAudience = false; tokens are HS256 (symmetric). Mitigations: the signing key is secret and auto-generated, lifetime and signature are validated. Consider pinning issuer/audience, and note that client-credentials and user tokens share one key and scheme (separated only by claims).
Anonymous endpoints with run capability. /workflows/{id}/run and /workflows/external/* are anonymous at route level and rely on in-handler checks (public-launch flag, callerId, launch ticket) plus the oauth rate limit. This is deliberate and documented in code and guarded by an architecture test, but deserves a threat-model walkthrough.
Rate limiting is per-IP and process-local. It uses fixed-window in-memory partitions built once at startup; settings changes need a restart; behind a proxy it depends on correct forwarded-header trust (ForwardedHeaders:TrustAllProxies exists as a switch and should be off in production). Multi-instance deployments don’t share counters.
Swagger toggle in production. Swagger:Enabled is flagged in code as temporary; remove or lock down once no longer needed.
Pass-through placeholders. Several node executors (UsCoreValidation, DataQualityScoring, Normalization, FlattenExtensions, PatientMatching, terminology nodes) inherit PassThroughNodeExecutor and forward their input unchanged, and some governance services are PassThrough* implementations. ConsentNodeExecutor also inherits it but only falls back to pass-through when no consent/governance service is registered; with ConfiguredConsentService and CompositeGovernancePolicyService registered by Infrastructure it filters resources. Confirm in the review which of these are claimed as delivered features versus roadmap.
Documentation drift. CLAUDE.md says 18 DbSets (actual ≈100), describes PipelineOrchestrator as the runtime topology (actual user path is RankedWorkflowOrchestrator). Update before sharing.
Licence exposure in third-party packages. Several packages are not under a plain permissive licence: MediatR and AutoMapper (Lucky Penny: RPL-1.5 or paid), QuestPDF (free only under US$1M revenue), and, in test projects only, FluentAssertions 8 and NBomber (non-commercial / paid). See section 8A before this product is distributed to customers.
Very large files. Program.cs (~1,100 lines) and WorkflowEndpoints.cs (~4,900 lines) hold a lot of inline logic. Candidates for extraction into endpoint modules / application services to improve testability.
Other incomplete areas: Gateway is a simple single-API proxy (fixed routes, no auth/rate limiting/load balancing of its own); ControlPlane is a scaffold; Runtime transform step is limited (field-level mapping lives mostly in the Mapping executor/engine); two pipeline execution paths coexist.

10. Reviewer Q&A bank

Likely questions with short, code-backed answers. Click to expand. Items marked Verify need a quick check by the team before the meeting.

A. Architecture & design

Why Clean Architecture with a separate Runtime plane?

The control plane (configuration, RBAC, licensing) changes for admin reasons; the runtime plane (graph execution, connectors, executors) changes for integration reasons. Separate Domain/Application/Infrastructure layers keep each independently testable, and architecture tests prevent leakage between them.

How do you add a new EHR vendor?

Add a FhirSourceConnectorBase subclass, a *SourceNodeExecutor, register both in DI (executor registry picks it up by NodeType). No switch edits — an architecture test bans switch on ApplicationType.

How do you add a new destination?

New Mapped*DestinationWriter, a DestinationNodeExecutor subclass, register in DI / writer factory, add a connection-test service and permission seed rows. Writers must not run DDL outside the schema-provider path (tested).

How do you add a new permission?

Add [StandardPermission(group, action)] to the endpoint and a row in RbacSeedData.Permissions. The HasPermission:<code> policy is auto-registered; startup logs a warning if the seed row is missing. See Documents/Adding-New-Permissions-HowTo.html.

Why both a Configured Pipeline and a Runtime workflow engine?

The Configured Pipeline is the earlier tenant-config-driven path (scheduler/trigger endpoints); the Runtime engine is the explicit graph model with a visual builder. Verify the intended end state (convergence vs. permanent coexistence) and prepare a one-line answer.

Why controllers in some places and minimal APIs in others?

Admin CRUD uses MVC controllers (attribute-based policies, Swagger). The workflow surface uses minimal APIs in one file with explicit in-handler authorization because one route serves three caller types. Honest trade-off: the file is very large.

Is MediatR used everywhere (full CQRS)?

No. MediatR behaviours exist in the Runtime plane; most controllers call application services directly. It is “CQRS-style where it helps,” not a blanket rule.

B. Request flow & behaviour

What happens to an unhandled exception?

Global handler maps known exceptions to 4xx with a safe message (and a lightweight informational governance record); unknown/5xx go to GlobalExceptionManager which assigns an ErrorReferenceId, classifies, persists details to ErrorLogs, and returns a generic category message. No stack traces to clients.

How can one request be traced across API, worker and logs?

A correlation id (X-Correlation-Id or derived from the workflow session) is stamped on Serilog context, OpenTelemetry activity tags, audit rows, error logs and run records. Background runs set an ambient actor scope with the same id.

Are long runs tied to the HTTP request?

Sync mode is (client disconnect cancels via linked token). Async mode runs in Task.Run with a new DI scope and returns 202 + status URL; it is tracked by IWorkflowRunTracker and cancellable. Verify: fire-and-forget runs are lost if the process restarts mid-run — confirm how orphaned “Running” rows are reconciled.

How are runs scheduled and made durable?

Dispatcher publishes commands through the queue abstraction (InMemory / RabbitMQ / Service Bus transports); consumer runs them in the Worker. With RabbitMQ/Service Bus messages survive restarts; with InMemory they do not (dev only).

How do runs handle FHIR bulk export?

A source node can defer to an async export job; the run is persisted as AwaitingBulkExport, prior node outputs and context are serialised onto the job, and BulkExportPollWorker resumes the run when the export completes (possibly in another process).

How is concurrency/back-pressure controlled?

Bounded parallel extraction (max 4 in PipelineOrchestrator), bulk-export concurrency limits (returns 429-style with Retry-After), license monthly quota guard, rate limiter on public endpoints.

C. Security

How is authentication done and where do tokens live?

JWT bearer (local HS256 or Entra). Browser stores the token in an HttpOnly cookie; CSRF double-submit protects state-changing calls. 60-minute access, 30-day refresh (hashed in DB).

Why aren’t permissions in the JWT?

So revocation is immediate and tokens stay small. Permissions are looked up per request from the DB through a short-lived cache keyed by uid.

How are secrets stored?

Config holds references only. Values live in Azure Key Vault or the DB secret store (encrypted with Data Protection; key ring persisted and optionally cert/Key-Vault-wrapped). App secrets (JWT key, PHI key) are auto-generated at first boot.

How is PHI protected?

AES-256-GCM on history columns; log masking; no query strings or raw FHIR resources in logs; de-identification (Safe Harbor / k-anonymity) and consent rules in the workflow; TLS + HSTS in transit.

What stops a brute-force or credential-stuffing attack?

Per-IP rate limit on auth endpoints, account lockout, MFA, PBKDF2 at 350k iterations, constant-time compare, timing-parity dummy hash for unknown clients.

How do you prevent CSRF given anonymous public endpoints?

CSRF applies only where the cookie is the credential. Endpoints with another credential must declare [CsrfExempt] or be anonymous; an architecture test enforces the declaration so it can’t be forgotten.

What is the tenant isolation story?

Tenancy covers identity: users and branding belong to one tenant (ICurrentTenantResolver). Connections, destinations, mappings, routes and workflows are not tenant-scoped (no tenant id on those entities), so isolation between customers today relies on one deployment per customer. Verify that is the intended model and be ready to say so; CLAUDE.md’s “Tenant aggregate owns all configuration” is no longer true: the old aggregate that owned configuration was removed (see IConfigurationRepository), and Tenant is now an identity and branding boundary only.

How is the audit trail made tamper-evident?

Hash-chained AuditLog rows (each stores its own hash and the previous hash), append-only enforcement in the interceptor, and a worker that re-verifies the chain.

Is the local JWT validating issuer and audience?

Currently no (ValidateIssuer=false, ValidateAudience=false) — signature and lifetime are validated. Be ready to discuss whether to tighten this; see section 9.

How are third-party (machine) clients authorised?

Client Credentials grant → JWT with token_use=client_credentials and no uid; cannot satisfy any permission policy; accepted only by handlers that explicitly check the claim. Deployment-wide grant (no per-workflow RBAC) — Verify that this scope is acceptable to the architect.

What about dependency/vulnerability scanning and secrets in source?

Verify: confirm CI runs dependency audit (dotnet list package --vulnerable, npm audit) and secret scanning; not determined from the code reviewed here.

HIPAA / SOC 2 mapping?

Code comments reference controls (e.g. HIPAA #7 CSRF/cookie auth, #11 key-ring encryption, SOC2 CC6.1 headers, CC6.2 rate limiting). Verify: no formal control-to-evidence matrix was found; consider producing one.

D. Data & persistence

How are schema migrations applied?

EF migrations (SQL Server in Infrastructure; PostgreSQL in a separate assembly); BootstrapDatabase at startup guarded by DatabaseBootstrapLock to avoid concurrent migration across instances.

How are concurrent edits handled?

Optimistic concurrency with RowVersion tokens.

How is data deleted / retained?

Soft delete via global filter; retention purge worker and policy services; audit tables are append-only and retained.

Can destinations alter customer database schemas?

Only through the mapping-schema providers with DDL type validators; writers themselves are tested to contain no unsuppressed DDL.

E. Operations & deployment

What are the deployment targets and how do configs differ?

Local Docker Compose; Windows VM service (no Docker; UseWindowsService, deploy scripts under deploy/windows); client Azure tenant via Bicep; future AWS/GCP. Every infra change must work across all four. Non-dev startup requires explicit ASPNETCORE_URLS.

Can the API scale horizontally?

Mostly: Redis for token cache and SignalR backplane, shared Data Protection key ring path required, a real queue broker (RabbitMQ or Service Bus). Limitations: in-memory rate limiter and run tracker are per-instance (cancel of an async run must hit the owning instance). Verify.

How do we monitor it?

Serilog → Seq/Azure Monitor; OpenTelemetry traces and metrics; /health; alert rules and endpoint health workers; SignalR live run status; Operations/Errors screens backed by governance tables.

How is licensing enforced?

License gate middleware (non-active license blocks API except recovery endpoints), ILicenseQuotaGuard before runs, EF interceptor on create, re-validation of allow-lists at run time, heartbeat and usage snapshots to the License Server.

What is the disaster-recovery / backup story?

Verify: not determined from code. Prepare answers for DB backup/restore, Data Protection key ring backup (loss makes encrypted secrets and launch tokens undecryptable), and Key Vault recovery.

F. Quality & process

How do you stop architectural erosion?

NetArchTest rules in CI (layering, no switch on ApplicationType, CSRF declaration, no DDL in writers).

What is the test coverage?

Verify: run coverage (coverlet is referenced) and quote the number; do not estimate.

Mostly yes (MIT, Apache-2.0, BSD-3-Clause).
