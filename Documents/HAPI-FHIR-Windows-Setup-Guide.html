HAPI FHIR Test Server — Native Windows Setup Guide

How to run fhirbridge-hapi-fhir directly on Windows (no Docker) as a Windows Service, for use as a plain "generic FHIR" test source — the same role it plays in local docker-compose.yml, replicated on a Windows VM.

Purpose Generic FHIR test source (no OAuth/SMART) for FHIRBridge's GenericFhir source connector
Runs as Windows Service via NSSM, wrapping a plain java -jar process
Database Embedded H2 — see Configuration section for a critical default-persistence gotcha
Port on this VM 7011 (HAPI's own software default is 8080 — see Configuration reference)

1.Overview

FHIRBridge's local E2E environment (docker-compose.yml) runs a plain, no-auth hapiproject/hapi FHIR R4 server as a stand-in "generic FHIR" source — used by the GenericFhir source connector path (see SourceConnectionRuntimeResolver.cs) for testing without a real EHR. This guide covers running the same underlying software (hapi-fhir-jpaserver-starter) directly on a Windows Server VM as a native Windows Service — no Docker, no container runtime — which is the option chosen after weighing three alternatives:

A. Docker on Windows

Needs WSL2 + Docker Engine (Docker Desktop isn't supported on Windows Server); reuses docker-compose.yml as-is. Not chosen — introduces a whole new deployment technology to a box that's 100% native Windows Services today.

B. Native Java + Windows Service — chosen

Build the HAPI FHIR JPA starter with Maven, run the resulting WAR with java -jar, wrap it as a Windows Service with NSSM. Most consistent with the existing "no Docker, native service" model.

C. Azure-hosted FHIR service

Azure Health Data Services FHIR service (managed PaaS) or Azure Container Instances running the same image. Best parity/least effort, but a separate Azure resource outside this VM. Not chosen for this setup.

3.1. Install the JDK

Download Temurin 21 for Windows x64 from adoptium.net. Either the MSI installer (offers to set PATH/JAVA_HOME for you) or the zip archive works — if you use the zip, you must set the environment variables yourself:

# Extract the zip somewhere permanent first, e.g. D:\Software\jdk-21.0.11+10, then:
[Environment]::SetEnvironmentVariable("JAVA_HOME", "D:\Software\jdk-21.0.11+10", "Machine")
$currentPath = [Environment]::GetEnvironmentVariable("PATH", "Machine")
[Environment]::SetEnvironmentVariable("PATH", "$currentPath;D:\Software\jdk-21.0.11+10\bin", "Machine")
Open a genuinely new terminal window to verify A PowerShell window that was already open when you set these keeps its own stale copy of PATH — changing the Machine-level registry value doesn't retroactively update it. See the Gotchas section for a way to force-refresh an already-open window instead of closing it. 
java -version
javac -version

4.2. Install Maven

Download the Binary zip archive (not source) from maven.apache.org/download.cgi. Extract it, then confirm the real path to mvn.cmd before setting env vars — some zip builds nest an extra folder level (e.g. extracting apache-maven-3.9.16-bin.zip into a folder literally named apache-maven-3.9.16-bin puts the actual tool one level deeper, at apache-maven-3.9.16-bin\apache-maven-3.9.16\bin\mvn.cmd):

Get-ChildItem -Path "D:\Software\apache-maven-3.9.16-bin" -Recurse -Filter "mvn.cmd"

Then, using whatever path that actually shows:

[Environment]::SetEnvironmentVariable("MAVEN_HOME", "<path containing bin\mvn.cmd>", "Machine")
$currentPath = [Environment]::GetEnvironmentVariable("PATH", "Machine")
[Environment]::SetEnvironmentVariable("PATH", "$currentPath;<path containing bin\mvn.cmd>\bin", "Machine")

Verify (new window, or force-refresh — see Gotchas):

mvn -version

Confirm the output's Java version: line matches the JDK you installed in step 1 — if it shows something else, JAVA_HOME isn't set correctly.

5.3. Clone & build

git clone https://github.com/hapifhir/hapi-fhir-jpaserver-starter.git C:\inetpub\wwwroot\hapi-fhir-source
cd C:\inetpub\wwwroot\hapi-fhir-source
mvn clean package spring-boot:repackage -DskipTests=true -Pboot

The first build takes a while (Maven downloads a large dependency tree, including FHIR structure definitions for multiple FHIR versions). Watch for BUILD SUCCESS. The runnable artifact lands at C:\inetpub\wwwroot\hapi-fhir-source\target\ROOT.war — despite the .war extension it's a self-contained Spring Boot executable; no application server (Tomcat etc.) is needed.

Stage it into its own deploy folder, matching the fhirbridge-* naming convention already used under C:\inetpub\wwwroot\ by the rest of the deployment:

New-Item -ItemType Directory -Path "C:\inetpub\wwwroot\fhirbridge-hapi-fhir" -Force
New-Item -ItemType Directory -Path "C:\inetpub\wwwroot\fhirbridge-hapi-fhir\logs" -Force
Copy-Item "C:\inetpub\wwwroot\hapi-fhir-source\target\ROOT.war" "C:\inetpub\wwwroot\fhirbridge-hapi-fhir\hapi-fhir.war"

6.4. Manual test run

Always test in the foreground before wrapping as a service, so any startup error is visible directly instead of buried in an NSSM log file:

cd C:\inetpub\wwwroot\fhirbridge-hapi-fhir
java -jar hapi-fhir.war --server.port=7011

First boot takes a minute or two (initializes the H2 schema). Once the log settles, check from a second window:

Invoke-WebRequest -Uri http://localhost:7011/fhir/metadata -UseBasicParsing
Run this from inside the deploy folder java -jar hapi-fhir.war only works if your current directory actually contains hapi-fhir.war — if you see Error: Unable to access jarfile hapi-fhir.war, you're either in the wrong folder (cd into C:\inetpub\wwwroot\fhirbridge-hapi-fhir first) or the staging copy step above didn't run.

A 200 with a large JSON CapabilityStatement body confirms it's genuinely working. Ctrl+C to stop before moving on.

7.Configuration reference

Port — HAPI's own default is 8080; this deployment uses 7011

The starter listens on 8080 by default, with the FHIR endpoint at /fhir. On this VM it's explicitly overridden to 7011 instead, so the actual base URL here is http://<host>:7011/fhir (/fhir/metadata for the CapabilityStatement).

How the port is set / how to change it Pass --server.port=<port> as a Spring Boot argument — either directly when testing manually: 
java -jar hapi-fhir.war --server.port=7011
or, once it's registered as a service (see below), by editing the NSSM AppParameters setting and restarting: 
C:\Tools\nssm\nssm.exe set FHIRBridge.HapiFhir AppParameters "-jar C:\inetpub\wwwroot\fhirbridge-hapi-fhir\hapi-fhir.war --server.port=7011"
Restart-Service FHIRBridge.HapiFhir
To move it to a different port later, just repeat this with the new number, restart the service, and update the matching firewall rule (step 10) if one is in use.

Database — embedded H2, in-memory by default

Default persistence: none — data is lost on every restart The starter project's checked-in default (application.yaml) is: 
spring:
  datasource:
    url: 'jdbc:h2:mem:test_mem'
    username: sa
    password: null
mem: means H2 runs entirely in memory inside the JVM process — there is no database file on disk at all with this default, and every resource you create disappears the moment the service restarts or the process is stopped. This is fine for a quick manual smoke test, but almost certainly not what you want for something meant to behave like a persistent test source.

To make it persist to disk, override the datasource URL to use H2's file: mode instead of mem:. Either edit src\main\resources\application.yaml before building, or (simpler, no rebuild needed) pass it as a Spring Boot argument/env var at runtime:

# As a command-line argument:
java -jar hapi-fhir.war --spring.datasource.url="jdbc:h2:file:C:/inetpub/wwwroot/fhirbridge-hapi-fhir/database/h2db"

# Or as an environment variable (useful for the NSSM service definition):
SPRING_DATASOURCE_URL=jdbc:h2:file:C:/inetpub/wwwroot/fhirbridge-hapi-fhir/database/h2db

With file: mode, H2 creates h2db.mv.db (and related files) under the given folder on first run — that's what needs to be included in any backup if you want the test data to survive a server rebuild, and it's also what you'd delete to reset the server back to an empty database.

Production-grade note HAPI's own documentation is explicit that H2 (in either mode) is meant for dev/test, not production load — and that the starter project ships with no security implementation out of the box. Given this server's role here is a generic FHIR test source, that's an acceptable tradeoff; it is not a substitute for a real, access-controlled FHIR datastore. If heavier/production-grade use is ever needed, HAPI supports pointing spring.datasource.* at Postgres or SQL Server instead — the same SQL Server instance already used elsewhere in this deployment would work.

8.5. Install NSSM

Download from nssm.cc/download, extract, and copy the right architecture's nssm.exe (from the win64\ folder on a 64-bit server) somewhere on PATH, e.g. C:\Tools\nssm\nssm.exe.

9.6. Register as a Windows Service

$java = (Get-Command java).Source
C:\Tools\nssm\nssm.exe install FHIRBridge.HapiFhir "$java" "-jar C:\inetpub\wwwroot\fhirbridge-hapi-fhir\hapi-fhir.war --server.port=7011"
C:\Tools\nssm\nssm.exe set FHIRBridge.HapiFhir AppDirectory "C:\inetpub\wwwroot\fhirbridge-hapi-fhir"
C:\Tools\nssm\nssm.exe set FHIRBridge.HapiFhir DisplayName "FHIRBridge HAPI FHIR (test source)"
C:\Tools\nssm\nssm.exe set FHIRBridge.HapiFhir Start SERVICE_AUTO_START
C:\Tools\nssm\nssm.exe set FHIRBridge.HapiFhir AppStdout "C:\inetpub\wwwroot\fhirbridge-hapi-fhir\logs\stdout.log"
C:\Tools\nssm\nssm.exe set FHIRBridge.HapiFhir AppStderr "C:\inetpub\wwwroot\fhirbridge-hapi-fhir\logs\stderr.log"

Useful NSSM commands afterward:

CommandEffect
nssm start FHIRBridge.HapiFhirSame as Start-Service
nssm stop FHIRBridge.HapiFhirSame as Stop-Service
nssm edit FHIRBridge.HapiFhirOpens a GUI to change any setting (path, args, env vars, log files)
nssm remove FHIRBridge.HapiFhir confirmUninstalls the service entirely

10.7. Firewall

Only needed if something outside this VM calls it directly. If FHIRBridge's own Api/Worker (running on the same box) are the only callers, skip this and bind loopback-only instead by adding --server.address=127.0.0.1 to the NSSM AppParameters.

New-NetFirewallRule -DisplayName "FHIRBridge HAPI FHIR" -Direction Inbound -LocalPort 7011 -Protocol TCP -Action Allow

11.8. Verify

Start-Service FHIRBridge.HapiFhir
Get-Service FHIRBridge.HapiFhir
"Running" only means the process launched — not that it's ready yet Get-Service showing Running just confirms NSSM successfully started the process; it does not mean Spring Boot has finished booting. First boot re-initializes the H2 schema and can genuinely take a minute or more. Immediately calling the FHIR endpoint at that point will fail with Unable to connect to the remote server. Check readiness properly instead of guessing: 
# Is anything actually listening on the port yet?
Get-NetTCPConnection -LocalPort 7011 -State Listen -ErrorAction SilentlyContinue

# What is it actually doing? (this is exactly why AppStdout/AppStderr were wired up in step 6)
Get-Content "C:\inetpub\wwwroot\fhirbridge-hapi-fhir\logs\stdout.log" -Tail 50
Get-Content "C:\inetpub\wwwroot\fhirbridge-hapi-fhir\logs\stderr.log" -Tail 50
Look for a line like Started Application in NN seconds near the end of stdout.log — that's the actual "ready" signal, not the Windows Service status. 
Invoke-WebRequest -Uri http://localhost:7011/fhir/metadata -UseBasicParsing

12.Gotchas encountered while setting this up

Setting a Machine-level env var doesn't update an already-open PowerShell window [Environment]::SetEnvironmentVariable(..., "Machine") writes to the registry, but a PowerShell process only reads PATH/env vars once, at startup. Rather than closing and reopening a window every time, force the current session to re-read it: 
$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User")
Copy-pasted commands with a placeholder left in literally Commands containing an obvious placeholder like <ACTUAL_PATH> need that text replaced with a real path before running — running it verbatim sets the env var to a literal string containing angle brackets, which silently doesn't point at anything real.
Zip archives sometimes nest an extra folder level Don't assume a downloaded zip's internal folder name matches the zip's filename minus .zip/-bin — e.g. extracting apache-maven-3.9.16-bin.zip here produced apache-maven-3.9.16-bin\apache-maven-3.9.16\bin\mvn.cmd, one level deeper than expected, and the NSSM zip did the exact same thing (nssm-2.24\nssm-2.24\win64\nssm.exe). Always confirm with Get-ChildItem -Recurse -Filter before wiring up PATH or a variable pointing at the executable.
The default database is in-memory, not file-based Easy to miss: the starter project's shipped default (jdbc:h2:mem:test_mem) discards all data on every restart. If you test it, add real data, then restart the service and find it "empty" again, this is why — see the Configuration reference above for switching to file: mode.
