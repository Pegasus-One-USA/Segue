1.Overview

Azure Blob Storage is now a first-class destination in FHIRBridge's workflow wizard. The previous BlobStorage destination type existed only as a generic "PUT the file to a pre-signed URL" hack shared with the S3 writer — it never used the Azure Storage SDK and had no real support for account keys, managed identity, or Azure AD service principals. This work replaced it with a genuine Azure.Storage.Blobs-SDK-backed writer supporting five distinct authentication modes, because client storage setups vary widely and the product can't assume any one shape.

2.What was built

  • Real Azure SDK writer. MappedBlobStorageDestinationWriter uploads NDJSON blobs via Azure.Storage.Blobs instead of a raw HTTP PUT, with proper content-type, metadata, and access-tier support.
  • Five authentication modes. Connection String, Account Name + Key, SAS URL/Token, Managed Identity, and Service Principal (Azure AD) — selectable per destination.
  • Auto-created container, or not. A "Create container if it doesn't exist" toggle, automatically disabled behind the scenes for a container-scoped SAS (which has no permission to create its own container).
  • Cached, credential-aware client. One BlobContainerClient is built and cached per destination + credential combination; rotating the secret automatically busts the cache (no restart needed).
  • Dedicated health check. Blob destinations get their own reachability check instead of the generic "HEAD the secret as a URL" one every other file-based destination shares (that assumption doesn't hold once the secret can be a connection string or client secret).
  • Backwards-compatible. Any destination row saved under the old SAS-PUT-URL behavior is automatically detected and coerced to SAS mode — nothing breaks retroactively.
  • Container-name validation at three layers. Inline in the wizard form, in the backend request validator, and as a last line of defense in the writer itself — catching Azure's naming rules before Azure does.

3.Authentication modes — all five, and where to get each value

The wizard's Authentication dropdown currently shows three modes. The other two (Managed Identity and Service Principal) are fully implemented end to end on both backend and frontend, but their dropdown options are commented out in the template for now — nothing was removed, so re-enabling them later is a one-line uncomment in destination-wizard.component.html.

1. Connection String

Enabled
wizard value: connectionString · default mode

The simplest option — one field holds the full connection string, which already bundles the account name, key, and endpoint suffix together.

FieldConnection string
Where to get itAzure Portal → your Storage account → Security + networking → Access keys → click "Show" next to key1 (or key2) → copy the Connection string field directly.

2. Account Name + Key

Enabled
wizard value: accountKey

For when you have the raw account name and key separately, rather than a pre-combined connection string.

Account nameTop of the storage account's Overview page, or the same Access keys page.
Account keyStorage account → Security + networking → Access keys → "Show" → copy the Key value itself (not the whole connection string) for key1 or key2.
Endpoint suffix (optional)Defaults to core.windows.net. Only change it for a sovereign cloud — Azure Government is core.usgovcloudapi.net, Azure China is core.chinacloudapi.cn. Confirm from the domain shown on the Access keys/Endpoints page.

3. SAS URL or Token

Enabled
wizard value: sasUrl · least-privilege option

No raw account key ever leaves Azure. Works with either an account-wide SAS or a narrower container-scoped SAS (the writer detects which one it is automatically and skips container auto-create for a container-scoped SAS, since that SAS has no permission over the account itself).

SAS URL or tokenEither: Storage account → Security + networking → Shared access signature (account-wide — set allowed services/permissions/expiry → "Generate SAS and connection string" → copy the Blob service SAS URL), or at the container level: Storage account → Containers → (your container) → Shared access tokens (narrower, recommended) → set permissions/expiry → "Generate SAS token and URL".
Account URL (only if you pasted a bare token, not a full URL)Storage account → Endpoints (or the Access keys page) → Blob service URL, e.g. https://acct.blob.core.windows.net.
Must include Write permission A SAS generated with only Read/List checked produces exactly the Azure error 403 InsufficientAccountPermissions — Write operations are not allowed the first time FHIRBridge tries to upload a blob. When generating the SAS, check Write (and Create/Add if "Create container if it doesn't exist" is enabled).

4. Managed Identity

Hidden in wizard — implemented
wizard value: managedIdentity · no secret is ever stored

The host running FHIRBridge (App Service, VM, AKS) authenticates as itself via DefaultAzureCredential — no Key Vault secret is resolved at all for this mode. Only works when FHIRBridge itself runs in Azure; it cannot work from a dev box.

Account URLStorage account → Endpoints → Blob service URL.
User-assigned identity client ID (optional)If using a user-assigned managed identity: the Managed Identity resource → Overview → Client ID. Leave blank for a system-assigned identity.
Required setup step (not a form field)On the compute host → Identity blade → turn the identity on. Then on the storage account → Access Control (IAM) → Add role assignment → role Storage Blob Data Contributor → assign it to that identity.

5. Service Principal (Azure AD)

Hidden in wizard — implemented
wizard value: servicePrincipal · for cross-tenant or non-Azure-hosted setups

For when FHIRBridge runs outside Azure entirely (on-prem, another cloud) so managed identity isn't an option, or the storage account lives in a different Azure AD tenant.

Account URLStorage account → Endpoints → Blob service URL.
Tenant IDMicrosoft Entra ID → Overview → Tenant ID.
Client IDMicrosoft Entra ID → App registrations → (your app) → Overview → Application (client) ID. No app yet? App registrations → New registration.
Client secretSame app registration → Certificates & secrets → New client secret → copy the Value immediately — Azure only shows it once.
Required setup step (not a form field)Storage account → Access Control (IAM) → Add role assignment → role Storage Blob Data Contributor → assign it to that app registration.
Common to every mode The container name field is whatever container blobs should be written to — create it ahead of time under Storage account → Containers → + Container, or leave "Create container if it doesn't exist" checked and FHIRBridge will create it automatically (permissions allowing).
To re-enable Managed Identity / Service Principal in the wizard Uncomment the two <option> elements in the Authentication <select> in portal/src/app/components/node-library/destination-wizard/destination-wizard.component.html (currently wrapped in an HTML comment with a note explaining why). Every other piece — form fields, validators, backend parsing, DI, tests — is already live and requires no further change.

4.Container naming rules & validation

Azure rejects an invalid container name with an opaque 400 InvalidResourceName error at write time. FHIRBridge now catches this before it ever reaches Azure, at three layers, all enforcing the same rule:

  • 3–63 characters total length.
  • Lowercase letters, numbers, and hyphens only — no uppercase, underscores, or other punctuation.
  • Must start and end with a letter or number — no leading or trailing hyphen.
  • No consecutive hyphens (e.g. fhir--export is invalid).
LayerWhat it does
destination-wizard.component.ts / .htmlA Validators.pattern on the container field gives an inline error the moment you type an invalid name, before you can even save.
CreateDestinationConfigurationRequestValidator.csDefense in depth for any client calling the API directly (not just the wizard) — returns a field-level dest_blobContainer validation error.
BlobDestinationSettings.csLast line of defense inside the writer itself, catching any legacy row saved before this check existed.
Regex: ^(?!.*--)[a-z0-9][a-z0-9-]{1,61}[a-z0-9]$

Valid:    fhir, fhirbridge-exports, a23
Invalid:  FHIR_Export (uppercase/underscore), ab (too short),
          -fhir (leading hyphen), fhir- (trailing hyphen),
          fhir--export (consecutive hyphens)

5.Write modes — Append vs Upsert

A destination-level Write mode field on the Blob form now decides how a batch of mapped records becomes blob(s) — matching the same choice SQL/Mongo already expose via their own write-mode control, so re-running a pipeline can either always add new data or actually update existing records, your choice per destination.

Append

Default
wizard value: append

The original, only-ever-shipped behavior. Every pipeline run writes one brand-new, timestamped NDJSON blob containing that run's whole batch — object storage's natural "write-once" shape, suited to a data-lake / audit-trail consumer reading an append-only stream. There is no "update a record" concept in this mode at all.

container/prefix/Patient_20260812130455123.ndjson
container/prefix/Patient_20260812140212871.ndjson   <- a new file every run, nothing overwritten

Upsert

wizard value: upsert

Gives Blob real "update a record" semantics matching SQL/Mongo's own upsert mode. Each record gets its own blob, named by whichever mapped field is flagged as the upsert key on the mapping canvas (the same 🔑 toggle SQL/Mongo already use) — falling back to the record's own source resource id if no key field is designated. Re-running the pipeline overwrites that exact blob instead of accumulating a new one.

container/prefix/Patient/abc-123.json   <- overwritten in place if Patient abc-123 changes on the next run
container/prefix/Patient/xyz-789.json
Key resolution order1) the mapped field flagged IsUpsertKey for this resource type, if any. 2) the record's own SourceResourceId. 3) if neither resolves, the record still gets written (never silently dropped) under a one-off unique name — it just can't be reliably updated next run without a stable identity to key off of.
Content formatOne plain JSON object per blob (application/json), not NDJSON — there's only ever one record per blob in this mode.
A mixed multi-resource-type batch now splits per resource type either way Blob was added to the workflow engine's per-resource-type write splitting (the same mechanism SQL/Mongo already used) — a destination fed records from several resource types in one batch now gets one write call (and, in Append mode, one blob; in Upsert mode, one folder) per resource type, instead of everything landing in a single blob whose metadata could only ever name one of the resource types actually inside it.

6.Architecture — how a write happens

1
BlobDestinationSettings.ParseReads the destination's non-secret dest_blob* config bag (auth mode, container, account URL, path prefix, etc.) and validates container name + per-mode required fields.
2
BlobContainerClientFactory.GetTargetAsyncResolves the Key Vault secret (skipped entirely for Managed Identity), builds a cache key from the destination + a hash of the secret (never the secret itself), and either returns the cached BlobContainerClient or builds a new one via the SDK for whichever auth mode applies.
3
MappedBlobStorageDestinationWriter.WriteAsyncOptionally creates the container, builds the blob name from the mapping profile's destination object + timestamp (+ optional path prefix), serializes the batch as NDJSON, and uploads via BlobClient.UploadAsync with content-type/metadata/access-tier set.
4
Rotation-aware cachingBecause the cache key includes a hash of the resolved secret, rotating a Key Vault secret or SAS token automatically invalidates the cached client on the very next write — no restart needed.

11.Known limitations & follow-ups

  • Managed Identity / Service Principal hidden in the wizard. Fully implemented on both ends, but the two dropdown options are commented out for now (see §3) — a deliberate, easily-reversed scope decision, not a bug.
  • Standalone Destination Connections admin screen doesn't support Blob yet. That screen's toFormType() only recognizes SQL/CSV — the same gap that already exists for MongoDB there, so this is consistent with existing precedent rather than a regression. Blob destinations can only be created/edited from the workflow canvas wizard.
  • No "Test Connection" probe for Blob. Unlike SQL's live connection test, there's no equivalent live check in the wizard yet — you find out about auth/permission problems on the first real workflow run. A dedicated probe endpoint is a natural follow-up.
  • No automated Azurite integration test. An azurite service was added to docker-compose.yml for manual local testing, but there's no automated integration test exercising a real (emulated) container yet.

12.Troubleshooting — real errors seen and their fixes

400 InvalidResourceName — "The specified resource name contains invalid characters"

Cause: the container name doesn't follow Azure's naming rules (see §4) — typically uppercase letters or underscores.

Fix: already prevented going forward by the three-layer validation added in this work; rename the container to lowercase-letters/digits/hyphens only.

403 InsufficientAccountPermissions — "Write operations are not allowed"

Cause #1 (most common): the SAS was generated with only Read/List permission, not Write. Fix: regenerate the SAS with Write (and Create/Add if container auto-create is on) checked, then paste the new SAS into the destination — editing the old one's expiry doesn't retroactively add permissions.

Cause #2: the account URL points at the -secondary endpoint of a geo-redundant (RA-GRS/GZRS) storage account. Secondary endpoints are read-only by design and reject every write with this exact error, regardless of what the SAS/key/identity allows. Fix: use the primary endpoint (no -secondary suffix) — confirm under Storage account → Endpoints.

Cause #3: a Read-only ARM resource lock on the storage account or its resource group. This blocks all data-plane writes account-wide, no matter what any SAS/key/identity grants. Fix: Storage account (and its resource group) → Locks → remove the Read-only lock, or change it to Delete-only.

"Nothing to configure — This module type doesn't have a configuration screen yet"

Cause: a Blob node created during earlier development, before the phase-config, workflow-catalog, and workflow-builder fixes were all in place. Its saved transformId/state predates the fix and doesn't self-heal on edit (editing only merges form fields, it doesn't re-derive transformId).

Fix: delete the old node and re-add "Azure Blob Storage" fresh from the Node Library — a newly created node now works end to end.
