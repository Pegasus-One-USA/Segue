1.Overview

Azure Blob Storage is now a first-class destination in FHIRBridge's workflow wizard. The previous BlobStorage destination type existed only as a generic "PUT the file to a pre-signed URL" hack shared with the S3 writer — it never used the Azure Storage SDK and had no real support for account keys, managed identity, or Azure AD service principals. This work replaced it with a genuine Azure.Storage.Blobs-SDK-backed writer supporting five distinct authentication modes and two independent write-behavior settings, because client storage setups and integration patterns vary widely and the product can't assume any one shape.

2.What was built

  • Real Azure SDK writer. MappedBlobStorageDestinationWriter uploads blobs via Azure.Storage.Blobs instead of a raw HTTP PUT, with proper content-type, metadata, and access-tier support.
  • Five authentication modes. Connection String, Account Name + Key, SAS URL/Token, Managed Identity, and Service Principal (Azure AD) — selectable per destination, covering every realistic way a client's storage account might be set up.
  • Two independent write-behavior settings. Delivery (Bulk upload vs Individual records) and, only for Individual, Record mode (Insert / Upsert / Update) — see §7.
  • Auto-created container, or not. A "Create container if it doesn't exist" toggle, automatically disabled behind the scenes for a container-scoped SAS (which has no permission to create its own container).
  • Cached, credential-aware client. One BlobContainerClient is built and cached per destination + credential combination; rotating the secret automatically busts the cache (no restart needed).
  • Dedicated health check. Blob destinations get their own reachability check instead of the generic "HEAD the secret as a URL" one every other file-based destination shares (that assumption doesn't hold once the secret can be a connection string or client secret).
  • Backwards-compatible. Any destination row saved under the old SAS-PUT-URL behavior, or under this feature's earlier single dest_writeMode field, is automatically detected and coerced correctly — nothing breaks retroactively.
  • Container-name validation at three layers. Inline in the wizard form, in the backend request validator, and as a last line of defense in the writer itself — catching Azure's naming rules before Azure does.
  • Multi-resource-type batches split correctly. A destination fed several resource types in one batch now gets one write call (and one blob/folder) per resource type, instead of everything silently merging into one mislabeled blob.

3.Quick start — your first Blob destination

A concrete, step-by-step walkthrough for wiring up a new Blob destination on the workflow canvas, from a source through mapping to Azure.

1

2
Add the nodeOn the workflow canvas, open the Node Library and pick Azure Blob Storage under Cloud / FHIR destinations, attached downstream of a Mapping node (a Mapping node is inserted automatically if you attach it somewhere else).
3

4
Advance past ConfigureLeaving this step provisions the real DestinationConfiguration row immediately (create-on-save) — a real destinationId exists from this point on, the same way it does for every other destination type.
5
Pick data groups & map fieldsSelect the FHIR resource types you want (step 2), then map each one's fields to blob output columns (step 3) — the canvas card for this destination is labeled "blob" so it's clear these are per-resource blob names, not SQL tables.
6
(Individual delivery only) Set an upsert keyIf you picked Individual delivery and want Upsert/Update record mode to key off a specific field rather than the record's own source id, click the 🔑 toggle on that field in the mapping canvas.
7

4.Authentication modes — all five, and where to get each value

The wizard's Authentication dropdown currently shows three modes. The other two (Managed Identity and Service Principal) are fully implemented end to end on both backend and frontend, but their dropdown options are commented out in the template for now — nothing was removed, so re-enabling them later is a one-line uncomment in destination-wizard.component.html.

1. Connection String

Enabled
wizard value: connectionString · default mode

The simplest option — one field holds the full connection string, which already bundles the account name, key, and endpoint suffix together. Internally this becomes new BlobServiceClient(connectionString).

FieldConnection string — goes into the Key Vault secret, never ConnectionMetadataJson.
Where to get it (Portal)Azure Portal → your Storage account → Security + networking → Access keys → click "Show" next to key1 (or key2) → copy the Connection string field directly.
Where to get it (CLI)az storage account show-connection-string --name <account> --resource-group <rg>
FormatDefaultEndpointsProtocol=https;AccountName=acct;AccountKey=…;EndpointSuffix=core.windows.net

2. Account Name + Key

Enabled
wizard value: accountKey

For when you have the raw account name and key separately, rather than a pre-combined connection string. Internally this becomes new BlobServiceClient(accountUrl, new StorageSharedKeyCredential(accountName, accountKey)).

Account nameTop of the storage account's Overview page, or the same Access keys page. Metadata key: dest_blobAccountName Required.
Account keyStorage account → Security + networking → Access keys → "Show" → copy the Key value itself (not the whole connection string) for key1 or key2. Goes into the Key Vault secret.
Endpoint suffix (optional)Defaults to core.windows.net. Only change it for a sovereign cloud — Azure Government is core.usgovcloudapi.net, Azure China is core.chinacloudapi.cn. Confirm from the domain shown on the Access keys/Endpoints page. Metadata key: dest_blobEndpointSuffix.
Where to get it (CLI)az storage account keys list --account-name <account> --resource-group <rg>

3. SAS URL or Token

Enabled
wizard value: sasUrl · least-privilege option

No raw account key ever leaves Azure. Works with either an account-wide SAS or a narrower container-scoped SAS, and also with a bare token (no scheme/host) if you also supply the Account URL separately. The client factory inspects the resolved secret at build time and picks the right shape automatically:

Full URL, has a path segmentTreated as a container-scoped SAS — built directly as new BlobContainerClient(sasUri). Container auto-create is automatically disabled for this shape, since a container SAS has no permission over the account itself.
Full URL, no path segmentTreated as an account/service-scoped SAS — built as new BlobServiceClient(sasUri).GetBlobContainerClient(container). Container auto-create still works.
Bare token (no scheme/host)Combined with the separately-supplied Account URL field into a full URL, then treated as an account-scoped SAS.
Where to get it (Portal, account-wide)Storage account → Security + networking → Shared access signature → set allowed services/resource types/permissions/expiry → "Generate SAS and connection string" → copy the Blob service SAS URL.
Where to get it (Portal, container-scoped — recommended)Storage account → Containers → (your container) → Shared access tokens → set permissions/expiry → "Generate SAS token and URL".
Account URL (only for the bare-token case)Storage account → Endpoints → Blob service URL, e.g. https://acct.blob.core.windows.net. Metadata key: dest_blobAccountUrl.
Must include Write permission A SAS generated with only Read/List checked produces exactly the Azure error 403 InsufficientAccountPermissions — Write operations are not allowed the first time FHIRBridge tries to upload a blob. When generating the SAS, check Write (and Create/Add if "Create container if it doesn't exist" is enabled and you're using an account-scoped SAS — a container-scoped SAS can't create containers regardless).

4. Managed Identity

Hidden in wizard — implemented
wizard value: managedIdentity · no secret is ever stored or resolved

The host running FHIRBridge (App Service, VM, AKS) authenticates as itself via DefaultAzureCredential — the Key Vault secret is never resolved at all for this mode (BlobDestinationSettings.RequiresSecret is false here, and it's the only mode where that's true). Only works when FHIRBridge itself runs in Azure; it cannot work from a dev box.

Account URLStorage account → Endpoints → Blob service URL. Required — this mode has no account-key fallback to derive it from.
User-assigned identity client ID (optional)If using a user-assigned managed identity: the Managed Identity resource → Overview → Client ID. Leave blank for a system-assigned identity. Passed as DefaultAzureCredentialOptions.ManagedIdentityClientId.
Authority host (optional, sovereign clouds)Only needed for Azure Government/China — e.g. https://login.microsoftonline.us/. Metadata key: dest_blobAuthorityHost.
Required setup step (not a form field)On the compute host → Identity blade → turn the identity on. Then on the storage account → Access Control (IAM) → Add role assignment → role Storage Blob Data Contributor → assign it to that identity.

For when FHIRBridge runs outside Azure entirely (on-prem, another cloud) so managed identity isn't an option, or the storage account lives in a different Azure AD tenant. Internally: new ClientSecretCredential(tenantId, clientId, clientSecret).

6.Container naming rules & validation

Azure rejects an invalid container name with an opaque 400 InvalidResourceName error at write time. FHIRBridge now catches this before it ever reaches Azure, at three layers, all enforcing the same rule:

  • 3–63 characters total length.
  • Lowercase letters, numbers, and hyphens only — no uppercase, underscores, or other punctuation.
  • Must start and end with a letter or number — no leading or trailing hyphen.
  • No consecutive hyphens (e.g. fhir--export is invalid).
LayerWhat it does
destination-wizard.component.ts / .htmlA Validators.pattern on the container field gives an inline error the moment you type an invalid name, before you can even save.
CreateDestinationConfigurationRequestValidator.csDefense in depth for any client calling the API directly (not just the wizard) — returns a field-level dest_blobContainer validation error.
BlobDestinationSettings.csLast line of defense inside the writer itself, catching any legacy row saved before this check existed. Throws InvalidOperationException with the exact message quoted in §16.
Regex: ^(?!.*--)[a-z0-9][a-z0-9-]{1,61}[a-z0-9]$

Valid:    fhir, fhirbridge-exports, a23
Invalid:  FHIR_Export (uppercase/underscore), ab (too short),
          -fhir (leading hyphen), fhir- (trailing hyphen),
          fhir--export (consecutive hyphens)

The identical regex is used in three independent places (JavaScript in the wizard, C# in the validator, C# in the writer) — kept in sync by hand rather than shared, since each layer is a different language/runtime with no natural single source of truth to share it from.

7.Write modes — two independent settings

The Blob form (Configure step, right after Container name) has two independent settings controlling how mapped records become blob(s) — deliberately split apart rather than folded into one dropdown, since they answer two different questions: how many records share a blob, and (only once that's "one blob per record") what happens to a record relative to whatever already exists at its key.

1. DeliveryHow many records share one blob — Bulk upload (all records, one blob) or Individual records (one blob per record). Wizard control: blobForm.granularity. Metadata key: dest_blobGranularity.
2. Record modeOnly shown once Delivery is set to Individual. Decides what happens to a single record's blob relative to whatever's already there under its key — Insert, Upsert, or Update. Wizard control: blobForm.recordMode. Metadata key: dest_blobRecordMode.

Setting 1 — Delivery: Bulk upload vs Individual records

Bulk upload — all records in one blob

Default
wizard value: bulk

The original, only-ever-shipped behavior. Every pipeline run writes one brand-new, timestamped NDJSON blob containing that run's whole batch — object storage's natural "write-once" shape, suited to a data-lake / audit-trail consumer reading an append-only stream. There is no per-record identity or "update a record" concept at this setting, regardless of Record mode (which doesn't apply here at all — WriteBulkAsync never even looks at it).

container/prefix/Patient_20260812130455123.ndjson    <- ALL of this run's Patient records, one file
container/prefix/Patient_20260812140212871.ndjson   <- a new file every run, nothing overwritten

Content type application/x-ndjson; one JSON object per line, one line per record.

Individual records — one blob per record

wizard value: individual

Each record gets its own blob, named by whichever mapped field is flagged as the upsert key on the mapping canvas (the same 🔑 toggle SQL/Mongo already use) — falling back to the record's own source resource id if no key field is designated. Selecting this reveals the Record mode setting below, which decides exactly what "one blob per record" means when that blob already exists from a previous run, plus two more fields — Folder pattern and File name pattern — that control exactly where and how each record's blob is named (see §8).

container/prefix/Patient/abc-123.json
container/prefix/Patient/xyz-789.json   <- a separate blob per record, one folder per resource type

Content type application/json; one JSON object per blob.

Setting 2 — Record mode (Individual delivery only): Insert vs Upsert vs Update

InsertAlways add new. Every record gets a brand-new blob — even a record already written before gets another one, never overwriting the last. The blob name is suffixed with a fresh timestamp + GUID every time specifically so it can never collide, even for a repeated key.
UpsertUpdate if it exists, else insert. Writes to the key-derived blob path unconditionally — creates it if absent, overwrites it if present. This is the default, and the natural behavior of a plain blob upload (no existence check needed — UploadAsync with the BlobUploadOptions overload always succeeds, present or not).
UpdateOnly if it exists. Only overwrites the key-derived blob path if it's already there; if it isn't, the record is skipped entirely — never creates a new blob. Requires one extra BlobClient.ExistsAsync call per record before deciding.
Key resolution order (all three modes) 1) the mapped field flagged IsUpsertKey for this resource type/destination object, if any (via MappingProfile.Fields, scoped by ResourceType/DestinationObject when those are set on the field). 2) the record's own SourceResourceId. 3) if neither resolves: Insert still writes under a uniquified name (stem "record"); Upsert still writes under a one-off unique name (it just can't be reliably updated next run without a stable identity); Update has nothing to check existence against, so it skips the record rather than guessing.
DeliveryRecord modeBehavior when a record's blob already existsBehavior when it doesn'tReturned Count reflects
bulk— (ignored)N/A — always one new blob for the whole batchrecords.Count (always)
individualinsertWrites anyway, under a different (uniquified) name — old blob untouchedWrites under a uniquified nameEvery record (always written)
individualupsertOverwrites itCreates itEvery record (always written)
individualupdateOverwrites itSkipped — not writtenOnly records that had an existing blob
A mixed multi-resource-type batch now splits per resource type either way Blob was added to the workflow engine's per-resource-type write splitting (the same mechanism SQL/Mongo already used, via DestinationNodeExecutors.MultiTableRelationalDestinationTypes) — a destination fed records from several resource types in one batch now gets one write call (and, at Bulk delivery, one blob; at Individual delivery, one folder) per resource type, instead of everything landing in a single blob whose metadata could only ever name one of the resource types actually inside it. The SQL-only ;mode=... target suffix that mechanism also splices in is explicitly skipped for Blob (and defensively stripped in the writer too, as a second layer) so it can't corrupt a blob name.

8.Blob naming patterns & metadata reference

Bulk delivery's naming is fixed (unchanged since the feature first shipped). Individual delivery's Folder pattern and File name pattern are user-configurable placeholder templates — a small resolver in MappedBlobStorageDestinationWriter substitutes recognized tokens and leaves everything else (literal text, including / for nested folders) untouched.

ScenarioPattern
Bulk, no path prefix{stem}_{yyyyMMddHHmmssfff}.ndjson
Bulk, with path prefix{prefix}/{stem}_{yyyyMMddHHmmssfff}.ndjson
Individual, any mode{prefix?}/{resolved FolderPattern}/{resolved FileNamePattern}

{stem} (Bulk only) is MappingProfile.DestinationObject after three cleanup passes, in order: (1) strip a trailing ;mode=... suffix (the SQL-only write-mode suffix, defended against even though it's skipped for Blob upstream), (2) strip a trailing .ndjson/ .json/.csv/.tsv/.txt extension (guards against a row whose target still carries the CSV-shaped default from before this feature existed), (3) replace any character in Path.GetInvalidFileNameChars() with _. The same cleaned value feeds the {name} token below.

Placeholder tokens (Folder pattern & File name pattern)

TokenResolves to
{name}The cleaned mapping-profile stem (same value as Bulk's {stem}) — the resource/destination-object name, e.g. Patient.
{id}The record's resolved upsert key (🔑-flagged mapped field, falling back to SourceResourceId — same resolution order as before). Falls back to the literal record if neither resolves (Folder pattern never uses {id} — no single record exists yet when the folder is built).
{guid}A fresh Guid.NewGuid(), hex-formatted (N), generated per record for File name pattern or once per batch for Folder pattern.
{date:<.NET custom format>}The current UTC time formatted with the given .NET custom date/time format string, e.g. {date:yyyyMMddHHmmssfff} or {date:yyyy/MM/dd}. A genuinely malformed format string (e.g. an unterminated quoted literal) falls back to yyyyMMddHHmmssfff rather than failing the write.
A / inside {date:...} nests real subfolders The resolved pattern is split on / before each segment is sanitized (not after) — so a pattern like {name}/{date:yyyy/MM/dd} produces real nested folders (Patient/2026/08/14/...) instead of a single segment with slashes replaced. Every other character outside Path.GetInvalidFileNameChars() passes through literally, so static text mixed with tokens (e.g. patients-{date:yyyyMMdd}) works as expected.

Defaults, by Record mode

Record modeDefault Folder patternDefault File name patternWhy
Insert{name}{id}_{date:yyyyMMddHHmmssfff}_{guid}.jsonInsert never looks a blob up again, so its default is deliberately always-unique — {date:...} + {guid} guarantee no two writes ever collide, even for a repeated key.
Upsert{name}{id}.jsonUpsert/Update must re-derive the exact same name on a later run to find the record again, so the default is deliberately static — no {date:...}/{guid} at all.
Update{name}{id}.jsonSame as Upsert.

Both fields are fully overridable — set dest_blobFolderPattern/dest_blobFileNamePattern (or the wizard's Folder pattern/File name pattern inputs) to anything using the tokens above. A blank value means "use this Record mode's default," so switching Record mode later doesn't leave a stale pattern from a different mode behind. The wizard shows a non-blocking warning if an Upsert/Update File name pattern contains {date:...} or {guid} — those modes' key resolution depends on writing to the same path every run, and either token breaks that. 

// Insert, defaults, key resolved to "abc-123":
container/prefix/Patient/abc-123_20260814101500123_3f9a1c7b8e5d4a2f9c1b6e7d4a3f8c92.json

// Upsert/Update, defaults, key resolved to "abc-123":
container/prefix/Patient/abc-123.json

// Custom Folder pattern "{name}/{date:yyyy/MM/dd}" + File name pattern "{id}-{date:yyyyMMdd}.json" (Insert):
container/prefix/Patient/2026/08/14/abc-123-20260814.json

Naming pattern validation — only what Azure allows in a blob name

Both pattern fields are checked, at the same three layers §6 already uses for the container name, against what Azure itself permits in a blob name — placeholder tokens are exempt (their braces/colons are fine), only the literal text you type around them is restricted:

  • No backslash (\) or control characters. / is the only supported nesting delimiter — use it, not \, for a nested folder.
  • Cannot end with . or /. Azure rejects a blob name ending that way.
  • 1024 characters or fewer — Azure's own blob-name length ceiling (checked here at 512 characters on the raw, unresolved pattern, leaving headroom for token expansion).

A blank value is always valid at every layer — it means "use this Record mode's own default" (§8), and every built-in default already satisfies these rules.

9.Architecture — classes, call flow, and per-mode traces

Class map

ClassRole
BlobDestinationSettingsImmutable record parsed from ConnectionMetadataJson + Target; validates container name and per-auth-mode required fields; the single source of truth for every setting in §5.

Call sequence for one write

1
BlobDestinationSettings.Parse(destination)Reads every dest_blob* key (§5), validates the container name (§6) and per-auth-mode required fields, throws InvalidOperationException with a specific message on any failure (§16 lists them verbatim).
2
BlobContainerClientFactory.GetTargetAsync(destination, settings, ct)Resolves the Key Vault secret via ISecretProvider (skipped entirely when settings.RequiresSecret is false — Managed Identity only), builds a cache key from destination.Id + AuthMode + ContainerName + AccountUrl + SHA-256(secret)[..16] ("none" in place of the hash for Managed Identity), and either returns the cached BlobDestinationTarget or builds a fresh one for whichever auth mode applies (see the per-mode client construction in §4's "Internally, this becomes…" notes).
3
MappedBlobStorageDestinationWriter.WriteAsyncShort-circuits on an empty batch (Count == 0). If CreateContainerIfNotExists and the target supports it, calls CreateIfNotExistsAsync(PublicAccessType.None, null, ct), swallowing (with a log warning) a 403/409 — the identity most commonly just lacks account-level create rights while still having write access to an already-existing container; the upload below surfaces the real error if the container genuinely doesn't exist.
4
Dispatch on GranularityWriteBulkAsync (one NDJSON blob for the whole batch) or WriteIndividualAsync (loops records, branching on RecordMode per the table in §7) — see the per-mode traces below for exactly what each does.
5
Rotation-aware cachingBecause the cache key includes a hash of the resolved secret, rotating a Key Vault secret or SAS token automatically invalidates the cached client on the very next write — no restart needed. Client construction alone never calls Azure, so cache misses are cheap.

→ WriteIndividualAsync(...)
   for each record:
     keyValue = ResolveKeyValue(record, keyField)
     if keyValue is null:
       continue   // nothing to check existence against — skip, don't guess

14.Known limitations & follow-ups

  • Managed Identity / Service Principal hidden in the wizard. Fully implemented on both ends, but the two dropdown options are commented out for now (see §4) — a deliberate, easily-reversed scope decision, not a bug.
  • Standalone Destination Connections admin screen doesn't support Blob yet. That screen's toFormType() only recognizes SQL/CSV — the same gap that already exists for MongoDB there, so this is consistent with existing precedent rather than a regression. Blob destinations can only be created/edited from the workflow canvas wizard.
  • No "Test Connection" probe for Blob. Unlike SQL's live connection test, there's no equivalent live check in the wizard yet — you find out about auth/permission problems on the first real workflow run. A dedicated probe endpoint is a natural follow-up.
  • No automated Azurite integration test. An azurite service was added to docker-compose.yml for manual local testing, but there's no automated integration test exercising a real (emulated) container yet.
  • Update mode's existence check is one extra round trip per record. For a very large individual-delivery batch in Update mode, this roughly doubles the number of Azure calls compared to Insert/Upsert. No batching/parallelization has been added for this yet.
  • The Upsert/Update "unique-token in a static pattern" warning is advisory, not enforced. The wizard shows a callout (§8) if a {date:...}/{guid} token appears in an Upsert/Update File name pattern, but nothing blocks saving it — a self-defeating pattern (one that can never be found again) is only ever surfaced as a UI hint, never rejected server-side.

15.Troubleshooting — every error seen and its fix

400 InvalidResourceName — "The specified resource name contains invalid characters"

Cause: the container name doesn't follow Azure's naming rules (see §6) — typically uppercase letters or underscores.

Fix: already prevented going forward by the three-layer validation added in this work; rename the container to lowercase letters/digits/hyphens only.

403 InsufficientAccountPermissions — "Write operations are not allowed"

Cause #1 (most common): the SAS was generated with only Read/List permission, not Write. Fix: regenerate the SAS with Write (and Create/Add if container auto-create is on and it's an account-scoped SAS) checked, then paste the new SAS into the destination — editing the old one's expiry doesn't retroactively add permissions.

Cause #2: the account URL points at the -secondary endpoint of a geo-redundant (RA-GRS/GZRS) storage account. Secondary endpoints are read-only by design and reject every write with this exact error, regardless of what the SAS/key/identity allows. Fix: use the primary endpoint (no -secondary suffix) — confirm under Storage account → Endpoints.

Cause #3: a Read-only ARM resource lock on the storage account or its resource group. This blocks all data-plane writes account-wide, no matter what any SAS/key/identity grants. Fix: Storage account (and its resource group) → Locks → remove the Read-only lock, or change it to Delete-only.

"Nothing to configure — This module type doesn't have a configuration screen yet"

Cause: a Blob node created during earlier development, before the phase-config, workflow-catalog, and workflow-builder fixes were all in place. Its saved transformId/state predates the fix and doesn't self-heal on edit (editing only merges form fields, it doesn't re-derive transformId).

Fix: delete the old node and re-add "Azure Blob Storage" fresh from the Node Library — a newly created node now works end to end.

InvalidOperationException: "Destination '<name>' has no blob container configured (Target or dest_blobContainer)."

Cause: neither Target nor dest_blobContainer is set — shouldn't happen via the wizard (Container name is a required field), but possible via a direct API call.

Fix: set the container name.

InvalidOperationException: "…is not a valid Azure Blob container name…"

Cause: a legacy row saved before the container-name validator existed, or a direct API call bypassing the wizard's inline check. See §6 for the exact rule.

Fix: rename the container to satisfy the naming rule and re-save.

InvalidOperationException: "…uses Account Key auth but has no dest_blobAccountName configured."

Cause: Account Key mode selected but Account name left blank.

Fix: fill in Account name (§4, mode 2).

InvalidOperationException: "…uses Managed Identity auth but has no dest_blobAccountUrl/dest_blobAccountName configured."

Cause: Managed Identity mode selected but neither Account URL nor Account name (to derive it from) was supplied.

Fix: fill in Account URL (§4, mode 4) — this mode has no other way to know which storage account to talk to.

InvalidOperationException: "…uses Service Principal auth but is missing dest_blobTenantId/dest_blobClientId."

Cause: Service Principal mode selected but Tenant ID and/or Client ID left blank.

Fix: fill in both (§4, mode 5).

A record silently doesn't appear as a new blob in Update mode

Cause: this is expected, not a bug — Update mode only overwrites a blob that already exists; a record with no pre-existing blob under its key is skipped by design (see §7's behavior table). DestinationWriteResult.Count reflects only the records actually written, so a lower-than-expected count in the run history is the signal this happened.

Fix (if you actually wanted it created): switch Record mode to Upsert, which creates-or-overwrites unconditionally.

Every run creates a brand-new blob even though I expected updates

Cause: Delivery is set to Bulk (the default) — Bulk has no per-record identity concept at all, by design; Record mode has no effect at this setting.

Fix: switch Delivery to Individual records, then pick Upsert or Update as appropriate.

Container auto-create silently does nothing even though the toggle is on

Cause: the resolved auth is a container-scoped SAS — SupportsContainerCreate is false for that shape regardless of the toggle, since a container SAS has no permission over the account itself to create anything.

Fix: either pre-create the container yourself, or switch to an account-scoped SAS/another auth mode if you need auto-create.

Update mode never finds a record to update — it just keeps skipping

Cause: the File name pattern includes a {date:...} or {guid} token — every run resolves to a different name, so BlobClient.ExistsAsync on this run's freshly-resolved name never finds last run's blob. The wizard warns about this (§8) but doesn't block saving it.

Fix: remove the {date:...}/{guid} token from the File name pattern (or clear the field to use the Update default, {id}.json) so the same key always resolves to the same name.

"...contains a character Azure blob names don't allow" / "...cannot end with '.' or '/'"

Cause: the Folder pattern or File name pattern contains a backslash/control character, or ends with a literal . or / — see §8's naming-pattern validation rules.

Fix: use / instead of \ for nested folders, and make sure the pattern's last literal character isn't . or / (a trailing placeholder token like {guid} or .json is fine).

A custom date format in a pattern doesn't error, but the resulting name looks wrong

Cause: the format string was syntactically valid .NET but not what was intended — ResolvePattern only falls back to the fixed yyyyMMddHHmmssfff format on a genuine FormatException (e.g. an unterminated quoted literal); most typos in a .NET custom format string still parse, just not the way you expected.

Fix: check the token against the .NET custom date/time format string reference (§8).
