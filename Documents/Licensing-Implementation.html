1.Overview

FHIRBridge is sold as on-prem/client-tenant software with no ongoing access to a client's environment after deployment. This work adds a complete commercial licensing system on top of that reality: a signed license token that names a customer's limits (users, workflows, source connections, hospitals, resource/destination types, monthly processed records, monthly successful executions), a central enforcement point that actually blocks a customer from exceeding those limits, a re-check at the moment a pipeline/workflow actually runs (not just when it was configured), a global "the whole app is locked until a valid license is applied" gate with a header banner and a full-screen overlay, and a separate, isolated, standalone project a PegasusOne admin uses to mint real customer licenses without ever touching the main product's codebase or database.

2.What was built

  • Signed license tokens (ES256 JWS). A compact, tamper-evident token carries the customer's name, edition, issue/expiry dates, and every quota/restriction dimension as claims. Verified with a hardcoded public key — no network call needed to check a license, so it works fully offline/air-gapped.
  • Central quota enforcement. One place (LicenseQuotaGuard + LicenseEnforcementSaveChangesInterceptor) enforces every dimension: max users, max workflows, max source connections, allowed source/destination/resource types, allowed hospitals, max processed records/month, max successful executions/month.
  • Execution-time re-validation. Allow-list checks (source type, hospital, destination type) are re-checked at the moment a pipeline/workflow run actually triggers — not just when the connection/route was first created — so a license renewed with narrower terms, or a connection whose URL was edited after creation, is still caught.
  • Global "license must be active" gate. Once any user exists, every API action except first-run registration, login/logout, and the License screen itself is blocked with a 403 while the license isn't Active — with a persistent header banner and a full-screen overlay on the working area (sidebar and user menu stay usable) telling the admin why.
  • Fail-open by design. No license present, an unlimited dimension, a null/empty allow-list, or the guard's own internal error all pass the check — this is a commercial boundary, not a security boundary, and an internal bug must never lock a paying customer out of their own console.
  • Tamper-evident usage ledger & heartbeat. A hash-chained UsageLedgerEntry table snapshots usage daily; a Worker heartbeat posts it to a PegasusOne-hosted endpoint when reachable, and simply logs a warning and retries next tick when it isn't — a permanently offline install can never be crashed or blocked by this.
  • A standalone license-minting server. A brand-new, git-independent ASP.NET Core project (FHIRBridge.LicenseServer) that mints and records real customer licenses and receives their usage check-ins — deliberately isolated from the main product for security.

3.New standalone project — FHIRBridge.LicenseServer

Update — merged into this repo. Originally a fully separate git repository (D:\Project\FHIRBridge\FHIRBridge-LicenseServer). It has since been merged into this monorepo at src/LicenseServer/FHIRBridge.LicenseServer so the whole product ships from one repo/CI pipeline — see §19. It still runs as its own ASP.NET Core process, its own PostgreSQL database, and still duplicates (never references) the claim-shape logic it needs from the main product, for the same isolation reasoning below — only the source-control boundary changed, not the process/deployment/code-sharing boundary.
Separate process, separate database, zero code sharing. No project or package reference into the main FHIRBridge product's own code. It duplicates only the small pieces of claim-shape logic it needs (mirrored, not shared) so that a compromise of one codebase can never directly touch the other. Runs as its own ASP.NET Core Razor Pages app, its own PostgreSQL database, on its own port (5220 in local dev, 3021 in shared/deployed environments).

What it does:

  • Mints signed licenses. An internal admin (username/password login, no self-registration) fills in a form — customer, edition, expiry, every quota dimension, activation window, allowed source/resource/destination types (checkboxes, narrowed to only what the product actually supports today), allowed hospitals — and it signs an ES256 JWS token with the same claim shape the main repo verifies against, using the real production signing key (see §19) rather than a shared dev key.
  • Records every issued license. Each mint is persisted to IssuedLicenses (customer, limits, summaries, activation window, the requesting install's RequestHost if minted against a License Request, the raw token, the exact claims JSON that was signed) for an audit trail of what was ever issued.
  • Receives usage check-ins. A CheckInEndpoints/CheckInContracts ingest surface accepts the periodic heartbeat batches the main product's LicenseHeartbeatWorker sends, recording per-installation usage over time.
  • Receives and tracks license requests. A customer install can ask for a license directly from its own License screen — see §20 for the full workflow, including deny/history/edit on this server's own admin pages.
  • Self-migrating. Applies its own EF Core migrations against its own PostgreSQL database on startup — no manual DB setup step for a fresh install of this tool itself.

4.How a license is generated

1
An admin fills in the Create License formOn FHIRBridge.LicenseServer (production) or the portal's temporary "Dev: Mint a test license" page (development only) — customer id/name, edition, expiry date, and every quota/allow-list field. Blank numeric fields default to -1 ("unlimited"); blank allow-lists mean "everything allowed".
2
The fields are serialized into JWT claimsLicenseTokenMinter.BuildClaimsJson (LicenseServer) / the equivalent in tools/FHIRBridge.LicenseMinter (main repo's offline CLI) builds a JSON payload: iss (always "pegasusone"), sub (customer id), nbf/exp as Unix seconds, and one claim per quota/restriction dimension.
3
The claims are signed with ES256 (ECDSA P-256)JsonWebTokenHandler().CreateToken(claimsJson, credentials) using an ECDsaSecurityKey loaded from the signing private key — producing a compact, three-part JWS string (header.payload.signature).
4
The issued license is recordedThe token, the exact claims JSON, and per-field summaries are saved to IssuedLicenses in the LicenseServer's own database — a permanent record of what was ever issued to that customer.
5
The token is handed to the customer / appliedThe raw token string is copied and either sent to the customer to paste into their own install's License screen, or (in dev) applied directly via POST /api/v1/license.

5.How a license is checked & enforced

1
Signature & issuer verificationSignedLicenseValidator.Validate imports the ES256 public key (hardcoded, same on every install — see LicensePublicKey) and verifies the token's signature and iss claim. A malformed, tampered, or wrong-issuer token comes back Invalid — this method never throws, so a bad token can never crash the app.
2
Claims are parsed into a LicenseStatusEvery quota/allow-list claim is read (absent or -1 both mean "unlimited"); nbf/exp decide whether the result is Active or Expired. ILicenseService.Current holds this in memory, refreshed at startup and whenever a new token is applied — a cheap in-memory read on every request, no re-parsing per call.
3
Global gate — is the license Active at all?A middleware in Program.cs, placed right after authentication, blocks every /api/v1/* request (anonymous or authenticated) with a 403 unless the license state is Active — except a short allow-list (first-run registration, login/logout/refresh/me, the License screen itself, and its dev-only minting helper) so a locked install always has a way back in.
4
Create-time quota & allow-list checksLicenseEnforcementSaveChangesInterceptor — an EF Core SaveChangesInterceptor, the same pattern the existing audit-hash-chain interceptor uses — watches every SaveChangesAsync call for a newly-Added User/SourceConnection/ResourcePipelineRoute/WorkflowDefinition/DestinationConfiguration row and calls the matching ILicenseQuotaGuard method before the save completes. One central place — a new quota dimension never means touching six different service call sites again.
5
Execution-time re-validationAllow-list checks don't only run once at creation. EnsureSourceConnectionStillAllowedAsync/EnsureDestinationTypeAllowedAsync are re-checked at the moment a run actually triggers — in both the Configured Pipeline plane (ConfiguredPipelineService.StartAsync/StartWebhookAsync) and the Runtime plane (WorkflowEndpoints's /run and /checkpoint/{token}) — for every distinct source/destination that specific run will touch, before any extraction begins.
6
Run-trigger caps (expiry, monthly quotas)EnsureCanStartNewRunAsync checks expiry plus the two monthly caps (processed records, successful executions) at the very start of every run-trigger method, in both planes — never mid-run. The monthly counts are read from execution history with a short (45s) cache, so a burst of run requests doesn't hammer the database.
7
Fail-open on any internal errorEvery one of the checks above catches its own dependency failures, logs a warning, and lets the action through — a bug in the licensing code itself must never be the reason a paying customer's pipeline stops running.

6.The license token's claim shape

Identical on both sides — the main repo's SignedLicenseValidator/tools/FHIRBridge.LicenseMinter and the standalone LicenseServer's LicenseTokenMinter build/read the exact same claim names, deliberately kept in sync by hand since neither project references the other.

ClaimMeaning
iss / subAlways "pegasusone" / the customer id.
customerName / editionDisplay-only fields.
nbf / expIssued-on / expires-on, Unix seconds. nbf doubles as the issued timestamp (no separate iat).
maxUsers / maxWorkflows / maxSourceConnectionsRow-count caps. -1 = unlimited.
maxProcessedRecordsPerMonthCap on resources processed within the current calendar month.
maxSuccessfulWorkflowExecutionsPerMonthCap on successful runs (both pipeline planes combined) within the current calendar month.
allowedSourceTypes / allowedDestinationTypes / allowedResourceTypesString arrays of enum member names. Absent/empty = everything allowed.
allowedHospitalsArray of { vendor, baseUrl, displayName } — specific hospital endpoints this license permits connecting to.
featuresFree-form feature-flag strings, checked via ILicenseService.HasFeature.

20.License Request — a customer install's outbound ask

A deployed install doesn't always have a license yet, or needs another one for a renewal. The License Request workflow lets an admin ask the licensor for one directly from their own product's Settings screen, without leaving the app or knowing the licensor's minting process — and lets whoever runs FHIRBridge.LicenseServer see and act on that ask.

Any number of requests, each independent. This started as a strict one-request-per-install rule (a SingletonGuard unique index enforced it at the schema level). It was later reworked so every "Submit Request" click creates its own independent row with its own freshly generated key — an install can submit as many as it needs (one per renewal, or several while testing) and every one shows up as its own entry, both in the install's own "Your Requests History" list and on the LicenseServer's History page.
1
Admin submits (or resends/edits) a requestSettings → License → License Request tab. The browser's own origin (window.location.origin — e.g. https://fhirbridge.acmehealth.com or http://localhost:4200) is captured client-side and sent as requestedFromUrl, since the API's own Host header only reflects where the API itself is bound, never the portal's port.
2
A 64-char random key is generated and the request is recordedLicenseRequestService.CreateAndSubmitAsync — 32 random bytes, hex-encoded — then tries the licensor's direct intake API (POST {LicensorApplicationUrl}/api/license-requests).
3
Direct call succeeds → Submitted; fails → Failed, with a manual-fallback codeA network/DNS/timeout/non-2xx failure never surfaces as an error to the admin — the request lands in Failed with an AES-256-GCM encoded blob (LicenseRequestPayloadEncoder) they copy and share with support instead, decoded on the LicenseServer's own /LicenseRequests page.
4
The LicenseServer records it, upserted by the request's keyA resend of the same request (Edit + re-attempt) updates that one row in place — contact details, RequestHost, submission count — and clears any prior Fulfilled/Denied decision so it needs a fresh look. A genuinely new "Resend"/"Submit" always creates a brand-new row with its own key instead.
5
An operator mints or denies itOn /LicenseRequests (pending only) or /LicenseRequests/History (everything), clicking a row opens full details with an inline Edit form and either Create License (pre-fills the mint form, embeds the request's key as the requestKey claim) or Deny (records DeniedAtUtc/an optional internal-only reason).
6
Activation re-validates the keyLicenseService.ApplyAsync: if the token being applied carries a requestKey claim, it's looked up via ILicenseRequestRepository.GetByUniqueKeyAsync against any of this install's own past requests — proving the license was minted for a request this install actually made, not one copied from elsewhere. A token with no requestKey claim skips this check entirely.
