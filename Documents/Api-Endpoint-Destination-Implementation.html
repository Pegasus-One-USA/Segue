1.Overview

ApiEndpoint (DestinationType.ApiEndpoint, enum value 27) is the general-purpose, "bring your own endpoint" outbound REST destination. It exists so an arbitrary customer- or partner-owned HTTP API never forces a workaround: it exposes the widest configuration surface of any destination type in FHIRBridge — HTTP method, eight authentication modes, custom headers/query parameters, a caller-supplied request body shape with placeholder substitution, byte- and count-bounded batching, gzip compression, retry with exponential backoff, and a configurable success/failure contract. It is registered to its own writer, MappedApiEndpointDestinationWriter, and its own wire-level sender, ApiEndpointSender — unlike some destinations (e.g. AzureFhirService), it does not reuse another type's writer.

2.What was built

  • New DestinationType.ApiEndpoint enum value, registered to a dedicated MappedApiEndpointDestinationWriter in ConfiguredDestinationWriterFactory.
  • ApiEndpointSettings — parses the flat dest_api*-keyed ConnectionMetadataJson bag (the same convention every other writer's wizard fields use) into a strongly-typed, validated settings record. Credential material is never in this bag — it lives only in DestinationConfiguration.SecretReference's Key Vault entry.
  • ApiEndpointSender — the wire half: resolves the secret, applies the configured auth scheme, optionally gzips and/or HMAC-signs the body, and sends with bounded exponential-backoff retry (transport faults, timeouts, 429 and 5xx are retried; any other 4xx is not).
  • MappedApiEndpointDestinationWriter — splits mapped records into batches bounded by both record count and serialized byte size, frames each batch per the configured payload shape, and either uses the fixed envelope every other writer produces or the caller's own {{fieldName}}-templated body.
  • A dedicated Angular form (ApiEndpointDestinationFormComponent), duplicated identically across the V1 (node-library) and V2 (node-library-v2) destination wizards — same pattern every other destination form follows in this codebase.
  • Full workflow-canvas wiring — appears in the Node Library palette as dest-apiendpoint (ApiEndpointDestinationNode), opens its own configuration form, saves/edits/runs correctly, and is phase-enabled in both phase-config.service.ts and phase-config-v2.service.ts.
  • Runtime DAG node — ApiEndpointDestinationNodeExecutor, same shape as every other destination node: consumes MappedRecordBatch and requires an upstream Mapping node.
  • Admin "New Connection" card — ApiEndpoint added to destination-connections's CREATE_TYPES/EDITABLE_TYPES, with dest_apiEndpointUrl added to its TARGET_FIELD_KEYS resolver.

3.Complete configuration key reference

Every key below lives in DestinationConfiguration.ConnectionMetadataJson as a flat string-keyed JSON object — the same dest_* convention every other destination's wizard fields use. Parsed by ApiEndpointSettings.Parse (backend) and produced by ApiEndpointDestinationFormComponent.getFullConfig() (frontend). Credential material is never one of these keys — it is written to DestinationConfiguration.SecretReference's Key Vault entry instead.

Secret storage The single credential control in the Angular form (secretValue / dest_apiSecret in getFullConfig()) is not written into ConnectionMetadataJson — it is passed separately as inlineSecret/metadata.secret to CreateDestinationConfigurationRequest, which stores it via DestinationConfiguration.SecretReference in Key Vault. What that one control means depends on dest_apiAuthMode: a bearer token, a static API key, "username:password" for Basic, the HMAC shared secret, the OAuth2 client secret, or a base64-encoded PFX (optionally suffixed |<password>) for client-certificate mTLS. It is never repopulated when editing/reusing an existing connection.

4.Authentication modes

ApiEndpointAuthMode is deliberately the widest auth surface of any destination writer in FHIRBridge, so an arbitrary customer- or partner-owned API never forces a workaround.

None

none
No credential attached at all — an already-public or network-restricted endpoint. No secret required; RequiresSecret is false.

Bearer

bearer
Secret sent verbatim as Authorization: Bearer <secret>.

API Key — Header

apiKeyHeader
Secret sent in a configurable header (dest_apiAuthHeaderName, default X-Api-Key).

API Key — Query

apiKeyQuery
Secret appended to the request URL as a query parameter (dest_apiKeyQueryParamName, default api_key) — the shape a number of public/partner APIs still require.

Basic

basic
Secret is stored pre-formatted as "username:password" and sent as Authorization: Basic <base64> — the same convention used across every other Basic-auth destination in this codebase.

HMAC-SHA256

hmacSha256
Body signed with HMAC-SHA256 over "{unix timestamp}.{uncompressed body}" (not the body alone, so a captured request cannot be replayed outside the verifier's freshness window). Signature sent as sha256=<hex> in dest_apiSignatureHeaderName (default X-Signature-256); the timestamp is sent separately in dest_apiTimestampHeaderName (default X-Signature-Timestamp). Same convention as DataLakeWebhookAuthMode.HmacSha256.

OAuth2 Client Credentials

oauth2ClientCredentials
Requires dest_apiTokenEndpoint and dest_apiClientId (optional dest_apiScope). The access token is acquired and cached through the shared destination token provider (IFhirDestinationTokenProvider, Redis-backed in production) — a workflow writing hundreds of batches acquires one token, not one per request. Sent as Authorization: Bearer <token>.

Client Certificate (mTLS)

clientCertificate
The secret holds a base64-encoded PFX, optionally suffixed |<password> when the PFX itself is password-protected. Presented at the TLS handshake, not as a header. Because this needs its own HttpClient carrying that specific certificate, it builds a fresh, disposable handler per call rather than pulling from the shared named HttpClientFactory pool every other auth mode uses — an accepted tradeoff since this destination type is expected to be low-volume relative to the batched destinations (Blob/S3/lake) that actually need pooling.

5.Payload shapes

ApiEndpointPayloadShape controls how a batch of mapped records is framed in the request body.

jsonArray defaultA single JSON array of record objects — [{...},{...}]. The most broadly accepted shape for a generic API.
ndjsonOne JSON object per line, joined with \n (not Environment.NewLine — a reader parsing line-delimited JSON expects LF regardless of which OS produced the file). Content-Type defaults to application/x-ndjson.
envelopeWraps the array with run/route provenance: { meta: { resourceType, destinationObject, recordCount, routeName, correlationId, emittedOnUtc }, records: [...] }.
recordPerRequestOne HTTP request per record — for an endpoint that cannot accept a batch at all. Every other batching setting (dest_apiBatchSize, dest_apiMaxRequestBytes) is then ignored, matching DestinationType.RestApi's own behavior.

6.Request body template & placeholder substitution

Most partner/customer APIs expect a specific body shape that already has meaning to their own system (an order schema, a specific event contract) — hand-mapping every one of those fields onto new per-destination settings-table columns would be unworkable. Instead, dest_apiBodyTemplateJson lets the caller paste the exact JSON their API expects, with {{fieldName}} placeholders anywhere inside it.

  • Exact match — a string value that is exactly one placeholder (e.g. "{{Age}}") is replaced with the field's own typed JSON value: a number stays a number, not the string "42".
  • Embedded match — anything else (e.g. "id-{{Age}}") has its placeholders string-interpolated in place; static text with no placeholder at all is copied through verbatim.
  • Non-string values (numbers, booleans, null) in the template are copied through untouched — a template can mix fixed, static fields with mapped ones.
  • Field resolution — most placeholder names resolve against the record's mapped Values (the same fields the Mapping Profile screen already assigns for every other destination — SQL columns, CSV headers, etc.), but four envelope fields are also addressable by name without needing a redundant mapping: pipelineRunId, resourceType, destinationObject, sourceResourceId.
  • When no template is configured, the writer falls back to the fixed envelope every other destination writer uses: { pipelineRunId, resourceType, destinationObject, sourceResourceId, writtenOnUtc, values: {...} }, plus resource (the raw source JSON) when dest_apiIncludeSourceJson is on.
  • The template field deliberately sits outside the form's "Advanced" disclosure — unlike every other advanced control, it can be the reason someone chose this destination type at all.

Example template mapping a Patient record onto a hypothetical partner event contract:

{
  "event": "patient.sync",
  "externalId": "{{sourceResourceId}}",
  "patient": {
    "firstName": "{{FirstName}}",
    "lastName": "{{LastName}}",
    "dob": "{{DateOfBirth}}"
  },
  "meta": { "source": "fhirbridge", "runId": "{{pipelineRunId}}" }
}

7.Batching, retry & failure handling

  • Dual-bounded batching — a batch closes when either dest_apiBatchSize (record count) or dest_apiMaxRequestBytes (serialized bytes) is hit first, because a record count safe for a 20-column Patient row can be far too large for an Observation batch. A single record that alone exceeds the byte cap is still sent as its own batch — truncating or dropping it would lose data.
  • Idempotency key — X-Idempotency-Key is stable across retries and across re-runs of the same batch ({pipelineRunId}:{resourceType}:{destinationObject}:{batchIndex}, lower-cased), so an endpoint that honors it can de-duplicate a re-driven run instead of landing every record twice.
  • Provenance headers sent on every request, before any configured static headers (which can override them): X-Idempotency-Key, X-FHIRBridge-Resource-Type, X-FHIRBridge-Destination-Object, X-FHIRBridge-Record-Count, X-FHIRBridge-Attempt.
  • Retry classification mirrors DataLakeWebhookSender: only transport faults, timeouts, HTTP 429 and 5xx are retried. Any other 4xx means the endpoint is telling us this exact request is unacceptable — retrying just burns the budget. A 429's Retry-After header (delta-seconds or an absolute date) is honored when present; otherwise backoff is dest_apiRetryBackoffSeconds × 2^(attempt-1).
  • Success is any status in dest_apiExpectedStatusCodes when configured, otherwise any 2xx.
  • On exhausted retries, dest_apiOnFailure decides the outcome for that batch:
    fail defaultThrows, failing the destination node and the whole run — the safe default, since a silently dropped batch is invisible data loss.
    isolateBatchRecords the batch's failure reason in DestinationWriteResult.RecordErrors and keeps going with the remaining batches — the run lands as PartialSuccess.

8.What goes out on the wire

Method & URLdest_apiHttpMethod against dest_apiEndpointUrl (or Target), with dest_apiQueryParamsJson plus the API key (for apiKeyQuery) appended as query parameters.
Content-Typedest_apiContentType, or auto-selected from the payload shape (application/json, or application/x-ndjson for NDJSON), UTF-8.
Content-Encodinggzip header added when dest_apiCompression = gzip. HMAC signatures (if used) are always computed over the uncompressed body, so a verifier reconstructing the signature from the JSON it parsed doesn't need to know which transfer encoding was negotiated.
HeadersProvenance headers (see §7), then any dest_apiHeadersJson entries — applied last, so a customer-supplied header can override a provenance default if their API needs a specific name for it — then the auth-mode-specific header (Bearer/API-key/Basic/HMAC), when applicable.
BodyFramed per dest_apiPayloadShape (§5), built from either the fixed envelope or the dest_apiBodyTemplateJson template (§6).

9.Architecture & write flow

MappedApiEndpointDestinationWriter.WriteAsync is invoked the same way every IConfiguredDestinationWriter is, from both execution planes described in the top-level CLAUDE.md: the Configured Pipeline (IConfiguredDestinationWriter via ConfiguredDestinationWriterFactory) and the Runtime DAG (ApiEndpointDestinationNodeExecutor → DestinationNodeExecutor base → the same factory). Both planes resolve the same writer, so behavior is identical regardless of which pipeline runs it.

  1. ApiEndpointSettings.Parse(destination) reads and validates the dest_api* bag.
  2. BuildBatches splits records into count/byte-bounded batches (or one batch per record, for recordPerRequest), building each record's line via BuildRecordLine — either the substituted template or the fixed envelope — then Frames the batch per payload shape.
  3. Each batch is handed to ApiEndpointSender.SendAsync, which resolves the secret (if any), applies compression/signing/auth, and sends with retry.
  4. Per-batch results roll up into one DestinationWriteResult: written count, written resource ids, and (for isolateBatch) any per-batch failure reasons in RecordErrors.

13.Permissions & phase gating

  • Permission group — like the other lake/webhook destinations, ApiEndpoint has no dedicated PermissionGroupCode member, so it resolves through the generic sourceconnections fallback (SourceSystemPermissionGroups.GroupFor) both in the wizard's client-side gate (destWizardPermissionPrefixes) and on the backend (ControllerAuthorizationExtensions.HasPermissionAsync).
  • Phase gating — 'dest-apiendpoint' is listed in PHASE_1_CONFIG.enabledTransformIds in both phase-config.service.ts (V1) and phase-config-v2.service.ts (V2), so the destination is visible in the Node Library palette today (not held back like the Phase 2+ types, e.g. AzureSql, Snowflake).

14.How this differs from RestApi and DataLakeWebhook

DestinationType.RestApiOne record per request, no auth beyond a raw secret, no batching, no retry. The bare-bones predecessor.
DestinationType.DataLakeWebhookPurpose-built for data-lake ingestion front doors (Fabric Eventstream, Databricks/Snowpipe Streaming, an API-Gateway/Lambda front door, Event Grid, Splunk HEC). Always assumed to carry PHI, so it is https-only by design with no opt-out.
DestinationType.ApiEndpointThe general destination for an arbitrary customer- or partner-owned HTTP API. Widest configuration surface of the three (8 auth modes vs. DataLakeWebhook's smaller set), plain http allowed by default (opt into dest_apiRequireHttps for a PHI-carrying integration), and the only one of the three offering a caller-supplied request body template.

15.Known limitations

  • No live schema / no field-mapping table picker — like Blob/DataLakeWebhook/DataFabricAzure, this is a file/record-shaped destination: mapping targets are typed strings, not columns read from a live schema.
  • Client-certificate mode is not connection-pooled — each send with authMode = clientCertificate builds a fresh HttpClientHandler/HttpClient rather than reusing the shared named client pool, an accepted tradeoff for what is expected to be a low-volume auth mode.
  • Body template only reads mapped values — a template placeholder can address a mapped field or one of the four envelope fields (pipelineRunId/resourceType/destinationObject/sourceResourceId); it cannot reach into the raw source FHIR JSON directly (use dest_apiIncludeSourceJson with the fixed envelope for that instead, which is mutually exclusive with a template).
  • No Test Connection probe — unlike SQL-family and some FHIR-native destinations, the wizard does not offer a live "Test Connection" call before saving; the first real signal of a misconfiguration is the first pipeline run.
