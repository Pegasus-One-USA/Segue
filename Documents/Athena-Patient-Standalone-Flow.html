Patient Standalone Integration

How to trigger a patient-facing SMART on FHIR Standalone workflow against your EHR vendor (athenahealth, Epic/MyChart or eCW/Healow — your choice) from your own application, using an API client (Client ID + Client Secret). Your server asks FHIRBridge for a one-time launch ticket and sends the patient's browser to FHIRBridge's run page, which handles the EHR sign-in and consent, runs the workflow and sends the patient back to you. A second, lower-level way (build your own sign-in screens) is kept in sections 3–5. Every step is the same for each vendor; section 6 lists the few differences.

Flow typePatient Standalone (authorization-code + PKCE), any supported EHR
You implementone server call for a launch ticket + a browser redirect and return page
You set up in the portalSource, EHR Endpoint, Workflow, API client

01Set up the workflow and collect your values

You set everything up yourself, in the FHIRBridge portal, with the credentials for your own organisation. Do these once, in this order. After that, every value your application needs is one click away (section 1.1).

Set-up checklist (in the portal)
1

Source connection. Settings → Source Connections → New: choose your EHR vendor (athenahealth, Epic or eCW/Healow) with the Patient application type, and enter the client id, FHIR base URL and scopes of the app you registered with that vendor. Its redirect URI must be {baseUrl}/api/v1/oauth/callback, and the same address must be registered in your app with the vendor (section 1.1).

2

EHR Endpoint. Settings → General → EHR Endpoints → Add: the endpoint(s) your patients sign in to — one per hospital or practice (section 1.2). Then use the row's Copy Code menu to copy its code.

3

Workflow. Workflows → New: pick the source connection above, add a destination (where the data is written) and save until the status reads Ready. Then open the row's ⋮ menu and choose Allow public launch — the patient sign-in needs it on.

4

API client. Settings → General → API Clients → New Client (super administrators only). Copy the Client Secret when it is shown — it is shown once. Then open the client's ⋮ menu → Allowed Caller URLs and add the page address(es) your application triggers from and returns to (an exact page, or a whole domain).

5

Collect the values (section 1.1): Client ID, Client Secret, Workflow Id, the launch-ticket URL and the EHR Endpoint code. Put them in your server's configuration, then wire up the calls in section 2.

The values you collect

You collect the values below from the portal (section 1.1). Store them as fixed configuration in your own application — the Client Secret in your server-side secret store (environment variable, user-secrets, a vault), never in browser code. There is nothing for your end users to configure; these values do not change unless you regenerate the secret or change the set-up.

ValueMeaning

EhrEndpoint IdThe id FHIRBridge's launch endpoint needs to mint the EHR's authorize URL for the hospital or practice the patient signs in to. In the new flow you send it as ehr_endpoint_code

Someone with administrator access to FHIRBridge (not your end users) can read every value below from the portal. If you do not have that access, ask whoever administers your FHIRBridge instance — this table tells them exactly where to look.

1.2 Adding EHR Endpoints and getting their codes

An EHR Endpoint is one hospital or practice that a workflow can connect to. Enter each one once; the patient (or your application) then chooses between them by code.

Where to enter one

Portal → Settings → General → EHR Endpoints → Add. Fields:

FieldWhat to enter
VendorThe EHR vendor: Epic, Athenahealth, Healow (eCW), Cerner, MEDITECH Greenfield, Generic FHIR. A workflow can only be run against endpoints of its own source's vendor.
Endpoint TypeMyChart for a customer's production instance (the patient audience); Epic or Ecw for a vendor sandbox (the provider audience).
Vendor Endpoint IdThe vendor's own identifier for this organisation — for example Epic's organisation id from its endpoint directory, athenahealth's practice id, or eCW's practice id. It is not the code you send.
NameWhat your people and patients see in lists, e.g. "Acme Health System".
FHIR Base URLThat organisation's FHIR R4 base URL.
Format Type / StatusR4 and active for a normal endpoint.
Run-time overrides (optional)Only used when a backend workflow is run against this endpoint: Token Endpoint, Client Id, Key Id, JWKS URL (Epic), Practice Id (athenahealth). A blank field keeps the workflow's saved value.

How to get the code

  • One endpoint: open the endpoint's ⋮ menu and choose Copy Code. A "Copied" message confirms it is on your clipboard.
  • The complete list: call the endpoint below from your server. It returns every endpoint's code, name and vendor, so your application can show a hospital picker or look a code up by name.

ehr-endpoints.ts (your server)
// Run this on your server — it needs the Client Secret. Cache the result; the list changes rarely.
export async function listEhrEndpoints(vendor: 'Athenahealth' | 'Epic' | 'Healow') {
  const response = await fetch(`${process.env.FHIRBRIDGE_BASE_URL}/api/v1/workflows/external/ehr-endpoints`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      client_id: process.env.CLIENT_ID,
      client_secret: process.env.CLIENT_SECRET,
      return_url: process.env.APP_RETURN_URL,        // must be one of the API client's Allowed Caller URLs
    }),
  });
  if (!response.ok) throw new Error(`FHIRBridge refused the request (${response.status})`);

  const all: { code: string; name: string; vendor: string }[] = await response.json();
  return all.filter(endpoint => endpoint.vendor === vendor);   // e.g. offer these to the patient
}

A request whose return_url is not on the client's Allowed Caller URLs is refused with 403 caller_url_not_allowed; wrong credentials give 401 invalid_client.

Two registrations that must match
  • Allowed Caller URLs (API Clients): every return_url you send — and every page that calls the list endpoints — must be on the client's list, otherwise the request is refused with "caller URL is not whitelisted".
  • Redirect URI (athenahealth developer portal): {baseUrl}/api/v1/oauth/callback must be registered there and identical to the redirect URI on the source connection.
  • Only if you use the direct calls in sections 3–5: your page's origin (scheme + host + port) must be added in Settings → General → Allowed Origins, because the browser then calls FHIRBridge directly and cross-origin.

02Recommended: trigger with an API client

Your server proves who it is with the Client ID and Secret and asks FHIRBridge for a launch ticket. Only that short-lived ticket — never the secret — goes through the patient's browser. FHIRBridge's own run page then takes the patient through the EHR's sign-in and consent, runs the workflow, and sends the browser back to your page. You build no sign-in screens and handle no athenahealth tokens.

Where the data goes In this flow the workflow writes what it fetched to the destination configured on the workflow (a database, file, FHIR server, and so on). Your page learns only the outcome (Triggered, Succeeded or Failed) and the run id. If your application needs the FHIR resources returned to the browser itself, use the direct calls in sections 3–5 instead. Patient search terms and a patient id are also not part of this flow: a patient's own sign-in decides whose record is read.

2.2 The launch-ticket call

Made from your server, anonymous apart from the Client ID and Secret in the body. Send JSON (or a form post) to {baseUrl}/api/v1/workflows/external/launch-ticket.

FieldRequiredAccepted valuesWhat it does
client_idYesTextYour API client's Client ID. Identifies which application is asking.
client_secretYesTextYour API client's Client Secret. Proves it is you. Server-side only; wrong or missing gives 401 invalid_client.
workflow_idYesWorkflow Id (GUID)Which workflow to run. Must exist; otherwise 404 workflow_not_found.
ehr_endpoint_codePatient: yes
Others: optional		An EHR Endpoint code (GUID) from section 1.2. Anything that is not a GUID is ignored.For a patient workflow: which hospital's portal the patient signs in to. For a backend workflow: runs this one execution against that hospital's connection values (FHIR base URL, token endpoint, client id, key id, practice id) instead of the workflow's saved ones; the endpoint must be the same vendor as the workflow, and bulk-export workflows cannot use it. An unknown code, or a vendor mismatch, stops the run with a clear error.
return_urlRecommendedAn absolute https:// address (http:// only for localhost) that is on the API client's Allowed Caller URLs. window_modeNonew · same (default). Any other value behaves as same.Tells FHIRBridge's page whether it was opened in a separate window (new) or replaces your page (same). You choose which by how you navigate to run_url: window.open for a new window, window.location for the same one.
close_on_completeNotrue or 1 to close; anything else (default) does not.Only with window_mode=new. true: the window closes itself when the run is done (if the browser refuses, it falls back to return_url). Otherwise it stays open and goes to return_url.

The response is { "ticket": "…", "run_url": "https://…/run-page?ticket=…", "expires_in": 90 }. Send the browser to run_url straight away.

When the browser comes back Your return_url receives ?status=Triggered|Succeeded|Failed and, when known, &workflowRunId=…. Strip those parameters from the address bar once you have read them (history.replaceState), so a refresh does not replay them. To follow a run after the fact, call GET {baseUrl}/api/v1/workflows/external/run-status/{workflowRunId} — it needs no credential and returns status (Running, Succeeded, PartialSuccess, Failed, Cancelled) plus a general errorMessage with a Reference ID you can quote to us.

Program.cs
public sealed class EhrOptions
{
    public string BaseUrl { get; set; } = "";
    public string WorkflowId { get; set; } = "";
    public string EhrEndpointId { get; set; } = "";
    public string ClientId { get; set; } = "";
    public string ClientSecret { get; set; } = "";
}

builder.Services.Configure<EhrOptions>(builder.Configuration.GetSection("Ehr"));
builder.Services.AddHttpClient("fhirbridge");

// Called by your own page. Returns only the one-time run URL; the secret never leaves this server.
app.MapPost("/api/ehr/launch", async (
    LaunchRequest request,
    IOptions<EhrOptions> options,
    IHttpClientFactory httpClientFactory,
    CancellationToken ct) =>
{
    var athena = options.Value;

    var response = await httpClientFactory.CreateClient("fhirbridge").PostAsJsonAsync(
        $"{athena.BaseUrl.TrimEnd('/')}/api/v1/workflows/external/launch-ticket",
        new
        {
            client_id = athena.ClientId,
            client_secret = athena.ClientSecret,
            workflow_id = athena.WorkflowId,
            ehr_endpoint_code = athena.EhrEndpointId,
            return_url = request.ReturnUrl,           // must be one of your Allowed Caller URLs
            mode = request.Mode ?? "async",
            window_mode = request.WindowMode ?? "new",
            close_on_complete = request.CloseOnComplete ? "true" : "false",
        },
        ct);

    if (!response.IsSuccessStatusCode)
    {
        // 401 = bad credentials, 403 = return_url not whitelisted. Log it; show the patient something generic.
        var detail = await response.Content.ReadAsStringAsync(ct);
        app.Logger.LogWarning("FHIRBridge launch-ticket refused: {Status} {Detail}", (int)response.StatusCode, detail);
        return Results.Problem("Could not start the connection. Please try again later.", statusCode: 502);
    }

    var ticket = await response.Content.ReadFromJsonAsync<JsonElement>(cancellationToken: ct);
    return Results.Ok(new { runUrl = ticket.GetProperty("run_url").GetString() });
})
.RequireAuthorization(); // your own login, not FHIRBridge's

public sealed record LaunchRequest(string ReturnUrl, string? Mode, string? WindowMode, bool CloseOnComplete);

Your server — Node.js / Express JavaScript

server.js
import express from 'express';

const app = express();
app.use(express.json());

const { FHIRBRIDGE_BASE_URL, WORKFLOW_ID, EHR_ENDPOINT_ID, CLIENT_ID, CLIENT_SECRET } = process.env;

app.post('/api/ehr/launch', requireLogin, async (req, res) => {
  const response = await fetch(`${FHIRBRIDGE_BASE_URL}/api/v1/workflows/external/launch-ticket`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      client_id: CLIENT_ID,
      client_secret: CLIENT_SECRET,          // stays on this server
      workflow_id: WORKFLOW_ID,
      ehr_endpoint_code: EHR_ENDPOINT_ID,
      return_url: req.body.returnUrl,        // must be one of your Allowed Caller URLs
      mode: req.body.mode ?? 'async',
      window_mode: req.body.windowMode ?? 'new',
      close_on_complete: req.body.closeOnComplete ? 'true' : 'false',
    }),
  });

  if (!response.ok) {
    console.warn('FHIRBridge launch-ticket refused', response.status, await response.text());
    return res.status(502).json({ error: 'Could not start the connection.' });
  }

  const { run_url } = await response.json();
  res.json({ runUrl: run_url });
});

app.listen(3000);

Your page — TypeScript browser

Open the new window inside the click handler (browsers block pop-ups opened later), then point it at the run URL once your server answers. Use the same-window variant if you prefer a full-page redirect.

get-my-records.ts
const RETURN_URL = window.location.origin + window.location.pathname;

export async function getMyRecords(options: { newWindow?: boolean; closeOnComplete?: boolean } = {}) {
  const useNewWindow = options.newWindow ?? true;

  // Must happen synchronously in the click handler, or the browser treats it as an unwanted pop-up.
  const popup = useNewWindow ? window.open('', '_blank') : null;

  try {
    const response = await fetch('/api/ehr/launch', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        returnUrl: RETURN_URL,
        mode: 'async',                                   // or 'sync' to wait for the run to finish
        windowMode: useNewWindow ? 'new' : 'same',
        closeOnComplete: options.closeOnComplete ?? false,
      }),
    });
    if (!response.ok) throw new Error('Could not start the connection.');

    const { runUrl } = await response.json();
    if (popup) popup.location.href = runUrl;   // FHIRBridge's page: sign-in, consent, run
    else window.location.href = runUrl;        // same window
  } catch (error) {
    popup?.close();
    throw error;
  }
}

// On page load: handle the browser coming back from FHIRBridge
export function handleReturn(): { status: string; workflowRunId: string | null } | null {
  const params = new URLSearchParams(window.location.search);
  const status = params.get('status');
  if (!status) return null;

  const result = { status, workflowRunId: params.get('workflowRunId') };
  window.history.replaceState(null, '', window.location.pathname);   // a refresh must not replay this
  return result;
}

document.getElementById('connect-btn')?.addEventListener('click', () => getMyRecords());

const back = handleReturn();
if (back?.status === 'Failed') showMessage('The connection could not be completed. Please try again.');
else if (back) showMessage(back.status === 'Triggered' ? 'Your records are being retrieved.' : 'Done.');

Optional — follow a run TypeScript

run-status.ts
// run-status needs no credential, so it can be called from the browser or your server
export async function waitForRun(baseUrl: string, workflowRunId: string, timeoutMs = 120_000) {
  const deadline = Date.now() + timeoutMs;
  while (Date.now() < deadline) {
    const r = await fetch(`${baseUrl}/api/v1/workflows/external/run-status/${workflowRunId}`);
    const { status, errorMessage } = await r.json();
    if (status !== 'Running') return { status, errorMessage };   // Succeeded | PartialSuccess | Failed | Cancelled
    await new Promise(resolve => setTimeout(resolve, 2000));
  }
  return { status: 'Running', errorMessage: null };
}

2.5 Checking that the workflow ran and succeeded

status=Triggered on your return page only means the run started. To confirm it finished and worked, use the portal or the status call.

In the portal — Execution History

  1. Open Workflows, find the workflow, open its ⋮ menu and choose Execution History. (You can also open Execution History from the main menu and filter by workflow.)
  2. Find your run. The newest are at the top. The workflowRunId returned to your return_url, or the run's Correlation ID, identifies it. Every run has its own Correlation ID.
  3. Read the row: Status, Duration, EHR Endpoint (Default, or the hospital's name when a code was passed) and Triggered By (ExternalTrigger for runs started with an API client).
  4. Click the row for the detail page. Its Source EHR section shows the source, the hospital used, and any Group ID or search criteria passed for that run. A failed run shows its error message and a Reference ID you can open under Operations → Errors.
StatusMeaningWhat to do
RunningStill in progress (including a bulk export being waited on).Check again shortly. Async runs are Running until they finish.
SucceededEvery step completed and the data reached the destination.Nothing. Check the destination if you want to see the data.
Partial SuccessThe run finished but some resource types or records were skipped; the message lists them.Read the message; usually a scope or permission the EHR did not grant for that resource.
FailedThe run stopped with an error.Open the run, read the message, quote the Reference ID if you contact support.
CancelledSomeone cancelled it from the detail page.Trigger again if it was not intended.

From your application — the status call

Use the workflowRunId from the return page. No credential is needed, which is why the response never contains record details: only status and, for a failed run, a general errorMessage with a Reference ID.

check-run.sh
curl "https://your-fhirbridge-host/api/v1/workflows/external/run-status/WORKFLOW_RUN_ID"

# { "status": "Failed", "errorMessage": "The workflow did not complete successfully. Reference ID: ERR-20261001-000123" }

03Alternative: build your own sign-in screens

Use this only if you need it The direct calls below let your own page drive the sign-in and receive the FHIR resources in the browser. They use no API client — the run is authorised by the workflow's public-launch setting plus the per-browser callerId — and they need your origin on FHIRBridge's CORS list. If you only need the workflow to run and write to its destination, section 2 is simpler and keeps the secret off the browser.

Three actors: the patient's browser, your application's frontend, and FHIRBridge — which itself redirects out to athenahealth's real login mid-flow.

Two things easy to get wrong
  • callerId has two unrelated meanings depending on the call. On public-patient-standalone-url it's the browser URL FHIRBridge's /oauth/callback redirects back to once the token exchange completes. On token-status / validate-run / run / discard-token it's the interactive token cache key (SmartAuthorizationCodeTokenProvider keys on this, not the source connection id) — send the same value on every call in one browser session, or a token that really is cached will look missing.
  • sessionId (only on public-patient-standalone-url) is what actually becomes that cache key server-side. Persist whatever FHIRBridge returns (localStorage, since a full-page navigation would wipe an in-memory value) and echo it back as callerId on every later call. Same value, two field names — FHIRBridge's existing wire shape.

04API reference (direct calls)

All calls target {baseUrl} (the FHIRBridge Base URL from section 1.1), anonymous — gated instead on the workflow's public-launch opt-in, which we've already enabled for the Workflow Id we gave you.

POST

No CSRF token needed for this flow FHIRBridge's double-submit CSRF check only fires for callers that already hold FHIRBridge's own session cookie (its own logged-in portal users). Your application authenticates none of that way — validate-run and discard-token are anonymous, and run is explicitly exempted — so none of these calls need an X-CSRF-Token header.

Two sides to implement: a small backend endpoint that hands your frontend the three values from section 1.1, and the frontend logic that drives the browser flow against FHIRBridge using them.

5.1 Backend — expose the provided configuration ASP.NET Core

Store the three values we gave you as configuration, and expose them to your own frontend with a simple read-only endpoint. No database table and no settings-management UI are needed — these values don't change unless we tell you they've rotated.

// Strongly-typed options bound straight from configuration — the three values FHIRBridge gave you
public class EhrOptions
{
    public string WorkflowId { get; set; } = "";
    public string BaseUrl { get; set; } = "";
    public string EhrEndpointId { get; set; } = "";
}

builder.Services.Configure<EhrOptions>(builder.Configuration.GetSection("Athena"));

// Gated by your own app's login (not FHIRBridge's) — hands the three fixed values to your
// frontend so it can drive the flow. No write endpoint: these values never change from inside your app.
app.MapGet("/api/ehr-config", (IOptions<EhrOptions> options) =>
{
    var athena = options.Value;
    return Results.Ok(new {
        workflowId = athena.WorkflowId,
        baseUrl = athena.BaseUrl,
        ehrEndpointId = athena.EhrEndpointId,
    });
});

5.2 Frontend — drive the launch against FHIRBridge TypeScript

Plain fetch calls — the shape is the same for any HTTP client or frontend framework.

connect-get-data.ts
// Fetched once from your own backend's /api/ehr-config
const config = await fetch('/api/ehr-config').then(r => r.json());
const FHIRBRIDGE_BASE_URL = config.baseUrl;
const WORKFLOW_ID = config.workflowId;
const EHR_ENDPOINT_ID = config.ehrEndpointId;

// Persisted across the full-page redirect to athenahealth and back
let sessionId = localStorage.getItem('ehrSessionId') ?? undefined;
let patientId: string | null = null;

async function connectGetData() {
  // 1. Pre-flight — surfaces config problems before bouncing through a login that would never work
  const validation = await fetch(
    `${FHIRBRIDGE_BASE_URL}/api/v1/workflows/${WORKFLOW_ID}/validate-run`,
    {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ patientId, patientSearchCriteria: null, callerId: sessionId ?? null }),
    },
  ).then(r => r.json());

  if (!validation.isValid) {
    throw new Error(validation.errors.map((e: any) => e.message).join(' '));
  }

  // 2. Is there already a usable token for this session?
  const params = new URLSearchParams();
  if (sessionId) params.set('callerId', sessionId);
  if (patientId) params.set('patientId', patientId);
  const { hasValidToken } = await fetch(
    `${FHIRBRIDGE_BASE_URL}/api/v1/workflows/${WORKFLOW_ID}/token-status?${params}`,
  ).then(r => r.json());

  if (!hasValidToken) {
    // 3. No token — mint a launch URL and hand the browser off. This never returns; the browser
    //    navigates to athenahealth's login, back to /oauth/callback, then to callerId below.
    const mintParams = new URLSearchParams({ ehrEndpointId: EHR_ENDPOINT_ID });
    mintParams.set('callerId', window.location.origin + window.location.pathname);
    if (sessionId) mintParams.set('sessionId', sessionId);

    const mint = await fetch(
      `${FHIRBRIDGE_BASE_URL}/api/v1/workflows/${WORKFLOW_ID}/public-patient-standalone-url?${mintParams}`,
    ).then(r => r.json());

    localStorage.setItem('ehrSessionId', mint.sessionId); // persist BEFORE navigating away
    window.location.href = mint.launchUrl;
    return;
  }

  // 4. Token is valid — fetch the data
  const result = await fetch(
    `${FHIRBRIDGE_BASE_URL}/api/v1/workflows/${WORKFLOW_ID}/run`,
    {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ patientId, patientSearchCriteria: null, callerId: sessionId ?? null }),
    },
  ).then(r => r.json());

  if (result.workflowRun.status !== 'Succeeded') {
    throw new Error(result.workflowRun.errorMessage ?? 'Workflow run failed.');
  }

  // 5. Pull the Patient resource(s) out of the Source node's output
  const sourceOutput = Object.values(result.outputsByNodeId ?? {})
    .find((o: any) => o.nodeType.endsWith('SourceNode'));
  const patients = (sourceOutput?.payload?.resources ?? [])
    .filter((r: any) => r.resourceType === 'Patient');

  return patients;
}

// Called once, on page load, after the full-page redirect back from athenahealth
async function handleOAuthReturn() {
  const params = new URLSearchParams(window.location.search);
  const workflowRunId = params.get('workflowRunId');
  window.history.replaceState(null, '', window.location.pathname); // strip so a refresh doesn't replay this

  if (workflowRunId) {
    const { patientId: resolved } = await fetch(
      `${FHIRBRIDGE_BASE_URL}/api/v1/workflows/runs/${workflowRunId}/launch-result`,
    ).then(r => r.json());
    patientId = resolved;
  }

  return connectGetData(); // token is now cached — fetches immediately, no redirect
}

// Wire your own button + the OAuth-return check on page load
document.getElementById('connect-btn')?.addEventListener('click', () => connectGetData());

const returnParams = new URLSearchParams(window.location.search);
if (returnParams.get('workflowRunId') || returnParams.get('signedIn') || returnParams.get('launchError')) {
  handleOAuthReturn();
}

5.3 Minimal, framework-free HTML page no build step

The same flow with no build step — useful as a smoke test against your FHIRBridge instance before wiring it into your real application.

ehr-connect.html
<button id="connect-btn">Connect</button>
<pre id="out"></pre>
<script>
  // Paste the three values FHIRBridge gave you
  const FHIRBRIDGE_BASE_URL = 'https://your-fhirbridge-host';
  const WORKFLOW_ID = '00000000-0000-0000-0000-000000000000';
  const EHR_ENDPOINT_ID = '00000000-0000-0000-0000-000000000000';

  let sessionId = localStorage.getItem('ehrSessionId') || undefined;

  async function connect() {
    const status = new URLSearchParams();
    if (sessionId) status.set('callerId', sessionId);
    const { hasValidToken } = await fetch(
      `${FHIRBRIDGE_BASE_URL}/api/v1/workflows/${WORKFLOW_ID}/token-status?${status}`,
    ).then(r => r.json());

    if (!hasValidToken) {
      const mint = new URLSearchParams({ ehrEndpointId: EHR_ENDPOINT_ID });
      mint.set('callerId', location.origin + location.pathname);
      if (sessionId) mint.set('sessionId', sessionId);

        `${FHIRBRIDGE_BASE_URL}/api/v1/workflows/${WORKFLOW_ID}/public-patient-standalone-url?${mint}`,

        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ patientId: null, patientSearchCriteria: null, callerId: sessionId }),
      },

    document.getElementById('out').textContent = JSON.stringify(run, null, 2);
  }

  document.getElementById('connect-btn').addEventListener('click', connect);
  // On return from athenahealth, the token is already cached — clicking Connect again fetches immediately.
  if (new URLSearchParams(location.search).get('workflowRunId')) {
    history.replaceState(null, '', location.pathname);
    connect();
  }
</script>

06Differences by vendor

The same API client, launch-ticket call and return handling work for athenahealth, Epic/MyChart and eCW alike — only the source connection, the Workflow Id and the EhrEndpoint Id differ (one API client serves every workflow). If your integration needs more than one vendor, you set up each one the same way and keep a separate Workflow Id / EhrEndpoint Id pair per vendor. For Epic/MyChart, list the hospitals your patient can choose from with POST {baseUrl}/api/v1/workflows/external/ehr-endpoints (body: client_id, client_secret, return_url) from your server, show the names, and send the chosen code as ehr_endpoint_code.
