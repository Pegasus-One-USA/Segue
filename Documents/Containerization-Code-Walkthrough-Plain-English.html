How to Read This Document

Every file is shown in small chunks. Under each chunk of real code, there's a green box labeled "In plain English" that explains what that chunk does and why — no assumption that you can read code. If you only read the green boxes and skip the code itself, you'll still get the full picture. The code is there so you (or anyone else) can point at an exact line if a question ever comes up later.

One repeated idea worth knowing up front: several files create 5 near-identical blocks (one per container: the database, the cache, the main app, the demo app, the background worker). Rather than explain the same pattern 5 times, the first one is explained fully and the rest just call out what's different about them (how much computer power they get, what port they use, etc.).

Glossary — Words You'll See a Lot

WordWhat it means, in plain terms
ContainerA sealed, self-contained package that holds one piece of software plus everything it needs to run (its own mini operating system files, settings, etc.). Because everything it needs travels with it, it runs identically on a laptop, a test server, or in Azure/AWS — no "works on my machine" surprises.
ImageThe blueprint a container is built from — like a recipe. You build an image once, then can start as many running containers from it as you like.
DockerfileA step-by-step recipe (a text file) describing how to build one image: "start from this base, copy these files in, run this build command," etc.
Docker ComposeA tool that reads one file (docker-compose.yml) listing several containers and starts them all together, already able to talk to each other. Used here for running the whole product on a single computer.
Terraform / BicepTools that let you write down, as a checklist-style text file, exactly what cloud resources you want (servers, databases, storage, networking). Running the tool then builds all of it automatically and consistently — instead of a person clicking through dozens of web console screens by hand, which is slow and error-prone.
Environment variableA labeled setting attached to a container when it starts, like a sticky note that says "use this database address" or "run in production mode." The software inside reads these to configure itself.
SecretA setting that's sensitive — a password or signing key — handled with extra care (kept out of plain logs, not typed directly into shared files).
PortA "door number" a piece of software listens on. If a container's software listens on port 80, other things reach it by knocking on port 80.
Tag / LabelA little sticky note attached to a cloud resource (or container) recording things like "this belongs to Project X." Used later to find everything a deployment created, to report on its cost, or to clean it all up.
RegistryA storage locker for images — you upload ("push") a built image there once, and any computer with access can download ("pull") and run it later.
ReplicaA running copy of a container. "1 replica always on" means there's always exactly one copy running, 24/7, even with zero visitors.
Key VaultMicrosoft Azure's dedicated, purpose-built secure locker specifically for passwords and other secrets — the recommended place to keep them in Azure, with a record kept of who accessed what and fine control over who's allowed to. Once a password is written in, everything else reads it from there — including if someone deliberately changes it later, that change sticks.
NAT GatewayA one-way mail-forwarding service for containers that don't have their own public internet address. It lets them send requests out to the internet (e.g. to download a software update) and receive the reply, but nobody on the outside internet can use it to reach in and contact the container directly.
TLS / HTTPS / CertificateThe padlock-icon, encrypted version of a web address (https:// instead of http://). It requires a "certificate" — a bit like a notarized ID card for a website — issued either by a recognized outside authority (trusted automatically by browsers) or generated by the deployment itself ("self-signed," which works and still encrypts everything, but shows visitors a "not trusted" warning until it's swapped for a purchased one).

🐳Docker & Local Files

These files describe how to build the 5 containers and run them together on one computer (yours, or a test server), for $0 in cloud costs.

.dockerignore

A short "don't copy these" exclude-list used whenever an image is being built.

**/bin/
**/obj/
**/node_modules/
**/.angular/
**/dist/
.git/
tests/
docs/

When building an image, the computer normally has to gather up all the files it might need and hand them to the builder. Without this list, that would include every already-compiled leftover file, every downloaded code library, the entire git history, and the test suite — gigabytes of stuff that isn't actually needed to run the product. This file just says "skip all of that," which makes every build faster and the resulting image smaller.

docker/fhirbridge-app/Dockerfile

The recipe for the main product image — it bundles the customer-facing website and the main API into one package.

FROM node:20-alpine AS portal-build
ARG PORTAL_CONFIG=production
WORKDIR /src/portal
COPY portal/package.json portal/package-lock.json portal/.npmrc ./
RUN npm ci
COPY portal/ ./
RUN npm run build -- --configuration=${PORTAL_CONFIG}

This first stage builds the customer-facing website (the Angular "portal"). It's like hiring a printer: give it the raw source files, and it hands back a finished, ready-to-serve website. node:20-alpine is just "a small, temporary workshop with the right tools already installed" — it gets thrown away afterward, only the finished website is kept.

FROM mcr.microsoft.com/dotnet/sdk:9.0 AS dotnet-build
WORKDIR /src
COPY src/ ./src/
RUN dotnet publish src/Api/FHIRBridge.Api/FHIRBridge.Api.csproj \
      -c Release --no-self-contained -o /app/publish/api \
    && dotnet publish src/Gateway/FHIRBridge.Gateway/FHIRBridge.Gateway.csproj \
      -c Release --no-self-contained -o /app/publish/gateway

A second, separate workshop — this one compiles the actual application code (written in C#) into two ready-to-run programs: the Api (the brains — handles data, rules, security) and the Gateway (the front door — the only piece the outside world is allowed to talk to directly). Building two things here instead of one is intentional and mirrors how the product already runs on the company's Windows server today.

FROM mcr.microsoft.com/dotnet/aspnet:9.0 AS final
WORKDIR /app
COPY --from=dotnet-build /app/publish/api ./api
COPY --from=dotnet-build /app/publish/gateway ./gateway
COPY --from=portal-build /src/portal/dist/fhirbridge-ui/browser ./portal
COPY containerization/docker/fhirbridge-app/entrypoint.sh ./entrypoint.sh
RUN chmod +x ./entrypoint.sh

EXPOSE 80
ENTRYPOINT ["./entrypoint.sh"]

This is the final, real image — the one that actually gets shipped and run. It gathers up the finished website, the finished Api, and the finished Gateway from the two workshops above into one lightweight package, along with a small startup script (explained next). EXPOSE 80 means "this container answers on door number 80" — that's the only door anyone outside the container is meant to knock on; the Api itself is deliberately never reachable from outside, for security, exactly like on the company's existing server today.

docker/fhirbridge-app/entrypoint.sh

The startup checklist this container runs every time it boots — it starts both the Api and the Gateway and keeps an eye on them.

env ASPNETCORE_URLS=http://127.0.0.1:5000 \
    ASPNETCORE_CONTENTROOT=/app/api \
    dotnet /app/api/FHIRBridge.Api.dll &
API_PID=$!

Starts the Api program running in the background, and tells it two things: (1) only listen for requests from inside this same container (127.0.0.1 is "myself only" — nothing outside can reach it directly, which is a deliberate security choice), and (2) where its own settings files live. The & at the end means "start it and keep going," not "wait for it to finish" — both programs need to run at the same time.

env ASPNETCORE_URLS=http://+:80 \
    ASPNETCORE_CONTENTROOT=/app/gateway \
    StaticFiles__RootPath=/app/portal \
    dotnet /app/gateway/FHIRBridge.Gateway.dll &
GATEWAY_PID=$!

Starts the Gateway — the public front door — telling it to answer on door 80 for anyone, where its own settings live, and where to find the finished website files it needs to serve to visitors.

terminate() {
  kill -TERM "$API_PID" "$GATEWAY_PID" 2>/dev/null || true
}
trap terminate TERM INT

wait -n "$API_PID" "$GATEWAY_PID"
EXIT_CODE=$?
terminate
exit $EXIT_CODE

Housekeeping so the container behaves well: if the container is asked to stop, both the Api and Gateway are shut down cleanly together (rather than one being abandoned). And if either one crashes unexpectedly on its own, the whole container is treated as failed and exits — so whatever's supervising it (Docker, Azure, AWS) notices and restarts it, instead of silently running in a half-broken state.

docker/demo-app/Dockerfile

Same recipe idea as above, for the separate "Demo App" product — but simpler, because the Demo App is a single program that serves its own website itself (no separate front door needed).

FROM node:20-alpine AS frontend-build
...
RUN npm run build -- --configuration=${DEMO_CONFIG}

FROM mcr.microsoft.com/dotnet/sdk:9.0 AS dotnet-build
...
RUN dotnet publish backend/HealthAppBackend.csproj -c Release --no-self-contained -o /app/publish

FROM mcr.microsoft.com/dotnet/aspnet:9.0 AS final
...
ENV ASPNETCORE_URLS=http://+:5500
ENV DEMOAPP_PORTAL_PATH=/app/portal
EXPOSE 5500
ENTRYPOINT ["dotnet", "HealthAppBackend.dll"]

Same two-workshop idea (build the website, build the program), but only one program comes out the other end, so there's no separate startup script needed — the container just runs that one program directly, listening on door 5500 for everyone.

docker/worker/Dockerfile

The recipe for the background Worker — the piece that runs scheduled jobs behind the scenes. It has no website and answers no door at all.

FROM mcr.microsoft.com/dotnet/sdk:9.0 AS dotnet-build
...
RUN dotnet publish src/Worker/FHIRBridge.Worker/FHIRBridge.Worker.csproj -c Release --no-self-contained -o /app/publish

FROM mcr.microsoft.com/dotnet/aspnet:9.0 AS final
...
ENTRYPOINT ["dotnet", "FHIRBridge.Worker.dll"]

The simplest of the three: build the one program, then run it. Nobody ever visits this container directly — it just quietly does its scheduled work in the background. (A note on the base image choice here is in the "bugs found" write-up in the technical guide — the first attempt used a slightly smaller starting point that turned out to be missing something this program needed, and was corrected after testing caught it.)

compose/docker-compose.yml

The master "start everything together" instruction sheet for running the whole product on one computer.

services:
  sqlserver:
    image: mcr.microsoft.com/mssql/server:2022-latest
    container_name: fhirbridge-ctr-sqlserver
    labels:
      com.fhirbridge.project: "FHIRBridge"
      ...
    environment:
      ACCEPT_EULA: "Y"
      MSSQL_PID: "Express"
      MSSQL_SA_PASSWORD: "${SQL_SA_PASSWORD}"
    ports:
      - "${SQL_HOST_PORT:-1434}:1433"
    volumes:
      - sqlserver-data:/var/opt/mssql
    healthcheck:
      test: [...checks the database actually responds...]

This block says: "start a database container using Microsoft's ready-made SQL Server image, the free Express edition." labels are the sticky notes mentioned in the glossary. MSSQL_SA_PASSWORD is the database's master password, pulled from a settings file rather than typed in here directly. volumes means "save the actual data to a safe spot on disk that survives even if the container itself is deleted and recreated." The healthcheck is a recurring "are you actually working yet?" ping — other containers wait for a "yes" here before they try to use the database.

  redis:
    image: redis:7-alpine
    command: redis-server --requirepass ${REDIS_PASSWORD}
    ...
  fhirbridge-app:
    build:
      context: ../../
      dockerfile: containerization/docker/fhirbridge-app/Dockerfile
    depends_on:
      sqlserver: { condition: service_healthy }
      redis: { condition: service_healthy }
    environment:
      ConnectionStrings__FHIRBridgeDb: "Server=sqlserver,1433;Database=FHIRBridge;User Id=sa;Password=${SQL_SA_PASSWORD};Encrypt=True;TrustServerCertificate=True;..."
      ConnectionStrings__Redis: "redis:6379,password=${REDIS_PASSWORD}"
      Authentication__SigningKey: "${JWT_SIGNING_KEY}"
      Portal__AllowedOrigins__0: "http://localhost:${DEMO_HOST_PORT:-5500}"
    ports:
      - "${APP_HOST_PORT:-8080}:80"
    restart: unless-stopped

redis is a small, fast memory cache — think of it as short-term sticky-note storage the app uses to avoid repeating slow work. As part of a recent HIPAA-compliance pass, it now also requires a password to connect (--requirepass) — previously anyone who could reach it on the network at all could read whatever was cached, with nothing else stopping them. Requiring a password too is "defense in depth": a second lock on the door, not just relying on the network layout to keep people out. The main app (fhirbridge-app) is told to wait until both the database and the cache report healthy before it starts, and is handed the exact address/password to find each at, a security signing key, and which other website is allowed to call it. The database connection also now explicitly turns encryption on (Encrypt=True) — the data flowing between the app and the database is scrambled in transit, not just carried over a connection that merely tolerates an unverified certificate. ports: "8080:80" means "on this computer, reach it at address 8080, even though inside the container it's answering on 80." restart: unless-stopped means "if this crashes, start it back up automatically" — important because of a known, harmless startup timing issue explained further in the technical guide.

  demo-app:
    ...
  worker:
    ...
    depends_on:
      sqlserver: { condition: service_healthy }
      redis: { condition: service_healthy }
      fhirbridge-app: { condition: service_started }

volumes:
  sqlserver-data:
  redis-data:
  fhirbridge-dataprotection-keys:

The Demo App and the Worker follow the same pattern as the main app above — their own settings, their own "wait until the database is ready" rule. The Worker additionally waits for the main app to have at least started first (not full proof against every timing issue, just reduces the odds of a rare startup collision — see the technical guide for the full story). The bottom volumes section is just naming the 3 "safe storage spots on disk" referenced earlier, so data survives container restarts.

compose/.env.example

A fill-in-the-blanks template for passwords and settings.

SQL_SA_PASSWORD=Ch4ngeMe!Str0ng
REDIS_PASSWORD=Ch4ngeMe!Str0ng
JWT_SIGNING_KEY=replace-with-a-long-random-string-at-least-32-chars

Before running anything, you copy this file to a real .env file and fill in actual passwords. REDIS_PASSWORD is new — the cache now requires one, same as the database always has. This example file is safe to store in the company's shared code repository (it has no real secrets in it); the real, filled-in .env file is deliberately kept out of the shared repository so real passwords never end up there.

scripts/build-images.sh (and its Windows twin, .ps1)

A one-command way to build all 3 custom images and, optionally, upload them somewhere.

while getopts "r:t:p" opt; do
  case "$opt" in
    r) REGISTRY="$OPTARG" ;;
    t) TAG="$OPTARG" ;;
    p) PUSH="true" ;;
  esac
done

Reads the options someone typed after the command name — which storage locker (registry) to upload to, what version label (tag) to stamp on the images, and whether to actually upload (push) or just build them locally.

for name in "${!IMAGES[@]}"; do
  docker build -f "${REPO_ROOT}/${dockerfile}" -t "${full_tag}" "${REPO_ROOT}"
  if [[ "$PUSH" == "true" ]]; then
    docker push "${full_tag}"
  fi
done

Loops through the 3 recipes (main app, demo app, worker) one at a time: build each into an image, and if uploading was requested, upload it. This is the single command a developer runs before every release — it replaces doing the same 3 builds by hand.

Terraform files — terraform/environments/local/

A second, alternative way to start the same 5 containers — using Terraform instead of the compose file above, for anyone who wants one consistent tool across local, Azure, and AWS.

locals {
  common_labels = {
    "com.fhirbridge.project"     = "FHIRBridge"
    "com.fhirbridge.component"   = "containerization"
    "com.fhirbridge.environment" = "local"
    "com.fhirbridge.managed-by"  = "Terraform"
  }
}

Defines the 4 sticky-note labels once, so they don't have to be retyped on every single container further down — the file just says "stick these same labels on everything."

resource "docker_container" "sqlserver" {
  name  = "fhirbridge-ctr-sqlserver"
  image = docker_image.sqlserver.image_id
  env = [
    "ACCEPT_EULA=Y",
    "MSSQL_PID=Express",
    "MSSQL_SA_PASSWORD=${var.sql_sa_password}",
  ]
  ports { internal = 1433, external = var.sql_host_port }
  volumes { volume_name = docker_volume.sqlserver_data.name, container_path = "/var/opt/mssql" }
  healthcheck { ... }
  dynamic "labels" { for_each = local.common_labels, content { label = labels.key, value = labels.value } }
  restart = "unless-stopped"
}

This is Terraform's version of the exact same database container described in the compose file above — same password setting, same saved-data location, same health check, same restart behavior, plus the 4 sticky-note labels attached automatically. The other 4 containers (cache, main app, demo app, worker) each get their own nearly-identical block later in the file, with just their own settings swapped in — same idea repeated, not worth re-explaining line by line.

scripts/cleanup-local.sh

The "we're done testing, remove everything" button for the local setup.

read -r -p "This removes every FHIRBridge local container ... continue? [y/N] " reply
[[ "$reply" =~ ^[Yy]$ ]] || { echo "Aborted."; exit 1; }

docker compose down -v

Asks "are you sure?" before doing anything destructive (unless told to skip the prompt), then removes all 5 containers, their network, and their saved data. Since everything here runs on your own computer for free, there's no billing urgency to run this — it's mainly just tidying up disk space.

☁Azure Files

These files describe the same 5-container setup, but built inside Microsoft Azure instead of on a local computer — which means it's reachable from the internet, and it costs money while it runs (see the Resource & Cost Inventory in the technical guide for exact figures).

azure/variables.tf

The list of "fill-in-the-blanks" settings this Azure setup needs before it can run.

variable "name_prefix"         { default = "fhirbridge" }
variable "resource_group_name" { default = "rg-tusharpuri" }
variable "image_tag"           { default = "latest" }
variable "sql_sa_password"     { sensitive = true }
variable "jwt_signing_key"     { sensitive = true }
variable "redis_password"      { sensitive = true }
variable "sql_port"            { default = 1433 }
variable "redis_port"          { default = 6379 }

A short checklist of things someone must provide (or accept the sensible defaults for) before this Azure setup can be built: what to name things, which existing "folder" (Resource Group, explained below) to build everything inside, which version of the software to deploy, and the passwords. Marking something sensitive tells Terraform to hide it from its own logs and screen output, the same way a password field on a website shows dots instead of letters. A few fill-in-the-blanks changed recently: this now points at an existing resource group (resource_group_name) instead of naming a brand-new one to create — more on why below — the cache now needs its own password too (redis_password), and a customer can now choose their own "door numbers" for the database and cache (sql_port, redis_port) instead of being stuck with the defaults shown here. Note the door numbers only apply to the database and cache — the two public-facing apps in Azure still always answer on the standard web address with no door number needed at all, for reasons explained further down.

azure/main.tf

The main blueprint — every Azure resource this deployment creates.

locals {
  common_tags = {
    Project     = "FHIRBridge"
    Component   = "containerization"
    Environment = var.name_prefix
    ManagedBy   = "Terraform"
  }
}

data "azurerm_resource_group" "main" {
  name = var.resource_group_name
}

A "Resource Group" is Azure's name for a folder that holds all the related pieces of one deployment together, so they can be viewed, managed, and later deleted as one unit. This block is a recent change: it used to create a brand-new folder for this deployment; now it just looks up one that's expected to already exist (named rg-tusharpuri by default) and builds everything inside it instead. The practical difference: tearing this deployment back down (further down this document) will remove everything it built, but will leave the folder itself standing, since this setup no longer owns it — useful when the folder is meant to be shared with other things, or managed by someone else's process.

resource "azurerm_container_registry" "acr" {
  name                = local.acr_name
  sku                 = "Basic"
  admin_enabled       = true
  tags                = local.common_tags
}

Creates the storage locker (registry) inside Azure where the 3 built images get uploaded to. This has to exist and already have images in it before the containers further down can be created — a bit like needing the warehouse built before you can stock shelves in it.

resource "azurerm_key_vault" "main" {
  name                       = local.key_vault_name
  sku_name                   = "standard"
  tenant_id                  = data.azurerm_client_config.current.tenant_id
  enable_rbac_authorization  = true
  soft_delete_retention_days = 7
  tags                       = local.common_tags
}

resource "azurerm_role_assignment" "terraform_kv_secrets_officer" {
  scope                = azurerm_key_vault.main.id
  role_definition_name = "Key Vault Secrets Officer"
  principal_id         = data.azurerm_client_config.current.object_id
}

This is new, added as part of a recent pass to bring the setup in line with HIPAA (the US law governing protection of patient health data). It creates a Key Vault — Azure's own dedicated, purpose-built locker for passwords and secrets, rather than passing them around as plain settings. It's the recommended way to handle secrets in Azure, and it comes with a record of who accessed what and fine-grained control over who's allowed to. The second block is a one-time permission grant: it lets whoever/whatever runs this setup script (identified by data.azurerm_client_config.current — effectively "the identity currently signed in") write the 3 passwords into the new vault during the very first deploy. It does not hand the containers themselves any special access — see below for how they actually get the password.

resource "azurerm_key_vault_secret" "sql_sa_password" {
  name         = "sql-sa-password"
  value        = var.sql_sa_password
  key_vault_id = azurerm_key_vault.main.id
}

resource "azurerm_key_vault_secret" "jwt_signing_key" { name = "jwt-signing-key", ... }
resource "azurerm_key_vault_secret" "redis_password"  { name = "redis-password",  ... }

The very first time this setup is deployed, the 3 passwords (the database password, the app's own security signing key, and the new cache password) get written into the vault from the settings file. From that point on, every container reads its password from the vault, not from the original settings file. That matters in practice: someone can later change or rotate a password directly in the vault — through the Azure Portal, or a single command — and it sticks. A later re-run of this same setup script won't quietly overwrite that change back to the old value, the way it would if the password just lived in a settings file.

resource "azurerm_log_analytics_workspace" "main" { ... }

resource "azurerm_container_app_environment" "main" {
  name                       = "${var.name_prefix}-env"
  log_analytics_workspace_id = azurerm_log_analytics_workspace.main.id
  tags                       = local.common_tags
}

A "Log Analytics Workspace" is where all the containers' activity logs get collected and stored, so problems can be investigated later. The "Container App Environment" is the shared neighborhood all 5 containers live in — it's what lets them find and talk to each other by name, and it's wired up to send its logs to that workspace.

resource "azurerm_storage_account" "main" { ... }
resource "azurerm_storage_share" "sql_data"   { name = "sql-data",   quota = 50 }
resource "azurerm_storage_share" "redis_data" { name = "redis-data", quota = 10 }

Sets up a proper Azure hard-drive-in-the-cloud, split into two labeled folders — one for the database's data, one for the cache's data — so that data survives even if the database container itself is ever restarted or replaced. The numbers (50, 10) are just size ceilings, not guaranteed usage — you're billed for what's actually stored, not the ceiling.

resource "azurerm_container_app" "sqlserver" {
  name                         = local.sqlserver_name
  revision_mode                = "Single"
  tags                         = local.common_tags

  template {
    min_replicas = 1
    max_replicas = 1

    container {
      name   = "sqlserver"
      image  = "mcr.microsoft.com/mssql/server:2022-latest"
      cpu    = 1.0
      memory = "2Gi"
      env {
        name        = "MSSQL_SA_PASSWORD"
        secret_name = "sql-sa-password"
      }
      volume_mounts { name = "sql-data", path = "/var/opt/mssql" }
    }
  }

  secret {
    name  = "sql-sa-password"
    value = azurerm_key_vault_secret.sql_sa_password.value
  }

  ingress {
    external_enabled = false
    target_port      = var.sql_port
    transport        = "tcp"
  }
}

This is the actual database container in Azure. min_replicas = 1, max_replicas = 1 means "always exactly one copy running, never zero, never more than one" — running the database twice at once on the same shared disk would corrupt it, and letting it turn off entirely isn't acceptable either, so it's pinned at exactly one. cpu = 1.0, memory = "2Gi" is how much computer power it's given (1 processor core's worth, 2 gigabytes of memory) — this directly drives its share of the Azure bill. ingress: external_enabled = false means "the public internet can never reach this directly" — only the other containers inside the same neighborhood can. The password no longer sits directly in this file as a plain value: the secret block's value is now a lookup of what's currently sitting in the Key Vault entry created above, rather than the raw settings-file value — everything downstream (this container, the Azure Portal, etc.) still just sees a plain secret named sql-sa-password, but where that value actually comes from has changed. And target_port = var.sql_port means the customer can now choose their own door number for the database instead of always being stuck with 1433.

resource "azurerm_container_app" "redis" {
  ...
  template { container { cpu = 0.5, memory = "1Gi", command = ["redis-server", "--port", tostring(var.redis_port), "--requirepass", azurerm_key_vault_secret.redis_password.value] } }
  ingress { external_enabled = false, target_port = var.redis_port, transport = "tcp" }
}

resource "azurerm_container_app" "fhirbridge_app" {
  ...
  template {
    min_replicas = 1
    max_replicas = 3
    container { cpu = 0.5, memory = "1Gi", ... }
  }
  ingress { external_enabled = true, target_port = 80 }
}

resource "azurerm_container_app" "demo_app" { ... max_replicas = 3 ... external_enabled = true, target_port = 5500 ... }

resource "azurerm_container_app" "worker" { ... max_replicas = 1 ... (no ingress block at all) }

The remaining 4 containers follow the exact same pattern as the database block above, just with their own settings: the cache gets less power and stays private just like the database, now also requires its own password (read from the vault the same way as the database's), and can have its own custom door number via var.redis_port; the main app and demo app are allowed to scale up to 3 copies automatically if lots of people are using them at once, and are the only two allowed to be reached from the public internet. Those last two keep their fixed doors (80 and 5500) rather than a customizable one — that's a real limitation of Azure's Container Apps product, not an oversight: public-facing apps in Azure are always served on the standard web address (like any ordinary https:// address, no door number needed), so there's nothing to make configurable there. The worker is private and fixed at exactly one copy, with no "door" configured at all since nobody ever visits it directly.

☁AWS Files

The same 5-container product, built inside Amazon Web Services instead. AWS doesn't have one single "put everything in one neighborhood" service the way Azure does, so this setup is spread across more files — networking, storage, and the containers themselves are each their own piece.

aws/variables.tf

variable "aws_region" { default = "us-east-1" }
variable "vpc_cidr"   { default = "10.90.0.0/16" }

Same idea as Azure's settings checklist, plus one AWS-specific item: vpc_cidr is the address range for this deployment's own private slice of network — think of it as choosing a block of house numbers on a street that's reserved exclusively for this project.

aws/main.tf

Networking, the image storage lockers, and the shared plumbing everything else depends on.

provider "aws" {
  region = var.aws_region
  default_tags {
    tags = {
      Project     = "FHIRBridge"
      Component   = "containerization"
      Environment = var.name_prefix
      ManagedBy   = "Terraform"
    }
  }
}

This one line does something the Azure version needed dozens of repeated lines for: it tells AWS "stick these same sticky-note labels on absolutely everything below, automatically." Nothing can accidentally end up unlabeled.

resource "aws_vpc" "main" { cidr_block = var.vpc_cidr }
resource "aws_internet_gateway" "main" { vpc_id = aws_vpc.main.id }
resource "aws_subnet" "public" { count = 2, ... }

Builds this deployment's own private network inside AWS (a "VPC"), a door to the public internet for it (the "Internet Gateway"), and splits it into two smaller sections ("subnets") in two different physical AWS data centers — so if one data center has a problem, the setup isn't entirely dependent on it. All of this is free; AWS doesn't charge for the networking plumbing itself.

resource "aws_subnet" "private" { count = 2, ... }

resource "aws_eip" "nat" { domain = "vpc" }

resource "aws_nat_gateway" "main" {
  allocation_id = aws_eip.nat.id
  subnet_id     = aws_subnet.public[0].id
}

resource "aws_route_table" "private" {
  route { cidr_block = "0.0.0.0/0", nat_gateway_id = aws_nat_gateway.main.id }
}

This block is new, added as part of a recent HIPAA-compliance pass. Previously, all 5 containers sat in the "public" subnets above, each with its own public internet address — mainly so they could reach the internet to download their own software updates and images. That meant the actual running program containers were directly reachable from the internet, which is more exposure than necessary. Now, two new private subnets are added instead, and the 5 containers live there — no public address at all, reachable only through the public "front door" (the load balancer, covered below) or from each other, never directly from the internet.

Private containers still occasionally need to reach out to the internet (again, mainly to download their own images), so a NAT Gateway is added — think of it as a one-way mail-forwarding service: private containers can send a request out and get the reply back, but nobody on the outside can use it to reach in and contact them directly. One honest trade-off worth flagging: only one NAT Gateway was added here, not one per data center zone. That's cheaper to run, but it does mean if that one gateway has a problem, outbound internet access for all 5 containers would be affected until it recovers. That's a deliberate, disclosed cost/simplicity choice, not an oversight.

resource "tls_private_key" "alb" { algorithm = "RSA", rsa_bits = 2048 }

resource "tls_self_signed_cert" "alb" {
  private_key_pem = tls_private_key.alb.private_key_pem
  subject { common_name = "${var.name_prefix}.local" }
  validity_period_hours = 8760
  allowed_uses = ["key_encipherment", "digital_signature", "server_auth"]
}

resource "aws_acm_certificate" "alb" {
  private_key      = tls_private_key.alb.private_key_pem
  certificate_body = tls_self_signed_cert.alb.cert_pem
}

Also new, and also part of the same HIPAA pass: this generates a "certificate" — required to turn on the padlock-icon, encrypted (https://) version of the website address, covered in the load balancer section below. Because there's no real, purchased company domain name attached to this deployment yet, the certificate here is self-signed — the deployment generates its own, rather than buying one from a recognized outside certificate authority. It still fully encrypts the connection, but browsers will show a "not trusted" warning until it's swapped out for a real, purchased certificate — a small, contained future swap once there's a real domain name to attach one to, not a redesign of anything here.

resource "aws_ecr_repository" "fhirbridge_app" { name = "${var.name_prefix}/fhirbridge-app" }
resource "aws_ecr_repository" "demo_app"       { name = "${var.name_prefix}/demo-app" }
resource "aws_ecr_repository" "worker"         { name = "${var.name_prefix}/fhirbridge-worker" }

3 storage lockers (AWS's version of a registry), one per custom image, waiting to receive the built images from the build script covered earlier.

resource "aws_secretsmanager_secret" "sql_sa_password" { ... }
resource "aws_secretsmanager_secret_version" "sql_sa_password" { secret_string = var.sql_sa_password }
# ...and the same again for jwt_signing_key and (new in this pass) redis_password

Stores the database password in AWS's dedicated, extra-secure vault for sensitive values (rather than as a plain setting), and the same again for the security signing key — plus, new in this HIPAA-compliance pass, a third entry for the cache's new password (covered below). This is a small, ongoing cost (a flat monthly fee per stored secret, so three now instead of two).

resource "aws_iam_role" "ecs_task_execution" { ... }
resource "aws_iam_role_policy_attachment" "ecs_task_execution_managed" {
  policy_arn = "arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy"

Creates a limited-permission "staff badge" that the containers use to do only the specific things they're allowed to: download their own images and write their own logs, and (via one more permission added right after this) read the two stored passwords above. It deliberately can't do anything beyond that.

aws/discovery.tf

resource "aws_service_discovery_service" "sqlserver" { name = "sqlserver" }

Sets up a private "phone book" so the main app, demo app, and worker can find the database and cache by a simple name (like sqlserver.fhirbridge.internal) instead of needing to know their exact, ever-changing network address. This is the AWS equivalent of what Docker Compose gives you automatically for free on a local computer — AWS needs it set up explicitly.

aws/alb.tf

  port            = var.fhirbridge_app_port
  protocol        = "HTTPS"
  ssl_policy      = "ELBSecurityPolicy-TLS13-1-2-2021-06"
  certificate_arn = aws_acm_certificate.alb.arn

}

  port            = var.demo_app_port
  protocol        = "HTTPS"
  certificate_arn = aws_acm_certificate.alb.arn
  default_action { forward -> demo_app }
}

Creates the single public "receptionist" address for this whole deployment — the one address the outside world actually visits. It listens on two doors (defaulting to 80 for the main app, 5500 for the demo app, and now customizable via fhirbridge_app_port / demo_app_port if a customer wants different ones) and forwards each visitor to the right container behind the scenes.

The other change here is part of the same HIPAA-compliance pass: both listeners now speak HTTPS (protocol = "HTTPS"), the encrypted, padlock-icon version of the address, using the self-signed certificate generated in main.tf above — previously this was plain, unencrypted http://. This "receptionist" (the Load Balancer) runs continuously and has its own flat hourly charge — it's one of the bigger fixed costs in the AWS setup.

aws/tasks.tf

The exact recipe for each of the 5 containers — what image to run, how much power to give it, what settings to hand it.

resource "aws_ecs_task_definition" "sqlserver" {
  cpu    = "1024"
  memory = "4096"
  container_definitions = jsonencode([{
    name  = "sqlserver"
    image = "mcr.microsoft.com/mssql/server:2022-latest"
    environment = [ { name = "ACCEPT_EULA", value = "Y" }, { name = "MSSQL_PID", value = "Express" } ]
    portMappings = [ { containerPort = var.sql_port, hostPort = var.sql_port } ]
    secrets = [ { name = "MSSQL_SA_PASSWORD", valueFrom = aws_secretsmanager_secret.sql_sa_password.arn } ]
    mountPoints = [ { sourceVolume = "sql-data", containerPath = "/var/opt/mssql" } ]
  }])
}

The database's recipe card: how much computer power it gets (cpu/ memory — these numbers are AWS's units, roughly 1 processor core and 4 gigabytes of memory here), which image to run, its startup settings, and — importantly — the password is pulled directly from the secure vault described earlier rather than being written in plain text anywhere in this file. The door number it answers on is now a fill-in-the-blank setting too (var.sql_port, still defaulting to 1433) instead of being hardcoded, so a customer can pick their own.

resource "aws_ecs_task_definition" "redis" {
  cpu    = "256"
  memory = "512"
  container_definitions = jsonencode([{
    name    = "redis"
    image   = "redis:7-alpine"
    command = ["sh", "-c", "redis-server --port ${var.redis_port} --requirepass \"$REDIS_PASSWORD\""]

resource "aws_ecs_task_definition" "fhirbridge_app" { cpu = "512",  memory = "1024" ... }
resource "aws_ecs_task_definition" "demo_app"       { cpu = "256",  memory = "512"  ... }
resource "aws_ecs_task_definition" "worker"         { cpu = "256",  memory = "512"  ... }

Same recipe-card idea repeated for the other 4 containers, each sized appropriately for what it needs to do — the database gets the most power since it does the heaviest lifting, the smaller supporting pieces get less. The cache's recipe card picked up two changes as part of the HIPAA-compliance pass: it now requires a password to connect (pulled from AWS's own secure vault, the same pattern as the database's password), and its door number is customizable via var.redis_port as well. The main app, demo app, and worker recipe cards are also updated behind the scenes to connect to both the database and the cache with the new password and encryption settings — same idea as everywhere else in this document, not repeated here for each one.

aws/services.tf

Tells AWS to actually keep each recipe running, continuously.

resource "aws_ecs_service" "sqlserver" {
  desired_count = 1
  network_configuration {
    subnets          = aws_subnet.private[*].id
    assign_public_ip = false
  }
  service_registries { registry_arn = aws_service_discovery_service.sqlserver.arn }
}

resource "aws_ecs_service" "fhirbridge_app" {
  desired_count = 1
  network_configuration {
    subnets          = aws_subnet.private[*].id
    assign_public_ip = false
  }
  load_balancer { target_group_arn = ..., container_name = "fhirbridge-app", container_port = 80 }
}

desired_count = 1 is the instruction "always keep exactly one copy of this running — if it ever crashes, start a new one automatically." The database gets registered in the private phone book from earlier (so other containers can find it by name); the main app instead gets plugged into the public receptionist (the Load Balancer) so visitors from the internet can actually reach it.

The network_configuration block on every one of the 5 containers is new, and is where the "no direct public address" change from the HIPAA-compliance pass actually takes effect: subnets = aws_subnet.private[*].id places every container in the private subnets added in main.tf, and assign_public_ip = false means none of them get their own address on the open internet anymore. Previously all 5 had public addresses (mainly so they could fetch their own images); now only the Load Balancer's front door is public, and the containers reach the internet when they need to via the NAT Gateway instead. This is the AWS equivalent of Azure's min_replicas setting, and is the single biggest ongoing cost driver in the whole AWS setup — 5 containers, running continuously, every one of them billed by the second.

🔧The One Code Fix

Everything above is new. Exactly one existing file in the actual product code needed a small change, found by actually running the container and clicking around in it rather than just reading the code.

src/Gateway/FHIRBridge.Gateway/Program.cs

// before
context => !context.Request.Path.StartsWithSegments("/api")

// after
context => !context.Request.Path.StartsWithSegments("/api")
    && !context.Request.Path.StartsWithSegments("/swagger")

The "front door" program (the Gateway) has one job for any web address that isn't part of the main app's data API: just show the website. But it had a narrow blind spot — it only knew to make an exception for addresses starting with /api (which correctly get sent to the Api program instead of the website), and forgot to make the same exception for /swagger (a built-in technical documentation page for developers). The practical effect: visiting that documentation page showed the regular website instead, by mistake. The fix is exactly two added words — "and also make an exception for /swagger" — so that page now correctly shows the real documentation instead.

Why this is the only code change Every other file in this whole containerization effort is brand new — packaging instructions, cloud blueprints, and helper scripts sitting alongside the existing product. This one two-word fix is the only place an actual, pre-existing behavior of the product itself needed correcting, and it was found by genuinely testing the finished container rather than assumed to be fine from reading the code.
