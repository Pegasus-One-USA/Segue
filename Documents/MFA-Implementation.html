1.Overview

FHIRBridge already had a fully-built TOTP (Time-based One-Time Password) engine on the backend — secret generation, code validation, backup codes — but it was completely unreachable from the product: the Angular portal had no enrollment screen and the login flow had no way to ask for a second factor. This work built everything needed to actually turn that dormant backend capability into a real, usable 2FA feature, end to end, plus two admin-facing controls (force MFA for a user, and account recovery when someone loses their authenticator) and a related password-reset convenience tool.

2.What was built

  • Two-step login with MFA. A correct password now returns either a session (no MFA) or a short-lived challenge token (MFA enabled) — the client submits the challenge plus a TOTP/backup code to a second endpoint to finish signing in.
  • Self-service enrollment & disable. Users can turn MFA on (scan a QR code or enter the secret manually, confirm a code, save one-time backup codes) and off from their own Security settings page.
  • Admin account recovery. A SuperAdmin can force-disable a user's MFA without a code — for when someone loses their phone and their backup codes.
  • Admin-forced MFA policy. An admin can require MFA on any user's account; if they haven't enrolled yet, their very next login (and every subsequent navigation) is gated to a dedicated enrollment screen until they finish.
  • Admin password-reset link tool. A secondary, smaller feature added alongside the MFA work: since outbound email isn't wired up yet, an admin can generate a password-reset link for a user and hand it to them directly.
  • Two independent code-review passes. A correctness-focused pass (8 parallel reviewers) found and fixed a real security gap and several bugs; a follow-up cleanup pass removed duplicated logic.

3.Implementation approach

Rather than inventing new patterns, this work deliberately mirrors mechanisms the codebase already uses elsewhere, so the new feature reads as a natural extension of the existing app instead of a bolted-on subsystem:

Challenge-token minting reuses the refresh-token trick

The MFA challenge token is minted by calling the existing IAccessTokenIssuer.IssueRefreshToken() purely for its "random bytes → SHA-256 hash, the hash is the token" mechanic (just with a 5-minute expiry instead of 30 days) — no new token-generation code was written.

Session gating extends the existing password-change gate

FHIRBridge already blocks all API routes except a small allowlist when a pwd_change_required JWT claim is true. A second claim, mfa_setup_required, was added following the exact same shape, and the two checks were generalized into one data-driven loop in Program.cs instead of a second copy-pasted middleware block.

One enrollment UI, two hosts

The QR-code/secret/confirm-code/backup-codes UI was built once as a standalone MfaEnrollmentPanelComponent and embedded in both the self-service Security page and the forced first-login setup page — each host just decides whether "Cancel" is offered and what happens once enrollment finishes.

Guard-based redirect, not scattered special-casing

A single route guard (mfaSetupGuard) runs alongside the existing authGuard on the app shell's parent route. Because Angular evaluates parent-route guards before any child route activates, this one guard automatically protects every page in the authenticated app — no individual page needed its own check.

A stricter policy for a more sensitive action

Bypassing a user's second factor entirely is more sensitive than the general "edit user" permission Admins already hold, so a new SuperAdminOnly authorization policy (mirroring the existing UnifiedAdmin policy's structure) restricts that one action to the highest privilege tier, enforced on the server — not just hidden in the UI.

4.Login flow, step by step

1
POST /auth/internal/loginEmail + password. If the account doesn't have MFA enabled, this alone completes the login and returns tokens.
2
Challenge issuedIf MFA is enabled, the server mints a 5-minute, single-use challenge token and returns { requiresMfa: true, mfaChallengeToken } — no session yet, and no lockout penalty for not having a code yet.
3
POST /auth/internal/login/mfaChallenge token + a 6-digit TOTP code (or a backup code). A wrong code here counts as a real failed attempt toward account lockout.
4
Session issuedOn success, the account is re-checked (still enabled, still allowed to log in locally) before tokens are minted — closing a gap where a disabled account could otherwise ride out an already-issued challenge.
5
Forced-setup checkIf an admin requires MFA for this account and it still isn't enrolled, the access token carries mfa_setup_required: true — the frontend guard immediately redirects to /auth/setup-mfa, and the backend gate middleware blocks every other API route until enrollment finishes.

15.Known limitations & follow-ups

Password-reset-link endpoint reuse The admin "generate password reset link" tool reuses the existing public, anonymous forgot-password endpoint rather than a dedicated admin-authenticated route. This matches the stated "local testing, email isn't wired up yet" use case, but before any production use it should get its own authenticated endpoint with a proper audit trail of which admin triggered it.
Mock/demo mode doesn't simulate forced setup MockAuthService (used only when running the portal without a real backend) simulates the login-time MFA challenge, but not the admin-forced "must set up MFA" policy — that path is only exercised against the real API.
Two parallel authorization-policy classes SuperAdminOnlyRequirement/Handler duplicate the shape of the pre-existing UnifiedAdminRequirement/Handler rather than sharing one generalized role-set mechanism. This was a deliberate trade-off to avoid modifying pre-existing authorization infrastructure used throughout the app, in favor of a small, low-risk, consistent duplicate.
