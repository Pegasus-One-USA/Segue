1.Overview

FHIRBridge ships six build outputs from a single GitHub Actions workflow, .github/workflows/deploy.yml: three Kestrel-hosted backend services, one demo-app backend, and two static Angular builds. Nothing here is IIS-hosted — every backend is a standalone Kestrel process. On Windows these run today as native Windows Services; the same published output can run under systemd on Linux with no C# code change, because every host already calls both .UseWindowsService()/AddWindowsService() and .UseSystemd()/AddSystemd() right after WebApplication.CreateBuilder(args) — each call is a no-op unless the process is actually launched by that OS's service manager.

Why a self-hosted runner at all: the production server is not reachable from the internet, so a GitHub-hosted runner can't SSH/WinRM into it. Instead the server itself runs a self-hosted GitHub Actions runner that polls GitHub outbound — no inbound firewall rule is needed for that connection. The build job (compiling, publishing, packaging) always runs on a GitHub-hosted ubuntu-latest runner and never touches the VM directly; only the deploy job runs on the self-hosted runner, and it only unzips an already-built artifact and moves files around locally.

2.How a Deploy Gets Triggered

TriggerHowNotes
Manual dispatch Actions tab → Deploy workflow → Run workflow (or gh workflow run deploy.yml) Always allowed, on any branch. The only trigger that doesn't depend on commit message text.
Push with commit message Publish Push a commit to main whose exact message is Publish Deliberately strict equality check so ordinary commits never accidentally trigger a deploy.

Since only the commit message is checked (not whether the commit changes any files), the usual way to trigger a deploy without any real code change is a blank commit:

git commit --allow-empty -m "Publish"
git push origin main

The exact condition lives in the build job's if::

if: github.event_name == 'workflow_dispatch' || github.event.head_commit.message == 'Publish'
Which branches Only main is listed under on.push.branches today. Edit that list in deploy.yml to allow other branches to auto-deploy the same way.
Optional hardening, not yet enabled workflow_dispatch already requires a manual click. For a second approval gate immediately before the deploy job touches the server, create a production environment (Settings → Environments) with required reviewers — the deploy job already targets that environment name, so this takes effect with no workflow changes.

3.The Build Job

Runs on ubuntu-latest — shared by both deployment targets today, though right now it only produces Windows binaries (see Linux gaps for what a Linux build path still needs). Steps, in order:

  1. actions/checkout@v4
  2. actions/setup-dotnet@v4 — .NET 9.0.x
  3. actions/setup-node@v4 — Node 20, npm cache keyed on both frontends' lockfiles
  4. dotnet restore FHIRBridge.sln
  5. dotnet publish ×4, each win-x64, framework-dependent (--self-contained false):
    • src/Api/FHIRBridge.Api/FHIRBridge.Api.csproj → publish/Api
    • src/Gateway/FHIRBridge.Gateway/FHIRBridge.Gateway.csproj → publish/Gateway
    • src/Worker/FHIRBridge.Worker/FHIRBridge.Worker.csproj → publish/Worker
    • Demo_TestApp/backend/HealthAppBackend.csproj → publish/DemoApi
  6. npm ci && npm run build -- --configuration production in portal/
  7. Same in Demo_TestApp/frontend/
  8. Stage static builds: 
    mkdir -p publish/Portal publish/DemoPortal
cp -r portal/dist/fhirbridge-ui/browser/. publish/Portal/
cp -r Demo_TestApp/frontend/dist/frontend/browser/. publish/DemoPortal/
  9. Zip everything (run from inside publish/): zip -r ../fhirbridge-deploy.zip Api Gateway Worker DemoApi Portal DemoPortal
  10. actions/upload-artifact@v4, name fhirbridge-deploy, 14-day retention

Result: one artifact, fhirbridge-deploy.zip, containing six top-level folders: Api, Gateway, Worker, DemoApi, Portal, DemoPortal.

Configuration model (ConfigRoot overlay)

Every service's environment-specific config (appsettings.Production.json, etc.) is deliberately never part of the build artifact. It lives entirely under a separate root, C:\inetpub\FHIRBridge_Configurations, mirroring the exact same per-app folder names used under C:\inetpub\wwwroot: 

C:\inetpub\FHIRBridge_Configurations\fhirbridge-api\appsettings.Production.json
C:\inetpub\FHIRBridge_Configurations\fhirbridge-gateway\appsettings.Production.json
C:\inetpub\FHIRBridge_Configurations\fhirbridge-worker\appsettings.Production.json
C:\inetpub\FHIRBridge_Configurations\demoapp-api\appsettings.Production.json
C:\inetpub\FHIRBridge_Configurations\fhirbridge-portal\   (currently empty)
C:\inetpub\FHIRBridge_Configurations\demoapp-portal\      (currently empty)

After every deploy mirrors an app's published files into its wwwroot folder, the script copies that app's ConfigRoot subfolder on top — an overlay copy (robocopy $ConfigSource $Dest /E ..., no /MIR), so it only ever adds/overwrites files that already exist from the config side; it never deletes anything the artifact mirror just placed. Because config lives in a folder tree the artifact mirror step never touches, there's no risk of a deploy deleting or overwriting it. Ops can edit these files directly on the server at any time; changes take effect on that service's next restart.

var swaggerEnabled = app.Environment.IsDevelopment() || app.Configuration.GetValue("Swagger:Enabled", false);
...
if (swaggerEnabled) { app.UseSwagger(); app.UseSwaggerUI(); }

Rollback

  • Re-run the workflow from an earlier commit (Actions → Deploy → Run workflow → choose the branch/tag/SHA to build from), or
  • Manually re-run Deploy-FHIRBridge.ps1 against a previously-downloaded artifact zip you've kept around.

There's no automatic artifact retention beyond GitHub's 14-day default (retention-days: 14 in deploy.yml) — increase it there for a longer rollback window.

systemd unit generation

Just like the Windows script only calls New-Service when the service doesn't already exist, the Linux script only writes /etc/systemd/system/<name>.service the first time — if the unit file is already there, it's left completely alone on every later deploy. A generated unit looks like:

[Unit]
Description=<DisplayName>
After=network.target

[Service]
Type=simple
WorkingDirectory=<DestDir>
ExecStart=/usr/bin/dotnet <DestDir>/<DllName>
Restart=on-failure
RestartSec=5
User=<ServiceUser>
[AmbientCapabilities=CAP_NET_BIND_SERVICE   ← Gateway only]
[CapabilityBoundingSet=CAP_NET_BIND_SERVICE ← Gateway only]

[Install]
WantedBy=multi-user.target

After writing a new unit, the script runs systemctl daemon-reload then systemctl enable <name> before starting it.

Stopping / starting

Instead of Get-Service/WaitForStatus, the script polls systemctl is-active <name> in a loop (once per second, up to ServiceStopTimeoutSeconds) after issuing systemctl stop / systemctl start, throwing if the expected state is never reached in time.

Then: 
sudo systemctl daemon-reload
sudo systemctl restart fhirbridge-gateway
Do this once per service, right after its first deploy — exactly mirroring the Windows flow of setting ASPNETCORE_URLS via services.msc after the first deploy creates that service.

Reusing Gateway.exe as a static portal host

Every non-prod environment decouples the portal from Gateway — unlike production, where Gateway serves the portal and proxies the API from the same origin/port, here fhirbridge-portal and demoapp-portal are each independently reachable on their own port. This needed zero new C# code: FHIRBridge.Gateway's existing Program.cs already does exactly two independent, config-driven things (see src/Gateway/FHIRBridge.Gateway/Program.cs:19-52) — serve static files if StaticFiles:RootPath is set, and proxy /api/**//swagger/** via YARP regardless. So the same published FHIRBridge.Gateway.exe is deployed three times per environment, in three different config-only roles:

Deploy folderRoleConfig
fhirbridge-portalStatic-onlyStaticFiles:RootPath pointed at this folder's own wwwroot\ subfolder (where the built portal lands); ReverseProxy left effectively unused.
fhirbridge-gatewayProxy-onlyStaticFiles:RootPath left empty — Gateway already just logs a warning and skips static serving in that case; ReverseProxy:Clusters:api-cluster:Destinations points at this environment's own Api instance port.
demoapp-portalStatic-onlySame as fhirbridge-portal, but serving the Demo app's portal build instead.

deploy/windows/Deploy-FHIRBridge-Environment.ps1 (sibling to the production-only Deploy-FHIRBridge.ps1, which it does not modify) implements this via two functions: Deploy-Service (the regular, one-executable-per-service case — used for Api, Worker, DemoApi, and the proxy-only Gateway) and Deploy-StaticPortal (mirrors the Gateway artifact and a built Angular site into a wwwroot\ subfolder alongside it, for the two static-only roles). Both reuse the same robocopy mirror + ConfigRoot-overlay pattern as the production script.

Unlike the production script, ASPNETCORE_URLS is not a manual post-deploy step here — each service's port comes straight from the environment's own port table, and Set-ServiceEnvironment writes it to that Windows Service's registry Environment value (REG_MULTI_SZ) every deploy, right before Start-Service. fhirbridge-api binds loopback-only (http://127.0.0.1:<port>, matching production's security posture); every other service binds http://+:<port>. fhirbridge-worker gets none, since it has no HTTP endpoint to bind at all.

The proxy-only Gateway's health check needs one added config route Gateway has no /health endpoint of its own, and its YARP config only proxies /api/** and /swagger/** by default — neither reaches Api's /health. Add a third route to this instance's appsettings.Production.json matching /health to the same api-cluster, so Deploy-FHIRBridge-Environment.ps1's health check (http://localhost:<gateway-port>/health) has something real to hit.

Triggers & chained approval gates

Each environment auto-deploys only from a blank commit whose message is the exact literal string Deploy, pushed to that environment's own branch — a commit with that message which isn't blank is deliberately ignored. Manual workflow_dispatch is always available too, on any branch, and skips the blank-commit check (an explicit manual run is already a deliberate action). 

git commit --allow-empty -m "Deploy"
git push origin develop   # (or main / quality / any branch, depending on the environment)

GitHub's native "required reviewers" per Environment only enforces any one of the assigned reviewers approving — not a true quorum. To genuinely require multiple distinct people, Staging and QA chain two sequential single-reviewer gate environments instead of one multi-reviewer one; Dev uses a single gate; Working has none:

guard→ staging-approval-1→ staging-approval-2→ deploy (Staging)
guard→ qa-approval-1→ qa-approval-2→ deploy (QA)
guard→ dev-approval-1→ deploy (Dev)
guard→ deploy (Working)

Each approval-N job's only purpose is its environment: protection rule — it has a single trivial step and exists purely to block until that environment's assigned reviewer clicks approve, before the next job in the chain can start.

Angular build configurations & CORS

Production's apiBase/fhirbridgeBase are intentionally empty (environment.prod.ts in both portal/ and Demo_TestApp/frontend/) because the portal is same-origin with its API there. Since every non-prod environment's portal is now genuinely cross-origin from its own API (different port), each got its own new Angular build configuration and environment file, mirroring the existing production/development pattern in both apps' angular.json:

New fileSets
portal/src/environments/environment.{staging,qa,dev,working}.tsapiBase → that environment's own Gateway origin (e.g. Staging: http://localhost:2003)
Demo_TestApp/frontend/src/environments/environment.{staging,qa,dev,working}.tshealthAppBase → that environment's own demo backend origin, fhirbridgeBase → that environment's own Gateway origin
CORS must be configured per environment or the portal can't call its API FHIRBridge.Api's CORS is already dynamic and config/DB-driven (DynamicPortalCorsPolicyProvider, reads Portal:AllowedOrigins — src/Api/FHIRBridge.Api/Program.cs:159-167 — and can be edited live via the admin UI with no restart), so no code change is needed, but each environment's Api instance must have that environment's portal origin (e.g. http://localhost:2000 for Staging) added to its allow-list, or the portal will fail every API call with a CORS error. Same idea for the Demo app backend's AllowedFrontendOrigin.

5.Known Gotchas & Lessons Learned

Real incident: missing column after a schema change The demo app backend has no EF Core migrations — it calls db.Database.EnsureCreated() at startup, which only creates the schema the very first time a database doesn't exist yet. It does not add columns to an already-existing database on subsequent runs. This caused a real production failure: a new field (ProviderLaunchContext) was added to WorkflowSettingsEntity for a later feature, but the production HealthAppDb database had already been created before that change — so its WorkflowSettings table never got the new column. The first request that touched it (GET /api/patient-standalone-settings) threw SqlException: Invalid column name 'ProviderLaunchContext', which — because this app has no exception-handling middleware — surfaced to the browser as a dropped connection / failed fetch rather than a clean 500. 
ALTER TABLE [WorkflowSettings]
ADD [ProviderLaunchContext] nvarchar(max) NOT NULL DEFAULT N'';
Takeaway: every time a field is added to an entity in this app, production (and any other pre-existing database) needs the same kind of manual ALTER TABLE, or the same class of error will recur the moment something queries the new column.
Robocopy exit codes Robocopy returns exit codes 0–7 for various flavors of success (e.g. 2 = "extra files purged"), not just 0. The deploy script checks for ≥8 as the actual failure threshold and explicitly resets $global:LASTEXITCODE to 0 afterward — otherwise a successful-but-nonzero robocopy exit could leak into the script's own final exit code and make GitHub Actions report a false failure.
Generic browser error messages aren't diagnostic Both Swagger UI's "Failed to fetch — CORS / Network Failure / URL scheme…" message and Chrome's net::ERR_EMPTY_RESPONSE are shown for a wide range of underlying causes. Neither one, by itself, tells you whether the real cause is CORS, a crashed process, a stuck SQL transaction, or a missing column. Isolate with a control request (does a totally unrelated endpoint on the same origin work?) and check the server side directly (service status, SQL Server blocking-session queries, event logs) before assuming any one specific cause.
appsettings.Production.json is never in the repo or the artifact It's intentionally excluded from git entirely and provisioned by hand, once, directly on the server (now under ConfigRoot). CI never sees or manages these files.
