FHIR Cardinality Mapping Validator

Expanded static prototype for design-time validation across many FHIR resource types, scalar fields, repeating arrays, and N-level nested nodes into destination tables.

Mapping Row Builder

Select a resource and source field. If the field crosses any FHIR element with max cardinality "*", the validator asks how the array should be handled.

If custom path is filled, it overrides the selected source field and detects any [0] or [*] as a repeating FHIR node.

Sample Destination Preview

Generated from the configured mapping rows and each row's Array handling choice, using synthetic sample data. First item only → one value; Repeat parent row → multiple rows; Separate destination → child table with a parent foreign key; Store as JSON → a JSON array in one cell; Reject if multiple → single value flagged. Use the button to export a standalone example HTML file.

Array Handling Options

Use first item only Saves one row per parent resource. Example: $.address[0].city.
Repeat parent row Creates multiple destination rows when the array has multiple items. Parent scalar fields repeat.
Separate destination/table Recommended for normalized SQL. Example: Patient and PatientAddress.
Store array as JSON Keeps the full repeating structure in one JSON column for staging or analytics.

Static Cardinality Metadata Snapshot

This prototype now includes an expanded static metadata snapshot across 100+ FHIR R4 resource types — foundation/infrastructure (Bundle, MessageHeader, OperationOutcome, Parameters, Subscription, Binary, Basic, Linkage), terminology/conformance (ValueSet, CodeSystem, ConceptMap, StructureDefinition, CapabilityStatement, Questionnaire), administrative, clinical, medication, scheduling, billing/financial (ClaimResponse, CoverageEligibilityRequest/Response, PaymentReconciliation, Invoice, ChargeItem, Contract, InsurancePlan), definitional/knowledge (PlanDefinition, ActivityDefinition, Measure, MeasureReport, Library), consent, provenance, audit, device, specimen, imaging, questionnaire, and workflow resources. Every resource also carries nested/complex extension nodes (extension.extension.valueString, modifierExtension, extension.valueCodeableConcept.coding.code) and deep N-level paths up to 5–6 levels (e.g. InsurancePlan.plan.specificCost.benefit.cost.amount.value, MeasureReport.group.stratifier.stratum.population.count, ConceptMap.group.element.target.dependsOn.value). It also keeps generic JSON-path array detection for any N-level custom path. Backend implementation should use generated FHIR StructureDefinition snapshots instead of hand-maintained metadata.
