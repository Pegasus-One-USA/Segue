# Source Connection / Source Configuration Split — Context & Implementation Plan

> **Audience:** Claude Code (or any developer) told to "implement with this context file."
> **Created:** 2026-07-28, branch `feature/governancelogging`.
> **Context:** Today, `SourceConnection` bundles two unrelated concerns into one row: reusable connection identity (URL, auth, JWKS/private key ref, audience/client details, interactive launch settings) and per-workflow retrieval configuration (search criteria, resource types, scopes, pagination, retry/timeout, bulk-export options, sync cursor). Because retrieval config lives *on* the connection, the portal's workflow builder forks a brand-new `SourceConnection` — cloning auth/URL/JWKS along with it — every time a user only changes search criteria for one workflow. This document is the complete plan to split those concerns so a connection is created once and reused across workflows, while retrieval/search config stays independently editable per workflow.

## Standing authorization — read before starting

When told to "implement with this context file," proceed through the items below in order **except** where a section is marked **⚠ Decision required** — those need a human answer first.

Three design decisions were already locked with the user on 2026-07-28 (do not re-litigate these):
1. `WebhookConfiguration` moves to reference the new workflow-specific entity (`SourceConfiguration`), not the reusable `SourceConnection` — webhook filtering is workflow-specific.
2. OAuth `Scopes` move off `SourceConnection.Authentication` and onto `SourceConfiguration`, one scope set per workflow. Token-acquisition code unions scopes across every active `SourceConfiguration` referencing a connection at request time (read-time union), replacing the old write-time aggregation (`IEpicSourceConnectionScopeSyncService`/`EpicSourceConnectionScopeSyncService`).
3. The EF migration backfill is **1:1 only** — every existing `SourceConnection` gets exactly one `SourceConfiguration` carrying over its old `Retrieval`/`Scopes`/webhook data. No attempt to detect and de-duplicate already-forked connections; that's a manual portal follow-up, not part of this migration.

**Verification discipline**: for anything touching EF migrations or real DB state, verify against a DB copy or the docker-compose SQL Server (`localhost,1433`) before calling a slice done — do not assume a migration's `Up()`/backfill SQL is correct without running it. For runtime/auth changes (token scope union), write a temporary `_Scratch*.cs` test, run it, confirm, then delete it, per the verification pattern in [11-destination-schema-ownership-plan.md](11-destination-schema-ownership-plan.md).

**Slice 3 (Runtime Plane / portal wizard) — partially done (2026-07-28), portal-only, no backend `SourceConfiguration` entity involved.**

A second critical discovery while starting this slice: the Runtime Plane **already has a per-node override mechanism** that avoids the duplication problem for two of the fields that actually matter, without needing the `SourceConfiguration` entity introduced in Slices 1-2 at all:
- `SourceNodeExecutors.ExecuteAsync` (`src/Runtime/FHIRBridge.Runtime.Infrastructure/Workflows/Executors/SourceNodeExecutors.cs:165-178,182`) reads a `"Resources"` and a `"searchParameters"`/`"Search criteria"` key directly off the workflow node's own JSON config, ahead of anything resolved from the referenced `SourceConnection` — this is a real, already-shipped per-workflow override, not something that needed building.

So the wizard's fork-on-any-edit behavior was **not** a runtime necessity for Resources/Search Criteria — it was purely `epic-audience-form.component.ts`'s `hasExistingChanged()` treating every form field as connection-level, with no awareness that two of them already have a working per-node override. Given this, the actual fix needed no new node-config schema and no coupling to `SourceConfiguration` — it's a single, contained change:

- `hasExistingChanged()` (`portal/src/app/components/epic-source-wizard/epic-audience-form/epic-audience-form.component.ts`) now excludes `resources`, `subscriptionResourceType`, `webhookResourceType`, `searchRestResourceType`, `bulkExportResourceType`, and `searchCriteria` from its diff (alongside the pre-existing `clientSecret` exclusion), so editing only these fields while in "Existing Source" mode reuses the connection instead of forking. Every other field (Base URL, auth/JWKS, page size/sort/retry/timeout, bulk-export settings, schedule) still forks on edit — unchanged, and correctly so, since those genuinely have no per-node override today.

**Regression found and fixed (2026-07-28): "Epic scopes are required" when creating a Backend System connection in Settings.** Backend System (and Standalone, EHR Launch, Patient are unaffected — see below) has `showResourcePicker: false` in `AUDIENCE_FIELD_CONFIG` — it has no shared resource picker, and normally derives its scopes from the Data Retrieval Method section's own Resource Type control (`activeRetrievalResourceTypes()`). Hiding that whole section in entity mode (the fix above) left `activeRetrievalResourceTypes()` always empty there, so `scopeString()` and `wizard.service.ts`'s entity-mode save both silently sent `scopes: []`, tripping `ConfigurationService.ValidateEpicSourceConnection`'s `"Epic scopes are required."` check on every Backend System (and Standalone) connection saved from Settings.

Fix: `showResourcePickerSection` computed (`audienceConfig().showResourcePicker || wizardMode() === 'entity'`) — entity mode now always reads resource types from the `resources` FormControl (`selectedResources()`) instead of `activeRetrievalResourceTypes()`, in `scopeString()`, the `save()` `wiz.resources.set(...)` call, and the `syncValidators()` required-field check. This works because `resources` is already correctly populated in entity mode regardless of audience — `WizardService.openEntity()` seeds it from the existing connection's `retrieval.resourceTypes` (or `DEFAULT_RESOURCES` for a new connection) before the component even initializes; the bug was purely in later code reading the wrong source, not a missing value. Canvas mode (the workflow wizard) is completely unaffected — `showResourcePickerSection()` reduces to the original `audienceConfig().showResourcePicker` there.

**Verified**: `tsc --noEmit` and `ng build` both clean. Reproduced the exact bug via direct API call (`scopes: []` → 400 `"Epic scopes are required."`), then confirmed the fixed behavior (`scopes` populated from `DEFAULT_RESOURCES` → `system/{Resource}.rs`, matching what the fixed component now computes) → 201 Created. Test connection created and deleted afterward, no residue.

**Second regression found and fixed (2026-07-28, same day): "Create Source Connection" did nothing for Backend System + manual JWKS.** Found and verified via a real Playwright-driven browser session (finally — working credentials made this possible), not just code trace. `clearInapplicableFields()` (called on every audience-dropdown change) has always cleared the `resources` control to `[]` when switching from an audience with a resource picker to one without (`if (prevCfg.showResourcePicker && !nextCfg.showResourcePicker) { patchValue({ resources: [] }) }`) — harmless before, since Backend System never needed `resources` populated (canvas mode used `activeRetrievalResourceTypes()` instead). But the form defaults to `provider-ehr-launch` (`showResourcePicker: true`) on open, and the very first thing anyone does when creating a Backend System connection is switch the Epic Audience dropdown away from that default — which now, after the first regression fix above, immediately blanks the just-required `resources` control with no picker UI to refill it. `form.invalid` silently blocked `save()` — no error, no toast, no network request, exactly the "click Create, nothing happens" symptom, since `focusFirstInvalidField()` has no DOM element to scroll to for a control with no rendered UI.

Fix: `clearInapplicableFields` now computes `prevShowsResources`/`nextShowsResources` as `cfg.showResourcePicker || wizardMode() === 'entity'` (the same override as `showResourcePickerSection`) — in entity mode both are always true regardless of audience, so neither clearing branch ever fires there; canvas mode is unaffected.

**Third finding, resolved (2026-07-28, same day): "Private Key / JWKS URL" didn't autopopulate when picking "Existing Source" in the canvas wizard.** Root cause distinct from the two regressions above — this was never a regression from today's work, and (per an explicit pre-existing code comment in `workflow-builder.component.ts:348`) it was a *deliberate* design choice: the JWKS URL is never sent to the backend (`SourceConnection` has no such column) because the real URL for a Generated/Imported key is only knowable once a build assigns a connection id, so it's corrected into the *workflow node's own* `ConfigurationJson` after the fact (`reconcileGeneratedJwksUrls`). That mechanism only covers connections built through the canvas wizard, which always have a node to store the correction on — a Settings-created connection has no node at all, so cloning it via "Existing Source" had nowhere to recover the value from.

Chose the minimal, no-backend-change fix (confirmed with the user rather than reversing the documented design): `resolvedSourceConnectionId` now also resolves from `selectedExistingId()` when `sourceMode() === 'existing'` (previously only checked entity-mode/editing-node paths), and the `liveJwksUrl` auto-fill effect now also fires whenever `keyLoadedFromExistingConnection()` is true — not just for Generate/Import key sources — since the backend has no marker distinguishing how a cloned connection's key was originally obtained, and leaving `jwksUrl` (a field required whenever auth method is JWT) blank on every clone risked reproducing the exact "click Update, nothing happens" bug from the `resources` fix. Auto-filling FHIRBridge's hosted URL is exactly correct for Generate/Import, and a visible, editable placeholder to overwrite for Manual/external — strictly better than a blank, silently-blocking required field either way. Hint text updated to say as much.

**Verified live in the browser** (Playwright): selected "Existing Source" → an Epic Backend System connection with a previously-configured key → `jwksUrl` auto-filled to `http://localhost:5000/api/v1/source-connections/{id}/.well-known/jwks.json`, field valid (`ng-invalid: false`), matching hint text displayed. Also independently confirmed, via temporary diagnostic logging (removed after use), that the save button *not* closing the dialog in this same test was caused by two unrelated, pre-existing things — not the JWKS fix: `authzEndpoint` depends on a live network call to Epic's real sandbox `.well-known/smart-configuration` completing (a timing race in fast automated clicking, not a bug a human would hit), and `runMode` is a field that has always required manual selection for Search REST regardless of new-vs-cloned (visible, clearly marked required, not a silent failure). Neither `jwksUrl` nor `resources` appeared in the invalid-controls list after the fix.

**Fourth finding, resolved (2026-07-28, same day) — the actual "BS Gaurav → BS Gaurav-1" duplication the user originally asked to eliminate.** This is the deepest and most consequential of today's fixes: a direct, structural consequence of narrowing Settings to connection-only fields (the fix earlier in this document). A connection created via Settings now always has `retrieval: null` — by design, exactly as intended — but the canvas wizard's retrieval section is *not* hidden there (only Settings hides it), so cloning any Settings-created connection via "Existing Source" left `retrievalMethod` itself (not just `runMode`) required-and-blank, with a cascade behind it: the per-method Resource Type control (`searchRestResourceType` etc.) was also never defaulted when `retrieval` was null. The user was forced to configure retrieval from scratch to get past validation on *every single clone* of *every* Settings-created connection — and doing so, even by picking values that matched what a similar connection might have, always diffed against a blank baseline and forced a fork. This is what produced "BS Gaurav-1": not an edge case, but the *guaranteed* outcome of cloning any connection built through the very page this whole plan set out to fix.

Fix, in `populateFormFromSourceConnection`:
- `retrievalMethod` now resolves to `resolvedRetrievalMethod = retrieval?.retrievalMethod || 'search-rest'` — a sensible default (matching the method used by the large majority of real Backend System/Standalone sources) instead of `''`.
- The per-method Resource Type control (looked up via `resolvedRetrievalMethod`, not the original possibly-absent one) defaults to `FHIR_RESOURCES` (the platform's curated MVP1 set — the same constant already used elsewhere for this exact purpose) when the original has no resource types, instead of being skipped entirely.
- `runMode` resolves to `'incremental'` or `'manual'` (never blank) based on `incrementalSyncEnabled` — `'manual'` when false, since it is the only Run Mode value requiring no further fields (Schedule/Poll Frequency and the Full Refresh calendar block only appear for `'incremental'`/`'full'`), so restoring it never forces an edit the way defaulting to `'full'` would.
- One remaining, *legitimate* required field surfaces as a side effect: Backend System + `search-rest` + `Patient` in the resource set requires non-empty Search Criteria (a real Epic constraint — unscoped Patient search is rejected outright, business-rule 59159). This is fine as-is: `searchCriteria` was already excluded from `hasExistingChanged()`'s diff by the very first fix in this document, so filling it in — which the user must do regardless, to satisfy Epic itself — still never forces a fork, and the field is visibly rendered (not hidden), so `focusFirstInvalidField()` correctly surfaces it instead of silently blocking.

**Verified live end-to-end** against the exact connection the user reported the bug against (`BS Gaurav`, `e050a562-...`, a real Settings-created connection with `"retrieval": null` confirmed via direct API read): counted 45 total source connections beforehand, cloned `BS Gaurav` via "Existing Source" in the canvas wizard, confirmed `retrievalMethod` auto-resolved to `search-rest`, filled in only the one legitimately-required Search Criteria field, clicked save — dialog closed (success), re-counted source connections: still 45, `BS Gaurav-1` did not gain a `BS Gaurav-2` sibling. Confirms the fix closes the loop on the user's own reported reproduction, not just a synthetic test case.

**Known, pre-existing, unrelated limitation surfaced along the way** (documented, not fixed today): pageSize/sortOrder/retryPolicy/timeoutSeconds/bulk-export settings/schedule configured in the wizard for a *reused* connection are written into the workflow node's own field bag but never actually read by `SourceNodeExecutors` at runtime (which only reads `"Resources"` and `"Search criteria"` from node config) — they only take effect when a fork creates a new connection whose own `Retrieval` gets populated from them. This is the same Runtime Plane gap already noted as "not started" below; today's fix does not change this, it only stops the *unnecessary* forking that was happening on every clone regardless of whether these fields were ever touched.

**Fourth finding, resolved (2026-07-28, same day): cloning a Settings-created Backend System connection via "Existing Source" — with zero edits — still forked a new connection (e.g. "BS Gaurav" → "BS Gaurav-1").** The deepest and most structural of today's findings. Root cause: a connection created in Settings has `retrieval: null` entirely (correct, by the earlier Settings-narrowing fix) — but `populateFormFromSourceConnection` left several *required* fields blank when cloning such a connection into the canvas wizard (where the Data Retrieval Method section is NOT hidden, unlike Settings): `retrievalMethod` itself (no fallback — defaulted to `''`), the per-method Resource Type control (`searchRestResourceType` etc., only set when the original had `retrieval.resourceTypes`), and `runMode` (never set at all — no backend field exists for it, only the derived `incrementalSyncEnabled` boolean). The user was forced to pick *something* for each to pass validation, and picking anything at all — even the value the original effectively had — flipped `hasExistingChanged()` to true purely because the untouched baseline was `''`/empty, forking a new connection on **every single clone** of a Settings-created Backend System/Standalone source.

Fix — `populateFormFromSourceConnection` now resolves a complete, self-consistent, non-forcing baseline whenever retrieval data is absent (or incomplete):
- `retrievalMethod` defaults to `'search-rest'` (the common case) instead of `''`.
- The per-method Resource Type control defaults to `FHIR_RESOURCES` **excluding `'Patient'`** — not because Patient is special to exclude, but because Backend System + Search REST + Patient is the one combination Epic rejects outright unscoped (`searchCriteriaRequiredForPatient`), which would have required fabricating a Search Criteria value with no safe way to invent one. Excluding it sidesteps that cascade without faking data.
- `runMode` defaults to `'manual'` whenever `incrementalSyncEnabled` isn't explicitly `true` — the only Run Mode value requiring no further fields (Schedule/Poll Frequency and the Full Refresh calendar block only appear for `'incremental'`/`'full'`).

**Verified live end-to-end**, iteratively, using temporary diagnostic logging (added and removed twice as each layer of the cascade surfaced, confirmed absent from the final diff): cloned "BS Gaurav" (a real Settings-created connection) via "Existing Source" with **zero edits**, clicked Save — dialog closed successfully (no fork), and the canvas confirmed *"BS Gaurav added to the canvas"* — not a `-1` suffix. Full solution `tsc --noEmit` and `ng build` both clean with no diagnostic code remaining.

**Still not started**:
- `WebhookConfiguration.SourceConnectionId` → `SourceConfigurationId` repoint (deferred — `WebhookConfiguration` doesn't read `Retrieval`/`Scopes` at all today, so it doesn't block anything OAuth-critical).
- Dropping the now-redundant `Retrieval`/`Scopes` columns from `SourceConnections` (blocked on deciding whether the Runtime Plane should ever fully cut over to per-node/per-workflow `SourceConfiguration` records for the fields that still lack a per-node override — page size, sort, retry, timeout, bulk-export settings, schedule. Given the discovery above, this may not be worth pursuing at all: extending per-node overrides to those fields the same way Resources/Search-criteria already work would close the remaining gap with less risk than fully wiring `SourceConfiguration` into the Runtime Plane's resolution path — worth a fresh design conversation before committing to either approach).

**Blast radius measured 2026-07-28**: `SourceConnectionId`/`.Retrieval`/`Authentication.Scopes`/`UpdateScopes`/`RecordRetrievalSync` appear in 108 files. Most are auto-generated EF migration `*.Designer.cs`/snapshot files (regenerate via tooling, never hand-edit) or test files. Real production call sites (~25-30 files) span `FHIRBridge.Application` (`ConfigurationService`, `ConfigurationMapper`, DTOs), `FHIRBridge.Infrastructure` (`SourceConnectionRuntimeResolver`, `SourceConnectionSyncCursorStore`, `SourceConnectionTestService`, `SourceCapabilityDiscoveryService`, `EpicSourceConnectionScopeSyncService`, `ConfiguredPipelineService`, `ScheduleEvaluationService`, `FhirSubscriptionManagementService`, `RouteToWorkflowGraphProjection`, `InteractiveSourceAuthorizationService`, `SourceJwksService`), `FHIRBridge.Runtime.*` (`FhirSourceConfiguration`, `FhirSourceConnectorBase`, `SourceNodeExecutors`, `SmartAuthorizationCodeTokenProvider`, `CompositeFhirAccessTokenProvider`, `WorkflowExecutionContext`), and `Api`/`Worker` (`OAuthController`, `PatientStandaloneLaunchController`, `SubscriptionsController`, `WorkflowEndpoints`, `EndpointHealthCheckWorker`).

Given that size, this plan is deliberately **additive-first**: land new structure without breaking any of those ~25-30 call sites, then cut over consumers in a controlled follow-up slice, rather than a single 100+ file rename.

## 2. Target domain model

### `SourceConnection` (redefined — reusable, trimmed)
- `Name`, `SourceSystemType`, `ApplicationType?`, `BaseUrl`, `IsEnabled`
- `Authentication`: `AuthenticationType`, `ClientId`, `TokenEndpoint`, `ClientSecret`, `PrivateKey`, `KeyId` — **no `Scopes`**
- `Interactive?`: unchanged (`RedirectUris`, `LaunchUrl`, `TrustedIssuers`, `PatientSelectionMethod`, `PostLaunchRedirectUri`, `LaunchDisplayMode`)

### `SourceConfiguration` (new — one per workflow use of a connection)
- `ConnectionId` (FK → `SourceConnection`, required)
- `Name` (workflow-instance display name)
- `Scopes[]` (moved from `SourceConnection.Authentication.Scopes`)
- `Retrieval?`: unchanged shape, moved wholesale from `SourceConnection.Retrieval`

### FK repoints (Slice 2, not Slice 1 — see §4)
- `MappingProfile.SourceConnectionId` → `MappingProfile.SourceConfigurationId`
- `WebhookConfiguration.SourceConnectionId` → `WebhookConfiguration.SourceConfigurationId`
- `SourceCapabilityProfile`, `Governance/SmartLaunchLog` stay pointed at `SourceConnection` (capability discovery and launch audit are connection-level, not workflow-level)
- `PipelineRunRouteExecution` gets an **added** `SourceConfigurationId` snapshot column alongside its existing `SourceConnectionId` (both kept — it's a denormalized history snapshot, not a live FK)

### Runtime scope union (Slice 2)
Token acquisition (`FhirSourceConnectorBase` / wherever the access token is actually requested) unions `Scopes` across every active `SourceConfiguration` referencing a given `SourceConnection`, instead of reading a single aggregated value off the connection. Token cache keys (currently keyed by `SourceConnectionId` in `DistributedFhirAccessTokenCache`) need re-evaluation — if two `SourceConfiguration`s on the same connection request different scope subsets, a single cache key per connection would serve one workflow a token missing scopes the other needs. Likely resolution: cache key becomes `(SourceConnectionId, sorted scope set hash)`, not `SourceConnectionId` alone. **⚠ Decision required before Slice 2**: confirm this cache-key change is acceptable, since it changes token-request/cache-hit behavior for every existing Backend Services connection.

## 3. Slice 1 — additive, non-breaking (this session)

Goal: land the new table/entity with zero impact on any existing compiled call site. Solution builds and behaves identically to today after this slice.

1. **Domain**: add `SourceConfiguration` entity (`src/FHIRBridge.Domain/Entities/SourceConfiguration.cs`) holding `ConnectionId`, `Name`, `Scopes[]`, `Retrieval?`. Do **not** yet remove `Retrieval`/`Scopes` from `SourceConnection` — both live in parallel this slice.
2. **EF Core**: new `SourceConfigurationConfiguration` (owns `Retrieval`, plain `Scopes` array column, FK to `SourceConnection`). Register `DbSet<SourceConfiguration>` on `FHIRBridgeDbContext`.
3. **Migration**: creates `SourceConfigurations` table; backfills exactly one row per existing `SourceConnection` (copying `Retrieval` + `Authentication.Scopes` verbatim); adds a **nullable** `MappingProfile.SourceConfigurationId` column, populated by the backfill (`SourceConfigurationId = ` the new row created for that mapping's existing `SourceConnectionId`). Existing `MappingProfile.SourceConnectionId` and `SourceConnection.Retrieval`/`Authentication.Scopes` are untouched — nothing reads the new column yet, so this is safe to deploy standalone.
4. **Verification**: run migration against docker-compose SQL Server, confirm one `SourceConfigurations` row per pre-existing `SourceConnections` row, confirm `MappingProfile.SourceConfigurationId` populated correctly, confirm full solution build + `dotnet test` pass counts unchanged from baseline.

## 4. Slice 2 — cutover (follow-up, not this session)

Repoint the ~25-30 real call sites to read/write through `SourceConfiguration` instead of `SourceConnection.Retrieval`/`Scopes`, implement the read-time scope union (pending the ⚠ decision above), drop the now-dead `Retrieval`/`Scopes` columns from `SourceConnections`, drop the old `MappingProfile.SourceConnectionId` column, repoint `WebhookConfiguration`.

## 5. Slice 3 — portal (follow-up, not this session)

`epic-audience-form.component.ts`'s fork-vs-reuse logic splits by field group: editing only retrieval/scope fields updates/creates a `SourceConfiguration` and reuses the existing `SourceConnection` unchanged; editing connection fields (URL/auth/JWKS) still triggers the fork-or-share prompt, but now only duplicates the small connection record. Settings → Source Connections page narrows to connection-only fields.
