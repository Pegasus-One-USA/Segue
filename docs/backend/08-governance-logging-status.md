# Governance & Observability Logging — Implementation Status

> **Audience:** the next developer (human or Claude) picking up governance/audit logging work.
> **Last updated:** 2026-07-18 (rev. 7 — Tier 4, the final tier of the "100% parity" plan, `docs/backend/09-governance-logging-100-percent-plan.md`: Data Lineage with gated/audited PHI reveal, and a real Alert Engine), branch `feature/rolebasedHealthapp` (or successor).
> **Why this doc exists:** on 2026-07-17 the entire prior audit/lineage logging subsystem (`UserActivityAuditLog`, `OperationalAuditLog`, `ResourceLineageEntry`, `FieldLineageEntry` + portal pages) was removed (`e14a4cf2`). This left `docs/compliance/policies/10-audit-controls.md` and `docs/compliance/hipaa-soc2-control-matrix.md` describing controls (§164.312(b) Audit Controls, hash-chained audit trail) that no longer existed. Everything below was built to close that gap, from a combined 13-phase plan (Phase 0 – Foundation through Phase 12 – Testing). **Both compliance docs have since been updated (rev. 3) to reference the real tables — no more stale `UserActivityAuditLog` mentions.**

## ⚠️ Operational gap — updated status (rev. 4)

**`src/Worker/FHIRBridge.Worker/Program.cs` now hosts five services**: the legacy polling `Worker` (calls `IConfiguredPipelineService.StartAsync` **directly**, synchronously — this is the scheduler that actually runs in production), `EndpointHealthCheckWorker`, and — new in rev. 4 — `RetentionPurgeWorker` and `AuditChainVerificationWorker` (both were themselves previously-built-but-never-hosted dormant classes; see below). It still does **not** register `ScheduleDispatcherWorker`, `PipelineRunCommandProcessor`, or `WebhookIngestionCommandProcessor` — that queue-based path remains dormant, and this is now a confirmed decision, not an open question.

**Architecture decision made (rev. 4):** presented to the user as a real design choice (not a logging task) — keep `Worker.cs`'s direct-call polling as the one true scheduler, versus migrating to the queue-based path. **Decision: keep polling; mark the queue path as dead code.** `ScheduleDispatcher.DispatchDueRunsAsync` claims due work via `IScheduleEvaluationService.ClaimDueRunsAsync` (an atomic claim), while `Worker.RunDueRoutesAsync`'s due-check (`ScheduleExpressionMatcher.IsDue`) has no claiming/locking at all — running both simultaneously would very likely **double-process the same due routes** around the same tick. Rather than delete the dormant classes outright, `ScheduleDispatcher`/`ScheduleDispatcherWorker`/`PipelineRunCommandProcessor`/`WebhookIngestionCommandProcessor`/`Hl7MllpListenerService` each received an explicit `<remarks>` doc block stating they are **NOT CURRENTLY REGISTERED / NOT CURRENTLY HOSTED** and why, so a future reader doesn't mistake "compiles and looks wired up" for "actually runs." A second, more urgent issue was discovered and documented in the same pass: `WebhookIngestionController` already enqueues via `IWebhookIngestionDispatcher` in production with **no consumer running in any transport configuration** — i.e. inbound webhooks are silently accepted and then never processed. That's a functional gap, not just a logging one, and is called out separately so it doesn't get lost.

**What was actually fixed (rev. 3):** `Worker.RunDueRoutesAsync` and `Worker.RunDueWorkflowsAsync` — the code that's actually running — now log to `SchedulerHistory` (`SchedulerId = "worker:poll"` or `"worker:workflow:{id}"`) and, for the route path, to `ErrorLog` on failure. This also fixed a latent bug: previously an exception from `pipelineService.StartAsync` had no catch anywhere between it and `BackgroundService.ExecuteAsync`, so a single failed run would **permanently fault the whole polling worker** (it would silently stop ticking forever). It's now caught, logged, and the worker keeps ticking on the next interval — matching the resilience `RunDueWorkflowsAsync`'s per-workflow catch already had.

**Still genuinely empty, and correctly so:** `RetryHistory`. The live `Worker.cs` path has no retry logic at all (unlike `PipelineRunCommandHandler`/`WebhookIngestionCommandHandler`, which use `MessageRetry.ExecuteAsync` but only run on the dormant queue path) — there is nothing to retry-log until the scheduling-path decision above is made one way or the other.

## Data model — all tables that exist today

All in `src/FHIRBridge.Domain/Entities/Governance/`, configured in `src/FHIRBridge.Infrastructure/Persistence/Configurations/Governance/`, migrations `AddGovernanceLogging` → `AddOperationsLogging` → `AddExportNotificationLogging` → `AddValidationEndpointHealthLogging` → `AddSmartLaunchLogging` → `AddConfiguredPipelineRunCorrelationId` (all under `src/FHIRBridge.Infrastructure/Persistence/Migrations/`). The last one isn't a new governance table — it adds a `CorrelationId` column to the pre-existing `ConfiguredPipelineRunRecord`/`ConfiguredPipelineRuns`.

| Table | Append-only? | Purpose | Written from |
|---|---|---|---|
| `AuditLogs` | Yes, hash-chained | Every config/entity change (Created/Updated/Deleted) | `AuditingSaveChangesInterceptor` (automatic, zero call-site changes) |
| `DataAccessLogs` | Yes | Every patient/resource governance decision (allowed/denied), PHI-free | `ConfiguredPipelineService.PrepareResourcesForRouteAsync` |
| `AuthenticationLogs` | Yes | Login/logout/lockout/MFA (local) + SSO login success/failure + OAuth token issuance/refresh for source connections (`AuthenticationType = "OAuth:{grantType}"`, `UserEmail` field repurposed to hold the source connection name — there's no dedicated column for that, and it wasn't worth a 14th table for one field) | `LocalAuthService`, `SsoAuthService`, `CompositeFhirAccessTokenProvider.GetAccessTokenAsync` (single dispatch point for every vendor/grant-type token acquisition) |
| `SmartLaunchLogs` | Yes | SMART on FHIR launch completing (EHR/Standalone/Workflow) — no portal user involved | `InteractiveSourceAuthorizationService.CompleteAsync` |
| `SecurityEvents` | No (`Resolved` flag is mutable) | Lockout thresholds, anomalies | `LocalAuthService` |
| `SchedulerHistory` | Yes | Scheduler dispatch decisions | **Live:** `Worker.RunDueRoutesAsync`/`RunDueWorkflowsAsync` (the actual running scheduler). Also written by the still-dormant `ScheduleDispatcher` if that path is ever enabled. |
| `RetryHistory` | Yes | Retry attempts against transient failures | `PipelineRunCommandHandler`, `WebhookIngestionCommandHandler` — **still dormant**, only reachable via the unregistered queue-based path (see gap above) |
| `ErrorLogs` | Yes | Unhandled exceptions | **Live:** Api global exception handler, `Worker.RunDueRoutesAsync`/`RunDueWorkflowsAsync`. Still dormant: `PipelineRunCommandProcessor`/`WebhookIngestionCommandProcessor` (same reason as `RetryHistory`). |
| `ApiRequestLogs` | Yes | Every outbound HTTP call (method/URL-no-query-string/status/duration) | `ApiRequestLoggingHandler`, global via `ConfigureHttpClientDefaults` — **this one is live**, covers all HttpClients regardless of the gap above |
| `ExportHistory` | Yes | Every destination write completing | `ConfiguredPipelineService.ExecuteRouteAsync` |
| `NotificationHistory` | Yes | Outbound notifications — **Email only**, the one real channel that exists | `EmailDeliveryStrategy` |
| `ValidationFailureLogs` | Yes | US-Core/data-quality normalization warnings, PHI-free | `ConfiguredPipelineService.PrepareResourcesForRouteAsync` (via `normalizationResult.Warnings`) |
| `EndpointHealthChecks` | Yes | Periodic connectivity checks — **source connections only** | `EndpointHealthCheckWorker` (disabled by default: `EndpointHealthCheck:Enabled`) |

Foundation: `FHIRBridge.Governance` (new BuildingBlocks project) — `IGovernanceLogger` (one method per category above, not per entity/resource type), entry DTOs in `GovernanceEntries.cs`. `EfGovernanceLogger`/`NullGovernanceLogger` in `src/FHIRBridge.Infrastructure/Governance/` implement it depending on whether a DB is configured.

`IAppendOnlyEntity` (new marker interface, `FHIRBridge.SharedKernel.Abstractions`) + a guard in `AuditingSaveChangesInterceptor` throws on any Modify/Delete against the "Yes" rows above.

## Phase-by-phase detail

### Phase 0 — Governance Foundation Library (~70%)
**Done:** `IGovernanceLogger` interface, all entry-DTO records, DI registration (Ef/Null variants for DB-present/absent).
**Not done:** a dedicated `IExecutionContext`/`ICorrelationContext` (AsyncLocal-based) so correlation flows automatically through arbitrary call chains — today correlation is threaded manually as method parameters (works, but every new call site has to remember to pass it). No `GovernanceMiddleware`. No generic `IEventPublisher` for SIEM/webhook export.

### Phase 1 — Schema (~85%)
**Done:** the 13 tables listed above.
**Not done:** `DataLineage` table (deliberately deferred — see below). `ConfigurationSnapshot` table (not needed: Version History reuses `AuditLogs`' existing `OldValueJson`/`NewValueJson`, see Phase 8). Metadata/reference tables (`EventTypes`, `SeverityLevels`, `AlertRules`, `AlertRecipients`) — not needed yet since no Alert Engine exists.
**Resolved (rev. 3):** `ConfiguredPipelineRunRecord` now has a `CorrelationId` column (migration `AddConfiguredPipelineRunCorrelationId`) — the run-header record itself is correlation-searchable now, not just the governance rows generated during the run. Threaded through `ConfiguredPipelineRunDto` → `EfConfiguredPipelineRunRepository`; `ConfiguredPipelineService.CompleteRunAsync` already had `correlationId` in scope, it just wasn't being persisted before.

### Phase 2 — Auth + Config + Data Access (~100%)
**Done:** `LocalAuthService` logs login/logout/lockout/MFA failure. `AuditingSaveChangesInterceptor` automatically captures every `IAuditableEntity` change — this is genuinely zero-touch: a new config entity type gets audit coverage for free, no call-site change needed. `ConfiguredPipelineService` logs every governance allow/deny decision. `SsoAuthService.LoginAsync` logs to `AuthenticationLogs` (token-validation failure, "no enabled account linked" failure, success — `AuthenticationType = "SSO:{Provider}"`). `InteractiveSourceAuthorizationService.CompleteAsync` (the SMART on FHIR token-exchange step, shared by EHR launch/standalone/workflow launch) logs to `SmartLaunchLogs` on success/failure, classified by `DetermineLaunchType`.
**Also done (rev. 3):** OAuth token issuance/refresh. `CompositeFhirAccessTokenProvider.GetAccessTokenAsync` — the single dispatch point every vendor/grant-type token acquisition funnels through (fresh mint or refresh on a cache miss against `DistributedFhirAccessTokenCache`) — now logs success/failure to `AuthenticationLogs` (`AuthenticationType = "OAuth:{grantType}"`). One field-reuse tradeoff worth knowing about: there's no Segue user for this event, so the source connection's name goes in the `UserEmail` slot rather than adding a 14th table for one extra field.
**Not done:** the various `Start*` methods on `InteractiveSourceAuthorizationService` (building the authorize redirect) are still not logged — only the terminal `CompleteAsync` outcome is, a deliberate scope call (redirect construction has no real security-relevant outcome yet).

### Phase 3 — Workflow/pipeline lifecycle events (~30%)
**Done:** nothing new was added here — the Runtime plane's pre-existing `PipelineRunEvent` stream (`PipelineStarted`→`PipelineCompleted/Failed`) was left as-is and is still the only lifecycle event stream. The Configured pipeline plane has no equivalent lifecycle-event stream; Phases 2/5/6 (data access, export, validation, errors) partially substitute for it but there's no single "this run started/completed" governance event for the Configured plane distinct from `ConfiguredPipelineRuns`/`PipelineRunRouteExecutions` (which predate this work).
**Not done:** version/snapshot capture (Workflow/Mapping/Destination JSON + version pinned to a run, for reproducibility).

### Phase 4 — Scheduler, Retry, API Client, Queue, Endpoint Health (~75% blended)
**Done, and now live (rev. 3):** `SchedulerHistory` is written from `Worker.RunDueRoutesAsync`/`RunDueWorkflowsAsync` — the scheduler that's actually running in production — not just the dormant `ScheduleDispatcher`. This also fixed a latent bug: `RunDueRoutesAsync` had no try/catch around the pipeline call, so one failure would permanently fault the whole `BackgroundService`; it's now caught, logged to `ErrorLog`, and the worker keeps ticking. `ApiRequestLogs` remains live (global `DelegatingHandler`, query string stripped to avoid leaking tokens/PHI-ish search params).
**Still dormant, correctly so:** `RetryHistory` — the live `Worker.cs` scheduling path has no retry logic at all (only `PipelineRunCommandHandler`/`WebhookIngestionCommandHandler` do, via `MessageRetry.ExecuteAsync`, and those only run on the still-unregistered queue-based path). This isn't a bug to fix with more logging — it reflects that retries genuinely don't happen outside that path today. See the operational-gap section above for why enabling that path isn't a safe drop-in fix (risk of double-processing due routes).
**Resolved (rev. 4):** the "is the queue path ever getting enabled" question is now a documented decision, not an open gap — see the operational-gap section above. No behavior changed; the dormant classes are just now clearly marked as dormant.
**Not done — Queue Monitor:** 0%. Needs a new `IQueueMonitorProvider` abstraction plus real integration with RabbitMQ's management HTTP API and Azure Service Bus's admin client — genuinely new external-system work, not a logging-hook exercise like everything else here. Repeatedly deferred across sessions as the "hardest, most novel" remaining item.
**Partial — Endpoint Health:** covers source connections only, by reusing the pre-existing `ISourceConnectionTestService.TestAsync` (the same service the portal's "Test Connection" button uses). Destination connectivity is **not** covered — there is no generic per-destination-type test service (each of the 21 destination types would need its own), only per-type "test before save" flows used by the config wizard.

### Phase 5 — Mapping/Destination/Notification/Validation (~65%)
**Done:** `ExportHistory` (one hook in `ConfiguredPipelineService`, covers all 21 destination types), `NotificationHistory` (Email channel only — the only real notification channel that exists in the codebase), `ValidationFailureLogs` (reused `normalizationResult.Warnings`, already PHI-free — **no changes to the existing PHI-bearing `PipelineRunResourceRecord` entity were needed or made**).
**Not done — Data Lineage:** 0%, deliberately deferred every time it came up. The data lives in `PipelineRunResourceRecord.FetchedJson`/`NormalizedJson`/`MappedValuesJson` — fields explicitly documented as PHI and already encrypted at rest via `IPhiFieldEncryptor`. Exposing them through a new Governance/Operations endpoint needs the same decryption/masking discipline the existing execution-history screen has, reviewed deliberately — **do not casually add a read endpoint over these three columns.**

### Phase 6 — Error handling + Alerting (~55%)
**Done:** `ErrorLogs`. Api's global exception handler (`Program.cs`, `UseExceptionHandler`) logs every unhandled exception. **Now also live (rev. 3):** `Worker.RunDueRoutesAsync`/`RunDueWorkflowsAsync` (the actual running scheduler) log to `ErrorLog` on failure. Still dormant: `PipelineRunCommandProcessor`/`WebhookIngestionCommandProcessor`'s try/catch/log/rethrow — not reachable via the currently-hosted `Worker` polling loop (see the operational-gap section).
**Not done:** Alert Engine (rule evaluation over these tables → `AlertHistory` → notification dispatch) — 0%, not started.

### Phase 7 — Governance/Operations APIs (~75%)
**Done:** `GovernanceController` (`api/v1/governance/*`: audit-logs, authentication-logs, data-access-logs, security-events, smart-launch-logs, reports/hipaa-audit, **correlation-search**) and `OperationsController` (`api/v1/operations/*`: scheduler-history, retry-history, errors, api-requests, exports, notifications, validation-failures, endpoint-health). All correlation-id filterable except endpoint-health (not a per-run concept). Single `governance.read` permission gates all of them (new `PermissionGroupCode.Governance`, granted to SuperAdmin/Admin automatically and the built-in **Audit** role).
**Also done (rev. 4):** `GET /api/v1/governance/correlation-search?correlationId=...` — the unified "paste a CorrelationId, see everything" endpoint. `IGovernanceQueryService.GetCorrelationSearchResultAsync` composes all the existing per-category query methods (self-composition, no duplicated query logic) plus the pipeline-run header record itself (`IConfiguredPipelineRunRepository.GetByCorrelationIdAsync`, new), returning one `CorrelationSearchResultDto` spanning the run header, `AuditLogs`, `DataAccessLogs`, `AuthenticationLogs`, `SecurityEvents`, `SchedulerHistory`, `RetryHistory`, `ErrorLogs`, `ApiRequestLogs`, `ExportHistory`, `NotificationHistory`, and `ValidationFailureLogs`.
**Not done:** no dashboard/summary/analytics aggregation endpoints.

### Phase 8 — Portal (~65%)
**Shipped screens** (Angular, standalone components, `portal/src/app/governance/` and `portal/src/app/operations/`):
- **Governance** sidebar section: **Correlation Search** (new, rev. 4 — one search box, 12 conditionally-rendered result sections), Audit Logs (+ per-row **diff view** and **entity version history** scoping — see below), Authentication Logs, **SMART Launch Logs**, Data Access Logs, Security Events, Compliance Reports.
- **Operations** sidebar section: Scheduler History, Retry History, Errors (expandable stack traces), API Requests, Exports, Notifications, Validation Failures, Endpoint Health.

**Version History / Configuration Comparison — done, cheaply:** each `AuditLogs` row already carries `OldValueJson`/`NewValueJson` for that one change, so no new backend endpoint or table was needed. The Audit Logs screen has a **"View diff"** action (client-side JSON key diff, added/removed/changed) and a **"History"** action (scopes the list to one entity via new `entityType`/`entityId` query filters on the existing endpoint).

**Not done:** no separate "Security" or "Monitoring" sidebar sections (everything lives under Governance/Operations instead of the originally-sketched 5-section taxonomy). No Data Lineage screen, no Queue Monitor screen, no Retention Policies / Alert Rules / Log Settings admin screens.

### Phase 9 — Reporting (~20%)
**Done:** one real report — `GET /api/v1/governance/reports/hipaa-audit?from=&to=`, PDF via QuestPDF (already a dependency, pattern copied from `MappedPdfDestinationWriter`). Covers: **hash-chain integrity verification of the entire `AuditLogs` table** (not just the report window — reports VERIFIED/BROKEN with the exact `SequenceNumber` if broken), authentication summary, data-access summary, security-events-by-severity, errors-by-severity. `AuditLog.ComputeHash(...)` was refactored from private-constructor-only to a public static method plus `VerifyOwnHash()`, specifically so this verification could reuse it instead of duplicating the hash logic.
**Not done:** every other named report from the original catalog (Workflow, Endpoint, Auth-specific, Security, Patient Access, API Analytics, Usage, Export reports) — not built. No separate SOC2-branded report distinct from the HIPAA one (the one report covers overlapping evidence for both).

### Phase 10 — OTLP / external observability export (0%)
Not started at all. `FHIRBridge.Observability` (pre-existing OTel/Serilog) was not touched. No `TraceId`/`SpanId` columns added to any governance table. No generic SIEM webhook publisher.

### Phase 11 — Security hardening (~75%)
**Done:** `IAppendOnlyEntity` + interceptor guard (blocks Modify/Delete on 8 of the 9 append-only-flagged tables — `SecurityEvents` is intentionally exempt, its `Resolved` flag needs to be mutable). Hash-chain tamper evidence for `AuditLogs`, verifiable via the Compliance Report. PHI masking: no new work needed — every new table was designed PHI-free by construction (identifiers only, per the same bar as the pre-existing `DataAccessLog`-style reasoning), so the existing `PhiMaskingEnricher` didn't need extending.
**Also done (rev. 4):** retention/purge enforcement is now live. New generic `GovernanceLogPurgeableStore<TEntity>` (`IPurgeableStore` implementation parameterized by a timestamp-selector expression, using EF Core's `ExecuteDeleteAsync` bulk delete) is registered for 9 tables — `SchedulerHistory`, `RetryHistory`, `ErrorLogs`, `ApiRequestLogs`, `ExportHistory`, `NotificationHistory`, `ValidationFailureLogs`, `EndpointHealthChecks`, `SecurityEvents`. Deliberately **not** registered for `AuditLogs`/`AuthenticationLogs`/`SmartLaunchLogs`/`DataAccessLogs` — those four stay unbounded, 7-year HIPAA evidence. `RetentionPurgeService.RunAsync` was fixed to resolve a **per-store** retention policy (`GetPolicy(store.DataClass)`) instead of one global cutoff for every store, so each table class can get its own retention window. `RetentionPurgeWorker` itself — previously built but never hosted — is now registered in `Program.cs` and actually runs. Because EF Core's InMemory provider doesn't support `ExecuteDeleteAsync`, this was verified against a real SQL Server (the project's own `docker-compose.yml` container) rather than assumed correct from a passing InMemory test. Scheduled chain-verification: `IAuditChainVerificationService` was extracted from `QuestPdfComplianceReportService`'s previously-private, duplicated hash-walk logic, and is now shared by both the Compliance Report (on-demand) and the new `AuditChainVerificationWorker` (daily by default, configurable via `AuditChainVerification:IntervalHours`) — a chain break raises a `Critical` `SecurityEvent` (`EventType = "AuditChainBroken"`). POL-010 §3.2 updated to describe the now-automated cadence.
**Not done:** nothing further identified for this phase beyond the broader report/portal/testing catalog gaps tracked elsewhere.

### Phase 12 — Testing (~25%)
**Done, and actually exercised at runtime (not just compiled):**
- `AuditLogHashChainTests` — hash determinism and what a broken-chain link looks like.
- `QuestPdfComplianceReportServiceTests` — generates a real PDF against an EF InMemory database and asserts on the `%PDF-` magic header (this was written specifically because "the report renders" is genuinely new runtime behavior a clean compile doesn't validate).
- Updated `LocalAuthServiceMfaTests` and `EmailDeliveryStrategyTests` for the new constructor dependencies.

Current suite totals: **150 unit tests** (149 pass; 1 known pre-existing, unrelated failure — `DestinationExecutionHistoryGateTests.Update_throws_when_destination_has_execution_history`, confirmed failing on the clean baseline *before* any of this work, not a regression), **5/5 architecture tests**, **101/101 integration tests**, **70/70 Runtime unit tests**. One other test (`GeneratedFileDownloadLinkServiceTests.Rejects_a_tampered_token`) was observed to be flaky/order-dependent, unrelated to this work — confirmed by isolated reruns.

**Not done:** no dedicated integration tests for the new `GovernanceController`/`OperationsController` endpoints (they're exercised indirectly since the existing integration suite boots the full host and would fail if DI/permission wiring were broken, but there's no `GET .../audit-logs → 200` style test). No retention tests, no DR tests, no load tests.

## Recommended next steps, in priority order

The entire `docs/backend/09-governance-logging-100-percent-plan.md` (all 4 tiers, 16 items, the full 31-screen spec) is now closed — see the "What's genuinely NOT 100%" callout above for the honest residual caveats within that spec. What's left is explicitly outside that plan's scope:

2. **The rest of the report catalog** (Workflow, Endpoint, Auth-specific, Patient Access, Usage, Export reports) beyond HIPAA + SOC2 Evidence.
3. **Shipping OTLP to a real backend in each environment** — the wiring is real and verified locally against the docker-compose collector; a production Azure Monitor connection string (or a real collector endpoint) is an environment-config task, not a code task.
4. **Destination Endpoint Health for the remaining 9 destination types** (database-direct writers, SFTP) — needs bespoke per-type checks, deliberately not built alongside the generic target-reachability provider.
5. Dedicated integration/retention/DR tests for everything built across this effort — the existing suite exercises the DI wiring indirectly (a broken registration fails the host boot), but there's no `GET .../alert-rules → 200` style test catalog.

## Revision log

- **2026-07-18, rev. 7 (100%-parity plan, Tier 4 — final tier):** **Data Lineage:** built as designed and pre-approved — `GET /api/v1/governance/data-lineage/{resourceRecordId}` returns the tree structure (source field JsonPath → mapping rule/NormalizationType → destination column TargetField → export destination/format/status/timestamp) by joining `PipelineRunResourceRecord` (safe columns only, explicitly projected to avoid ever touching the encrypted `FetchedJson`/`NormalizedJson`/`MappedValuesJson` columns) → `PipelineRunRouteExecution` → `MappingProfile.Fields` → `ExportHistory`; gated by the same `governance.read` as every other governance screen.
