FHIRBridge · control-plane persistence

What the backend stores — on create vs. on execute

The customer's mapped clinical data lands in their destination (SQL/CSV). Separately, FHIRBridge writes to its own operational database at every step. This traces exactly which of the 19 tables get rows — and what's in them — when a workflow is built and when it runs. Values continue the Acme Health · Epic EHR-launch example.

When a workflow is created (config-time)

Each wizard step calls UnifiedTenantConfigurationService, which mutates the Tenant aggregate, saves, and writes one OperationalAuditLog row per action. On every save the AuditingSaveChangesInterceptor auto-stamps CreatedBy · CreatedOnUtc · RowVersion (or the Modified equivalents). No clinical data, no run rows yet.

When the workflow is executed (run-time)

A run (scheduled, webhook, or the EHR-launch trigger) goes through ConfiguredPipelineService. It writes audit rows as it progresses, a lineage row per resource, and one run-summary row at the end. The mapped clinical data is written to the customer's destination — not here.

Cross-cutting writes (not tied to a single step)

Three mechanisms write regardless of which workflow action fired them.

AuditingSaveChangesInterceptor — every configuration table

STAMPall IAuditable rows
On every SaveChanges: CreatedBy/CreatedOnUtc on insert, ModifiedBy/ModifiedOnUtc on update, RowVersion bumped. A "delete" is flipped to a soft delete (IsDeleted, DeletedBy, DeletedOnUtc) — rows are never physically removed, so audit/lineage stays resolvable.

UserActivityAuditLogs — auth & data-access only

INSERTUserActivityAuditLogs
Written on login/logout/failed-login and on patient data-access reads — NOT on config CRUD or pipeline runs. Hash-chained: each row's EntryHash includes the PreviousHash, so tampering is detectable. Fields: UserEmail, Activity, Category, Severity, Status, IpAddress, UserAgent, RequestPath.

Users — updated on sign-in

UPDATEUsers
LastLoginOnUtc, RefreshTokenHash (+expiry), FailedLoginCount/LockoutEndUtc on bad attempts. Only hashes are ever stored — never a raw password, token, or client secret.

The one rule that explains the split: the FHIRBridge database stores metadata about the data movement — configuration, run history, audit, lineage — and deliberately never stores the FHIR clinical payload. That always flows source → map → the customer's destination. Lineage links the two by SourceResourceId without copying content.
