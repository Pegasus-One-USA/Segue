How the settings execute, and why they scale to all 145 resource types

Two separate questions, answered in order: (1) when a resource actually flows through the pipeline, at which stage does each console setting get read and applied — and what happens when one fails? (2) we've only shown rich configuration for 5 resource types — how does the same model cover the other 140 without hand-authoring each one?

1 Runtime execution — where each setting is consumed

Nothing in the console runs on its own schedule. Every setting is read at one specific point in the existing configured pipeline (extension flattening → US-Core validation → data-quality scoring → patient matching, then governance, then destination fan-out). The console doesn't add new pipeline stages — it adds inputs to stages that already exist.

2 Scaling to all 145 resource types

The console has only shown 5 resources with real content: Observation, Condition, MedicationRequest, Practitioner, Patient. That's not a sample of 145 — it's the entire set that needs bespoke content. The other ~135 are administrative resource types (Appointment, Coverage, Schedule, NamingSystem, and so on) that never had resource-specific terminology or business rules to begin with — a fact already visible in the registry you supplied: every non-clinical entry in FHIRResourceCapabilities_V3.json carries the identical generic block, word for word. The system doesn't need to scale to 145 hand-authored configs. It needs to scale to ~10 authored configs plus one shared default that every other resource inherits automatically.

The Safe Harbor matrix scales the same way: each of the 18 categories is defined once against an identifier concept ("Names," "All dates except year"), and applicability to a resource is a lookup, not a hand-written row. Only resources that can actually carry that data type — Patient, Practitioner, Device, Coverage, Account, DocumentReference, AuditEvent — get a real action; everything else resolves to "Not applicable" automatically.
This also sets the onboarding rule for new resource types: everything starts in Tier B — safe, structural-only, no assumptions — and only moves to Tier A when someone deliberately authors terminology or rules for it. That's a registration, never a code change to a shared switch, which is the same "registry over switch" pattern the rest of FHIRBridge already enforces for connectors and auth strategies.
